# Supported SVG Features

PeachPDF renders SVG — inline `<svg>` elements in HTML, standalone SVG (`<img src="x.svg">` / `data:image/svg+xml`), and SVG used as a CSS `background-image`/`list-style-image` url() source — as real vector PDF content. Shapes become native PDF path-construction operators, gradients become native PDF shadings, and clips/masks/patterns become native PDF constructs. SVG stays vector except for one deliberate case: a `<filter>` that uses a primitive PDF has no operator for (a blur, lighting, morphology, and so on — see [Filters](#filters)) is evaluated over pixels and embedded as a bitmap at the document's [raster resolution](usage-examples.md#rasterized-effects-and-resolution). Everything else preserves scalability and keeps the PDF's file size small regardless of the output resolution. This page documents exactly what is and is not supported. Where a feature is only partially supported, the specific gaps are noted.

## SVG Root & Document Structure

| Element | MDN Reference | Notes |
|---------|--------------|-------|
| `svg` | [svg](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/svg) | Inline (`<svg>` inside HTML), standalone (`<img src="x.svg">`, `data:image/svg+xml`), and as a CSS `background-image`/`list-style-image` url() source are all supported — see [HTML & CSS Support](html-css-support.md#backgrounds) for the CSS-side details. `viewBox`, `width`, `height`, and `preserveAspectRatio` are all honored. | `symbol` | [symbol](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/symbol) | Never painted directly; establishes its own viewport (`viewBox`/`preserveAspectRatio`) only when referenced via `<use>`, sized by the `<use>` element's `width`/`height` (defaulting to the current viewport's size, per spec) |

| `switch` | [switch](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/switch) | Renders only the first buildable child. PeachPDF has no `requiredFeatures`/`requiredExtensions`/`systemLanguage` conditional-support axis to evaluate, so this is equivalent to every other candidate always failing its (nonexistent) test — a deliberate v1 simplification |
| `a` | [a](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/a) | Groups children like `<g>`, and additionally becomes a real PDF link annotation (same-page `#id` fragments become `/GoTo` links, other `href` values become `/URI` links) covering the transformed content's bounding box. A rotated/skewed anchor's link region is approximated by its axis-aligned bounding box, since PDF link annotations are themselves always axis-aligned rectangles |

On a leaf shape (no children), applied as a simple alpha multiply on the shape's own fill/stroke/text color. On a container (`<g>`, `<a>`, nested `<svg>`, or a `<use>` referencing one (directly, or through further `<use>` aliases) — including a container whose only content is `<text>` or `<image>`) it's rendered as a genuine, isolated PDF transparency group — the container's children are painted into an offscreen Form XObject and flattened, then that single flattened result is composited once at the container's own opacity, so overlapping children never double-blend where they overlap. |
| `currentColor` | [currentColor](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/currentcolor) | Resolves to the CSS `color` property of the inline `<svg>`'s HTML ancestor; for standalone SVG (no CSS context), resolves to black |
| `color-interpolation-filters` | [color-interpolation-filters](https://developer.mozilla.org/en-US/docs/Web/SVG/Attribute/color-interpolation-filters) | Honoured on a `<filter>` and its primitives when the filter is evaluated over pixels (see [Filters](#filters)); a vector-only filter always computes in sRGB. |
| `color-interpolation` | [color-interpolation](https://developer.mozilla.org/en-US/docs/Web/SVG/Attribute/color-interpolation) | Honoured on a `<linearGradient>`/`<radialGradient>` (own value, else the nearest ancestor's; `auto` is sRGB): `linearRGB` blends the stops in linear light, by sampling extra stops between each pair, so a black-to-white gradient is visibly lighter at its midpoint than the sRGB default. Honoured on a `<mask>` too: `linearRGB` takes the mask's luminance from its content's colors converted to linear light, so mid-gray content is more transparent than under the sRGB default. The conversion applies to solid fills/strokes and gradient stops in the mask content; a pattern or raster `<image>` inside a mask keeps its sRGB values |
| `icc-color()` / `<color-profile>` | [color](https://developer.mozilla.org/en-US/docs/Web/SVG/Attribute/color) | A `<color> icc-color(name, c1, ...)` in `fill`, `stroke`, `stop-color`, `flood-color` or `lighting-color` is converted to sRGB through the `<color-profile name="..." href="...">` of that name (a `data:` URI or a fetched resource; `rendering-intent` honoured). Gray, RGB and CMYK profiles work, with components in 0..1. When the profile is missing, cannot be parsed, or the component count does not fit, the sRGB color written before the `icc-color()` is used, as the specification prescribes. The CSS `@color-profile` rule and the `color-profile` property are not supported |

### Context paint

`context-fill` and `context-stroke` (SVG 2) are values of `fill` and `stroke` that stand for the fill and stroke of the *context element*:

- **`<use>`** is the context element of what it instantiates, so one shape can be reused with a different fill and stroke per use: the shape says `fill="context-fill" stroke="context-stroke"` and each `<use>` gives them. A nested `<use>` changes the context for its own content; a keyword written on the `<use>` itself refers to the context outside it. `fill="context-stroke"` (a fill taking the stroke) is valid.
- **A marker** draws with the fill and stroke of the shape it is placed on, for every instance separately — including a `<text>` inside the marker, and a shape's `FillPaint`/`StrokePaint` filter input.
- **Elsewhere** there is no context element and the keywords paint nothing, unless the document was built for something that supplies one: the SVG document of an [OpenType SVG glyph](html-css-support.md#fonts) is drawn for text, so `context-fill` is the text's fill (its colour) and `context-stroke` its stroke, which is none because PeachPDF's text has no stroke paint.

Gradients and patterns pass through `<use>` and through a marker, each keeping the context element's own coordinate space and bounding box: a gradient or pattern on the shape a marker is drawn on is mapped through the marker's placement (its position, rotation and scale) so it lines up with the shape as if the marker were not there, and a gradient or pattern through `<use>` is measured against the box of what the `<use>` instantiates, mapped through any `transform` between that element and the shape actually painting it. This holds whether the `<use>` targets a shape, a `<g>`, a `<symbol>`, or a nested `<svg>` — for the latter two, the box is that target's own established viewport content, mapped the same way `viewBox`/`preserveAspectRatio` map it when actually painted.

| Element | MDN Reference | Notes |

| `radialGradient` | [radialGradient](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/radialGradient) | `cx`/`cy`/`r`, plus focal point `fx`/`fy` (independent of the center, per spec), same `gradientUnits`/`gradientTransform`/`spreadMethod` support as `linearGradient`. ## Clipping, Masking, Patterns

| Element | MDN Reference | Notes |
|---------|--------------|-------|
| `clipPath` | [clipPath](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/clipPath) | Full support; `clip-rule` (`nonzero`/`evenodd`) controls the clip region's fill rule. `clipPathUnits` (`userSpaceOnUse` — the default — and `objectBoundingBox`, where the clip's `0..1` geometry auto-scales to the referencing element's bounding box) are both supported. Renders as a real PDF clipping path (`W n`), not a mask. A clip shape's own `transform` is applied to its clip geometry — whether set directly on the shape, on a wrapping `<g>`, or on a `<use>` (including its `x`/`y`), so one shape defined in `<defs>` can be reused as a clip at several positions (and composes correctly with `objectBoundingBox` units) |
| `mask` | [mask](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/mask) | Renders as a real PDF luminosity soft mask (`/SMask` via `/ExtGState`) — mask content is painted (not just used for geometry, unlike `clipPath`) into an offscreen form, and its luminance becomes the mask's alpha. `maskUnits`/`maskContentUnits` (`objectBoundingBox`/`userSpaceOnUse`) are both supported, including the spec's `-10%`/`-10%`/`120%`/`120%` default region |
| `pattern` | [pattern](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/pattern) | `patternUnits`/`patternContentUnits` (`objectBoundingBox`/`userSpaceOnUse`), `patternTransform`, `viewBox`/`preserveAspectRatio`. Implemented by rendering the pattern's content once into a PDF Form XObject "tile," then drawing that same tile repeatedly (clipped to the filled shape's geometry) across the fill region — every repeat is a reference to the same underlying vector content, never a rasterized bitmap, but this is not a native PDF `/PatternType 1` tiling pattern object. Capped at 10,000 tile placements per fill as a safety guard against pathological pattern/shape size ratios |

**Inheritance:** content inside `<pattern>`, `<mask>`, `<marker>` and `<clipPath>` inherits presentation properties (`fill`, `stroke`, `stroke-width`, `fill-opacity`, font properties, …) from the definition element's own ancestors — and from the definition element itself — not from the element that references it. `<svg fill="#fff">` around a `<mask>` whose unstyled content should paint white therefore works as it does in a browser. (A pattern never inherits a paint that references itself, and a marker never inherits a `marker-*` reference to itself, so neither can draw itself without end.)

## Filters

| Element | MDN Reference | Notes |
|---------|--------------|-------|
| `filter` | [filter](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/filter) | A real primitive graph. When every primitive can be expressed in PDF (`feFlood`, `feOffset`, `feMerge`, `feTile`, the Porter-Duff `feComposite` operators, `feBlend`, a channel-independent `feColorMatrix`, and a linear `feComponentTransfer`), it is evaluated over PDF tiles and the result stays vector: ordinary fills, placements, blend modes, soft masks, and PDF `ExtGState /TR` transfer functions. **If any primitive needs pixels, the whole filter is evaluated over pixels instead:** the element's content is painted into a bitmap covering the filter region, every primitive runs on it, and the result is placed on the page at `PdfGenerateConfig.RasterizationDpi`. Supports named `result`/`in`/`in2` references to any earlier primitive (not only the immediately-preceding one), plus the reserved input names `SourceGraphic`, `SourceAlpha`, `FillPaint`, `StrokePaint`, `BackgroundImage` and `BackgroundAlpha`. `FillPaint` and `StrokePaint` fill the whole filter region with the referencing element's `fill` or `stroke` paint (a colour, gradient or pattern; `none` is transparent; `fill-opacity`/`stroke-opacity` are not applied). `BackgroundImage` is what was painted behind the element inside its isolation group: for an inline `<svg>`, the page behind it over white paper (its ancestors' backgrounds, the SVG's own background included) followed by the SVG's own content painted before the element; `BackgroundAlpha` is that image's opacity. An SVG used as an `<img>`, a CSS image or a standalone document is a separate document, so its backdrop is only its own earlier content over transparency, and a group inside the SVG with `opacity`, `mask` or `filter` starts its backdrop empty. `feImage` places a stand-alone image (raster, or SVG through a `data:` or fetched URL) into its primitive subregion using its own `preserveAspectRatio`, or, for an `href="#id"` fragment, renders that element in the filtered element's user space, moved by the subregion's `x`/`y`. A fragment that names nothing leaves the primitive transparent. Any filter using one of these inputs or `feImage` is evaluated over pixels. Browsers generally treat `BackgroundImage`/`BackgroundAlpha` as transparent, so a document that relies on them looks different there. Over white paper an inline SVG's `BackgroundAlpha` is fully opaque across the filter region. The filter region (`x`/`y`/`width`/`height`, `filterUnits`) defaults to the spec's `-10%`/`-10%`/`120%`/`120%` of the referencing element's bounding box, in both `objectBoundingBox` (the default) and `userSpaceOnUse` units; an element with no measurable bounding box (text, for instance) uses its viewport instead. `primitiveUnits` applies to the lengths of the pixel primitives. **A `<filter>` containing a primitive or type this renderer does not support (an unknown `fe*` element, or an `feComposite` operator that does not parse) is rejected as a whole at parse time: the referencing element paints completely unfiltered, the same as a `filter` attribute naming a nonexistent id — never a partially-applied graph.** |
| `feFlood` | [feFlood](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feFlood) | Full support — fills the filter region with `flood-color`/`flood-opacity` |
| `feOffset` | [feOffset](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feOffset) | Full support — `dx`/`dy`, resolved per `primitiveUnits` |
| `feMerge` / `feMergeNode` | [feMerge](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feMerge) | Full support — layers each child `feMergeNode`'s `in` via ordinary compositing, in document order |
| `feTile` | [feTile](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feTile) | Repeats its input's own subregion across the whole filter region |
| `feComposite` | [feComposite](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feComposite) | `over`, `in`, `out`, `atop`, `xor` — all via alpha-masked compositing in vector form (`SourceAlpha` and every alpha-based `in`/`in2` reference a real `/Alpha`-subtype PDF soft mask, not a luminosity approximation). `arithmetic` (`k1`–`k4`) needs pixels: it makes the filter a bitmap one |
| `feBlend` | [feBlend](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feBlend) | All standard blend modes, via the same real PDF blend mode (`ExtGState /BM`) CSS `mix-blend-mode` uses — see [HTML & CSS Support](html-css-support.md#filters-and-blend-modes) |
| `feColorMatrix` | [feColorMatrix](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feColorMatrix) | `type="matrix"` with a channel-independent (diagonal) matrix is applied via a PDF `ExtGState /TR` transfer function and stays vector; `type="luminanceToAlpha"` uses the same `/Luminosity` soft mask `mask` uses. `type="saturate"`, `type="hueRotate"` and any `type="matrix"` with a nonzero off-diagonal term mix colour channels, which PDF cannot express, so they make the filter a bitmap one (the full 4×5 matrix is applied per pixel) |
| `feComponentTransfer` | [feComponentTransfer](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feComponentTransfer) | `type="linear"` (`slope`/`intercept`) on `feFuncR`/`feFuncG`/`feFuncB` is composed into a PDF `/TR` transfer function and stays vector; a missing channel function defaults to identity, per spec. `type="gamma"`, `"table"`, `"discrete"` and any non-identity `feFuncA` make the filter a bitmap one |
| `feGaussianBlur` | [feGaussianBlur](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feGaussianBlur) | `stdDeviation` (one or two numbers, in user units or fractions of the bounding box per `primitiveUnits`). A zero or negative deviation disables its axis; both disabled passes the input through. Bitmap evaluation |
| `feDropShadow` | [feDropShadow](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feDropShadow) | `dx`, `dy`, `stdDeviation`, `flood-color`, `flood-opacity`. Bitmap evaluation |
| `feMorphology` | [feMorphology](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feMorphology) | `operator` `erode`/`dilate`, `radius` per axis. The area outside the filter region counts as transparent. Bitmap evaluation |
| `feConvolveMatrix` | [feConvolveMatrix](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feConvolveMatrix) | `order`, `kernelMatrix`, `divisor`, `bias`, `targetX`/`targetY`, `edgeMode` (`duplicate`, `wrap`, `none`), `preserveAlpha`; `kernelUnitLength` is ignored (the kernel runs at the bitmap's own pixel pitch). A malformed kernel rejects the filter. Bitmap evaluation |
| `feTurbulence` | [feTurbulence](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feTurbulence) | `type` `turbulence`/`fractalNoise`, `baseFrequency`, `numOctaves`, `seed`, `stitchTiles`; the specification's reference algorithm, so a given seed draws the same noise as other conforming renderers. Bitmap evaluation |
| `feDisplacementMap` | [feDisplacementMap](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feDisplacementMap) | `scale`, `xChannelSelector`, `yChannelSelector`; nearest-pixel sampling, transparent where a pixel is displaced from outside the region. Bitmap evaluation |
| `feDiffuseLighting` / `feSpecularLighting` | [feDiffuseLighting](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/feDiffuseLighting) | `surfaceScale`, `diffuseConstant`/`specularConstant`, `specularExponent`, `lighting-color`, and a `feDistantLight`, `fePointLight` or `feSpotLight` child (with `limitingConeAngle`). The surface normal uses the specification's Sobel kernels, with its edge and corner variants. Bitmap evaluation. A lighting primitive with no light source rejects the filter |

**Colour space and subregions (bitmap evaluation).** Each primitive computes in the colour space `color-interpolation-filters` names — `linearRGB` (the initial value) or `sRGB` — converting its inputs as needed, and the last result is converted to sRGB for the page. Intermediate results are 8 bits per channel in whichever space, so the darkest few sRGB levels quantize in linear light (an sRGB value below about 8 can round to 0 in a `linearRGB` pass). A vector-only filter cannot do this (PDF has no working space to interpolate in) and computes in sRGB throughout. Per-primitive `x`/`y`/`width`/`height` subregions are honoured and make the filter a bitmap one; a primitive without one covers the whole filter region (the specification's default is the union of its inputs' subregions, which this simplifies).

Every primitive above builds a fresh PDF tile from its input(s) rather than mutating shared state, so a named `result` can be referenced by more than one later primitive, and non-adjacent references (a primitive whose `in` names a result from several steps earlier, not just the previous one) work exactly like an adjacent reference.

## Raster & Nested Content

| Element | MDN Reference | Notes |
|---------|--------------|-------|
| `image` | [image](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/image) | `href`/`xlink:href` resolves as a `data:` URI, a network URL, or a local file path — the same resource-loading pipeline HTML `<img>` uses (so it obeys `<base href>`, and a network URL requires a network loader to be configured, exactly like `<img>`). A raster payload (PNG, JPEG, etc.) embeds as a real PDF image XObject; an `image/svg+xml` payload (detected by a `.svg` extension or a `Content-Type: image/svg+xml` response header) renders as its own real vector scene graph (never rasterized), with its own `url(#id)` references resolving against its own definitions. A nested SVG payload's *own* `<image>` elements resolve recursively — a network/file `<image>` inside a referenced SVG is fetched too, with its relative hrefs resolved against that nested SVG's own location. `x`/`y`/`width`/`height`/`preserveAspectRatio` are all honored — including for raster images, which are fit into their box per `preserveAspectRatio`'s alignment/meet/slice rules, the same math used for viewports elsewhere in this renderer. An unresolvable `href` (no configured loader, missing resource, malformed payload) leaves the element blank rather than erroring. A relative `href` inside a standalone (`<img src="x.svg">` / fetched) SVG resolves against the SVG's own location |
| Nested `svg` | see `svg` above | Establishes its own viewport, coordinate system, and clip |
| `foreignObject` | [foreignObject](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/foreignObject) | Embeds HTML in SVG user space, in an **inline `<svg>` in an HTML document**: the element's children are laid out by the ordinary HTML engine as an isolated block `width` user units wide (one user unit being one CSS pixel), and painted at (`x`, `y`) clipped to the `width`×`height` viewport. Document and inline styles apply to the HTML, selectors inside match as HTML (case-insensitively), and `transform`, `opacity`, `clip-path`, `mask` and `filter` on the `foreignObject` apply to it like any other element. The `width`/`height` must be positive lengths (percentages are not resolved; a missing one paints nothing). Limits: the content is never split across pages, a `<a href>` inside is not a link annotation, and it adds nothing to the tagged-PDF structure. In a standalone SVG (`<img src="x.svg">`, a `data:` URI, a CSS image) the element is not built, so a surrounding `switch` falls through to its next child |

Network and file-path `<image>` references are fetched through PeachPDF's general asynchronous resource-loading pipeline ahead of the (synchronous) SVG scene-graph build; a `data:` URI still resolves inline with no I/O. As with any external asset, a network URL only loads when a network loader is configured — otherwise the element simply renders blank.

## Text

| Element | MDN Reference | Notes |
|---------|--------------|-------|
| `text` | [text](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/text) | `x`/`y`/`dx`/`dy`/`rotate` as both single values **and per-character lists** (`x="10 20 30"`, `rotate="0 15 30"`, SVG 1.1 §10.4) — each glyph is positioned/rotated by its own list value, a new absolute `x`/`y` starts a text chunk, and `text-anchor` (`start`/`middle`/`end`) is applied per chunk. `font-family`/`font-size`/`font-weight`/`font-style`/`font-stretch` (as both presentation attributes and `style=`) inherit from any ancestor (`<g>`/`<svg>`/`<use>`), and relative `font-size` (`em`/`%`, and the measured `ex`/`ch`/`cap`/`ic`/`lh`, taken from the parent's font) resolves against the parent's used size (`rem` and the `r*` forms against the root's); `letter-spacing`/`word-spacing` accept the same units against the element's own font. Bridges directly into PeachPDF's existing font/text-measurement pipeline — the same font resolution and OpenType shaping ordinary HTML text uses, including `letter-spacing`, `word-spacing`, `text-transform` (`uppercase`/`lowercase`/`capitalize`/`full-width`), `font-variant-ligatures`/`-caps`/`-numeric`/`-east-asian`, `font-feature-settings`, `font-kerning`, and `text-decoration-line`/`-style`/`-color` (`underline`/`overline`/`line-through`, own value only — not inherited, per CSS Text Decoration 3 — but a descendant with no decoration of its own still shows an ancestor's line flowing across it, matching real browser behavior; see the known-simplifications list for this feature's own v1 scope). **`fill` and `stroke`:** a solid `fill` is painted as a selectable text run; a gradient/pattern `fill` (`fill="url(#…)"`) or any `stroke` instead outlines each glyph to a vector path and fills/strokes it through the same paint machinery shapes use (see the known-simplifications list below for the outlined-text trade-offs) |
| `tspan` | [tspan](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/tspan) | A `tspan` without its own `x`/`y` flows immediately after the preceding text in the `<text>` subtree; a `tspan` with its own `x` and/or `y` starts a new absolute position (text chunk). Loose text and child `tspan`s are laid out in document order (text authored after a child element keeps its place), and its own per-character `x`/`y`/`dx`/`dy`/`rotate` lists apply to its characters. Font properties and paint (`fill`/`stroke`/etc.) are inherited from the enclosing `text`/`tspan` when not overridden |
| `tref` | [tref](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/tref) *(deprecated in SVG2, still supported here)* | `href`/`xlink:href` resolves to another element's own text content, reused as this run's text |
| `textPath` | [textPath](https://developer.mozilla.org/en-US/docs/Web/SVG/Element/textPath) | `href`/`xlink:href` resolves to a `<path>` **or a basic shape** (`rect`/`circle`/`ellipse`/`line`/`polyline`/`polygon`), whose geometry the run's glyphs — including any nested `<tspan>`s — are laid along: each glyph is placed at its own midpoint distance along the path and rotated to the path tangent, plus any per-character `rotate`/`dx`/`dy`. `method` (`align`, the default, turns each glyph rigidly to the tangent; `stretch` bends each glyph's outline along the curve point by point) and `spacing` (`auto` is laid out as `exact`, which the specification allows). `startOffset` (a length or a `%` of the total path length), `text-anchor`, and `side` (`left`/`right`) shift/flip where the run runs along the path; a glyph whose midpoint falls before the start or past the end of the path is not rendered. Uses the same glyph-outline paint as gradient/stroked text, so a `<textPath>` also supports gradient/pattern `fill` and `stroke`. The outlines are painted in the text's user space: a `userSpaceOnUse` gradient/pattern stays fixed there, and an `objectBoundingBox` one measures against the whole text (the union of its glyph cells), not each glyph. Always flows horizontally along the path regardless of the `<text>` root's own `writing-mode` — there is no vertical variant of path-following text |
| `writing-mode` / `text-orientation` | [writing-mode](https://developer.mozilla.org/en-US/docs/Web/CSS/writing-mode) / [text-orientation](https://developer.mozilla.org/en-US/docs/Web/CSS/text-orientation) | `writing-mode` (resolved once from the `<text>` root — see below) advances the pen down the column instead of along a line for `vertical-rl`/`vertical-lr`; `sideways-rl`/`sideways-lr` and SVG 1.1's legacy `tb`/`tb-rl`/etc. keywords fall back to `horizontal-tb`. `text-orientation` (`mixed`, the default; `upright`; `sideways`) is genuinely per-glyph and can be overridden on a nested `<tspan>`: `mixed` classifies each glyph by Unicode's [Vertical_Orientation property](https://www.unicode.org/reports/tr50/) (the same table the HTML pipeline shares), painting CJK/kana upright and Latin/digits rotated 90°; `upright`/`sideways` force one answer for every glyph on that run. An explicit per-character `rotate=""` always overrides the orientation-driven default rotation for that glyph. An upright glyph's down-the-column advance consults the font's own real OpenType vertical metrics (`vhea`/`vmtx`) when it carries them (mainly professional CJK vertical fonts), clipped to its own reserved cell so a glyph never bleeds into its neighbor's; a font without real vertical metrics — the common case — falls back to approximating the advance as the font's own line height. An upright glyph's anchor position additionally consults the font's real `VORG` vertical-origin table when it has one — CFF/CFF2 fonts only, per the OpenType spec's own restriction; a TrueType-outline font's `VORG` table (rare in practice) is never consulted, and such a font falls back to the plain top-of-cell anchor exactly as a font with no `VORG` at all does. A rotated glyph's down-the-column footprint is always its own natural pre-rotation width, matching real browser behavior for sideways-oriented text |
| `direction` / `unicode-bidi` | [direction](https://developer.mozilla.org/en-US/docs/Web/CSS/direction) / [unicode-bidi](https://developer.mozilla.org/en-US/docs/Web/CSS/unicode-bidi) | A full [Unicode Bidirectional Algorithm (UAX #9)](https://www.unicode.org/reports/tr9/) implementation, matching how CSS text integrates bidi ([CSS Writing Modes 3 §5.2](https://www.w3.org/TR/css-writing-modes-3/#bidi-mapping)) and shared with HTML's own bidi resolver: `direction` (`ltr`/`rtl`, inherited, resolved from any ancestor) sets the `<text>` root's paragraph base direction; `unicode-bidi` (`normal`/`embed`/`isolate`/`bidi-override`/`isolate-override`/`plaintext`, **not** inherited — resolved fresh per element, per spec) on a `<tspan>` contributes an explicit embedding/isolate/override push over exactly the characters that `<tspan>` (including its own descendants) contributes. Per-character bidi class (which characters actually reorder) is always auto-detected from each character's real Unicode `Bidi_Class`, independent of `direction`/`unicode-bidi` — a strong-right-to-left run (e.g. Arabic or Hebrew text) reorders and a mirrorable character pair (parentheses, brackets) swaps identity even with no `direction`/`unicode-bidi` set anywhere, matching real browser behavior |

**Known text simplifications:**

- **Outlined text stays selectable.** A solid `fill` keeps the fast text-showing path (selectable, copy/paste- and tagged-PDF-friendly). A gradient/pattern `fill`, a `stroke`, or a `<textPath>` with `method="stretch"` draws each glyph as a filled/stroked vector outline, and the same text is also placed invisibly over it (PDF text render mode 3, the way a rasterized HTML subtree supplies its text), so it can still be selected and searched. This needs a decodable outline: a `glyf`-outline (TrueType) font, or any CFF/OpenType-CFF font (ordinary or CID-keyed). A bitmap-only font has no outline, so its glyphs are drawn through the raster backend: a gradient/pattern `fill` is painted through the glyphs' coverage, and a `stroke` is a band of the stroke width centred on their edge (an approximation, since a bitmap has no vector edge). A `<textPath>` on such a font turns its glyphs rigidly rather than bending them.
- A `<text>`'s bounding box for `objectBoundingBox` clipping, masking and paint is the union of its glyph cells (advance wide, ascent to descent) as laid out; a `<g>`/`<use>` containing text takes the union of its children's. A bitmap font's glyph cannot be bent (its pixels have no outline), so `method="stretch"` turns its glyphs rigidly, and its stroke is an approximation of the edge.
- **OpenType shaping** (see [Text shaping](html-css-support.md#text-shaping)) applies to `<text>`/`<tspan>`/`<textPath>` the same way it does to HTML text, including the outlined (gradient/pattern-filled or stroked) path — ligatures, caps/numeric/east-asian variants, arbitrary `font-feature-settings` tags, `font-kerning`-gated GPOS kerning, and per-language GSUB feature selection (an element's own `lang`/`xml:lang`, or its nearest ancestor's — including an inline `<svg>`'s surrounding HTML document, when nothing in the SVG's own tree sets one) are all requestable per-element, same as HTML.
- **Font selection and variants** follow HTML text too: `font-variant-alternates` with [`@font-feature-values`](html-css-support.md#css-at-rules), `font-palette` with [`@font-palette-values`](html-css-support.md#css-at-rules) (selecting the CPAL palette of a color font), `font-variant-emoji`, `font-variation-settings`, `font-optical-sizing`, numeric `font-weight` and `font-style: oblique <angle>`. An inline `<svg>` reads the page's `@font-feature-values`/`@font-palette-values` rules; a standalone SVG image reads those in its own `<style>`. Text painted as outlines (gradient/pattern fill, stroke, `<textPath>` with a non-solid paint) is drawn in the font's default palette.
- **Font family lists, shorthands and fallback**: the whole `font-family` list is honoured (first available family), and a character the chosen font has no glyph for is drawn from the next family in the list that has one, then from a system fallback font, as in HTML text. The `font`, `font-variant` and `text-decoration` shorthands are expanded wherever they appear — a stylesheet, `style=""`, or a presentation attribute (`font="12px serif"`, `text-decoration="underline"`).
- **Decoration geometry**: `text-decoration-thickness`, `text-underline-offset`, `text-underline-position` (`from-font`, `under`), the `double` and `wavy` styles, and `text-decoration-skip-ink` (underlines and overlines skip glyph ink by default; `none` turns it off, and under `auto` CJK text is left unskipped) work as in HTML text.
- **`text-shadow`** (inherited, any number of layers, blur radius included) paints under the text as in HTML. A glyph painted under its own transform (an explicit `rotate=""`, a vertical-mode rotated glyph, a glyph stretched by `textLength`, or a `<textPath>` glyph) offsets its shadow in user space and blurs it through that transform.
- **`paint-order`** decides whether a stroked or gradient-filled `<text>` paints its stroke before its fill (`paint-order: stroke` for a halo). It applies to text only — shapes always paint fill, stroke, markers.
- **Whitespace**: by default whitespace collapses and the ends are trimmed. `xml:space="preserve"` and the CSS `white-space` values `pre`, `pre-wrap` and `break-spaces` keep every space; a line break becomes a space unless the text is [auto-wrapped](#auto-wrapped-text), and a tab becomes `tab-size` spaces under `white-space` (default 8) or one space under `xml:space`. `tab-size` takes a number.
- **Baselines**: `dominant-baseline` (`alphabetic`, `middle`, `central`, `hanging`, `mathematical`, `ideographic`, `text-top`, `text-bottom`), `alignment-baseline` on a nested element and `baseline-shift` (`sub`, `super`, a length or a percentage of the font size, accumulating through nested elements) move text off its default baseline. Where the font has an OpenType `BASE` table, the `ideographic`, `hanging`, `mathematical` and `central` baselines (the last as the middle of the ideographic character face) are read from it, for the horizontal axis under horizontal writing and the vertical axis under a vertical `writing-mode`; the other baselines, and any baseline a font does not state, are approximated from the font's metrics. Under a vertical `writing-mode` the default baseline is `central` and a baseline property moves the column sideways (`baseline-shift` towards the line-over side); a column that sets none stays centred. On a `<textPath>` the shift moves each glyph along the path's normal, like `dy`. The `BASE` table is read for the font's default script (a font's per-script baselines are not selected by the text's script), and its per-language `MinMax` extents and variable-font deltas are not read.
- **`textLength`** with `lengthAdjust="spacing"` (the default) on `<text>` and `<tspan>` spreads or squeezes the gaps between characters so the element spans exactly that length (a single character is left alone). `lengthAdjust="spacingAndGlyphs"` instead scales each glyph's position and advance about the element's start and stretches the glyphs themselves along the line (decorations, shadows, `text-anchor` and the bounding box follow the stretched text; a nested element's stretch composes with its ancestors'). Both modes also apply on `<textPath>` (along the path's distance) and under a vertical `writing-mode` (down the column, with upright and rotated glyphs alike).
- **`font-size-adjust`** (`none`, a number, `from-font`, and the `ex-height`/`cap-height`/`ch-width`/`ic-width`/`ic-height` metric forms) scales the glyph font so the chosen metric of each face — the primary and every fallback face on its own — matches the given value, as in [HTML text](html-css-support.md#css-property-support). It never changes `font-size`, so `em` lengths and nested `font-size: 2em` keep the unadjusted size. **`font-synthesis`** and its `-weight`/`-style` longhands (the shorthand is expanded from a stylesheet, `style=""` or a presentation attribute) turn off the faux bold and faux italic a face gets when it lacks the requested weight or style; SVG text has no small-caps or sub/superscript synthesis for `-small-caps`/`-position` to switch off.
- **`-webkit-text-stroke`** (and its `-width`/`-color` longhands, accepted from a stylesheet or `style=""`; a vendor-prefixed name cannot be an XML attribute) strokes the glyph outlines of `<text>`/`<tspan>`/`<textPath>`: for text it applies to, it takes the place of `stroke` and `stroke-width` (the colour is `currentcolor` unless given), and it paints with the same outline path, so `paint-order`, `<textPath>` and the decorations behave as for a stroked text. A zero width draws nothing extra. **`text-rendering: optimizeSpeed`** turns off kerning and optional ligatures where `font-kerning` is `auto` and `font-variant-ligatures` is `normal`; the other keywords are accepted and change nothing for PDF output. **`font-language-override`** selects the OpenType language system for the text's substitution features, as in [HTML text](html-css-support.md#css-property-support) (a presentation attribute takes the quoted string, `font-language-override="'SRB'"`).
- <a id="auto-wrapped-text"></a>**Auto-wrapped text**: a `<text>` with an `inline-size` (SVG 2) or a `shape-inside` is laid out in line boxes instead of on one line.
  - **The box.** `inline-size` is the width of the line box; it starts at the `<text>`'s `x` and runs towards the end of the line (so leftwards for `direction: rtl`), and the first baseline is at `y`. `shape-inside` takes a basic shape (`inset()`, `circle()`, `ellipse()` or `polygon()`, in user space, with percentages of the viewport): each line uses the stretch of the shape that holds the whole line box, and a line that fits nowhere at its height is moved down; text that does not fit before the bottom of the shape is not painted. A set `shape-inside` replaces `inline-size`. `shape-subtract` cuts the same kind of shapes out of whichever box is in use; a line broken in two by a cut-out continues in the second stretch.
  - **Breaking.** Lines break at the opportunities of the Unicode line breaking algorithm, as in [HTML text](html-css-support.md#text-shaping) (a word wider than the box overflows on a line of its own, except in a shape, where the line moves to where the word fits). `hyphens: manual` (the default) breaks at a soft hyphen (U+00AD) and draws the hyphen; `hyphens: auto` also uses the hyphenation patterns of the text's `lang`; `hyphens: none` ignores soft hyphens.
  - **`white-space`.** `normal` and `nowrap` collapse spaces and line breaks (and `nowrap` never wraps); `pre` keeps spaces and breaks at each line feed without wrapping; `pre-wrap` keeps spaces, breaks at line feeds and wraps (spaces at the end of a line hang outside it); `pre-line` collapses spaces but breaks at line feeds; `break-spaces` wraps like `pre-wrap`. A line feed is a space in text that is not auto-wrapped.
  - **Line boxes.** `line-height` (`normal`, a number, a length or a percentage; inherited) sets each line's height from the tallest content on it. `text-indent` (a length or a percentage of the box width) indents the first line. `text-align` (`start`, `end`, `left`, `right`, `center`, `justify`, `match-parent`) aligns each line in the box; without it `text-anchor` stands in (`start`, `middle` as `center`, `end`), and `justify` stretches the spaces of every line except the last and one that ends in a line feed. Bidi reordering is done per line.
  - **What does not apply.** `textLength` and the per-character `x`/`y`/`dx`/`dy` lists have no effect on wrapped text (`rotate` still turns the glyphs it names), and `<textPath>` descendants lay out along their path as usual. Wrapping applies to horizontal writing modes only: under a vertical `writing-mode`, `inline-size` and `shape-inside` are ignored. `shape-inside` and `shape-subtract` do not take `url()` references, `path()` or a reference box, and a circle or ellipse is approximated by a polygon. `text-indent`'s `hanging`/`each-line` keywords, `text-align-last`, `text-wrap`/`white-space-collapse`, `hyphenate-limit-chars` and the `shape-margin`/`shape-padding` properties are not applied; `break-spaces` does not wrap after preserved spaces, and `line-height` leading is added around the content by splitting it evenly.
- **Arabic-family joining and Devanagari USE syllable reordering** (see [Text shaping](html-css-support.md#text-shaping)) also apply to `<text>`/`<tspan>` content — each character's real joining form or USE category is resolved over the whole `<text>` element's flattened character stream, and a maximal run of mutually-joining or same-syllable characters shapes, measures, and (for a right-to-left run) display-reverses as one atomic glyph run, the same per-word treatment HTML text gets. A run never crosses a `<tspan>` boundary, never forms across non-zero `letter-spacing` (which already disables optional joining/ligatures in real shapers), and never includes a character other than its own first with an explicit `x`/`y`/`dx`/`dy`/`rotate` — such a character has no well-defined position inside a shaped multi-character glyph ([SVG 2 §11.5](https://www.w3.org/TR/SVG2/text.html#GlyphsMultipleCharacters)), so the run simply ends there instead of guessing. Not supported for `<textPath>` (glyphs there are still isolated nominal forms, each positioned independently along the path) or under a vertical `writing-mode`.
- **`text-decoration` v1 scope**: painted for horizontal-tb, non-`<textPath>`, non-per-character-rotated text only. A vertical-writing-mode `<text>` and `<textPath>` glyphs don't yet paint a decoration line at all (a real per-glyph-rotated decoration path is a larger follow-up); a glyph with an explicit per-character `rotate=""` is skipped for the same "no well-defined single line" reason. No small-caps *synthesis* fallback exists for `font-variant-caps: small-caps`/`all-small-caps` the way HTML's `CssBox` has — SVG only requests the real OpenType `smcp`/`c2sc` GSUB features, silently inert on a font that lacks them.
- **`writing-mode`'s pen-advance axis is resolved once from the `<text>` root**, not per nested `<tspan>` — unlike `text-orientation`, a mid-text change of writing-mode has no defined real-world meaning to preserve, so a `writing-mode` set on a descendant is ignored for layout purposes (only the root's own resolved value is consulted).

| Feature | Notes |

| `viewBox` | Full support, including all 9 `preserveAspectRatio` alignment keywords (`xMinYMin`, `xMidYMid`, `xMaxYMax`, etc.) and both `meet` and `slice`, plus `none` (independent-axis stretch) |

## CSS Integration

| Feature | Notes |
|---------|-------|
| Presentation attributes | Every property above is readable as a plain XML attribute (e.g. `fill="red"`) |
| `style="..."` | Inline `style=` is supported on every element, taking precedence over presentation attributes and `<style>` rules, per CSS cascade rules |
| `<style>` element | Fully supported for both inline `<svg>` and standalone SVG, matched through PeachPDF's **full CSS selector engine** — type (`rect`), class (`.foo`), ID (`#foo`), compound (`rect.foo`), comma-separated lists, **descendant/child/sibling combinators** (`g rect`, `.wrap > circle`), **attribute selectors** (`[gradientUnits="userSpaceOnUse"]`, `[data-x^="a"]`, …), and **structural pseudo-classes** (`:first-child`, `:nth-of-type()`, `:only-of-type`, `:not()`, `:empty`, …). `:empty` matches an element with no children other than white-space-only text; comments and processing instructions do not count as children, while any child element, or any text or CDATA section that is not pure white space, does. Standard specificity/cascade order applies, including [`!important`](https://developer.mozilla.org/en-US/docs/Web/CSS/important): an `!important` declaration overrides normal declarations regardless of specificity ([CSS Cascade §Importance](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_cascade/Cascade#importance)). `var()` custom properties and `calc()`/`min()`/`max()`/`clamp()` length expressions are resolved too. Precedence is inline `style=` > `<style>` rule (by specificity) > presentation attribute. A guaranteed-invalid `var()` (missing custom property with no fallback, or a cyclic reference) is *invalid at computed-value time* ([CSS Custom Properties](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_cascading_variables/Using_CSS_custom_properties#invalid_at_computed-value_time)): the declaration still wins the cascade and the property computes to its inherited (or initial) value — it does **not** fall back to a lower-priority declaration such as the presentation attribute. The [CSS-wide keywords](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_cascade/Value_processing#cascade-wide_keywords) are supported on the SVG paint/geometry properties in a `<style>` rule: `initial` computes to the property's SVG initial value (`fill`→`black`, `stroke`→`none`, `stroke-width`→`1`, …), `inherit` takes the parent's value, and `unset`/[`revert`](https://developer.mozilla.org/en-US/docs/Web/CSS/revert)/`revert-layer` roll the author cascade back to a lower origin — since an SVG presentation attribute is itself author-origin (specificity 0), the property computes to its inherited/initial value rather than the presentation attribute (with no `@layer` support, `revert-layer` behaves as `revert`; every SVG paint property is inherited, so `unset` behaves as `inherit`) |
| `@property` registrations | Honored in SVG styling, standalone and inline. A custom property registered with an [`@property`](https://developer.mozilla.org/en-US/docs/Web/CSS/@property) rule contributes its `initial-value` (the value a `var()` reference resolves to when the property is otherwise unset), its `inherits` flag (a descendant that doesn't set an `inherits: false` property resolves it to the `initial-value` rather than the ancestor's value), and `syntax` validation (a set value that doesn't match falls back to the `initial-value`) — the same behavior as for HTML. A standalone SVG uses `@property` rules from its own `<style>`; an inline `<svg>` uses the host document's registry |
| Document CSS cascades into inline SVG | For an **inline** `<svg>`, rules in the HTML document's own `<style>`/`<link>` stylesheets that match SVG elements (e.g. `circle { fill: red }` in `<head>`) apply to the SVG shapes — inline SVG participates in the document cascade ([SVG 2 §6 Styling](https://www.w3.org/TR/SVG2/styling.html)). A **standalone** SVG (`<img src="x.svg">` / `data:image/svg+xml`) is an independent document and is styled only by its own `<style>` — host-document CSS does not reach it |
| Selector case-sensitivity | SVG is XML, so selectors match SVG element types, attribute names/values, classes, and IDs **case-sensitively** ([Selectors 4 §6](https://www.w3.org/TR/selectors-4/#casesens)) — e.g. `RECT {}` does not match `<rect>`. This holds even for an attribute name that would otherwise be on the HTML Standard's fixed [case-insensitive legacy-attribute list](html-css-support.md#attribute-selectors) (`type`, `dir`, `align`, ...) — that exception is scoped to elements in the HTML namespace only, so it never applies inside `<svg>`. (HTML matching stays ASCII case-insensitive by default for that same fixed list, and case-sensitive otherwise.) |
| `class` / `id` | Read for `<style>` selector matching, same as HTML (case-sensitively for SVG) |
| `display` | [display](https://developer.mozilla.org/en-US/docs/Web/CSS/display) | From a presentation attribute, `style=`, a `<style>` rule or the document cascade. `none` removes the element and everything under it from rendering, wherever it is reached from: a `<use>` instance, a pattern or marker's content, a `<tspan>` (whose text drops out of the run). A `<switch>` whose first candidate is `display: none` still picks it, so it renders nothing, as in a browser. `contents` strips `g`, `a`, `switch`, `use`, `tspan` and `textPath` from the formatting tree and keeps their content ([CSS Display 3, SVG elements](https://www.w3.org/TR/css-display-3/#unbox-svg)): the element's own `opacity`, `transform`, `clip-path`, `mask` and `filter` no longer apply, a `use` loses its `x`/`y` offset, a `tspan` or `textPath` loses its position and rotation lists and a `textPath` its path, while inherited properties such as `fill` still reach the content. On every other SVG element, `contents` computes to `none`. |

## Unsupported SVG Features

The following SVG 1.0/1.1 features are not supported, each for the reason given:

- **SMIL animation** (`animate`, `animateColor`, `animateMotion`, `animateTransform`, `set`) — a static PDF page has no animation/timeline model to target.
- **Scripting** (`script`, event-handler attributes like `onclick`) — no script execution context exists in a static PDF page.
- **`cursor`** — no pointer/cursor model exists for embedded vector content in a PDF.
- **`view`** — fragment-based view navigation has no equivalent in static PDF page content.
- **Legacy SVG glyph-outline fonts** (`font`, `glyph`, `missing-glyph`, `hkern`, `vkern`, `font-face` and its children) — this would duplicate PeachPDF's existing full TrueType/CFF/WOFF/WOFF2 font pipeline for a mechanism SVG2 itself deprecated in favor of ordinary web fonts; use real fonts via `font-family`/`@font-face` instead.
