# Porting notes: FreeType code in PeachDrawing.Text

Everything in this directory is derived from the FreeType Project and is used under the **FreeType Project License** (`FTL.TXT`, in this directory, byte-identical to upstream). FreeType is dual-licensed (FTL or GPLv2); PeachDrawing.Text takes the FTL. Nothing FreeType-derived lives outside this directory. The rest of the package is BSD 3-Clause; this directory is BSD 3-Clause *and* FTL, and the FTL's credit requirement is met by the notices listed at the end of this file.

Two families of files are here: the TrueType bytecode interpreter and glyph loader (`Tt*.cs`, with the arithmetic helpers `Ft*.cs`), which are FreeType's own; and the CFF engine (`Cff*.cs` and `Ps*.cs`), which is FreeType's loader for CFF fonts (`Cff*.cs`) around **Adobe's CFF engine** (`Ps*.cs`, the `psaux` module of FreeType, which Adobe Systems Incorporated contributed). The Adobe files carry Adobe's own header on top of the FTL: it says the work is made available under the FreeType Project License and adds a patent licence grant from each contributor, with a termination clause if the licensee starts patent litigation over the work. That header is reproduced unchanged in every C# file derived from an Adobe file, and the notice is listed separately in the package's `THIRD-PARTY-LICENSES.md`.

The FTL asks that source redistributions keep `FTL.TXT` unaltered, keep the copyright notices of the original files, and indicate additions, deletions and changes "clearly ... in accompanying documentation". This file is that documentation.

## Deliberate differences, listed individually

These are the places where the port does something other than FreeType on purpose; everything else was ported as written, and the reference tests (below) show that the result is the same.

* **`SHZ` is clamped to the zone.** FreeType's `Ins_SHZ` bounds its loop by the end of the last contour of `zp2`; in a composite glyph that bound can exceed the number of points of the zone, and FreeType then writes past the end of the array (into allocation slack). The port clamps the loop to the zone's point count, which changes nothing for a glyph FreeType handles inside its arrays.
* **`WCVTP`/`WCVTF` write a private copy of the cvt.** The size's cvt is shared by every glyph of the size and never changes after `prep`; a glyph program that writes it gets a copy made at the first write.
* **The twilight zone is copied per glyph** (each glyph starts from what `prep` left) instead of being shared and mutated across glyphs.
* **TrueType: the glyph loader's scratch is reused from glyph to glyph.** FreeType allocates its `FT_GlyphLoader` (two outlines and the components of a composite) with the face and grows it in place; here a thread keeps one `TtGlyphLoader`, reached through the thread's `TtExecContext`, with the arrays it works in: the two outlines, the composite path, the unscaled and original copies of the points, the copy of a composite's points that its own instructions are run on, a stack of components (a composite that is a component reads its own after its parent's), and a buffer for the instructions of the glyph being loaded (`TtExecContext.RentInstructionBuffer`; the interpreter reads them by length, never by the length of the array). A load starts from the loader's `Init`, which resets everything a new loader would have had. What a hostile font asks for is not kept: when a load ends, capacity above 4,096 elements (16,384 for the stack, 16 KiB of instructions, 512 components) is dropped. The engine makes its outline from the loader's arrays while it still holds them (`TtGlyphLoader.Load<TState, TResult>` hands a reader a `TtGlyphView` of spans) instead of from a copy; `Load(size, glyph)` still gives the copy, which the goldens compare with FreeType. The twilight zone copy of `TT_Load_Context` no longer clears the room it is about to fill, and the 16.16 blend coordinates that `GETVARIATION` returns are made once for the face (`TtFace.BlendCoordinates`), not for every glyph. None of it changes a result.
* **A second work limit** on top of the instruction limit (see "Work limit").
* **CFF: Type 1 and multiple-master code is not ported.** Adobe's engine also draws Type 1 glyphs; here it is only used for CFF and CFF2 fonts, so the branches for `isT1` (the `seac` and `callothersubr` operators of Type 1) are left out. The `MultipleMaster` operator of a Top DICT is checked as FreeType checks it and otherwise ignored.
* **CFF2: the location is the normalized vector FreeType keeps, given to the face.** FreeType opens a font that has an `fvar` table at its default instance (`FT_Set_Named_Instance( face, 0 )`), so its `blend` operators always see a normalized vector with one coordinate for each axis (all zero at the defaults), while a CFF2 font without `fvar` has none and blends as the default design. The face is made with exactly that: the coordinates of the typeface's location in 16.16 (the hinting engine makes it from the design coordinates of the typeface exactly as FreeType does, `FT_DivFix` and the `avar` map in 16.16, and not from the package's own coordinates, which are rounded to 2.14 as the variation tables and fontTools do and differ from FreeType's by at most 2 in 16.16). The advances follow `HVAR` in FreeType's 16.16 arithmetic (`TtBlend.AdjustAdvance`).
* **CFF2: the Private DICTs are read again for the location once, when the face is made.** FreeType reads a subfont's Private DICT again in `cf2_font_setup` whenever the blend vector it was read with is not the one the glyph needs, ignores the outcome of that read (a Private DICT whose second read fails stays as far as it was read), and does so for the subfont of the glyph being loaded; the read depends on the location only, so doing it for every subfont at the start gives every glyph the same Private DICT.
* **CFF2: three refusals FreeType does not make.** An INDEX whose 32-bit count makes FreeType's 32-bit unsigned size of the table of offsets wrap (a count of 2^30 or more) is refused, where FreeType reads it as a small table (a hostile font, opened by FreeType and drawn from a table the count has nothing to do with); the data sets of a variation store together may name at most as many regions as the font has bytes (each is read once, however many entries share it), where FreeType reads every data set in full each time, which a font of a few kilobytes can turn into gigabytes (the store of the variation tables of a TrueType font is bounded the same way); and the results of the `blend` operators of one Private DICT may take at most 64 KB (FreeType appends to a buffer that grows without limit, and a blend leaves its results on the stack, so `512 blend` repeated for two bytes each makes 2,560 bytes each time). All three end as an unhinted outline. A random mutation of the CFF2 table of the fixtures met the first one in 3 of 50,000 mutants, and no other difference.
* **CFF2: FDSelect formats.** FreeType 2.14.3 reads FDSelect formats 0 and 3 only, so a CFF2 font with several Font DICTs and an FDSelect of format 4 is refused (as it is here), although the format is valid CFF2.
* **CFF: a glyph load starts from a fresh engine state.** FreeType keeps one `CF2_Font` for a size and recomputes what depends on the transform or the font dictionary when it changes; the port makes one for each glyph, which gives the same values (nothing else goes into them). The state of the `random` operator, which FreeType keeps in the subfont (so that a glyph's numbers depend on the glyphs loaded before it) and seeds from the address of an object, starts each glyph from the font's own `initialRandomSeed`, which is what FreeType does when it is given the random seed 0. The reference data is made with that seed and with a face for each glyph.
* **CFF: the engine's working objects are kept by the thread from glyph to glyph.** FreeType allocates the objects of one glyph load on the stack and in the heap of its memory manager; here a thread keeps the big ones and makes them ready for each glyph (`Cf2Pool` in `Internal/Hinting/`, which is this package's own code): the hint maps (each has an array of 192 edges), the hint masks, the interpreter's buffers (`Cf2InterpBuffers`: `put`/`get` storage, the stack of subroutine buffers, the stem hints, the moves of the second pass of the hint adjustment, the operand stack) and the outline the engine builds. What a new object would have been is what `Reset`, `Init` and `Prepare` make: the edges of a hint map and the elements of the stacks are not cleared, since nothing reads an edge at or past the map's count or an element that was not pushed since (a copy of a map copies the edges that count). What was kept is released first, so that a thread does not keep a font's data, and capacity above 4,096 elements (points, stem hints, stack elements) is dropped. The engine makes its outline from the thread's outline arrays while it still holds them (`CffGlyphLoader.Load<TState, TResult>` hands a reader a `CffGlyphView` of spans, and the matrix and offset of the font are applied in place) instead of from a copy; `Load(size, glyph)` still gives the copy the goldens compare. A load that throws leaves what it took to the garbage collector. The hint-independent parts of `Cf2Blues` are recomputed for each glyph as before. None of it changes a result.
* **CFF: sizes over 2000 ppem are not hinted.** FreeType retries a glyph that its engine calls too big (a scale over 2000 ppem) unhinted and scales the integer-unit outline; here the load fails, and the caller gets the unhinted outline of this package.
* **CFF: stem darkening is off**, as it is in FreeType by default; the engine has it, and a caller turns it on through `OutlineRequest.StemDarkening` (the reference tests turn it on with FreeType's `no-stem-darkening` property). It uses FreeType's default darkening parameters; the driver's `darkening-parameters` property is not reachable.
* **CFF: a load that makes more than 65,535 points or contours fails** (`FT_OUTLINE_POINTS_MAX`), as it does in FreeType, and a Font DICT array of more than 256 entries makes the CID-keyed font be read as if it had none, as FreeType does.
* **CFF: two limits are tighter than FreeType's.** Its charstring instruction limit is 20,000,000; the port's is 2,000,000 (`Cf2Font.InstructionLimit`), since a real glyph runs a few thousand instructions and a hostile font can make every glyph run to the limit. And a charstring may declare at most 4,096 stem hints (`MaxStemHints` in `PsIntrp.cs`): FreeType keeps every one (a glyph of more than 96 fails at its first hint mask or move anyway), so a charstring of a megabyte of `hstem` operators would make it hundreds of megabytes of them first. The instruction budget is one for the glyph (the charstring, its `endchar` accent and the re-run for the winding order share it), where FreeType's is a local of each call. A glyph that reaches either limit fails to load, as any error of the engine does, and the caller gets the unhinted outline.
* **CFF hinting has no modes.** Adobe's engine has one behaviour, so `GridFitting.Monochrome` gives what `Standard` does, and the caches share the entries. The advance of a hinted glyph is the `hmtx` advance scaled and rounded to a whole pixel.
* **Interpreter errors are values, not exceptions**, until a load fails as a whole; the numeric codes are the port's own.

FreeType's other test material was looked at and deliberately not used:

* **FreeType's `tests/` directory** holds only `issue-1063` in 2.14.3 (ported, above).
* **`freetype2-testing`** (the fuzzing corpora and harnesses) is distributed under the GNU GPL version 2 only, not the FTL, so nothing of it (harness code or corpus files) was copied into this package. ## Deliberate differences from FreeType, all files

* **Language.** C to C#. Pointer arithmetic became indexes, `FT_Vector*` arrays became parallel `int[]` x/y arrays, function pointers (`func_round`, `func_project`, ...) became `switch` dispatch on the same state, `goto`-based error exits became `return`/exceptions where the exit did nothing else.
* **`FT_Long` is 32 bits.** FreeType's `long`-typed values (`FT_Long`, `FT_Pos`, `FT_Fixed`, `FT_F26Dot6`) are C# `int`, with wrap-around on overflow (`unchecked`), matching FreeType built for a 32-bit `long` (Windows, which is what the reference build is). Intermediate products are 64-bit as in FreeType's `FT_INT64` code path. No path of the C code depends on the width of `long` for well-formed input.
* **Square pixels only.** A `PixelsPerEm` is one number, so `x_ppem == y_ppem` always: the "stretched" cvt/ppem routines (`Current_Ratio`, `Read_CVT_Stretched`, ...) and the non-square branches of `MD`/`MDRP`/`IP` are not ported, and `FT_Vector_Length` is ported only for the composite-offset case that still needs it.
* **No shared mutable state.** In FreeType a size object owns an execution context whose cvt/storage/twilight zone glyph programs can modify for the *next* glyph. Here the state left by `prep` is immutable and every glyph starts from a copy of it, so a glyph's outline never depends on which glyphs were loaded before it. (The reference data is generated by re-running `prep` before each glyph, which gives FreeType the same guarantee.)
* **Work limits.** FreeType stops a program after `TT_CONFIG_OPTION_MAX_RUNNABLE_OPCODES` (1,000,000) instructions; that limit is kept, but it is one budget for the font program, one for the CVT program and one for each glyph loaded with all of its components (FreeType restarts the count for each program run, so a composite glyph could multiply it). On top of it a second limit bounds the *total loop work* (`SLOOP`-driven and `LOOPCALL` iterations, `IUP`, the flips, `ROLL`, and code skipped over) of a glyph, which FreeType leaves unbounded, so a hostile font cannot spend minutes in one glyph. Exceeding either is the same `Execution_Too_Long` error FreeType raises. A third limit allows one glyph load to read 1,024 glyphs, components included: FreeType refuses a glyph that contains itself and nothing more, so a composite of composites (each listing the next many times) takes exponential time there.
* **Caches are bounded.** A face keeps 16 sizes and 4,096 hinted glyphs (by weight as well, one million contours-plus-segments), evicting the least recently used. Glyphs asked for lately are also found without a lock in an array of immutable entries (which a hit does not refresh in the least-recently-used order, and which forgets an entry that the cache evicts), and a size is made once when several threads ask for it at the same time; none of it changes what a request answers.
* **Errors.** FreeType error codes became `TtError` values inside the interpreter (`exec->error` is kept, because FreeType's non-pedantic mode continues after most of them). Errors that make FreeType refuse to load a glyph become a `HintingException`, which the public API turns into "return the unhinted outline".
* **Variable fonts.** The variation code is FreeType's (`TtVar.cs`), so a hinted instance of a TrueType font is FreeType's exactly: the normalized coordinates, the tuples, the deltas and the interpolation of the points a tuple leaves out, `cvar`, `HVAR`, `VVAR`, and the ranges of `MVAR` are all in 16.16 as `ttgxvar.c` has them. The differences are these. (1) **Work limits.** FreeType does whatever a table asks for; the port refuses a glyph, or a location, that would take more than `TtBlend.MaxDeltaWork` (16,777,216) delta values and axes weighed for each tuple (each tuple that applies costs the points of the glyph and its deltas, so 4,095 tuples over a glyph of 2,048 points, each with a delta for every point, is the limit, and a font of 16,382 axes has 4,095 tuples of them; a hostile table can make each of its 4,095 tuples apply to 65,535 points, which costs FreeType hundreds of millions of additions and gigabytes of transient arrays a glyph), and the steps of the deltas of one `MVAR` value or of the cross-axis mapping of `avar` version 2 (`TtItemVarStore.MaxStoreWork`, 67,108,864 regions times axes, which a font of some megabytes can multiply into minutes); a refused glyph is the unhinted outline, a refused location is a face that is not made. (2) **Buffers.** The lists of points and the deltas of a tuple are read into buffers that are rented once for a glyph, and not allocated for each tuple. (3) **A face nothing was set on has no blend** (FreeType's `face->blend` is made by the first call of any of its functions of variation, even by one that only asks for the location): the TrueType instructions `GETINFO` (the variation bit) and `GETVARIATION` see no blend on it, and its `cvt` is not varied (a `cvar` tuple whose peak is 0 on every axis applies at every location, and FreeType applies it at the defaults as well when it has been asked for them); a face set to coordinates that are all 0 has a blend as FreeType's has, and its control values and `MVAR` values are varied by the tuples and regions that apply at the defaults, as `tt_set_mm_blend` varies them (the `FT_FACE_FLAG_VARIATION` FreeType sets for `FT_Set_Var_Blend_Coordinates` with all-zero coordinates, which makes its loader scale from unrounded 26.6 values without any delta, is not reproduced: no public path makes such a face). The public API's typeface at the defaults is the face nothing was set on. (4) **An `fvar` axis whose minimum is above its default, or whose default is above its maximum**, is a font the package's own reader does not treat as variable (FreeType makes the axis a single value); the hinting engine's tables (`TtVarTables`) do as FreeType does, which only a test that hands them such a font sees. (5) **A normalized vector that rounds to 0 in 2.14** (the coordinates of the public API are multiples of 1/64 of a design unit, and on a wide axis the smallest is less than 2^-15 of its range) is the default location to the package's `Typeface.WithAxes`, which does not make a location of it, and a location to FreeType. (6) **Reads past the end of the file** give zeros, where FreeType reads whatever follows in memory (the golden data has no such table).
* **Not ported:** `TT_CONFIG_OPTION_BYTECODE_INTERPRETER` debugging hooks and `FT_TRACE` calls, the incremental-loading interface, embedded bitmap strikes, `FT_LOAD_*` flags other than hinted/unhinted and the target mode, `FT_Render_Mode` values other than normal and mono.
