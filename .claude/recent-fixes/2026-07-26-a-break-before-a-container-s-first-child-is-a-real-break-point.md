# A break before a container's first child is a real break point

_Landed 2026-07-26._

**A break before a container's first child is a real break point** (issues [#347](https://github.com/jhaygood86/PeachPDF/issues/347) and [#307](https://github.com/jhaygood86/PeachPDF/issues/307), the pair #320 called the cheapest on the board, [CSS Fragmentation 3 §3.1](https://www.w3.org/TR/css-break-3/#break-between) and [§5.2](https://www.w3.org/TR/css-break-3/#break-margins)). Both were the same guard: the forced break resolved against `DomUtils.GetPreviousSibling(this, false)` and did nothing when it was null, and §5.2's truncation was gated on `prevSibling is not null` for the same reason. So a container's **first** in-flow child got neither its break taken nor its margin truncated — and `section > h1 { break-before: recto }` is the idiom that shape is usually written in.

**The load-bearing idea is that a first child does not need a predecessor invented for it — §3.1 already says which one it has.** The break point before a container's first in-flow child *is* the break point before the container, propagating outward through every box this one begins, so `PredecessorOfEnclosingFirstChildChain` climbs that chain and resolves against the first real predecessor it finds. Everything downstream — the §4.4 flush-boundary epsilons, `MarginTopCollapse(null)`, `PlacedByForcedBreak`, the directional parity walk and its blank-slot reservation — is then the existing sibling path, unchanged.

**The first attempt derived the target from `baseTop` in `PlaceBlockBox` instead** (following #349's "decide where the box is placed, not where the break is planned"), with a flush test asking whether the box already sat at a slot top. It is wrong, and the suite said so: `<body>`'s own default margin puts `baseTop` a few points below the slot top, so `<h1 style="page:chapter">` as the **first element of a document** — whose named-page transition makes `_isForcedBreak` true — was pushed onto page 2 and manufactured a blank page in front of it (`NamedPageLayoutIntegrationTests.NamedPageElement_RegistersZero_OnlyWhenGenuinelyFirstOnPage`, `NamedPageGeometryAttributionTests.FirstElementNamed_WithOwnMarginTop_Slot0UsesNamedRule`). The climb gets that case right *structurally* rather than by tuning an epsilon: it reaches the root, finds nothing precedes the box in the flow, and takes no break — which is §4.4's "no empty fragmentainer" falling out rather than being asserted.

**The side still comes from the immediate sibling, not the climbed anchor.** A `break-after` states something about the break point *after* that box, and for a first child the anchor's own break point is several levels out; only the target is resolved by climbing.

§5.2's half needed no arithmetic at all — `baseTop` was already defined without a sibling (`ContainingBlock.ClientTop`) and the boundary test reads nothing else from one, so only the guard had to go, plus a null-safe form of the forced-break-marker clause. `HtmlContainerInt.HasRealPageGrid` was extracted on the way in, retiring the duplicated `double.MaxValue` sentinel expression in `FragmentainerContext`'s ctor.

Tests: 10 in `DirectionalPageBreakIntegrationTests` (per-value first-child parity, both flush-boundary cases, the reserved blank slot, the preserved margin) and 5 in `PageBreakIntegrationTests` (border and padding both blocking collapse-through, the break-before pass count, a margin that stays in its slot, and the collapse-to-root characterization). Each guard was verified load-bearing by reverting it individually — 8 and 3 failures respectively. 100% diff coverage; full net8.0 suite green (6233). **All 63 pre-existing showcases rasterize pixel-identically in PDFium**, which is the expected result: none of them declares a break or an oversized margin on a first child. `paged_media_directional_breaks` gained a colophon that does, **verified in both PDFium and MuPDF** — it opens on a recto, preceded by the manufactured blank verso carrying its own running head and folio.

**Post-change review found one live defect and one shape worth not re-deriving.** Making the break real exposed that `DomUtils.GetPrecedingKeepWithNextRun` carries the *same* null-sibling assumption in a third place, so a heading chained to a container's relocating first child is stranded. **Giving it the same climb is not sound, and this was measured rather than reasoned:** it drives `LayoutDocument` into its own no-progress backstop, failing three `KeepWithNextIntegrationTests`. The reason is structural — a run's members are **moved**, and resolving a *target* across a container is fine because only the target moves, while moving the container's predecessor with the container left behind is not a state layout settles into. Filed as [#361](https://github.com/jhaygood86/PeachPDF/issues/361), effectively blocked on §3.1 propagation ([#303](https://github.com/jhaygood86/PeachPDF/issues/303)), and characterized so closing it turns the test into the invariant it was drafted as. The review also caught that both flush-boundary tests as first written pinned the *nothing-precedes* case rather than §4.4's epsilons — the fixture needs a predecessor that ends flush on a slot top for the climbed anchor to reach that code at all.

**Accepted gaps:** a first-child margin with nothing on the ancestor chain to block collapse-through belongs to the **root**, not the child, so it is still not truncated ([#359](https://github.com/jhaygood86/PeachPDF/issues/359) — the root has no containing block for the break to fall at the top of, and a break-before published from the context root has no parent link to travel up). The other two recorded here — keep-with-next not chaining across a container (#361) and §3.1 propagation leaving the container spanning the boundary (#303) — are **now fixed**; see the Recent-fixes entry for both.
