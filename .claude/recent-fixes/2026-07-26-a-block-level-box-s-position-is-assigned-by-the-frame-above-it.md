# A block-level box's position is assigned by the frame above it

_Landed 2026-07-26._

**A block-level box's position is assigned by the frame above it** ([issue #390](https://github.com/jhaygood86/PeachPDF/issues/390), stage 1 of 4). Blink's layout contract is that a child does not position itself; `CssBox.PerformLayoutImp` wrote its own `Location`, and #390 records what that costs — five separate mechanisms exist for retracting geometry a box has already written down.

**The load-bearing observation is that "place this box" was two questions wearing one method.** How wide the box is follows from its own style and its containing block. *Where* it goes does not: the answer is margin collapsing against the previous in-flow sibling, which fragmentainer that sibling ended in, and the keep-with-next run chained to it — none of which a box can see from inside itself. So `PlaceBlockBox` is now `ResolveOwnInlineSize` (the child's half) followed by `PlaceBlockChild(child)` **on the parent** (the frame's half), which is the one place a block-level box's `Location` is written during block flow.

**The root is not special-cased, and that is what makes the split total.** It has no frame above it, so it stands in for its own: `PreviousInFlowSibling` reports null for a box the frame does not own, which is exactly what `DomUtils.GetPreviousSibling` already answered for a box with no parent. Every other box has `ParentBox == this` there, so the lookup is the same call it always was — including a box whose `ParentBox` was nulled out from under it (`RemoveHeaderFooterFromTree`'s row-group root), which took the null answer before and takes it now.

**`PlaceBlockChild` is synchronous**, which is the same statement in a second form: everything an offset depends on has already been measured by the time it runs. It can still decline to place the child at all — §5.2's margin truncation may conclude the break falls *before* it — in which case neither a position nor a named-page registration is written, and the box contributes no fragment to the fragmentainer being filled.

**What stage 1 deliberately does not do**, because stage 2 is what makes it possible: the *call* is still made from the child's own frame, since block layout reads `Location` while laying its content out, so the parent's child loop cannot place a child after `PerformLayout` returns until the child returns a size instead of writing a position. The child therefore still writes its own `Location` — through the parent's method, against the parent's inputs — and every retraction mechanism (`FragmentEmitter.InvalidateFrom`, `ResetChildrenForRefill`, `DiscardLineBoxesFrom`, the §4.3 pass re-entry, the `widows` rewind) stays exactly as it is. Stages 2–4 of #390 are untouched.

Behaviour-neutral by construction and verified as such: **all 65 showcases are byte-identical** after normalizing creation date, `/ID` and subset tags. Full net8.0 suite green (6378), CLI suite green (93); **100% diff coverage**. Tests: `BlockPlacementSeamTests` (5 — the seam's inputs, which is the half a box cannot answer alone: the previous in-flow sibling it resolves against, the three kinds of sibling that lookup skips, and the root finding nothing before it). Docs: `docs/architecture.md` §5.
