# `contain`, `content-visibility: auto`, and `legend` as a block

Closes the rest of the containment issue (#2242) that the fieldset/button change left: `contain: layout|paint|content|strict`, `content-visibility: auto`, and the fieldset-with-legend sample.

## The load-bearing idea

One predicate, `DomUtils.AppliedContainment(box)`, turns the two stored strings (`contain`, `content-visibility`, parsed by `ContainGrammar.Of`) into a `Containment` flag set and removes what cannot apply (no box, non-atomic inline, internal table box other than a cell). Everything else asks it through `AppliesLayoutOrPaintContainment` / `AppliesPaintContainment` / `AppliesLayoutContainment`. The properties are stored as text (like `scroll-behavior`), not as an enum, because the value is a set; the fast path for the initial values is two short string compares, which matters because `ClipsWithoutScrolling` and `EstablishesIndependentFormattingContext` are asked of every box.

What layout/paint containment does here, each at its one existing seam:

- **Independent formatting context** - `DomUtils.EstablishesIndependentFormattingContext`. That predicate already ended the float scans, margin collapse through a box and float containment, so nothing else changed for floats or margins.
- **Clip** - `CssBox.ClipsWithoutScrolling` / `ClipsOverflowHorizontally` / `Vertically`: css-contain-2 §3.4 says paint containment is `overflow: clip` on every `visible` axis, and `overflow: clip` was already modelled that way. A box that is a scroll container is left alone.
- **Containing block** - `DomUtils.FormsAbsoluteContainingBlock` replaced `IsPositioned` in the five places that find an absolute box's containing block (`GetNearestPositionedAncestor`, `ClippingContainingBlockOf`, the two abspos margin passes in `CssBox`, `AbsoluteContainingBlockOf`). A `position: fixed` descendant of a contained box is made `absolute` where the tree is built (`DomParser.NormalizeFixedInContainment`, after the flex/grid item normalisation, when every ancestor's cascade has finished): fixed placement is woven through fragmentation (repeats on every page), and an absolute box resolved against an ancestor is exactly what the spec asks.
- **Stacking context** - `DomUtils.IsStackingContextBox`.
- **No baseline** - `CssLayoutEngine.AtomicInlineBaselineOf` returns the bottom margin edge for a layout-contained inline-block/flex/grid.
- **`html`/`body` propagation (§2)** - `HtmlContainerInt.ResolveCanvasBackground` stops body's background becoming the canvas when `html` or `body` is contained (the root's own still is), and `MonolithicContent.IsViewportPropagationSource` stops body being the viewport's overflow source. Nothing propagates `writing-mode`/`direction`/`text-orientation` from `body` in this engine, so there was nothing to disable there.

`legend { display: block; padding-inline: 2px }` is the HTML UA sheet (§15.3.3) and what Blink, WebKit (in its style adjuster) and Gecko do. There is still no "rendered legend" set into the fieldset border; the legend is a block at the top of the content.

## Found by running it

- `ClipsOverflowHorizontally` is `true` for a box that clips nothing at all (it assumes "not clipping without scrolling means a scroll container"), so a test of "does not clip" must ask `ClipsItsOverflow` / `ClipsWithoutScrolling`, not the axis helpers.
- A `display: contents` shell is not in the box tree, so `FindById` returns null for it; the predicate also returns `None` for `contents`/`none`.
- An inline-block's baseline is read from the rectangle laid out so far, so a contained one with a fixed `height` is still aligned by the bottom of its content rectangle, as `overflow: hidden` already is; the baseline test compares the text position and sees only the descent.
- Cross-browser source (Blink, WebKit, Gecko) was read for the exclusions, the fixed containing block, the stacking context and the paint clip; Gecko's formatting-context code and WebKit's stacking-context handling for containment could not be read, so those two follow the spec text and Blink.

## Known trade-offs

- `NormalizeFixedInContainment` gives a `position: fixed` box inside a contained box the used position `absolute` where the tree is built (a fixed box whose containing block is not the page is placed exactly like an absolute one, and fixed placement is woven through fragmentation). Checked rather than assumed: (1) it cannot go stale, because `contain` and `content-visibility` are on `InteractionRestyler`'s structural list, so a hover or focus rule that changes them is never applied in place - the document is loaded again and the normalisation runs over the new styles (`AFixedBoxFollowsItsAncestorsContainmentWhenAHoverTurnsItOnAndOff`); no other in-place path (`StyleUpdater`, live animation) writes either property; (2) the one thing a fixed box has that an absolute one lacks, its own stacking context (css-position-3), is kept through `CssBox.FixedInContainment`, read by `DomUtils.IsStackingContextBox`. Not asserted: repeating a fixed box on every page - the engine does not draw even an ordinary fixed box's background on a second page, so a test of "repeats outside, does not inside" would test something this change did not make. Ancestors with a `transform`, `filter` or `perspective` also make a fixed box's containing block (css-transforms-1, filter-effects-1); the clip chain follows that (`ClippingContainingBlockOf`) but placement does not, which this change does not touch.
- `AppliedContainment` re-parses `contain` for a box that has one (no allocation now: a span tokenizer) every time a predicate asks; boxes with the initial values pay two short string compares. Caching it on `DerivedStyle` would remove the repeat if a profile ever shows it.
- The harness stops partway through the showcases on a machine without the bundled Thai/Khmer fonts (it threw while saving `dictionary_line_breaking`), so the before/after showcase comparison covered only the first 74; the engine (19,146) and PeachPDF (1,752) suites and the new containment showcase, rasterized with MuPDF and PDFium, carry the evidence.

## Size containment, style containment, `contain-intrinsic-*` and `content-visibility: hidden`

- **Size (§3.1)**: one predicate again, `CssBox.AppliesSizeContainment`, read at the places an intrinsic size comes from. Width: `GetMinMaxSumWords` treats the box as one unbreakable run of its `contain-intrinsic-width` (or nothing) and skips its flex/grid/words/children branches, and `GetLargestChildWidth` stops at it, so float, abspos, inline-block, flex and grid shrink-to-fit all follow (every caller re-enters those two). Height: `ApplyHeight` gives an auto height the intrinsic height plus padding and border, applies `min-height` itself (it bypasses `GetBoxHeight`'s), and skips §10.6.7 float growth. Replaced: `MeasureIntrinsicSize` (and math, which bypasses it) gets 0 or the intrinsic size, no ratio, and the 20px broken-image placeholder becomes 0. `MonolithicContent.IsMonolithic` includes it. The baseline is untouched.
- **`contain-intrinsic-*`**: four longhands stored as text (`auto? [none | <length>]`), the shorthand through `ContainIntrinsicSizeShorthandConverter` (a group is `auto`+value, so the converter splits at an `auto` that follows a complete group and keeps a space token between the two, or `auto 20pt` reads back as `auto20pt`). The logical and physical longhand of an axis are one cascade: `NoteDeclarationOrder` already stamps any name containing `-inline-`/`-block-`, so only the two physical names were added to `LogicalDeclarationOrder`, and `CssBox.ContainIntrinsicLength` compares stamps and maps inline/block to width/height by writing mode. A vertical box's width reads the block size, but the engine does not lay a vertical float out by it (the accepted gap on vertical writing modes), so that is tested at the helper.
- **Style (§3.3)**: `CssCounterEngine.GetEffectiveCounterReset` adds an implicit reset for every counter the subtree increments or sets, and a box that isolates a counter hands what follows it the counter it had *before* that reset (`CssCounter.ParentScope`, already the pre-reset counter) instead of the last box in its subtree (`TryGetOutgoingCounter`, and `GetLastChildInScope` stops at it). Quotes: `GetQuoteDepthAtStart` starts a contained parent's children at 0, and `ApplyQuoteSubtree`, the raw aggregate and the exact walk treat a contained box as adding nothing. Literal "as if counter-reset" would leave the box's inner instance visible to its following siblings, which is the leak the section exists to stop, so isolation follows the outcome the section describes.
- **`content-visibility: hidden`**: `DomParser.SkipHiddenContents`, after `FlattenDisplayContents` and before `CorrectTextBoxes` (so no words are parsed for skipped text), gives every child `display: none`; the generic `display: none` handling (about 88 sites: layout, paint, fragments, accessibility, hit testing, counters, quotes) does the rest. `content-visibility` joined `contain` on `InteractionRestyler`'s structural list.
- **A trap that was already there**: `GetLastChildInScope` looped forever when every child of a box was skipped (it set `lastChild = box` and then `box = lastChild`). A child with a counter scope of its own could reach it before; skipping `display: none` children (which is also correct: they generate nothing and must not count) made it routine, and the engine suite hung rather than failed. It now returns the box when nothing was left.
- **Found by running it**: `contain: strict` (and `content-visibility: hidden`) now has height 0, so what overflows it is clipped away by the paint containment that comes with it - a float inside is not painted at all. The earlier float-containment tests had to stop using `strict` for that reason.

## inline-size containment, overflow-clip-margin and content-visibility: auto on screen

- **`contain: inline-size`**: a new `Containment.InlineSize` flag, not in `strict`/`content`, never together with `size`. `CssBox.AppliesSizeContainmentInAxis(widthAxis)` is size containment, or inline-size containment where that axis is the box's inline one (the width in a horizontal writing mode), and every size seam asks it per axis (`GetMinMaxSumWords`, `GetLargestChildWidth`, `ApplyHeight`, `MeasureIntrinsicSize`, math); `MonolithicContent` keeps asking for full size containment, since an inline-size-contained box still breaks. `container-type: size|inline-size` now implies style containment plus size or inline-size containment in `AppliedContainment` (css-contain-3 §3.1); the existing container-query tests, including the convergence loop, passed unchanged, and a shrink-to-fit container is now as wide as an empty box, which is what the spec says.
- **A trap in margin collapsing**: `IsMarginCollapseThrough` did not know a contained box is a formatting context root, nor that a box with a `contain-intrinsic-height` is not empty, so a `content-visibility: hidden` box (all children `display: none`) with an intrinsic height was collapsed through and what followed it started at its top. Both are asked now. `GetElementBounds` showing three boxes at one Y is how it showed.
- **`overflow-clip-margin`**: the clip edge is derived in two places (`RenderUtils.OverflowClipGeometryOf` for fragments and `ResolveOverflowClip` for the live push) and re-derived from `OverflowClipBasis.PaddingBox` when pixel snapping is on, so the margin lives in one helper, `RenderUtils.OverflowClipEdgeOf`, used by both derivations, and the basis carries the pushed-out edge (`SnapPaddingBox` keeps whatever offset from the border box it is given). Radii: the visual box's radii (`ComputeInnerRadii` with the distance to that edge) grown by the margin where the corner is rounded, then `ApplyCornerOverlap`; `ComputeInnerRadii` with negative insets would have rounded a square corner. The margin applies to an axis only when `ClipsAxisAtTheOverflowClipEdge` (the box is not a scroll container and the axis is `clip`, or `visible` under paint containment): `ClipsOverflowHorizontally` is also true for `hidden`/`scroll`. A PDF clip is also cut at the page area (the fragmentainer's band), so a margin that reaches into the page margin does nothing there; the PDF test puts the box inside the page.
- **`content-visibility: auto` on a screen**: `HtmlDocumentOptions.SkipOffscreenContent`, `HtmlDocument.ContentVisibilityNeedsUpdate` and `UpdateContentVisibilityAsync` (new public API; `SetViewport` is synchronous, canvas-less and called by four native hosts, so it was left alone). Un-skipping cannot flip `Display` back: `CorrectTextBoxes` leaves a `display: none` subtree unparsed (no words, no generated content), so the relevant set is kept on the container by source ordinal, `DomParser.SkipHiddenContents` consults it, and a change is a `ReloadAsync` (reparse and layout, scroll kept by ordinal), at most four passes. Only what an earlier pass added may be removed by a later one, unless the host moved the viewport: starting from nothing relevant, placeholder boxes are all near the viewport, so pass one shows everything and pass two skips what the real sizes put far away. Remembered sizes (`contain-intrinsic-size: auto`) are recorded before each reparse (`RememberAutoSizes`). A skipped auto box has `AutoSkipped` (rare state) and `AppliedContainment` adds size containment for it.
