# `shape-outside` and `shape-margin` narrow the lines beside a float to its shape

Load-bearing idea: the float lookups (`DomUtils`/`LeftFloatAt`) still find a float by its margin rectangle; only the **edge a line must clear** is shape-aware. `FloatShapeOutline` resolves the shape with the same `CssClipPathResolver` `clip-path` uses (one basic-shape grammar), flattens it once per float geometry (`ConditionalWeakTable` keyed on the box, invalidated by a geometry/value key), grows it by `shape-margin` (rows of the shape swept by a disc, sampled), clips it to the margin box and answers "how far does it reach over the band `[line top, top + line-height]`". The band, not a single row, is what makes the numbers match Chrome (a circle's first 12pt line clears 82.5, the row nearest the centre, not the top row).

Trap that cost a debugging round: the per-word loop in `FlowBox` resets `CurrentX` to the float's edge on every word while the cursor is inside the float's rectangle (`GetLastLeftIntersectingFloatBox` is a point-collision test on the rectangle). With a shape edge at 80 and a rectangle edge at 100 every word of the line was put at x=80 on one line. `LeftFloatAt(..., g)` therefore drops a shaped float once the cursor is at or past the shape's edge for this band. Any new place that re-applies a left float edge per word needs the same.

Verified against Chrome 152 (per-line start of a 100pt left float in a 200pt box, 10pt/12pt Arial) for circle, circle + shape-margin, ellipse, inset, inset(round), polygon: all within 0.8pt (`ShapeOutsideTests`). Gaps in the accepted-gap file of the same subject.

## Image shapes and `path()`

`shape-outside: url()` reads the float's loaded image (`CssBox.ShapeOutsideImage`, loaded in `EnsureAuxiliaryImagesLoadedAsync` with the other auxiliary images, because layout is synchronous and cannot fetch) and keeps, per pixel row, the leftmost/rightmost pixel above `shape-image-threshold`; the image is stretched over the **content box** (css-shapes-1 §2.1: "sized and positioned as if it were a replaced element ... the element's used content box size"), and a url() takes no shape-box. A shape that has no outline yet (image not loaded, SVG, unparsable) must answer with the margin rectangle, while an outline that merely misses a line's band answers "not narrowed": `LeftEdge` distinguishes the two by `Resolve` returning null. Chrome 152 matched the line starts for image, threshold 0/0.3/0.5 and `shape-margin` within 1pt when the float's size equals the image's natural size. Chrome ignores `path()` in `shape-outside`, so that case follows the spec (coordinates in px from the reference box origin) and is checked against the geometry only. Trap: in a test, `path('...')` inside a single-quoted `style` attribute silently drops the declaration - use `&quot;`.
