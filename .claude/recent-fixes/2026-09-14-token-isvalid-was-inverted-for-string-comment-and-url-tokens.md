# `Token.IsValid` was inverted for String/Comment/Url tokens

_Landed 2026-09-14._

**`Token.IsValid` was inverted for `TokenType.String`/`Comment`/`Url` tokens**: a cleanly-closed string, a properly-closed comment, or a well-formed `url(...)` all came back `IsValid: false`, while a malformed one (an unescaped newline before a string's closing quote, an unterminated comment, a bad `url(...)`) came back `IsValid: true` - the opposite of what the property's name says. Found while implementing `block-ellipsis` (CSS Overflow 4), which needed to read a single `<string>` token's well-formedness and got backwards results.

Root cause: `Lexer.NewString`/`NewComment`/`NewUrl` (`CSS/Parser/Lexer.cs`) each accept their own `bad` parameter (this lexer's vocabulary: "did tokenizing this hit an error path") and forward it straight into `Token.NewString`/`NewComment`/`NewUrl`'s `valid` parameter (`CSS/Tokens/Token.cs`) with no negation - `bad` and `valid` read as the same boolean instead of opposites. Fixed at the three Lexer wrapper methods (`!bad` instead of `bad`), the one place the vocabulary actually crosses.

Two call sites were quietly compensating for the bug rather than relying on the documented meaning:
- `Token.ToValue()`'s `TokenType.Comment` case appended the closing `*/` when `IsValid` was *false* and omitted it when `true` - backwards on its own, which happened to cancel out against the storage bug. Flipped to `IsValid ? "*/" : string.Empty` now that `IsValid` means what it says.
- `CssValueParser.TryParseSingleString` (added alongside this investigation) deliberately skipped checking `IsValid` at all, for the same reason `GetFontFaceFamilyName` already silently did. Now gates on `IsValid` properly, so a `<bad-string-token>` (an unescaped newline before the closing quote) is correctly rejected; an EOF-terminated string with no closing quote is *not* rejected, since CSS Syntax's own consume-a-string-token algorithm treats that as a parse error that still returns an ordinary `<string-token>`, not a `<bad-string-token>` - only the raw-newline case is genuinely bad. The Lexer's own classification for that distinction (already correct, just wired to the wrong sense) was not changed here.

No other call site read `Token.IsValid` for these three token kinds - grepped the whole codebase to confirm; every other consumer of a String/Comment/Url token reads `.Type`/`.Data`/`.FunctionName` only, none gate on `.IsValid`. `GetFontFaceFamilyName` (the other single-`<string>`-token caller) deliberately stays ungated - documented why, rather than left as a silent asymmetry with `TryParseSingleString`'s new strict gate.

A post-change review of this fix (reasoning about `TryParseSingleString`'s newly-strict `IsValid` gate) surfaced a second, previously-inert defect this fix made live: `StringDoubleQuote`/`StringSingleQuote`'s and `UrlDoubleQuote`/`UrlSingleQuote`/`UrlUnquoted`'s own REVERSE SOLIDUS-at-EOF handling (a backslash as the very last character before end of input) unconditionally raised a parse error and forced `bad: true` - but CSS Syntax's actual algorithms disagree for both: a string's own REVERSE SOLIDUS branch says "if the next input code point is EOF, do nothing" (not bad), and a valid escape check (used by the url tokenizer) excludes only a following newline, not EOF - "consume an escaped code point"'s own EOF branch appends U+FFFD REPLACEMENT CHARACTER instead of erroring. Fixed all five call sites to match: the String case now does nothing (next loop iteration hits the ordinary, already-correct EOF branch); the three Url cases append U+FFFD and continue. `IsValidEscape` itself (the shared helper `UrlUnquoted` used, which has the identical bad-at-EOF quirk and is called from many more places - Ident/Hash/AtKeyword/Number escape scanning) was deliberately left alone: none of those token kinds have a bad/valid duality the way String/Comment/Url do, so nothing there reads an inverted-or-wrong `IsValid`, and widening the fix into that shared helper would touch far more surface for a case (a literal trailing backslash at absolute end of input) with no live consequence outside the three kinds this fix already covers.

Verified: `CssTokenizationTests` (`PeachPDF.Tests/CSS/Tokenization.cs`) now asserts `IsValid` on both the well-formed and malformed sibling of each affected scan branch (String/Comment/Url), rather than only asserting `Type`/`Data` as before - the exact gap that let the inversion ship undetected - plus new cases pinning the corrected backslash-at-EOF behavior (including one confirming a raw newline after the backslash, unlike EOF, is still correctly a bad token). New `CssValueParserTryParseSingleStringTests.cs` unit-tests the fixed gating directly. Full net8.0 suite green; 100% diff coverage; zero-warning solution rebuild.
