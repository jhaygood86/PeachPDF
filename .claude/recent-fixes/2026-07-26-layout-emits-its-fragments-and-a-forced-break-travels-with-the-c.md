# Layout emits its fragments, and a forced break travels with the container the box begins

_Landed 2026-07-26._

**Layout emits its fragments, and a forced break travels with the container the box begins** (issues [#331](https://github.com/jhaygood86/PeachPDF/issues/331), [#303](https://github.com/jhaygood86/PeachPDF/issues/303), [#361](https://github.com/jhaygood86/PeachPDF/issues/361)).

**#303's load-bearing idea is that a break value states something about a break point, not about a box.** [§3.1](https://www.w3.org/TR/css-break-3/#break-between)'s break point before a container's *first* in-flow child **is** the break point before the container, and a `break-after` on its last is the one after it — so new `Html/Core/Fragmentation/BreakPropagation.cs` reads both sides of a break point through the chains they begin and end, and the outermost such container takes the break. #347 already resolved a first child's break against a predecessor found by climbing that chain, which put the break in the right place while leaving every container the box begins where it was: each spanned the boundary and painted an empty stub of its own chrome on the page the content left. That is what propagation removes.

**Propagation stops before the fragmentation context root and before any box whose children an engine places** — the #166 boundary. The first is why nothing had to be added for §4.4: a document whose very first element carries a forced break reaches the root, finds nothing before it in the flow, and takes no break, exactly as before.

**Combination is §3.1's own rule, and it is not "the innermost wins".** A directional value forces a page break *as well as* naming a side, so it subsumes a plain `page` whichever of the two is deeper; only two *conflicting* directional values fall back to "the value on the latest element in flow", which for a value travelling outward is the deeper one.

**§5.2 governance had to be split from taking the break** (`_adjoinsForcedBreakPoint`). A box whose value the container acted on still adjoins a *forced* break point, so its margin is not truncated. Without the split, hoisting the break silently reversed a stated choice: a box carrying a break that cannot be taken at all — nothing precedes the container — kept its margin before and lost it after. Caught by `FirstBoxInTheFlow_CarryingAnUntakenForcedBreak_KeepsItsMargin`.

**#361 is then two changes, both of which needed the container to travel.** `EarlyBreak.Discover` collects the keep-with-next run at the breaking box's **propagation anchor** and records the anchor as the decision's `Subject`, so the container moves with its run — which is the thing widening the sibling walk could not do, and why doing that alone drove `LayoutDocument` into its own no-progress backstop. `TakeEarlyBreak` hands the decision to the loop that owns the box the break falls *before* rather than to the immediate parent (handing it to the parent regardless names a box that parent's `Boxes` does not contain, and the restart degrades to translating the wrong box). And the resumption path gets the same treatment in `LayoutBlockChildren`: a token naming a break before a container's own first in-flow child becomes a break before the container, which is also the only place that run can be collected, since its members are the container's siblings and nothing reachable from the box that broke.

**The anchor is consulted only where it yields a run, deliberately.** Redirecting the decision onto the container regardless would bypass `CanBeLaidOutAgain`'s destination-fit guard — `TryRestartAt` has no fit test of its own, and a box laid out again where it still does not fit breaks again from its new top, which is the runaway that guard exists to prevent (measured at 100,000 pages when #332 landed).

**#331: new `Html/Core/Fragmentation/FragmentEmitter.cs` replaces `FragmentTreeBuilder`, which is deleted.** The driver hands each pass's slots over as that pass ends — from the slot it began filling to one below where the next resumes — and `Finish()` materializes the tree. `CollectCandidateSlots`, `CollectSpans`, `BandSpan` and the two-pass structure are gone; which fragmentainers exist is a structural consequence of how layout filled them. The **one** geometric question left is asked after the final pass: the highest band any geometry reaches, because content no break record names (a monolithic subtree, a box that overflows its page) extends past the slot the pass that laid it out was filling. First/last come from the break record where the box appears in a chain, intersected with its emitted slot set — an intersection rather than a choice, so a box that both breaks and carries monolithic descendants cannot be told it is first in a fragmentainer it continued into. `BoxKey` survives as the emitter's `FragmentKey`: `BoxFragment` does not record its owning proxy, so that association has to be carried deliberately.

**Four things the showcase diff found that the 6,289-test suite did not.** Each was invisible to unit tests and visible as a wrong page.
(a) **A box's own `Bounds` are not final until the pass that *completes* it.** A block-level box's decoration area is its border box, and a box continuing into a later fragmentainer has not had its height applied on the pass that freezes this slot — its bounds are still zero-height there. Read then, **every intermediate fragment of a multi-page block lost its background and borders**. So everything defined over the whole box rather than over one slot — the box's own bounds, §6.2's unbroken strip, the overflow clip, `WholeBoxRect` — is resolved at materialization; only which per-line rectangles and which words landed in a slot is a per-pass fact.
(b) **§6.2's unbroken strip is the sum of *every* rectangle the box produces**, including ones a later pass has yet to add, so it cannot be computed when a slot is frozen — computed per pass, an inline crossing a page break described a strip a page short. It is also computed from the emitter's **own record** rather than a re-read of `CssBox.Rectangles`: a box laid out again has its rectangles reset and the multicol engine discards a virtual pass's wholesale, so a line box a frozen slot recorded need not still be in the live dictionary at all (a `KeyNotFoundException` in three tests).
(c) **A pass's output is not always final, and the emitter must be able to un-freeze it.** §4.3's movers are bounded within the pass that *discovers* a decision, but a box only reaches its epilogue on the pass that *completes* it — so `break-inside: avoid` relocated a box out of an already-frozen fragmentainer and the frozen copy kept painting it there. `InvalidateFor(box, slot)` drops the frozen slots and they are emitted again at the end. It is hooked at the geometry-mutation funnels (the `Location` setter via a new `CssBoxProperties.OnBlockAxisRelocated`, `OffsetTop`, `RectanglesReset`, `ResetForRefill`, `TakeEarlyBreak`) and **guarded on the box having been frozen somewhere**, which is what keeps ordinary forward layout — where every box is placed for the first time — from re-emitting anything. This is [#355](https://github.com/jhaygood86/PeachPDF/issues/355)'s "the driver must be able to un-emit or defer" arrived at from the other direction.
(d) **A word on a line the pass discarded keeps the position of the abandoned attempt.** §4.1 says a line box never straddles a fragmentainer, so `CreateLineBoxes` discards the in-progress line — but its words stay where they were being built, inside the fragmentainer being left, until the resumed pass re-places them. Frozen in between, they appeared as ghosts at the foot of the page they had left. New `CssRect.AwaitsTheNextFragmentainer` marks them; being positioned again clears it. **Parking them at the band edge instead is wrong and was measured wrong**: a directional break may resume several bands further on, so the parked word appeared at the top of a page it never belonged to.

**Also moved: `ResolveCanvasBackground()` now runs before the first pass** rather than after the last. It is purely cascade-driven, and §3.2's content-empty-page rule reads `SuppressOwnBackgroundPaint` — resolved afterwards, the promoted root background made every slot look non-empty (the Acid2 2→3-page bug, from the other side).

Tests: `BreakPropagationIntegrationTests` (11, each verified load-bearing by neutralizing propagation — 6 fail without it), `FragmentEmitterTests` (renamed from `FragmentTreeBuilderTests` and re-pointed, +5 covering the structural slot reach, re-emission after a cross-pass relocation, the discarded-line word rule, the cross-pass strip, and a multi-page block keeping its decoration), plus `PageBreakIntegrationTests`' characterization of the stranded heading **promoted to the invariant it was drafted as** and a new test pinning that the nested and equivalent-sibling shapes agree. Full net8.0 suite green (6294); **98% diff coverage**. **62 of 63 showcases are byte-identical** after normalizing creation date, `/ID`, subset tags and annotation UUIDs — `box_decoration_break` is the one that differs, and it differs by *losing* a spurious `slice` closing border at a page break, **verified in both PDFium and MuPDF**.

**Accepted gaps:** `break-inside: avoid` and §2 monolithic content on a container's first child still move the element without the container unless a run is chained to it (see the anchor note above; **now fixed** — see the Recent-fixes entry for #365, which asks the fit question of the anchor); a monolithic subtree's span still comes from geometry rather than from a break record, since it appears in none; and re-emission means a fragmentainer can be built more than once per layout, which is correct but not free — a document whose movers reach back across passes pays for it.
