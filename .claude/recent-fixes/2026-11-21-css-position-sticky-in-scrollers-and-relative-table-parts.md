# css-position WPT: sticky at scroll 0 in a scroller, and `position: relative` on table parts

css-position went from 35 to 54 passing reftests (floor 32 -> 51; the CI-font margin is kept).

**Sticky.** Three separate causes, found one at a time by rendering a mini reftest rather than reading code:
- The WPT runner never called `HtmlDocument.SetViewport`, so no displacement was ever computed. It does now (`WptRenderer`).
- `ViewportState.Axis` clamped a sticky box into its containing block on *both* edges, so a box already outside it (negative margin, content overflowing a fixed-height parent) was pulled back in. Browsers only limit a box that is moving towards the edge; each clamp now runs only in the direction of the shift. This is also why `position-sticky-bottom-004/006` regressed the moment the viewport was applied.
- A sticky box held inside an `overflow` container is painted under a translation, but the container's clip was pushed inside that translation, so it moved with the box and clipped it away. `ClipShiftFor` (the carried-frame correction for scrolling) now also subtracts a sticky box's own displacement, and its callers in `FragmentPainter.Clips` are guarded by `View.IsEmpty` rather than `HasScroll`. Culling (`_scrollFrames`) is likewise off inside any view-shifted frame, not only a scrolled one: `Canvas.GetClip` is in the frame the clip was pushed in.

**Trap:** `position-sticky-rtl` passed before only because the engine paints nothing for its reference (an absolute box at `left: 0` in an rtl scroller) and nothing for the sticky box. Applying the viewport made the test draw the sticky box and exposed that gap; it is a lost pass, not a regression of sticky.

**Relative table parts.** `CssLayoutEngineTable` never applied `position: relative` to a caption, row group, row or cell. `ApplyRelativePartOffsetsAsync` runs once after the table is finished (unfragmented tables only, `resume is null`), outermost part first, through `CssBox.OffsetLeft/OffsetTop` so the subtree moves with it. Two traps:
- A box positioned against a row or row group is placed while that group still has no rectangle (`SetRowGroupBoxDimensions` fills it in from its rows afterwards), so such boxes are laid out again before the offsets. Boxes whose containing block is the *cell* must not be: their static position went with the cell's vertical-align shift (`AbsolutelyPositionedDirectChild_WithAutoOffsets_MovesWithTheAlignedContent` caught this).
- A `top`/`bottom` percentage on a row, row group or cell refers to the height its parent part *declares* (`RelativeContainingBlockHeight`); `ResolveDefiniteHeightValue` deliberately returns null for a table.

**Static positions (two more).** A box that was block-level before blockification (`CssBox.WasBlockLevelBeforeBlockification`, decided once in `BlockifyPositionedBox` and carried through sibling style sharing in `SiblingStyle`, or sharing changes the PDF) is placed at the container's content edge below the line it interrupts, not at the inline cursor (`LayoutAbsolutelyPositioned`). A child of a flex container with auto insets is aligned by `justify-content`/`align-self` as the only item (`AlignStaticPositionInFlex`, horizontal writing modes only). Trap: the CSS-OM `align-self` has no `safe`/`unsafe` keyword, so `safe end` parses to `auto`; three css-flexbox abspos tests that passed because both sides sat at the start now fail honestly (net css-flexbox +1). An absolutely positioned `display: table` with `top`/`bottom` set keeps its content height (it is not filled between the insets, `GetBoxHeight`) and its auto margins centre it (`ResolvePositionedAutoBlockMargins` treats a table's height as definite). Floor is 55 (58 locally).

**Looked at and left:** `position-absolute-replaced-*` fail because an SVG data-URL image with only a `viewBox` is 88px wide at `height: 100px` even in flow (an image-sizing bug, not positioning); `position-absolute-in-inline-005..012` need inline-block/inline-in-block work (the engine's own render of their *reference* is already wrong, an inline-block `.container` breaks into stacked boxes).

**Phase A (cross-module).** Three causes behind many scattered failures, each found by rendering a mini reftest:
- The WPT runner's loader returned null for `data:` URLs, so every data-URL image, stylesheet or font in WPT was a broken image (a `viewBox`-only SVG at `height: 100px` came out 88px wide: the broken-image box's ratio, not an SVG sizing bug). It now delegates to `HostResourceLoader.LoadAsync`. Gains in css-flexbox (+8), css-text, css-backgrounds; css-values `ic-unit-016` passed only because both sides were broken images.
- `align-items`/`align-self`/`justify-items`/`justify-self` accepted `safe`/`unsafe` only in front of `center`, so `safe end` was an invalid declaration (the render-layer map had the combined keywords all along). The grammar is now `[safe | unsafe]? <self-position>` (`Converters.AlignItemsConverter`); the old `...IllegalPrefixValues` tests had encoded the bug. `justify-content`/`align-content` still accept it only before `center`, and no layout honors `safe` beyond the static-position fallback in `AlignStaticPositionInFlex`.
- A table is as wide as its widest caption (CSS 2.1 section 17.4): `DeclaredCaptionWidth` feeds `EnforceMinimumTableWidth` and the top caption's extent. Before it, a caption with a declared width was laid out against the grid width, so a caption on a narrow or row-less table painted clipped or not at all (+12 across css2-flow, css2-positioning, css2-floats, css2-tables). Only a declared `width` counts; a caption's min-content width does not yet.

**Looked at and left (Phase A).** thead/tfoot absolute children: the abspos child is placed again correctly (trace: 58 = 8 + 50) but the painted result is still the pre-offset place; the repeated group is painted from a proxy snapshot and the table passes again in between, and I could not tell which one wins. `RefreshSnapshot` and a detached-containing-block origin tweak changed nothing and were reverted. `position-absolute-replaced-no-intrinsic-size`: the wrapper box of an abspos `<img>` with `height: max-content` is not centred by `ResolvePositionedAutoBlockMargins` (not definite); a `Boxes is [CssBoxImage]` guess changed nothing and was reverted. `position-sticky-table-pixel-rounding` depends on how Chrome snaps column edges; `position-sticky-fixed-ancestor-003` is a 4773 px anti-aliasing edge.

**Not done:** the four `thead`/`tfoot` `-absolute-child` tests (a repeated group is replayed through a `CssProxyBox` snapshot that is not re-taken when its source cells are laid out again), a relative caption, tables that fragment, and the remaining css-position families (abspos static position in vertical writing modes and multicol, flex static-position alignment, `position-absolute-in-inline-005..012`).

**Phase B6: bidi level of a place (closes the #1309 accepted gap, whose file is deleted).** Measured in Chrome (served the WPT cache locally, Ahem loaded by hand, `getBoundingClientRect`) rather than derived: in a 300px rtl line a 4px absolute inline box is at `[box]bbb` [296,300], `bbb[box]` [248,252], `aaa[box]bbb` [252,256]; in ltr always its left edge at the place. The rule is UAX #9 plus one fact: the place is a neutral that takes the direction of two same-direction neighbors (N1) or else its inline's embedding direction (N2), reorders as a run of its own beside the higher-level run it follows or precedes, and the box starts there **in the direction of the place's level** (odd level: its right edge on the place; even: its left). `PlaceOnFinalLine` returns the place's parity, `PlaceAtABidiRunBoundary` finds the edge, `CssBox.InlineStaticPlaceIsRtl` carries it to `StaticPositionIn`. A block-level box uses the line owner's direction instead. The old `AmongInlineContentInADirectionRtlParent_TheRightEdge...` test encoded the spec-reading guess (#2153) and was rewritten to the measured value. `abspos-block-level-001` passed before only because its reference (an inline `<span>` abspos) rendered wrong the same way; it is correct now. css-position 63 (floor 60).

**Phase B7: a positioned inline's containing block across a page break (closes the #1336 accepted gap, whose file is deleted).** The pass that stops at a break lays out the boxes it set aside (`CreateLineBoxes`' `Break` branch) before the inline's later lines exist, so a `bottom`/`right` was measured from the last fragment on the page being left. The load-bearing idea is the one the right/bottom fallbacks already had: they move the box by *the difference from where it is*, so they are safe to run again. A box whose containing block is a positioned non-atomic inline and whose `right` or `bottom` is set is recorded on the line owner (`BoxesAwaitingTheInlinesLastFragment`) when a break lays it out, and `CssBox.PlaceAgainstTheInlinesFinalFragments` moves it when the flow completes, invalidating the pages it used to sit on (`InvalidateEmittedFragmentainersReceiving`, #1349). Boxes with only `top`/`left` are right the first time, as before. Not covered: a box whose *width or height* fills between two insets and so depends on the final fragments (it needs a reflow, not a move).

**Phase B8: overflow columns on a continuous surface (narrows the multicol overflow accepted gap to paged media).** A container whose fill leaves content after its last column (`LayoutRunSegment`) used to hand it to the next *page*; on a screen surface that stacked the extra forced-break columns vertically. It now refills with one more column at a time up to `MaxOverflowColumns` (the same rollback the balance retries use) when the surface is continuous, the container is not inside an outer column, and the leftover is either a forced column break (`EndsAtAForcedColumnBreak` walks the break token's `ChildToken` chain to the innermost `IsBreakBefore` child and asks `ForcedColumnBreakFallsBefore`) or the container is height-capped. **Trap:** `HasRealPageGrid` is true in screen mode too (the viewport makes slabs), so "no page grid" is the wrong test; and the budget-limited carry (content taller than a slab) is also a `BlockBreakToken { IsBreakBefore }`, so without the forced-break test a tall balanced container grew columns sideways. css-multicol +7 (floor 146).

**Phase B9a: static positions in vertical flows, and left-to-right runs in a `direction: rtl` column (css-position +8, all vlr/vrl `static-position` files).** `CreateVerticalLineBoxes` skipped absolute boxes among the words, so they sat at the box's origin. They get `InlineStaticPosition` now (before `LayoutOutOfFlowDescendants`, or in the epilogue for an rtl column, whose lines are finalized there), read through the same `StaticPositionIn`; a bottom-anchored box needed a `StaticBottomEdge` beside `StaticRightEdge`. Chrome was the oracle again (served the WPT cache, Ahem by hand). Two traps found by running it: (1) `ApplyVerticalBidiReordering` reversed a run by `run.IsRtl` alone, which is only right when the paragraph is left to right: in a `direction: rtl` column a left-to-right run is placed top to bottom from the bottom edge (Chrome `AAA [188,236]` above `BBB [252,300]`), while a *sideways-lr* column reads bottom to top with a left-to-right paragraph and must not be reversed, so the test is the paragraph's base level, not `InlineStartIsBottom`; (2) reversing slots mirrors an inline box's padding with the words, so the run is placed word by word from the bottom, the physical bottom spacing of boxes ending at a word below it and the top spacing of boxes starting above (reproduces Chrome: aaa 210, bbb 279, ccc 352 for a `padding: 5px 0 9px` span), with the word spacing recovered as the natural room between words less the boxes' spacing. The runs of a rtl paragraph also come from `Bidi.ReorderLine` in visual order from the left, i.e. from the inline end: they are iterated reversed. `no-vertical-writing-mode-layout.md` records what is left. css-position floor 68.

**Phase B9b: vertical multicol (css-position +8, the `multicol/static-position` files), and a cascade bug it exposed.** Three causes, the last one general: (1) a childless block taller than a strip was one indivisible piece in `VerticalColumnFlow.Pack`, so the references (a 600-wide empty box in a 100-wide column) did not split; it records one piece per strip now (`Node.Splits`). (2) A strip's extent came from its leaf lines only, so a container 100 wide holding a 16-wide line was painted 16 wide in every strip after the first; `MeasureExtents` adds a block's own far edge. (3) **Sibling style sharing dropped logical properties.** The second and later siblings of the same tag and attributes (no `id`) adopt the first's computed style, but `inline-size`/`block-size`/`margin-inline-*`... are kept on the box and become physical properties in `ResolveLogicalProperties` *after* the style was captured: the adopters had `width: auto`. This was found by tracing a `START child ... W=auto` line, not by reading, because every probe that gave the elements an `id` (which turns sharing off) passed. It reaches any document with logical properties on repeated siblings, horizontal ones too. The fix does not share a style from a box that carries a logical longhand (`CssBox.HasLogicalProperties`). Trap: `css-grid` `grid-size-with-orthogonal-child-001` passed only because its second `<span>` lost its `inline-size`/`block-size`; with the sizes applied it measures two columns (200 wide) - the orthogonal grid item measurement was already wrong and is now visible (net css-grid 0: `-002` passes now). css-position floor 76.

**Phase B10a: an inline-level absolute box among block-level siblings (css-position +10, all `inline-level-absolute-in-block-level-context`).** `StaticPositionIn` put such a box at the block's content edge, below the previous sibling. Its place is a line of its own at that y: as narrow as the floats before it leave it, aligned by the block's `text-align` as an empty line is, and in a right-to-left block with the box's *right* edge there (the same odd-level rule as the bidi work). `CssLayoutEngine.StaticPositionOfALineAt` does it. Trap: the existing `ExtentBesideFloats` is for a block asking about *itself* and looks at floats before the block, never at the floats among its children; with the absolute child as the reference it found none (an absolute box starts a formatting context, so the right-float walk treats it as already outside), so the helper scans the block's earlier floating children directly. Not done, and the reason `position-absolute-in-inline-003..012` stay: an inline split by a block is rebuilt as hoisted anonymous blocks and a clone of the inline, with nothing linking the pieces, so its first fragment (the empty piece at the end of the line before the block) cannot be found; the fix is to link the pieces in `CorrectBlockInsideInlineImp`. css-position floor 86.

## A positioned inline split by a block keeps its first fragment

`CorrectBlockSplitBadBox` turns an inline split by a block into hoisted blocks plus a clone of the inline that holds what follows, with no link to what came before. `CssBox.SplitInlineLeading` now names the first fragment (the piece before the block, or an empty fragment at the end of the last line of the block the inline began in), and `DomUtils.InlineContainingBlockOf` takes its top from it (css-position-3 section 2.1). Fixes `position-absolute-in-inline-003`.

Also, an inline whose first word wrapped away has no rectangle on the line it began on (`FirstHostingLineBox`); `InlineContainingBlockOf` now uses an empty fragment at the end of that line's last non-space word (css-position `-004`).

Not done: `-005` to `-012` (inline-block and multicol variants) have other causes.

## An inline-block with a forced line break is laid out as an atomic box

An `inline-block` whose content fits one line was flowed into its parent's line boxes, so a `<br>` (or a preserved newline) inside it ended the parent's line, and the box was painted as per-line fragments. `LaysOutAsAnAtomicBox` now also takes the atomic path when the box holds forced breaks (`CountForcedLineBreaks`), unless that would make a box that has to split across a page or column: `FitsTheFragmentainer` keeps the old flow when the box would straddle the fragmentainer's end, and inside a multi-column container, whose measuring passes have no fragmentainer to ask. Two existing tests (`InsetShiftedInlineBlock_SecondInternalLine_MovesAloneToNextColumn`, `Clone_InlineBlockCrossingSeveralPageBreaks_ReopensItsTopInsetOnEveryPage`) pin that split behavior.

Effect on WPT: css2-flow +3, css-lists +1, css-position `-004`/`-006` closer. `flexbox-baseline-multi-line-vert-001` stopped passing: its reference uses an inline-block with `<br>` and a float, and had matched only because the test and the reference were wrong the same way. `-005` is down to two columns of anti-aliasing from a fractional container offset (the fallback font's space width), not a positioning difference.
