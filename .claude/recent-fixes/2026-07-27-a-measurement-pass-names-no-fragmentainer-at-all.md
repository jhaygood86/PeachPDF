# A measurement pass names no fragmentainer at all

_Landed 2026-07-27._

**A measurement pass names no fragmentainer at all** ([issue #400](https://github.com/jhaygood86/PeachPDF/issues/400) (c), the third step of what [#390](https://github.com/jhaygood86/PeachPDF/issues/390) stage 3 is blocked on). A box laid out at a provisional position — a flex or grid item measured at the container's content origin, anything inside a monolithic subtree — has coordinates it is about to be moved away from, so a question about a fragmentainer is *meaningless* there, not merely unanswerable. It was expressed as a suppressed flag (`FragmentainerContext.EnterMonolithic`), which answers only "may I break?".

**The load-bearing observation is that several places ask *which* fragmentainer and never ask whether breaking is live.** `CurrentFragmentainer is { HasOwnBand: true }` appears five times in `CssBox.LayoutBlockChildren` alone, none of them consulting `IsFragmenting` — so a table cell nested in a multi-column container reached the column arms of that loop while the *table* engine, which places its own rows and never reads a resumption record, was laying it out. Suppression could not stop it, because suppression was never what it asked. `HtmlContainerInt.DetachFragmentainer`/`RestoreFragmentainer` replace the flag with an absence, and `_fragmenting` becomes `readonly`.

**The driver's own last-resort relaxation is not a measurement pass and keeps a context**, which is why the flag could not simply be deleted: that pass is real, with a real slot the emitter reads, and only must not break again. It now constructs a `suppressed: true` context instead of mutating one.

**This is where a real content-loss bug surfaced.** A `<table>` inside a `column-count` container is laid out in full and only partly emitted: 10 words on the box tree, **0** emitted before this change — the whole table invisible — and **5** after, the cell's first block only. No break value is needed; the plain nesting is enough, and a plain table emits all 10. The remaining half is the columns engine not fragmenting a monolithic child at all, filed as [#406](https://github.com/jhaygood86/PeachPDF/issues/406) and pinned as a characterization with the plain-table control beside it, so closing it turns the characterization into an equality.

**All 65 showcases are byte-identical** — none nests a table in a multicol, which is exactly why the loss went unnoticed. Full net8.0 suite green (6449), CLI green (96); **100% diff coverage**. Tests: `SuppressedPassFragmentainerTests` (3) and 2 re-pinned in `FragmentainerContextTests` (the detach composing, and a suppressed context existing but not fragmenting) — the `EnterMonolithic` test they replace pinned a mechanism that no longer exists.
