# The no-progress recovery's two remaining holes closed; the third stays open

_Landed 2026-07-30._

[Issue #499](https://github.com/jhaygood86/PeachPDF/issues/499) tracked three open leaves under css-break-3's "avoid & break-point quality" area: [#422](https://github.com/jhaygood86/PeachPDF/issues/422), [#423](https://github.com/jhaygood86/PeachPDF/issues/423), and [#440](https://github.com/jhaygood86/PeachPDF/issues/440). The first two close here; the third does not, and why is the more useful record.

**#422 — the driver's pass budget could exhaust silently.** `HtmlContainerInt.LayoutDocument`'s `for` loop had exactly two `break` exits — no outgoing token, and a detected cycle routed into `LayoutTheRemainderMonolithically`. A genuine, non-cyclic walk (a `(slot, token)` pair the driver has never seen, every pass) trips neither, so the loop fell off its own end with the in-flight token never emitted. The fix adds a third path after the loop that reuses the same monolithic recovery — but a bare `break` only exits a `for` loop, it does not skip code that follows it, so the first attempt fired that recovery *unconditionally* after every ordinary exit too, doubling `LastResortRelayouts` and breaking five existing tests. A `concluded` flag, set immediately before each `break`, is what actually distinguishes "reached a real conclusion" from "ran out of passes" — found by running the existing suite, not by reading the diff. `MaxFragmentainers` (100,000) is a `private const`, so a test can't reach exhaustion in reasonable time; `MaxFragmentainersOverride` is a new `internal` per-instance settable field read as `MaxFragmentainersOverride ?? MaxFragmentainers`, giving `NoProgressBackstopTests` a `WalkingBox` double (a genuine walk, never repeating) that exhausts a shrunk budget in milliseconds.

**#423 — the recovery could still drop a nested column's content.** `LayoutTheRemainderMonolithically` runs under a `suppressed: true` `FragmentainerContext`, but a `columns` container nested inside it still builds its own per-column context (`inheritsSuppression: true`), which correctly computes `IsFragmenting == false` — yet three arms in `CssBox.LayoutBlockChildren` (the escaping-break, forced-column-break, and column-overflow arms) gated purely on `HasOwnBand: true`, never asking `IsFragmenting`. So the column engine could still record a break, which `RetargetToTheNextPage` restates and `PublishBreakToTheContextRoot` writes into the recovery's own `relaxed.OutgoingToken` — which `LayoutTheRemainderMonolithically` discards unconditionally by emitting with `outgoing: null`. This is the same shape already diagnosed for tables (#400(c)) and documented in three `fragmentation-*` invariants; the fix adds the missing `IsFragmenting` check to the three arms, matching a pattern already used elsewhere (`CssBox.cs`'s escaped-forced-break arm). With the gate in place, a suppressed column context stops trying to record breaks at all rather than recording one nothing reads, so there is nothing left to drain.

**Twelve items was not enough to reproduce the drop.** The first regression test used a `columns: 2` container with 12 short items — passed with the fix reverted, because a small multicol's own two-column capacity happens to hold all of it regardless of the gate. Sixty items reproduces it: without the fix, everything past the point the container exhausts both its columns is silently missing (confirmed by reverting the fix and rerunning — 47 of 61 words gone). With the fix, nothing is missing, but two items came back **duplicated** rather than lost — a straddling unbreakable box drawn on both pages it touches, which [#484](https://github.com/jhaygood86/PeachPDF/issues/484)'s note already documents as deliberate for content that cannot be moved while breaking is suppressed, and unrelated to what this fix is about. The test asserts containment (nothing missing), not exactly-once, with a comment saying why.

**#440 — investigated, not fixed, and deliberately left that way.** The issue's own report: naively widening `TryRewindForWidows` to call the shared `PassRewind.RollBackTo` loses 16 words from the `paged_media_horizontal_reflow` showcase (two interior pages 408→400), while the full suite and 68/69 showcases stay green. Three escalating reproduction attempts here — a minimal sibling-after-a-widows-rewind fixture, a showcase-shaped fixture through the lightweight `LayoutHarness`, and finally the *actual* `PdfGenerator.GeneratePdf` production path with real PDF text extraction (PyMuPDF) — all produced **byte-for-byte identical** output whether `TryRewindForWidows` used the narrow, current rollback or the naive shared one. The last of these is as close to the real defect's own conditions as this environment can get, and it still didn't reproduce the loss.

This matches, rather than contradicts, what the invariants already say: `paged_media_horizontal_reflow` is called out as platform-sensitive, having regressed on `windows-latest` only, twice. Georgia is not installed in this Linux sandbox, so the font substitution here produces different line-wrap boundaries than production — plausibly missing the exact line-count shape that the real defect depends on. **Shipping an unverified change to the trickiest rollback in the fragmentation engine, on the strength of a reproduction that cannot exercise the actual failure, is worse than leaving the narrower-but-safe behavior in place.** `TryRewindForWidows` is unchanged; the investigation (three repro attempts, the platform-sensitivity hypothesis, and the concrete suspects the issue itself named — `ResetForRefill`'s whole-subtree marking, and the settled-widths pass being the only place this rewind can occur) is recorded as a comment on #440, which stays open.

Tests: `NoProgressBackstopTests` gained `WalkingBox` and three tests for #422, plus `TheRecovery_KeepsAMulticolChildsContent` for #423 (6 new facts total, all in this one file). Full net8.0 suite green (7290), 0 warnings solution-wide, 100% diff coverage on the two changed files.
