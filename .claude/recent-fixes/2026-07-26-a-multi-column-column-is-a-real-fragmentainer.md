# A multi-column column is a real fragmentainer

_Landed 2026-07-26._

**A multi-column column is a real fragmentainer** ([issue #322](https://github.com/jhaygood86/PeachPDF/issues/322), [CSS Fragmentation 3 §2](https://www.w3.org/TR/css-break-3/#fragmentainer): "a column in multi-column layout, or a page in paged media"). Only pages were modelled, so `CssLayoutEngineColumns` did its own thing — one tall virtual column, then whole children re-banded into `(page-row, column)` slots with `OffsetTop`/`OffsetLeft`. Nothing inside a column could take a break, because there was no fragmentainer there to take one against.

The engine is now a **driver over its own fragmentainers**, the same shape `LayoutDocument` has for pages: establish a nested `FragmentainerContext` per column, fill it through the ordinary block-children loop (`CssBox.FillFragmentainerWithBlockChildren`, which is `LayoutBlockChildren` — duplicating it is how the two would drift apart), read back a token, open the next column there. What the last column cannot hold travels up the ordinary chain and the page driver opens the next page.

**Every column shares one band.** Columns differ in the inline axis, not the block axis, so `[containerTop, containerTop + target)` is every column's band and a resumed column starts at the same `ResumeContentTop` a resumed page would. That is what lets the whole block-axis break machinery be reused untouched — `break-inside: avoid`, `orphans`/`widows`, §2 monolithic content and §5.2 margin truncation all now work inside a column **without knowing about columns**.

**The limit that remains is the box model's, not a simplification, and it was measured twice from opposite directions.** A top-level child is atomic per column. A `CssBox` carries a single `Location`, and columns sit side by side inside one page band — so a box split across two of them has both halves at the same document Y *and* the same X: its continuation lines are laid out **over** the ones already there (observed as doubled text), and the emitter's band membership (`IntersectsBand`/`BandCut`, now `FragmentEmitter.cs`) is a question about **Y alone**, so it cannot tell the halves apart to draw the box's background in both. Moving the continuing box's `Location` fixes the words and is exactly what strands the decoration. **The sizing comment on #322 says a column fragmentainer type is not needed here; that is true only of the whole-child model, and the issue's own Work section is the correct reading.** Splitting a child across columns needs per-fragment geometry — which is [#366](https://github.com/jhaygood86/PeachPDF/issues/366), **now fixed** (see the Recent-fixes entry): a column states its own geometry as it is filled, and `ResumeInTheNextColumn` no longer rewrites a break *inside* a child as a break *before* it. At the time, it did, and `CssRect.WouldStraddleFragmentainer` answered no inside a column.

**Four things found by running it, not by reading it:**
(a) **A child that keeps zero lines must break *before* itself** (§4.4), or it leaves an empty box at the foot of one column with its text at the head of the next. A column makes this visible rather than making it true, so it is not gated on being in one — and the full suite is unchanged by it.
(b) **A column's extent must be measured over only the children it holds.** Children the fill never reached still carry the *measurement* pass's geometry — one tall virtual column — so asking all of them inflates the container to a full page and makes it escape. This is how a two-page document became six.
(c) **`column-fill: balance` needs the search *and* a retry.** The whole-child packing estimate is now an estimate rather than the model, and it packs slightly tighter than the real fill: measured `target = 112.1 × 2` against `measuredHeight = 234.3`, spilling the tail onto the next page. And balancing belongs to the fragment holding the **end** of the flow, which cannot be known before filling it — so a continuation starts at the page budget and is re-balanced afterwards. Getting that backwards renders a continuation as one tall column.
(d) **A box re-placed at a new position registers its named page again without withdrawing the first** — the same leak class #332 closed for the prologue. `PlaceBlockBox` now withdraws its own.

Also: the directional-break parity walk is suppressed inside a column, because which side of the sheet a page falls on is not a question a column can answer — ungated it reserved a blank page while the box merely moved to the next column, honouring half a decision.

Tests: `MulticolLayoutIntegrationTests` (33 — `break-inside: avoid` and monolithic content at a column boundary, the shared band top, resumption onto the next page, `column-fill: auto` vs `balance`, a child taller than its column, out-of-flow children, plus the two boundaries characterized below). Full net8.0 suite green (6257); **99% diff coverage**. Showcase: `multicol` renders correctly in **both PDFium and MuPDF**, and of 63 showcases it is the only one that differs at all — by one entry per column in the page-spanning section, since the boundary is now a real fit test rather than the packing simulation's prediction. **Accepted gaps at the time:** a child is not split across a column ([#366](https://github.com/jhaygood86/PeachPDF/issues/366), **since fixed**); and a multicol container whose content is only text never columnizes at all, because `CssBox.LayoutContents` tests `ContainsInlinesOnly` — vacuously true of a box whose children are all text — *before* `EstablishesMultiColumnContext`. Both characterized in that file rather than left silent.
