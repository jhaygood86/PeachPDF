# Editing the text of a focused field

`HtmlDocument` gained a small editing model for the one text-like `<input>` that has the focus (`GetEditState`, `SetEditSelection`, `InsertText`, `ReplaceEditText`, `DeleteEditText`, `SetComposition`, `SetCaretVisible`, `GetEditPlace`). The selection, composition and caret live in a `FormEditSession` on the container, which the painter reads; the value itself stays an attribute, so the form-state API, the accessibility tree and a PDF all see one thing.

- **A change of focus loaded the source again and undid every form change.** With a `:focus` rule in the style sheet, `ApplyStateAsync` re-parses the document, and `SetChecked`/`SetValue` had only edited the live attributes, so focusing another control put every checkbox and field back as the source has it. Every change now goes through `SetControlAttribute`, which remembers it by source ordinal, and `ReloadAsync` re-applies them after the parse (`WhatAControlHoldsSurvivesLoadingTheSourceAgainForAFocusRule`). Nothing in the first form-controls work could see this, because no test turned a `:focus` rule on.
- **The session belongs to one field.** `Ordinal` names it; when the focus is on another field the caret starts at the end of that field's text. A value set from outside ends a composition.
- **The caret is measured, not stored.** Its place is the width of the text before it in the field's font (`ScreenFormControlPainter.OffsetOf`), for a password the width of the bullets it shows, so the painter and `GetEditPlace` agree by sharing the helper. That is a left-to-right measure; a bidi caret (two places for one index) is not done.
- **Not done:** `textarea`, `number` stepping and filtering, undo, and word-wise movement (a host moves the caret with `SetEditSelection`).
