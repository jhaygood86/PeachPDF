# Monolithic content named and honoured, and break values carried onto structural clones

_Landed 2026-07-25._

**Monolithic content named and honoured, and break values carried onto structural clones** (issues [#323](https://github.com/jhaygood86/PeachPDF/issues/323) and [#327](https://github.com/jhaygood86/PeachPDF/issues/327), the two #320 nominated next, [CSS Fragmentation 3 §2](https://www.w3.org/TR/css-break-3/#monolithic) and §3.1/§3.2).

**#327 is three lines, and its value is that the box model stops lying** — not that anything moves. `InheritStyle`'s `everything: true` branch now copies `BreakBefore`/`BreakAfter`/`BreakInside` beside the `BoxDecorationBreak`/`PdfTagType` precedent. **It changes no output, and both reasons are worth keeping** because they are easy to mistake for bugs: a repeated `<thead>` proxy's values are read by nothing (the table engine positions its own rows instead of routing them through `CssBox`'s sibling-relative break machinery, and `CssProxyBox.PerformLayoutImp` never calls the base), and on the split side the values are inert *by specification* — only **inline** boxes are ever split by the block-in-inline correction, and §3.1/§3.2 do not apply to inlines. Independently, `DomParser` wraps each split fragment in an **anonymous block**, so `GetPrecedingKeepWithNextRun`'s sibling walk sees the wrapper, not the fragment. Both are pinned as characterizations in `StructuralCloneBreakValueBehaviourTests` — the first draft of that file asserted a keep-with-next pull that cannot happen, and the box-tree dump is what showed why.

**#323's load-bearing idea is that "monolithic" was two different questions wearing one name.** New `Html/Core/Fragmentation/MonolithicContent.cs` (sibling of `BreakValues`, same static-classifier shape) keeps them apart: `IsMonolithic` is §2's own set — replaced elements and scroll containers, which **no** UA may break — while `PaginatesItsOwnContent` is a *PeachPDF* constraint on four layout engines. The old explicit predicate (`CssBox.LayoutMonolithicContent`) encoded only the second and read as a spec claim. `CssRect`'s "too tall to fit anywhere" guard and the cloned-inset folding route through `FitsNoFragmentainer`, and every `BoxFragment` carries `IsMonolithic`.

**Three traps in making §2 real, each of which was a live defect or a live risk:**
(a) **The `IsFragmenting` gate is mandatory, and only the showcase diff found it.** The behaviour reaches the epilogue's existing `break-inside: avoid` mover — "may not be broken" and "asks not to be broken" want the same relocation. Ungated, it fired for a scroll container inside a **table cell** (the `transform` showcase's `.stage`), shifting it against the *page* grid while the table engine was placing it against its own row grid, and moving it out from under its row. Full suite stayed green throughout; the 62-showcase rasterization is what caught it. Inside those engines a monolithic box degrades to being split — the #166/#308 boundary.
(b) **A box that fits in no fragmentainer is deliberately left alone.** §2 says overflow, but overflowing discards every fragmentainer past the first, so a ten-page `overflow: hidden` wrapper would lose nine pages. The `overflow: hidden` clearfix idiom is far too common to accept that; PeachPDF keeps fragmenting it instead and says so in the docs.
(c) **The root and `<body>` are excluded**, because their `overflow` propagates to the viewport ([CSS Overflow 3 §3.3](https://www.w3.org/TR/css-overflow-3/#overflow-propagation)) rather than making them scroll containers. Without it Acid2's own `html { overflow: hidden }` declares the whole document unbreakable.

Note `overflow: clip` needs no special case *yet*: `Map.OverflowModes` doesn't accept it, so it never converts and the box keeps `visible` — §2's `visible | clip` exception satisfied by accident. Implementing `clip` means excluding it here explicitly.

**Three more defects the post-change review found, none of which the suite *or* the showcase diff caught** — they needed geometry measured directly, so budget for that when touching this mover. (a) **A `display: none` box was relocated on its neighbour's coordinates.** `LayoutContents` only positions a box that places itself as a block; everything else takes the else branch, which copies the *previous sibling's* `Location`/`ActualBottom`. A hidden panel with `overflow: hidden` — an ordinary modal or accordion body — therefore measured the sibling's height and got moved, inflating `ActualSize.Height` by a page and widening `FragmentTreeBuilder`'s slot walk with it. That condition is now the named `CssBox.PlacesItselfAsBlockBox`, which both the dispatch and the mover ask. (b) **A box exactly as tall as the band never moved**: the exclusion asked `>=` against the *nominal page height*, but a band-tall box fits a page perfectly. `FitsInBand` is deliberately **not** the negation of `FitsNoFragmentainer` — the latter asks "could this ever fit anywhere" and keeps the boundary it inherited from the per-word relocation, and collapsing them would move where words land. (c) **The exclusion measured the wrong band**: `PageSize.Height` while the mover measures and relocates against `PageBandHeightOf`, which per-page `@page` margins size differently — so under those it could move a box onto a page it does not fit, or refuse one the destination would have taken. It now asks about the *destination* slot.

Also a real §3.3 deviation: excluding `<body>` unconditionally is wrong, since its overflow propagates only while the **root's own** is `visible` — under `html { overflow: hidden } body { overflow: auto }` the body is a scroll container in its own right.

**A relocation boundary worth knowing before trusting "moves whole".** Where a box had already begun flowing text across the boundary before the epilogue ran, the mover shifted it *uniformly*, so the fragmentainer gap travelled into the box as interior blank space and inflated its height. **Fixed by #332** — the box is now laid out again at its destination — so `RelocatedBox_MatchesWhatBreakInsideAvoidAlreadyDoes` is now an invariant rather than a characterization. Its fixture still varies the filler deliberately: 140pt is the one alignment in that range where the two ways of relocating a box happened to agree anyway.

**MuPDF showcase renders are nondeterministic run to run** (the random font-subset tag): two runs of *identical* code differed on a rotating one or two files. PDFium was stable across every run, so it is the renderer to trust for a byte-level verdict — verify a MuPDF-only difference by re-running before believing it.

**Engine-set separation (the #315/#322 groundwork).** `FragmentainerContext.IsFragmenting` was `_fragmenting && !SuppressWordPageBreaks`, which welded together the two questions its own doc comment says are distinct — so breaking could never be enabled for a placed flex/grid item without also re-enabling the legacy per-word relocation. The flag has exactly **two** writers, both `PerformLayoutBlockified`, both wrapping a measurement re-layout; each now enters a monolithic scope alongside setting it. Provably equivalent, and verified pixel-identical across all 62 showcases in both renderers.

**What sizes #315, and why it is not a guard change:** `IsFragmenting` is *already* false throughout every flex and grid item layout, independently of `EnterMonolithic`, because every item routes through `PerformLayoutBlockified`. So deleting the wrapper for those two changes **nothing** — items still cannot fragment. `AssignLocations`/`PlaceItemInCell` only *translate* an already-laid-out item (`OffsetTop`/`OffsetLeft`), so there is no final-placement pass for breaking to be enabled in; #315 has to *add* one. Likewise #322 is not "remove `EnterMonolithic` from multicol": that engine lays every child out as one tall virtual column and re-bands whole children afterwards, so unsuppressed it mints tokens against virtual coordinates that its child loop never reads — silent content loss, plus `ApplyHeight` never running, plus `column-fill: balance`'s binary search bisecting over garbage heights.

Tests: `MonolithicContentTests` (22, the predicate against §2's sets), `MonolithicContentLayoutIntegrationTests` (11, real geometry incl. the fits-nowhere and fixed-box exclusions), `BreakValueCascadeTests` (9), `StructuralCloneBreakValueBehaviourTests` (5), plus a `TallOutOfFlowChildOfAnEngineContainer` theory pinning that `LayoutOutOfFlowChildren` — which discards any resumption record a child leaves behind — is safe only while its caller suppresses. New showcase `paged_media_monolithic_content`, **verified in both PDFium and MuPDF**. **Accepted gaps:** a monolithic box inside flex/grid/table/multicol is still split (commented onto [#166](https://github.com/jhaygood86/PeachPDF/issues/166)); content that fits in no fragmentainer keeps fragmenting rather than overflowing ([#350](https://github.com/jhaygood86/PeachPDF/issues/350) — deliberate, see (b)); and the engine set itself is unchanged — #315 and #322 stay open, sized in comments on each.
