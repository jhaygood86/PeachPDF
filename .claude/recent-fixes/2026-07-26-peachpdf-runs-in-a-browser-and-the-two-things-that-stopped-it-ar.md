# PeachPDF runs in a browser, and the two things that stopped it are library defects rather than demo plumbing

_Landed 2026-07-26._

**PeachPDF runs in a browser, and the two things that stopped it are library defects rather than demo plumbing** (new `src/PeachPDF.Demo.BlazorWasm/`, a Blazor WebAssembly app that renders an uploaded HTML/MHTML/ZIP to PDF entirely client-side).

**`PdfGenerateConfig.AllowLocalFileAccess`** (default `true`, so no existing caller changes). `PdfSharpAdapter` served `file:` URIs from an internal `FileUriNetworkLoader` *regardless of the configured loader*, and fell back to the working directory as a `file:` base whenever that loader had none — true of both `DataUriNetworkLoader` and `MimeKitNetworkLoader`. A consumer rendering untrusted HTML had no way to refuse. The CLI had already needed this and worked around it by deriving `CliNetworkLoader` from `FileUriNetworkLoader` purely so the adapter's `as FileUriNetworkLoader` test would route `file:` to it — a hack a plain `RNetworkLoader` subclass cannot reproduce, and one the CLI's own MHTML path silently bypassed (`--no-local-files` was ignored for `.mhtml` input; **now fixed**, because the flag moved to the config where it covers every input kind).

**The load-bearing detail is what making `BaseUri` nullable breaks.** It was previously *never* null, so `ResolveAgainstDocumentBase` always produced an absolute URI and no loader had ever been handed a relative one — `RUri.Scheme` throws on a relative URI, `DataUriNetworkLoader` reads it unguarded, and `StylesheetLoadHandler` doesn't pre-filter (unlike `ImageLoadHandler`). Without the `!uri.IsAbsoluteUri` guard now at the top of `GetResourceStream`, the demo's most basic case — an uploaded file with `<img src="logo.png">` — throws. Verified load-bearing by neutralizing it.

**The browser default font.** `CssConstants.DefaultFont` fell through `DetermineDefaultFont`'s platform ladder to `"Segoe UI"` on browser/WASM — a font nothing there can satisfy, so `CssBoxProperties.ActualFont` threw outright. Two changes, because the question is asked at two different times: a new `isBrowser` branch names Liberation Sans (via the existing `PickBestAvailableFont`, same shape as the Linux/Android arms), and `PdfSharpAdapter.AddFont` points the default at the **first** family registered when nothing yet resolves it. That latches itself — `IsFontExists` follows one mapping hop, so the second registration cannot steal it — and a family whose real name *is* the default still wins, since `GetCachedFont` consults registered families before the mapping table. Both take their deciding input as a parameter (`AdoptDefaultFontIfMissing(defaultFontFamily, registeredFamily, defaultFontExists)`), mirroring `DetermineDefaultFont`'s own precedent, because neither branch is otherwise reachable on a CI runner whose default font *is* installed.

**`hyphens: auto` no longer takes down a render on a host without Brotli.** `HyphenationEngine.LoadPatternSet` called `new BrotliStream(...)` unguarded, and the pattern resources are Brotli-compressed — so on a browser host any document using `hyphens: auto` failed entirely instead of merely laying out unhyphenated. The decompressor is now a parameter with a real default, so the platform-failure arm is testable at all.

**What the browser cannot do, measured rather than assumed.** `System.IO.Compression.Brotli` throws `PlatformNotSupportedException` on browser/WASM, and **installing the `wasm-tools` workload does not fix it**: relinking natively *does* link `libbrotlidec.a` (confirmed in the emcc link line, and the relinked runtime was confirmed loaded), yet the managed side still throws — so the demo ships **WOFF 1.0** rather than WOFF2, at 2.3 MB against WOFF2's 1.6 MB for twelve faces. Don't re-attempt the wasm-tools route. This is also why `hyphens: auto` is inert there.

**Font assets consolidated into a repo-root `assets/fonts/`** shared by Tests, TestHarness and the demo — four files were previously byte-identical copies in two projects. Each project links what it needs into its output via `<None Include="..\..\assets\fonts\X" Link="X">`, so `AppContext.BaseDirectory` lookups are unchanged. The demo needs more than a link: Blazor's asset manifest records a `LinkBase`d file as living in `wwwroot/fonts/`, so the dev server serves nothing unless it really is there — hence the `StageSharedFontAssets` copy target (publish copies them anyway, which is why only `dotnet run` shows the difference).

Tests: `LocalFileAccessTests` (17 — adapter-level `BaseUri`/`file:`/relative-URI arms, plus end-to-end twins for images, stylesheets, `@font-face` and the deny-beats-`FileUriNetworkLoader` precedence), `DefaultFontFallbackTests` (3), `CssConstantsTests` (+4), `HyphenationEngineTests` (+2), `CliRunnerIntegrationTests` (+2 theories, incl. the MHTML case that previously leaked). Full net8.0 suite green (6355), CLI green (96); **100% diff coverage** on the library change. **59 of 64 showcases byte-identical**, the other four differing only by random link-annotation UUIDs; `unicode_range` changed format (TTF → WOFF) and is **pixel-identical in both PDFium and MuPDF**. The demo itself was verified end-to-end in the browser for all three input kinds and again from the published `/demo/` sub-path artifact. **Accepted gaps** (all in the demo's README): no WOFF2 and no `hyphens: auto` per the above; `Arial Narrow` renders at normal width, since Liberation Sans Narrow is not part of Liberation 2.x and ships under a different licence; the tab is unresponsive during a render, which needs `WasmEnableThreads` and COOP/COEP headers GitHub Pages cannot serve.
