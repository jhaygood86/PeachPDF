# A resumed pass no longer re-opens an inline box it never closed, and the overflow clip comes from the fragment

_Landed 2026-07-25._

**A resumed pass no longer re-opens an inline box it never closed, and the overflow clip comes from the fragment** (issues [#336](https://github.com/jhaygood86/PeachPDF/issues/336) and [#325](https://github.com/jhaygood86/PeachPDF/issues/325), the two the #320 epic nominated next). Two independent fixes, landed together.

**#336.** Since #321 a pass fills one fragmentainer, so a resumed pass re-walks a block's inline content from the top and fast-forwards past the words it already placed — and it was **re-opening every box it walked through**, as if each were starting fresh on the new page. `FirstHostingLineBox` was the half the issue named, but five more per-box side effects in `CssLayoutEngine.FlowBox` fired for boxes the pass only walked through: the leading spacing, the inter-box word space, the trailing spacing, the "handle width setting" branch, and the whitespace-only-box space. **The one idea:** every per-box side effect has to ask whether *this* pass is opening, placing or closing that box, which the resume ordinal already answers — `opensHere` (`WordOrdinal` at entry `>= ResumeOrdinal`, exact because ordinals are dense and identical across passes) and `coordinates.PlacedSince(fromOrdinal)`. `PlacedSince`'s first disjunct (`fromOrdinal >= ResumeOrdinal`) is load-bearing twice: it gets a box that visits *no* words right, and it makes the whole thing provably inert at `ResumeOrdinal == 0`, so an unpaginated document is unchanged.

**Three traps.** (a) **The two halves cannot be split** — guarding `FirstHostingLineBox` alone moves the rectangle right to meet still-indented text, and removing the drift alone moves the rectangle *left* of the block's content edge; either half is a worse state than the bug, which is why they are one commit. (b) **`clone` re-opens once, at the resume point, not per box.** With the leading spacing suppressed on the way down, the cloning share is accumulated into a `clonedResumeStart` parameter and spent where the flow actually resumes — so it names exactly the boxes straddling the break. Writing it as `DomUtils.ClonedInlineStart(b, blockBox)` (the literal mirror of the wrap path) double-counts a cloning ancestor whose content begins *exactly* at the resume point, since that box opens here and already got its spacing. The exception is mandatory, not cosmetic: `UpdateRectangle` subtracts the leading spacing on *every* line under `clone`, so a continuation starting at `ClientLeft` with no re-open puts the rectangle outside the block. (c) **`opensHere`, not `PlacedSince`, guards the width branch and the height-deficit branch** — both compare an advance measured in this pass against a whole-box dimension, which only means anything for a box the pass both opened and finished (one that opens and breaks again never reaches them, since `FlowBox` returns as soon as the break is recorded). Getting this wrong is not theoretical: with `PlacedSince` the width branch still fired for a *straddling* box and merged a rectangle at this page's coordinates into the box's own, inflating the unbroken strip.

`BubbleRectangles`' compensation for a box whose leading spacing landed on a line its content then wrapped off gained `&& !ReferenceEquals(box.ParentBox.FirstHostingLineBox, line)`: a resumed pass's opening line is never `LineBoxes[0]` (earlier fragmentainers' lines are kept), so where the break fell at an inline's own first word the spacing came off twice. Reaching that in a test needs the wrap to come from *overflow* rather than a `<br>` — a `<br>` word sits on the line it opens, so it, not the following box's word, is that line's first.

A second commit does the same for the exit side: `ApplyAtomicInlineVerticalInsets` shifts every word a box has flowed, so a resumed pass moved a finished inline-block's earlier words down again once per later pass (error growing with the document, not a fixed offset); the height-deficit branch added a walked-through box's entire height to the flow again; and `LastHostingLineBox` is guarded for symmetry rather than for a live defect (nothing reads a clobbered value, but only because of `BubbleRectangles`' early return and `UpdateRectangle`'s upward-only recursion — properties of other methods, not of the pair). **Two more sites the post-change review found, each a real defect and each now covered:** the **float branches** re-established the line start as `float.right + leftSpacing` unconditionally, putting back exactly what the leading guard had just suppressed (they now re-apply `appliedLeftSpacing`, the amount this pass actually charged); and the **`inline-flex` branch** was wholly unguarded — an inline-flex contributes no word ordinals, so nothing else in the walk notices it belongs to an earlier fragmentainer, and re-entering it repositioned an already-placed box onto the resumed page, re-ran the flex engine over its children and set the cursor to the box's own right edge (observed moving a page-0 box to page 8). It exits with `continue` rather than falling through to the recursion, which would walk a flex container's children as inline content and **advance ordinals the placing pass never had** — the one thing that would break every guard here at once.

**#325.** `RenderUtils.ClipGraphicsByOverflow` was the last paint-path reader of live `CssBox` geometry, and `ProxyFragmentPainter` worked around it by writing a proxy's snapshot back onto the shared source boxes first. The clip is now resolved in `FragmentTreeBuilder` (`OverflowClipOf`, reading through the same `BoxGeometrySnapshot` the builder already descends a proxy's subtree with) and carried on `BoxFragment.OverflowClip`, already fragmentainer-local; paint only intersects it with the current clip stack, the one part that genuinely depends on where in the walk the fragment is reached. `CssProxyBox.ApplySourceGeometry` and `BoxGeometrySnapshot.Apply` had no other callers and are gone. Worth knowing: the containing-block walk **dead-ends inside a proxied subtree** — `RemoveHeaderFooterFromTree` nulls the row-group root's `ParentBox` and `ContainingBlock` skips `table-row`/`table-header-group`, so it can never reach the table or `<body>`, and the only boxes whose live geometry is stale are exactly the ones the snapshot holds.

Tests: `ResumedInlineDecorationLayoutIntegrationTests` (13), a strip-width case in `FragmentTreeBuilderTests`, and `RepeatedTableHeaderClipIntegrationTests` (3, including a purity check that painting a page does not move the live source boxes — the invariant #325 restores). Each guard was verified load-bearing by reverting it individually. Showcase: `box_decoration_break` gained section 5, an inline crossing a page break under both values, **verified in PDFium and MuPDF**. Of 61 showcases only `aspect_ratio` moves, by one stray space width on a continuation line. **Accepted gaps:** a *straddling* inline-block's inset still lands on the completing pass and so shifts the earlier page's already-finalized words ([#343](https://github.com/jhaygood86/PeachPDF/issues/343) — the *finished* case is what commit 2 fixes); `RenderUtils.PushAncestorOverflowClips` still reads live boxes (its ancestor chain is discovered during the paint walk, so the builder never sees it — only wrong for a hoisted stacking participant inside a repeated header); plus the deferred items below, each filed.
