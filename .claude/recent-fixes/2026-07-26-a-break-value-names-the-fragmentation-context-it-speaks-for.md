# A break value names the fragmentation context it speaks for

_Landed 2026-07-26._

**A break value names the fragmentation context it speaks for** (issues [#312](https://github.com/jhaygood86/PeachPDF/issues/312) and [#313](https://github.com/jhaygood86/PeachPDF/issues/313), [CSS Fragmentation 3 §3.1/§3.2](https://www.w3.org/TR/css-break-3/#break-between)). `column`, `avoid-column` and their page-context twins were classified by two predicates that could only answer for the page — `BreakValues.IsForcedPageBreak`/`AvoidsPageBreak` — so `break-before: column` and `break-inside: avoid-column` parsed, cascaded and did nothing. Both now take a `FragmentationContext` (`Page` | `Column`, no `Region` member: PeachPDF establishes none, which is what makes `region`/`avoid-region` inert *by construction* rather than by omission). A page break forces a column break too — a column cannot span pages — so `IsForcedBreak(v, Column)` accepts every value `IsForcedPageBreak` does; `Combine` gained the matching rung, since `page` subsumes `column` the same way a directional value subsumes `page`.

**The load-bearing idea is that a column break needs a different *vehicle*, not a wider predicate.** A forced page break is realized by **placement**: the box is put at the next page's content top and the emitter's slot walk covers what was stepped over. That cannot express a column break at all, because every column of a container shares one block-axis band — there is no lower coordinate that means "the next column". So the prologue keeps asking the *page* question and is unchanged, and the column question is asked in `CssBox.LayoutBlockChildren`, which raises a **break decision** — exactly the shape the column-overflow arm beside it already had. One reader (`BreakPropagation`), two contexts, two vehicles.

**Asking it there rather than in the prologue is also what makes it work at depth.** The prologue is once-per-box-per-*layout*, and multicol's measurement pass runs it under the *page* context; `ResetChildrenForRefill` reopens only the container's own children, so a flag set there would be right for a direct child and wrong for anything below it. The child loop is inside the column context by construction.

**`i > start` is the whole termination argument, and no latch was needed.** A child moved to the next column becomes the child that column's fill *starts* at, so the question is not put to it a second time. That also states §4.3's fourth tier for free: a box that asks not to be broken and fits no column is split rather than walked from column to column.

**#313's arm is observable only because of #366.** A child that does not fragment internally is already moved whole by the column-overflow arm, which asks no break value at all — so "do not break me by a column" named nothing that could happen until a child could genuinely split across one. The question is asked of the child's **pending record**, which *is* the statement that it did not finish here.

**Two boundaries, both deliberate, and both now fixed** (see the Recent-fixes entry for #383/#382). A forced *page* break inside a column degraded to a column break (the page vehicle places the box past the column band and the overflow arm converts it) — honouring it properly needed the record to say "this escapes the container", which is what `BlockBreakToken.EscapesNestedFragmentainer` now does. And a keep-with-next run was not pulled by a column break: a run's members are *moved*, and there is nowhere to move them to — which turned out to be the wrong question, since the break can be *stated before the run's head* instead. `GetPrecedingKeepWithNextRun` accordingly stopped being the page question asked unconditionally and now takes the context it is being asked about.

Full net8.0 suite green (6362), CLI suite green (93); **97% diff coverage** (the uncovered line was a `CurrentBreakContext` helper with no callers, since removed — the two call sites name their context outright). **63 of 64 showcases are pixel-identical in PDFium**; `multicol` gained section 8, which puts the same panel in the same box twice and differs only in its `break-inside` value — **on the left it splits at the column boundary, on the right it moves whole** — verified in both PDFium and MuPDF.
