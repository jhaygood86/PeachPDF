# Monochrome emoji / astral codepoints via cmap format-12, and a `Rune`-based CID pipeline

_Landed 2026-07-21._

**Monochrome emoji / astral codepoints via cmap format-12, and a `Rune`-based CID pipeline** (follow-up to #158): supplementary-plane codepoints (above U+FFFF, i.e. emoji) now resolve and render. Three things composed to make this work. (1) The CID text-emission pipeline was made codepoint-based: `CMapInfo.AddChars`/`FontHelper.MeasureString`/`XGraphicsPdfRenderer.DrawString` iterate `Rune`s (not UTF-16 `char`s), `CMapInfo.CharacterToGlyphIndex` is keyed by codepoint `int`, and `PdfToUnicodeMap` emits a proper UTF-16 `bfrange` destination (astral → surrogate pair). `OpenTypeDescriptor` collapsed to a single `CharCodeToGlyphIndex(Rune)` (the `char` overload and the dead `PdfWidthFromCharCode` were removed; the WinAnsi `Widths` loop routes through `new Rune(ch)`). BMP text is byte-identical, so the whole suite is the regression guard. (2) New cmap **format-12** support (`CMap12` reader + `CMapTable.Read` selection of a format-12 subtable alongside the format-4 one; `CharCodeToGlyphIndexCore` resolves `>0xFFFF` via `CMap12.MapCodeToGlyph`; `CMapCoverage.Extract(CMapTable)` adds astral ranges for fallback). (3) A real bug fix in the word splitter: `CommonUtils.IsAsianCharacter` was `char`-based and its range `0x4E00-0xFA2D` *includes the UTF-16 surrogate range*, so `CssBox.ParseToWords` split every astral character's surrogate pair into two lone-surrogate (→ U+FFFD) words before it ever reached the font; both are now `Rune`-based. Subset/embed/`ToUnicode`/`/W` were already plane-agnostic. **Color** emoji stays unsupported (outlines only — [issue #175](https://github.com/jhaygood86/PeachPDF/issues/175)). Verified end-to-end by rasterizing real bundled Noto Emoji output in both PDFium and MuPDF. See `Format12CmapAstralTests` (real Noto Emoji subset bundled as a test asset), `CommonUtilsTests`.
