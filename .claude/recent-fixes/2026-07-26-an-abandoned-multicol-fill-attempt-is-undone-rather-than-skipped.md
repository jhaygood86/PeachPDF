# An abandoned multicol fill attempt is undone rather than skipped

_Landed 2026-07-26._

**An abandoned multicol fill attempt is undone rather than skipped** ([issue #374](https://github.com/jhaygood86/PeachPDF/issues/374)). `CssLayoutEngineColumns`' attempt loop re-runs `FillColumns` whenever the `column-fill: balance` target has to be grown or re-derived, and `ResetChildrenForRefill` — whose job is to undo the attempt being abandoned — **returned early on a resumed pass**. So the retry re-produced line boxes a box already held and `CssLineBox.AssignRectanglesToBoxes` threw `An item with the same key has already been added` out of a `[DoesNotReturn]` `ReportError`: a hard failure the caller sees, for any paginated multi-column container of ordinary text whose content heights happen to want a second attempt on a resumed fragment.

**The load-bearing idea is that a resumed pass divides the children in three, and the early return was right about only one third.** Below the resume point they hold the geometry earlier pages' fragments were built from — resetting one blanks a fragment already emitted, which is the real reason the guard was there. Above it they are being laid out here for the first time, exactly as on a starting pass, and want the existing full `ResetForRefill`. And the child *at* it is neither: it is **continuing**, so its prologue must not run (`RectanglesReset` would blank the earlier fragment) but what this attempt added to it must still go. That is new `CssBox.DiscardLineBoxesFrom`, hung off `InlineBreakToken.CompletedLineCount` — the same index `CreateLineBoxes` already finalizes from, so no new accounting was needed. `RewindForRefill` walks the resumption chain itself, one link per ancestor, so the three-way split is applied at every level rather than only at the container's own children.

**A word is undone too, and that half was found only by running it.** The lines go, but the words they held keep the position the abandoned attempt gave them, and an attempt at a different target need not reach all of them again — measured as a ghost `own` painted at the top of a column three pages from where the word really is. `ResetForRefill` and the discard both mark their words `AwaitsTheNextFragmentainer`, which §4.1's own discarded line already does and which `CssRect.Top`'s setter clears on being positioned again, so what survives is exactly what this attempt did not place. The full-reset half of this is **not** specific to resumption — it was equally wrong for a retry on a starting pass, just far less likely to be reached.

**The removal reaches the right boxes because a line knows them.** `CssLineBox.Rectangles`' keys are exactly the boxes `AssignRectanglesToBoxes` gave an entry to, so discarding through them covers every descendant the line touched — including the inline boxes whose rectangles a resumed flow deliberately does **not** reset (`FlowBox`'s `if (coordinates.ResumeOrdinal == 0) b.RectanglesReset()`).

Tests: `MulticolLayoutIntegrationTests` (+6 — the issue's own fixture laying out rather than throwing, no rectangle left keyed by a discarded line box, and the workhorse: every word claimed exactly once across the whole fragment tree, which fails one way if the undo leaves a ghost and the other way if it discards the resumed child's earlier fragment along with this attempt's). Each guard verified load-bearing by neutralizing it individually, including narrowing `DiscardLineBoxesFrom` to `0`. Full net8.0 suite green (6313), CLI suite green (93); **100% diff coverage**. **62 of 63 showcases byte-identical**; `multicol` gained section 7, a re-balanced fill on a resumed page, which **throws on the unfixed build** and renders correctly in both PDFium and MuPDF.
