# `aspect-ratio`

_Landed 2026-07-22._

**`aspect-ratio`** ([CSS Box Sizing Level 4](https://www.w3.org/TR/css-sizing-4/#aspect-ratio)): a box with a definite width and an auto height takes its border-box height from the width via the ratio. Value grammar (`[ auto || <ratio> ]`, `<ratio> = <number [0,∞]> [ / <number [0,∞]> ]?`) lives in one shared `AspectRatioGrammar` (`src/PeachPDF/CSS/AspectRatioGrammar.cs`, `TryParse(tokens, out double? ratio)`) used by BOTH Layer A (`AspectRatioValueConverter` validates → invalid dropped at parse) and Layer B (`CssLayoutEngine.TryGetAspectRatioHeight` re-tokenizes `box.AspectRatio` and computes the height) — the `BasicShapeGrammar` precedent. The hook is in `CssLayoutEngine.GetBoxHeight`: when `box.Height` is auto and the ratio + a definite `Size.Width` are present, `height = Size.Width / ratio + ActualBoxSizeIncludedHeight` (correct for both `content-box` and `border-box`, since the included term is 0 for border-box where `Size.Width` is already the border-box width). **Crucially**, the ratio-derived height is marked `IsHeightCalculated` (the `isRatioHeight` term added alongside `isDefiniteHeight`) so a **percentage-height descendant resolves against it** — this is the Charts.css linchpin: the `tbody { aspect-ratio: … }` gets its height, and the bars (`height: calc(100% * var(--size))`) take theirs from it. A zero ratio term (`1 / 0`) or bare `auto` yields no usable ratio (no sizing); a definite `height` overrides. See `AspectRatioGrammarTests` and `AspectRatioLayoutIntegrationTests` (ratio→height, box-sizing, definite-height override, and the percentage-height-child chain).
