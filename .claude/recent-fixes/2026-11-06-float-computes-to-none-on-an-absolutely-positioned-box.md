# `float` computes to `none` on an absolutely or fixed positioned box

An absolutely positioned box that also said `float: left` kept `Float.Value == Left` in the cascade, so `IsFloated` stayed true for it and the line flow's float lookups (`GetLastLeftIntersectingFloatBox`, the right-float scans, `FloatBox` and the inline wrap-around) found it: text beside it started at the box's width (x=100 for a 100px box) where a browser has x=0. It is out of flow by its position (`IsOutOfFlow` already counted it), so the box itself was placed right, which is why it stayed unseen. What showed: text beside it narrowed (or, for a right float with no insets, pushed below it), and a page-float value (`float: top`/`bottom`/`top-bottom`/`snap`) collected as a page float that reserved its height at the top of the page, moving the container and the text down by the box's height. It became visible for text once `clear` stopped counting such a box as a float (#2241). CSS 2.1 §9.7 says the computed value of `float` is `none` there.

The fix is in the cascade, where `BlockifyPositionedBox` already coerces the box's `display` for the same section: for `position: absolute`/`fixed` a `float` that `IsFloated` or `IsPageFloated` answers for is set to `none`, the idiom `NormalizeFlexOrGridItem` uses for a flex item (the predicates are read all over layout, so coercing the computed value is what makes every reader agree; filtering in one reader would leave the others). `float: footnote` is not touched: an absolutely positioned box is never a footnote source (`IsFootnoteSource` refuses it), so it stays an ordinary positioned box and its stored value is harmless. The helper `ComputeFloatToNone` is shared with the flex/grid item case.

What was found by running it: the text had to be in its own block for the bug to show (an inline run directly in the positioned container was not narrowed, which is why the first PDF test passed without the fix), and an abs box placed away from the text (`left: 200px`, `right: 0`) never showed it. Compared with headless Chrome, the box and the text match for six shapes (no width, `float: right`, `fixed`, margins and padding, inside inline text, with a `clear`).

**The declarative API too.** A review found the same bug through `DocumentNode.SetStyle` and `StyleSheet` rules: that path never runs the HTML cascade, so step 10 never ran (text at x=95 instead of 20). `DomParser.BlockifyPositionedBoxes` now runs `BlockifyPositionedBox` over the declaratively built tree once the builder's and the stylesheet's styles are final (`HtmlContainerInt`, before the bidi pass), skipping boxes of a spliced HTML fragment, which had a real cascade. It has to be the whole step and not the float alone: on that path an absolutely positioned box only read as `block` because `ActualDisplay` blockifies a float, so coercing the float by itself would have left an inline positioned box; a declarative absolutely positioned inline box is now blockified as in HTML.

Known and left alone (found by the reviews, each older than this change): `aaa <span style="position:absolute">` in a multi-column container splits the run and "bbb" moves to the next column ([#2247](../accepted-gaps/text-after-an-absolutely-positioned-inline-box-in-a-multi-column-container-moves-to-the-next-column.md)); a `::before` with `display: contents; position: absolute` is placed after the text, with or without `float` ([#2248](../accepted-gaps/a-pseudo-element-with-display-contents-and-position-absolute-is-placed-after-the-text.md)); `position: running()` with `float: left` keeps `IsFloated` (running boxes are skipped by the float scans, so no text is narrowed).
