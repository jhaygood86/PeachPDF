# `float` computes to `none` on an absolutely or fixed positioned box

An absolutely positioned box that also said `float: left` kept `Float.Value == Left` in the cascade, so `IsFloated` stayed true for it and the line flow's float lookups (`GetLastLeftIntersectingFloatBox`, the right-float scans, `FloatBox` and the inline wrap-around) found it: text beside it started at the box's width (x=100 for a 100px box) where a browser has x=0. It is out of flow by its position (`IsOutOfFlow` already counted it), so nothing else was visibly wrong, which is why it stayed unseen until `clear` stopped counting such a box as a float (#2241) and the text was the only thing left that avoided it. CSS 2.1 §9.7 says the computed value of `float` is `none` there.

The fix is in the cascade, where `BlockifyPositionedBox` already coerces the box's `display` for the same section: for `position: absolute`/`fixed` a `float` that `IsFloated` or `IsPageFloated` answers for is set to `none`, the idiom `NormalizeFlexOrGridItem` uses for a flex item (the predicates are read all over layout, so coercing the computed value is what makes every reader agree; filtering in one reader would leave the others). Footnote floats are not touched, for the reason given there.

What was found by running it: the text had to be in its own block for the bug to show (an inline run directly in the positioned container was not narrowed, which is why the first PDF test passed without the fix), and an abs box placed away from the text (`left: 200px`, `right: 0`) never showed it. Compared with headless Chrome, the box and the text match for six shapes (no width, `float: right`, `fixed`, margins and padding, inside inline text, with a `clear`).
