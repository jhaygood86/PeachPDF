# The driver goes back to the pass that placed the run head

_Landed 2026-07-26._

**The driver goes back to the pass that placed the run head** ([issue #355](https://github.com/jhaygood86/PeachPDF/issues/355), [CSS Fragmentation 3 §4.3](https://www.w3.org/TR/css-break-3/#possible-breaks)). #332 made the keep-with-next run pull a **restart of the parent's child loop**, guarded by `resumeFrom >= start`. That guard was doing two jobs at once — keeping the restart inside this pass's child range, and protecting the fragments of a fragmentainer already filled — and only the first is the loop's. The second is the driver's, and since #331 it can withdraw what it emitted.

**The load-bearing idea is that the head does not have to be found again, only *told where to go*.** The pass to re-enter is named by the fragmentainer the head is in (`_passEntries`, one `(slot, token)` per pass, recorded before the pass runs — the one thing re-entry needs and cannot re-derive). The head gets the break's target through the same `ResumeAt` one-shot channel a break-before uses, and **every other member of the run, and every box after it, re-derives from the sibling above it** as the re-entered pass reaches it. That is exactly what `TryRestartAt` does inside one pass, and the reason neither has to compute a group offset.

**Folding the request into `TryRestartAt` rather than adding a call site is what keeps the guards honest.** Every guard above the range test — the head being one of this box's children, and the repeating-header table that does not survive a second layout — applies to the driver's replay as well as to the loop's, so the repeating-table scan moved *above* the range test rather than being duplicated. A granted request makes everything the pass produces moot, so the loop simply carries on: `resumeFrom = raisedAt + 1` is how "carry on" is spelt through the existing `i = resumeFrom - 1; continue;` call site, which is therefore unchanged, as are the other two callers.

**The pass is named by slot, and exact match is the honest test.** A pass can cover several fragmentainers — a forced break steps over one without ending the pass — so a head can sit in a fragmentainer *no* pass was filling, and there is then no pass to name; the correction falls back to moving the group, which is what it always did. "The last pass at or before the head's slot" was considered and is wrong: the pass after the one that placed the head can be filling the head's own slot, and re-entering *that* one starts after the head.

**One rewind per head per layout** (`_passesRewoundFor`, cleared in `LayoutDocument` — #371's finding 7: a latch cleared only at construction silently disables the correction on every layout after the first). It is defensive rather than reachable: `EarlyBreak.Discover` only collects a run that *fits* the destination, so the re-entered pass finds the constraint satisfied.

Tests: `EarlyBreakLayoutIntegrationTests` — the 115pt fixture **promoted from the characterization it was drafted as** (`PulledRun_FromAResumedPass_MovesTheGroupInsteadOfReLayingItOut` → `PulledRun_FromAnEarlierPass_LeavesNoFragmentOnThePageItLeft`, plus 115 added to the no-interior-gap theory), and `PulledRun_ClaimsEveryWordExactlyOnce` — #374's workhorse invariant, which fails one way if the re-entered pass leaves a ghost and the other way if un-emitting the head's fragmentainer discards content that legitimately belonged to it. Full net8.0 suite green (6369), CLI suite green (93); **94% diff coverage** (the two uncovered lines are the defensive decline above). **All 64 pre-existing showcases are pixel-identical in PDFium**, which is the expected result — none of them has a run head in an earlier pass. New showcase `paged_media_keep_with_next` does, and **on the unfixed build its paragraph arrives with the page gap still inside it, as blank space between two of its own lines**; verified in both PDFium and MuPDF.
