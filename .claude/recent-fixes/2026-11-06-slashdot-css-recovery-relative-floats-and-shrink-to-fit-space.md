# Slashdot: stylesheet recovery, relative floats, and the space after an inline-block

Three engine defects found by rendering slashdot.org beside Chromium 152 (the page is rendered with `MediaType.Screen`, margins 0, and compared box by box). Each was reproduced in a small page first, with the Chromium number next to ours.

**1. A malformed rule dropped the rest of the stylesheet.** `classic.ssl.css` has a selector list with its `{` missing (`#editor .spinner span.tag-server-busy.spinner,\ndisplay:none !important;\n}`). `StylesheetComposer.CreateSelector` stopped its prelude at the stray `}`, so `FillDeclarations` read the *next rule's block* as the invalid rule's declarations, and `IsNestedRuleAhead` then made every later rule a nested rule of it, to the end of the sheet: about 70% of the file (every link underlined, since `a { text-decoration: none }` was in the lost part). Fix: at the top level (`IsTopLevelRule`) a `}` is part of the prelude (css-syntax-3 section 5.5.3), so the one rule is invalid and the rest apply. Inside a group rule's block it still ends the block. `StrayCloseBraceRecoveryTests`.

**2. `position: relative` was ignored on a float flowed with inline content.** The offset was applied only in `CssBox.CommitBlockChildOffset` (block-level children); `PlaceFloatAtLineTop` placed the float and stopped. Extracted `CssBox.ApplyRelativeOffset` and call it from both. `RelativeFloatOffsetTests`.

**2b. What follows a relatively offset float flows against its static box.** Float-versus-float placement already subtracted relative offsets (`GetNextIntersectingFloatBox`'s `offsetX/Y`), but only when `!coordinates.LeftFloatsOnly`; the line flow's lookup (`LeftFloatsOnly`) skipped them, and the readers of a found float (`ShiftLineBesideFloat`, `LeftFloatAt`..., `FloatShapeOutline`) read `Location`/`ActualRight` directly. Now the lookup applies a float's *own* offset in that mode, and the direct readers use `CssBox.FlowLeftEdge/TopEdge/RightEdge/BottomEdge` (`Location - RelativeOffset`). `RelativeOffsetX/Y` are zeroed where a float or block child is placed afresh, since a stale value from an earlier pass would otherwise be subtracted from a Location that has not been offset yet. Trap: replacing every `.Location.X`/`.ActualRight` of a float in the engine at once double-subtracts wherever `coordinates.BlockerOffsetX/Y` is already applied (the first attempt did); only the readers that bypass those coordinates were changed. Offsets of a float's *ancestors* are still not applied in the line flow's lookup (it never did).

**3. The max-content measure left out the space after an inline-block.** `<i class="icon"></i> <span>Software</span>`: the markup's space is a word-less anonymous inline box. `FlowBox` advances over it (`CssLayoutEngine`, "handle box that is only a whitespace") but `CssBox.GetMinMaxSumWords` never counted it, so a shrink-to-fit box was one space narrower than its content (71.2 against Chromium's 75.1px) and Slashdot's navigation items were narrower than their text, which wrapped the bar. The measure now uses the same predicate as layout. `ShrinkToFitSpaceAfterInlineBlockTests`; two of its three theory cases fail without the fix.

**4. Not a bug: the search/login bar on the navigation row.** The comparison was wrong, not the engine. Slashdot has `@media (max-width: 1192px) { .nav-primary { width: 80% } .nav-user { width: calc(100% - 80%) } }`; the harness laid the page out 1185px wide (what Chromium's layout width is next to a 15px scrollbar) so it matched, while Chromium's `innerWidth`, the number media queries use, is 1200. At 1200 `nav-primary` is 874.9px against Chromium's 874. Compare a page at the width the *media queries* see (a scrollbar-less 1200), and expect Chromium with a scrollbar to wrap a bar that fits there by 15px.

**5. The footer (seven separate defects, found one repro at a time).** The footer is a full-width float, an inline-block quote with side margins and a relative offset, a footer float that clears it, rows of wrapping links, and an svg-background logo. `InlineLevelBoxesBesideFloatsTests` pins each:
- *An inline-block's `margin-top` moved the float before it.* `FoldOwnAdjoiningBlockStartMargins` walked into the first in-flow child of an anonymous block even when that child was inline-level, folding its margin into the position of the block holding both (CSS 2.1 section 8.3.1: only block-level margins collapse). It now stops at an inline-level child.
- *An inline-block too wide beside a float stayed beside it* (x past the viewport). `FitAtomicInlineOnLine` returned `Fits` for any box on an empty line; it now asks `ShiftEmptyLineBelowCrowdingFloats` (generalised from words to any item width) when a float narrows the line (section 9.5), asked from the line's start (`LeftFloatAtTheLineStart`: the lookup is a point test and the cursor has already been pushed past the float).
- *A left float after such an inline-block sat on top of it.* `FloatOverlapsLineBox` only knew right floats; a left float that overlaps an atomic inline laid out as a box of its own (block-level content, inline-table/flex/grid) now goes below the line.
- *`position: relative` was ignored on every inline-level box* (inline-blocks, inline boxes, replaced inlines; the block-level and float cases were handled). `ApplyInlineRelativeOffsets` runs in `FinalizeLineBoxes` once the line is final and moves the words and rectangles by `CssBox.ComputeRelativeOffset` (an atomic inline with its own box moves with its whole subtree); the line itself is untouched.
- *A line holding only a baseline-less inline-block had no strut descent* (a 30px box alone was a 30px line, Chromium's is 33): both `TryGrowLineForBaselessAtomic` and `FlowAtomicBlockContentChild` now add the strut's descent below the box's bottom margin edge, which is the baseline.
- *A wrapped line lost the margin of an inline box that begins it* (`<li style="display:inline;margin:0 10px"><a>word</a></li>`): the `li` holds an empty anonymous box before the `a`, so `IsFirstChildOfItsParent` was false and the walk that re-applies leading spacing stopped. Empty tag-less boxes no longer count as content in front.
- *An svg background with only a viewBox was drawn at its viewBox size* (the footer logo, a 374px viewBox in a 138px box, clipped to its corner). `PaintSvgLayer` now uses `SvgIntrinsicSize.ResolveForBox`/`RatioOnly` and `BackgroundLayerResolver.ResolveSize` fits a ratio-only image to the positioning area (CSS Images 3 section 5.3).

**6. osnews.com's navigation was a column** (`FloatedMenuMeasureTests`). `nav` and `ul.clearfix` are floats whose `li` items are floats, followed by a clearing block (`.clearfix:after`).
- `GetMinMaxSumWords` only summed floats when the box had no in-flow block-level child (`FloatsShareTheLine`); with one, each float was measured as a line of its own, so the box was as wide as its widest item. A run of two or more adjacent floats (`IsInRowOfFloats`) is now a row of its own, as wide as all of them (ended by an in-flow child or a float that clears), and competes with the other lines by whole line (width plus its decoration: comparing the width against another line's `paddingSum` broke Acid2's `.eyes`). A single float between blocks keeps its old treatment, which that Acid2 test depends on.
- An outside marker's margin was counted in a list item's max-content width, even with `list-style: none` (every floated `<li>` was 5px wider than its text); layout already skips outside markers (CSS Lists 3 section 3.1), and the measure now does.
- Not engine bugs on that page: the logo is a lazy-load placeholder that JavaScript swaps, and the green donation banner is JavaScript-inserted.

**Method worth repeating:** a layout dump of the same ids in both engines (Chromium by `getBoundingClientRect`, ours by a throwaway test with the engine's internals), then a one-feature page per hypothesis, run in both. Guessing from the screenshot named the wrong cause twice (text-indent, `a:hover`).

**Evidence:** `PeachBrackets.Engine.Tests` 18677, `PeachPDF.Tests` 1663 (9 skipped), `PeachBrackets.Tests` 964, all passing; slashdot.org's header (logo, navigation, Topics row, social icons) now matches Chromium's layout.
