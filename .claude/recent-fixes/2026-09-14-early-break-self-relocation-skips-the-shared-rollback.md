# Early-break self-relocation skips the shared rollback, and stale-slot catch-up over-commits

_Landed 2026-09-14._

**Early-break self-relocation skips the shared rollback, and stale-slot catch-up over-commits** (issue #1045): a `break-inside: avoid` block whose subtree contained a `<table>` could silently drop its other children — a preceding `<h2>`, say — when its own straddle was only discovered late (on the pass that *completes* the box, `CssBox.PerformLayoutEpilogue`), because `CssLayoutEngineTable`'s row-height estimate (`EstimateRowHeight`, which can undershoot) misjudged whether the table would fit at discovery time. Two independent gaps compose to produce the drop, and both were needed to fix it — fixing only one left the fixture failing at a different, narrower band.

Gap 1: `CssBox.TakeEarlyBreak`'s self-relocation path (`decision.BeforeBox == this`) sets `_earlyBreakRetryTop`/`_earlyBreakTaken` and tells `DriveBlockChildPass`'s retry loop to lay the box's whole subtree out again from scratch (`resume = null`). Every other pass re-entry in the codebase (`HtmlContainerInt`'s keep-with-next and widows rewinds, the multicol engine's abandoned-fill retry, the table engine's own row-straddle correction) calls `PassRewind.RollBackTo` first, which resets each replayed child via `ResetForRefill` — letting the prologue back in (`RectanglesReset`) and clearing `PlacedByForcedBreak`. This one didn't. A child already laid out once this generation (its `_prologueDone` already `true`) never got that reset on the retry, relying only on `CreateLineBoxes`'s incidental `LineBoxes.Clear()`/`AwaitPlacement()` to self-heal — sufficient to reposition a simple one-line heading's words, but not to retract the box's own settled `Rectangles`/decoration state the way a real rollback does. Fixed by adding the same `PassRewind.RollBackTo(null, child.Boxes)` call the other four sites already make, right before the retry.

Gap 2, found only once gap 1 was fixed and the same fixture still failed at a different offset band: `FragmentEmitter.CatchUpStaleSlotsBehind` rebuilds a stale slot (one `InvalidateFrom` reopened, e.g. the slot the box's now-superseded first attempt was frozen in) and then eagerly commits "found nothing here, and this box already produced a fragment somewhere, so it's done for good" observations via `CommitRemainingObservations(stale >= _lastEmittedSlot)`. That heuristic assumes nothing has been laid out past `_lastEmittedSlot` yet — true for ordinary forward layout, false for a box a §4.3 mover has already relocated forward within this same generation: the heading's live geometry already sits at the new slot, but the emitter hasn't walked that slot yet, so the "done for good" mark it durably records for the old slot silently prunes the heading out of the new one too (`CssBox.EmittedNothingAtOrBefore`'s `slotIndex >= _emittedNothingAtSlot` check has no way to tell "genuinely behind the frontier" apart from "frozen under a since-superseded position"). `FragmentEmitter.Finish()`'s own replay reasons through this identical hazard for the same kind of scattered-slot batch and deliberately never commits (`commit: false`) — `CatchUpStaleSlotsBehind` now matches it unconditionally, giving up a same-generation pruning optimization for this one, rare (invalidation-triggered) path rather than risk the false-forever mark. `CommitGeometricallySettledObservations` (the #917 perf fix, used from ordinary `EmitPass`) was deliberately *not* reused here: its own doc already excludes `CatchUpStaleSlotsBehind`'s caller context by name, since its safety proof requires the box's `ActualBottom` to be trustworthy geometry for the *whole* range being walked, which a scattered stale-slot batch can't promise for boxes other than the one that triggered the reopening.

Verified: the reduced fixture (a `break-inside:avoid` box with an `<h2>` then a `<table>`) fails without either fix and passes with both, across a 0–340pt filler-height sweep in 0.25pt steps; the issue's own literal A4/40pt-margin repro fails at exactly the reported 716.75/717.00pt band without the fix and passes at all four reported offsets with it; a second fixture modeled on the issue's more severe (unreduced) symptom — a preceding sibling's `padding-bottom` rather than a spacer, per the issue's own note that only the former reproduces it — also fails without the fix and passes with it. See `EarlyBreakLayoutIntegrationTests.cs`'s "a table sibling drives the self-relocation retry" section. Full net8.0 suite green (one pre-existing, unrelated memory-ratio benchmark flake confirmed identical on unmodified `main`); 100% diff coverage; zero-warning solution rebuild.
