# Early-break self-relocation skips the shared rollback, and stale-slot catch-up over-commits

_Landed 2026-09-14._

**Early-break self-relocation skips the shared rollback, and stale-slot catch-up over-commits** (issue #1045): a `break-inside: avoid` block whose subtree contained a `<table>` could silently drop its other children — a preceding `<h2>`, say — when its own straddle was only discovered late (on the pass that *completes* the box, `CssBox.PerformLayoutEpilogue`), because `CssLayoutEngineTable`'s row-height estimate (`EstimateRowHeight`, which can undershoot) misjudged whether the table would fit at discovery time. Two gaps were found and fixed together; only the second is empirically demonstrated as necessary for the reported symptom — see the honesty note below on the first.

`FragmentEmitter.CatchUpStaleSlotsBehind` rebuilds a stale slot (one `InvalidateFrom` reopened, e.g. the slot the box's now-superseded first attempt was frozen in) and then eagerly commits "found nothing here, and this box already produced a fragment somewhere, so it's done for good" observations via `CommitRemainingObservations(stale >= _lastEmittedSlot)`. That heuristic assumes nothing has been laid out past `_lastEmittedSlot` yet — true for ordinary forward layout, false for a box a §4.3 mover has already relocated forward within this same generation: the heading's live geometry already sits at the new slot, but the emitter hasn't walked that slot yet, so the "done for good" mark it durably records for the old slot silently prunes the heading out of the new one too (`CssBox.EmittedNothingAtOrBefore`'s `slotIndex >= _emittedNothingAtSlot` check has no way to tell "genuinely behind the frontier" apart from "frozen under a since-superseded position"). `FragmentEmitter.Finish()`'s own replay reasons through this identical hazard for the same kind of scattered-slot batch and deliberately never commits (`commit: false`) — `CatchUpStaleSlotsBehind` now matches it unconditionally, giving up a same-generation pruning optimization for this one, rare (invalidation-triggered) path rather than risk the false-forever mark. `CommitGeometricallySettledObservations` (the #917 perf fix, used from ordinary `EmitPass`) was deliberately *not* reused here: its own doc already excludes `CatchUpStaleSlotsBehind`'s caller context by name, since its safety proof requires the box's `ActualBottom` to be trustworthy geometry for the *whole* range being walked, which a scattered stale-slot batch can't promise for boxes other than the one that triggered the reopening. **This fix alone is what the shipped regression tests exercise, and reverting it in isolation reproduces the reported issue exactly** (the literal A4 repro fails at the reported 716.75/717.00pt band with only this fix reverted).

The second change, alongside it: `CssBox.TakeEarlyBreak`'s self-relocation path (`decision.BeforeBox == this`) sets `_earlyBreakRetryTop`/`_earlyBreakTaken` and tells `DriveBlockChildPass`'s retry loop to lay the box's whole subtree out again from scratch (`resume = null`). Every other pass re-entry in the codebase (`HtmlContainerInt`'s keep-with-next and widows rewinds, the multicol engine's abandoned-fill retry, the table engine's own row-straddle correction) calls `PassRewind.RollBackTo` first, which resets each replayed child via `ResetForRefill` — letting the prologue back in (`RectanglesReset`) and clearing `PlacedByForcedBreak`. This one didn't; added the same `PassRewind.RollBackTo(null, child.Boxes)` call the other four sites already make, right before the retry, bringing this one in line with the pattern.

**Honesty note on the second change**, because chasing it down changed what could honestly be claimed here: an initial version of this note claimed both changes were independently necessary, "fixing only one left the fixture failing at a different band." That was checked against a reduced fixture with a single-line heading, where — it turns out — reverting only the `CssBox.cs` change makes no observable difference at all; every regression test in `EarlyBreakLayoutIntegrationTests.cs` added for this issue passes identically with or without it. Looking for a fixture that *would* tell the two apart (a multi-line heading, so a discarded first attempt's stale `Rectangles` entries have somewhere to leak) instead turned up a **separate, pre-existing defect** — issue #1047, a word claimed twice rather than dropped, reproducible with a plain `<div>` in place of the `<table>` and present identically whether either of this issue's two changes is applied or reverted. That defect made every multi-line fixture attempted here unusable as a clean discriminator for the `CssBox.cs` change specifically. The change is kept anyway — it closes a real, invariant-documented inconsistency (`.claude/invariants/fragmentation-a-boxs-prologue-runs-once-per-layout-so-a-re-entered-pass-does-not.md`), was independently read as correct by two research passes and a post-change review pass, and costs nothing (full suite green, zero new warnings) — but its own necessity for *this* issue is not demonstrated by a failing test the way the `FragmentEmitter.cs` change's is.

Verified: the reduced fixture (a `break-inside:avoid` box with an `<h2>` then a `<table>`) fails without the `FragmentEmitter.cs` fix and passes with both changes, across a 0–340pt filler-height sweep in 0.25pt steps; the issue's own literal A4/40pt-margin repro fails at exactly the reported 716.75/717.00pt band without the fix and passes at all four reported offsets with it; a second fixture modeled on the issue's more severe (unreduced) symptom — a preceding sibling's `padding-bottom` rather than a spacer, per the issue's own note that only the former reproduces it — also fails without the fix and passes with it. See `EarlyBreakLayoutIntegrationTests.cs`'s "a table sibling drives the self-relocation retry" section. Full net8.0 suite green (one pre-existing, unrelated memory-ratio benchmark flake confirmed identical on unmodified `main`); 100% diff coverage; zero-warning solution rebuild.
