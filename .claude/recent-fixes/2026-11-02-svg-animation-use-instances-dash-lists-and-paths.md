# SVG animation: `<use>` instances, an inherited `font-size`, unequal dash lists, `d`, and an invalid negative keyframe

Five of the gaps listed in the umbrella issue for CSS animation on inline SVG, each measured against headless Chrome (paused animation with a negative delay; computed style, or the colour of a pixel for an instance, whose computed style a page cannot read).

**`<use>` instances.** An animation that leaves a property out of a keyframe starts from the value the element has without it, which for an inherited property is the parent's, found by walking `ISvgSourceNode.Parent`. For an element reached through a `<use>` that walk followed the *referenced element's own* ancestors (`CssBoxSvgSourceNode.Parent` reads `_box.ParentBox`), so `<use fill="#00f">` of an animated `<rect>` mixed from black. The static path was always right, because `BuildUse` hands the use's resolved paint down as `InheritedPaint`; only the animation reads text up the tree. The fix is `ISvgSourceNode.AsInstanceUnder(use)`: `BuildUse` wraps the target in a node whose `Parent` is the `<use>` and whose descendants carry the same instance, so `Parent` of the instance root is the `<use>` and the chain continues from there. `Parent` is read **only** by the animation code, so nothing static changes, and selector matching (`SvgCssBoxDomNode`) still sees the element where it is declared, as a browser matches it. Verified for a use on the element, on an ancestor of it, of a `<g>` with its own fill, a use of a use, a `<symbol>`, an `inherit` keyword, and that the *original* (not instantiated) rect still mixes from its own ancestor.

**An ancestor's `font-size` in `em` or `%`.** `ResolveEffectiveValue` already turned `letter-spacing`, `word-spacing`, `stroke-width` and `stroke-dashoffset` into pixels *at the declaring element* (`ToPixelsAtDeclaringElement`), but not `font-size`, so `g { font-size: 2em }` reached the text as `2em` and was resolved against the text's own size. `FontSizeToPixels` does the same with the one difference that matters: a `font-size`'s `em` and `%` are of the **parent's** size, not the element's own, so the basis is `FontSizeAt(declaring.Parent)`. Chrome: 10px root, `g { 2em }`, text to 40px is 30px at the middle (PeachPDF gave 40); nested `2em` then `1.5em` to 60px is 45.

**Dash lists of unequal length.** Both lists are repeated to the lowest common multiple of the two lengths and mixed item by item (`2 4` against `10 20 30` is six items). Only the unequal-length case is taken over (`TryMixDashLists`); equal lengths stay on the generic path so their output is unchanged. What stays a flip: `none`, a `calc()` item, a list with a negative item, and a pair whose two items have different units (`4px` against `10%` is a `calc()` in a browser, and a dash list is split on spaces, which a `calc()` holds: tracked as #2126). The mix is clamped at 0, as an overshooting easing would give a negative dash (Chrome clamps too: 0.54, 1.08, 0, 2.9, 0, 0 at the quarter of `cubic-bezier(.5, -1, .5, 2)`).

**`d`.** `PathDataInterpolator` mixes two `path()` values, or a `path()` against the attribute's bare data (which is what a keyframe that leaves `d` out starts from), when their commands are the same *types*. Chrome measured: an `H` against an `L`, a `V` against an `L`, an `S` against a `C`, a `Q` against a `C`, a different number of commands, and `none` all flip, while an implicit `L` after `M` is an `L`, `Z` and `z` match, and a relative command mixes against an absolute one as the point it reaches (so both go to absolute first). An arc's radii and rotation mix like numbers, but its two flags round half up (0 to 1 is 0 at the quarter and 1 at the middle; 1 to 0 is 1 at the middle). An overshooting easing extrapolates, with no clamp. The existing `SvgPathDataParser` could not be reused: it normalises every command to five segment kinds at parse time, so `H` against `L` and `S` against `C` are indistinguishable by then. `path(evenodd, "...")` is not mixed (flips): Chrome rejects it for `d` and keeps the underlying value; PeachPDF has always accepted it, which is older than this change and was left alone.

**A negative keyframe value the property cannot take.** `r`, `rx`, `ry`, `width`, `height`, `stroke-width`, `font-size` and a `stroke-dasharray` with a negative item are invalid with a literal negative number, and Chrome drops the keyframe (the animation runs between the ones left, or from the element's own value when none is). `SampleElement` now skips such a stop. The trap: the stylesheet parser folds a constant `calc()` to its number (`calc(-10px)` is stored as `-10px`; `calc(2px + 3px)` as `5px`, checked by printing the stored declarations), so `r: calc(-10px)`, which is valid in Chrome and clamps to 0, is dropped too and gives 12.5 where Chrome gives 0 (#2124). The mixed value of a *valid* pair is clamped by `NonNegativeProperties` (which has had `r`, `rx` and `ry` since the review of the calc mix).

**Found by running it, not by reading it.**
- A `<style>` inside an inline `<svg>` is global to the document, so a comparison page that puts one rule per case in the same document sees every rule on every element (the case that defined `g { font-size: 2rem }` changed the measured value of two earlier cases). Give each case its own class and keyframe names, or its own page.
- A Chrome number for a `<tspan>` is not comparable: a `<tspan>` has no element of its own in the tree and no `font-size` of its own that the model keeps.
- `rem` in an inline svg is the svg root's font size in PeachPDF and the HTML root's in Chrome, **also with no animation**; it makes an animation of `font-size` below a `rem` ancestor differ from Chrome and is not part of this fix (#2125).
- A fix script that builds a C# string from Python with `\\t` and `\\r` can land a real tab and carriage return in the source (the build error reads "Newline in constant"); the git blobs are LF and the working tree CRLF, and a script that converts `\n` twice leaves `\r\r\n`, which makes git treat the file as binary and report every line as changed (`git ls-files --eol` shows `w/-text`).

**Not done.** `d` with a fill rule, and the other items of the umbrella issue: the individual `rotate`/`scale`/`translate` properties and `filter` on an SVG element, and a `currentcolor` per element (the static path does not support it either). The mixed-unit dash item (#2126), the folded `calc()` (#2124) and the static `rem` (#2125) are tracked.

**Evidence.** The full probe was 60 cases against Chrome (the ancestor `font-size`, nine dash lists, seventeen path pairs, the negative keyframes and twelve `<use>` shapes); every case matches except the three tracked ones. Undoing each fix on its own fails exactly its tests: the instance wrapper 9, the `font-size` pixels 5, the dash and path hooks 35, the negative drop 6.
