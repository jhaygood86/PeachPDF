# letter-spacing/word-spacing animations: `normal`, `calc()`, and an invalid start

Follow-ups the maintainer measured against Chrome after [the SVG `initial` fix](2026-10-30-svg-initial-keyword-in-attributes.md); each reproduced before it was touched (#1989, #1990, #1991; the same cause for other properties is #1992, not fixed here).

**Where `normal` is read.** The first fix mapped `normal` to `0px` in `AnimationApplier.InUserUnits`, which only the SVG element path runs. The interpolator is shared with the HTML box path, so the mapping now lives in `CssValueInterpolator.Interpolate` (after the "both values equal" return, so `normal` to `normal` stays `normal`) and `InUserUnits` lost its copy. A box's `letter-spacing: normal` to `20px` was 0 at 0.25 and the end value from the midpoint; Chrome gives 5px, 10px, 15px.

**`calc()` against a length.** `Scan` reads a `calc(` as an `Open` token, so `0px` against `calc(10px + 0.5em)` never had the same shape and flipped. `TryMixWithCalc` writes the pair as `calc(<from> * (1 - t) + <to> * t)` (CSS Values 4 §10.1) where one side is a whole `calc()` and the other a single number with a length unit; layout resolves the result like any calc. Two traps: a unitless number is not accepted (a `calc()` of numbers, an `opacity`, would be mixed as lengths), and two `calc()` of the same shape keep going through the old term-by-term mix (`SameShape`), so existing output does not change. This is **not** specific to the spacings: `width: 40px` to `calc(100px + 2em)` flipped too, and now agrees with Chrome (65, 90, 115px; `AnimationCalcLengthTests`).

**Found by an independent review, then reproduced.** A bare `0` beside a length `calc()` flipped (`margin-left: calc(10px + 1em)` to `0` was 0 from the midpoint), because only a number with a length unit was accepted as the other side; a zero is now a `0px` there, but only when the `calc()` holds a length, since beside `calc(1 + 3)` a zero is a number (`z-index` still mixes as whole numbers). The same rule applies to the other side: a `calc()` that holds no length (a `var()` that held a number, `calc(5)` in a keyframe of a length property, which Chrome drops) is not added to a length, so those pairs keep flipping. And the non-negative clamp the number mix applies was bypassed, so an overshooting easing took `padding-left` below zero (-53pt): the mix is wrapped in `max(0px, ...)` for the properties in `NonNegativeProperties`. `stroke-dasharray` is left out of the calc mix, because a dash list is split on spaces and a `calc()` holds some, and the opacities because they are numbers. `NonNegativeProperties` gained the logical padding longhands and `column-rule-width`, which an overshooting easing took below zero like `padding-left`; the set is still not every property that cannot be negative.

**Invalid own value.** `UnderlyingValue` used the declared text, so `letter-spacing="x"` was the animation's start and could not be mixed. For the two spacings it is now the inherited value, as the cascade tier already reads it. The test is `SvgValueParsers.ParseLength(value) is not null` or `normal`: that is `null` for a percentage, so a percentage start is still read as inherited (#1287). It is a per-property check on purpose; `stroke-width="x"` has the same fault, and a shared test is not possible while `ParseLength` is `null` for `auto` and a percentage without a reference length (#1992).

**Found by running it.** `ActualWordSpacing` of an HTML box is the width of the space glyph **plus** the property (7.86pt at 0.25 for a 5px added spacing, not 3.75pt), so the word-spacing tests subtract the same box with `normal`. The maintainer's percentage numbers (1.25/2.5/3.75px for `normal` to `50%`) were not reproduced: PeachPDF gives 0 at every point because it reads the percentage as invalid; Chrome lays out 50% as half the font size (`ABCDEFGH` at 20px: 191.13 for `50%` and for `10px`, 111.13 for `normal`).

**Evidence.** Reverting `CssValueInterpolator.cs` fails 34 test cases (the new theories and existing animation tests); reverting `SvgTreeBuilder.cs` fails the 4 invalid-start cases. 16,833 engine tests, 1,499 `PeachPDF.Tests` (0 failed, 9 skipped), solution Rebuild with 0 warnings. The maintainer's byte-identical corpus was not re-run.

**Not done, tracked.** A percentage spacing (#1287), an invalid start for the other SVG properties (#1992), an ancestor's `em` spacing resolved at the animated element's own size when an animation starts from it (#1996), and an invalid `style` value that does not fall through to the attribute / a malformed `calc()` that reads as 0 (#1997). Three independent reviews of this change measured about 8,500 cells against Chrome and `main`: no cell that `main` had right is wrong now for the spacings; the 12 right-to-wrong cells it found (a `calc(5)` keyframe on a length property) are what the length rule above closed.
