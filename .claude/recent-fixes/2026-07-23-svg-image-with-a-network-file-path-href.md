# SVG `<image>` with a network/file-path `href`

_Landed 2026-07-23._

**SVG `<image>` with a network/file-path `href`** (issue #190): `SvgTreeBuilder.BuildImage` previously resolved `href`/`xlink:href` only via `DataUriUtils.TryDecodeDataUri` — any non-`data:` reference (network URL, `file:`, relative path) returned early and rendered nothing, because `SvgTreeBuilder.Build` is synchronous and had no way to await the async resource pipeline. Fixed by an **async pre-fetch pass** (`SvgTreeBuilder.PrefetchImageResourcesAsync`) that walks the source tree for every non-`data:` `<image>` href, resolves it via the same `CommonUtils.ResolveAgainstDocumentBase` + `RAdapter.GetResourceStream` path HTML `<img>` uses (network/`file:`/archive schemes uniformly, honoring `<base href>`), and returns a `href → (bytes, isSvg)` map (`SvgImageResource`); SVG is detected the same way `ImageLoadHandler` does (`.svg` extension or `Content-Type: image/svg+xml`). The map is passed into the still-synchronous `Build`, where `BuildImage` routes prefetched bytes through the same two decode helpers as the `data:` path (`BuildNestedSvgDocument` for `image/svg+xml`, `DecodeRasterImage` for raster). The prefetch runs in each caller's existing async context: `CssBoxSvg.MeasureWordsSize` (inline SVG, resolved against the host document base) and `ImageLoadHandler.LoadSvgFromStream` (standalone `<img src=x.svg>`, resolved against the **SVG's own URL** so relative `<image>` hrefs load from the SVG's location, mirroring fetched-stylesheet relative resolution). No configured loader → the fetch returns null → renders blank, exactly as before (no regression). Verified end-to-end in both PDFium and MuPDF (a fetched raster composites in the right box). See `SvgIntegrationTests` (network raster/nested-SVG/`Content-Type`-detected/`xlink:href`/standalone-relative) and `SvgTreeBuilderTests` (prefetched-map raster + nested-SVG, no-map-still-unresolved). (The former #251 gap — a non-`data:` `<image>` href nested *inside* an embedded `image/svg+xml` payload not being prefetched — is now fixed by the recursive prefetch; see the Recent-fixes entry below.)
