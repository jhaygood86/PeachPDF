# A forced break steps a pass over slots, and the cursor goes with it

_Landed 2026-07-27._

**A forced break steps a pass over slots, and the cursor goes with it** ([issue #400](https://github.com/jhaygood86/PeachPDF/issues/400) (b)'s remaining half, the second step of what [#390](https://github.com/jhaygood86/PeachPDF/issues/390) stage 3 is blocked on). A forced break is realized by **placement** — the box is put at `PageTopOf(k + n)` and the pass carries straight on from there, with no resumption record in between — so `FragmentainerContext.SlotIndex` said `k` while the pass was flowing content into `k + n`. The emitter has always known this (`EmitPass` takes a `throughSlot` precisely because "a forced break steps over one without ending the pass"); the context did not. `StepOverTo` makes `SlotIndex` a cursor, and `LayoutDocument` now asks the context how far the pass reached instead of re-deriving it from the record the pass stopped with.

**This is not only a model statement — the stale cursor was a live defect, and it is the thing found by running rather than by reading.** `CssBox.HasRoomAboveInThisFragmentainer` gates §5.4's orphans mover on "is there anything above this box in the fragmentainer being filled?", and reads `CurrentFragmentainer.BandTop`. A box placed **by** a forced break sits at the very top of one — but read against the band the pass *opened* with, it looked like a box with a whole page above it. So for a box whose first fragment could not meet its `orphans` minimum, the mover fired and pushed it one page further, **leaving the page the forced break named blank**: measured at `b.Location.Y = 340` instead of `180`, with emitted slots `[0, 2, 3, 4, 5]` instead of `[0, 1, 2, 3, 4]`. Both directions are pinned: `AForcedBreak_LandsOnThePageItNames_…` fails without the advance, and `AboveTheForcedBreaksBox_IsStillRoomAbove_…` fails if the cursor advances one slot too eagerly (that one gives up a constraint that *was* satisfiable, which no assertion on the fragment tree catches — the emitter skips a slot with nothing in it, so a too-eager cursor is invisible there).

**Monotonic, and a no-op for a column.** A pass fills fragmentainers in document order; a pass that has to reconsider an earlier one is re-entered by the driver with a context of its own (`TryRewindForRunPull`). And a column's band is not a slot of the page grid at all — `SlotIndex` there names only the page the column sits on — so stepping that cursor would re-band the column onto a page it never reached. A forced *page* break inside a column escapes to the page driver instead, which the arm just above the new call already does.

## What was deliberately not done, and the measurement behind it

**#400 (b) also wanted `CssRect.WouldStraddleFragmentainer`'s page arm converted to name the band from the fragmentainer being filled. It cannot be, and the blocker is not the table engine.** Instrumenting the predicate across the whole showcase corpus: with the cursor advancing, the fragmentainer's own band still disagrees with `BandStartingAt(Top)` on **2,463 straddle questions, 2,462 of which flip the answer**, and in **every** one the word is *below* the band the pass names — never above.

The cause is that block and inline flow still put content in a later fragmentainer **without recording a break**. A line whose bottom lands within `PageBoundaryEpsilon` of the band bottom is tolerated rather than moved (correctly — it fits); the next line then begins at that band's bottom, which `SlotStartingAt` attributes to the *following* band; and from there every §5.2 question resolves against that band instead, so the whole rest of the document flows on inside the one pass. Naming the pass's own band calls all of it a straddle.

Measured rather than argued: the full conversion (page arm → `CurrentFragmentainer.Band`, plus `InlineBreakToken`'s `SlotStartingAt(word.Top) + 1` → `cursor.SlotIndex + 1`, which the conversion forces because the resume slot must then come from the fragmentainer being left) changed **63 of 69 showcases**, and `flexbox` page 2 rasterizes as visibly overlapping, duplicated content. That second edit is also a direct violation of [the invariant that a resume target must come from where the break fell](../invariants/fragmentation-a-resume-target-must-come-from-where-the-break-fell.md), which is why it fails the way it does. Filed as [#435](https://github.com/jhaygood86/PeachPDF/issues/435) with these numbers; the page arm keeps a comment pointing at it.

**Evidence:** all **69 showcases byte-identical** (normalizing creation date/time, `/ID`, `/M`, annotation `/NM`, subset tags), full net8.0 suite green (6623), CLI green (96), **100% diff coverage**, zero-warning solution rebuild. Tests: 3 in `FragmentainerContextTests` (the step, monotonicity, the column no-op) and 3 in a new `FragmentainerCursorIntegrationTests`.

**A trap worth recording, and it is not about this code.** `git stash` lives in the common git dir, so it is **shared across worktrees** — a concurrent agent's stash landed at `stash@{0}` between a push and a pop here, and `git stash pop` restored *their* work into this tree and dropped their entry. Recoverable (`git stash store <sha>` puts an entry back with its message), but the fix is not to use `git stash` at all in a multi-worktree checkout: write a patch file. The same sharing bit the showcase baseline — the scratchpad directory is shared too, and a "before" corpus generated there was silently overwritten by another agent's run, which only showed up because `acid2.pdf` carries the generating worktree's path in a `file://` annotation URI.
