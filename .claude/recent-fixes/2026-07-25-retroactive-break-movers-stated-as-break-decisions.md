# Retroactive break movers stated as break decisions

_Landed 2026-07-25._

**Retroactive break movers stated as break decisions** ([issue #332](https://github.com/jhaygood86/PeachPDF/issues/332), the one #320 nominated next, [CSS Fragmentation 3 §4.1–§4.3](https://www.w3.org/TR/css-break-3/#possible-breaks)). `break-inside: avoid`, §2 monolithic content and `orphans`/`widows` each answered the same question — this box does not fit, so something must start on the next page — by **translating already-placed geometry**, each with its own copy of the keep-with-next guards.

**The defect that makes this more than a refactor:** a uniform shift is only sound for a box that had not yet reached the boundary. One that had was left holding the fragmentainer gap — its later lines had been laid out against the next band's top, so the shift carried that distance *into* the box as blank space between two lines and as height it does not use. New `Html/Core/Fragmentation/EarlyBreak.cs` (sibling of `BreakValues`/`MonolithicContent`) states which box the break falls before, where it lands, and **why** — the reason is not decoration, since §4.3 relaxation has to know which constraint to give up first. `Discover` is where the run pull lives, so the two §5.3 guards are written once instead of three times.

**Three guards are load-bearing, and each was found by running it, not by reading it:**
(a) **One correction per box per fragmentainer pass.** The relocated box's own epilogue asks the same question of the same geometry, and an unsatisfiable `avoid` is *relaxed* rather than skipped, so without the latch the answer is "still does not fit".
(b) **Relaxation itself keeps the translation.** Moving a box that fits nowhere is sound when it is *shifted* (as much as possible lands on one page) and a runaway when it is *laid out again*: it still does not fit, so it fragments from its new top, that opens another pass, and the pass re-asks. Measured walking a box down **100,000 pages** before the driver's own cap stopped it — the full suite went from 24s to 2m39s, which is how it announced itself.
(c) **Engines keep the translation.** A box inside flex/grid/table/multicol is laid out at a provisional position to be *measured* and translated into place afterwards, so re-flowing it there changes the measurement being taken. The #166 boundary, now stated once rather than implied four times.

**The run pull is the one correction a box cannot carry out for itself** — the break falls before a sibling already placed — so it is handed to the parent's `LayoutBlockChildren`, which restarts at the run head. Only the head is told where to go; every other member re-derives from the sibling above it, so nothing is translated and no group offset is computed. **The guard is structural, not geometric:** the head's index must be at or after the index the pass began at, since everything below belongs to a fragmentainer already filled. That replaces the old `runStartsOnSamePage` test, which asked the same question of coordinates that a pass boundary answers exactly. Callers that cannot re-run a sibling (`LayoutOutOfFlowChildren`, the `::marker` call in the epilogue, every engine) are **asked** via `_canRestartChildLoop` rather than assumed, so a request none of them would collect degrades to the move instead of being silently dropped.

**A latent registration leak fixed on the way in, and worth knowing before adding any other re-entry:** `RegisterNamedPageElement` and `RegisterNamedString` both *append*, and the prologue only nulled the box's own reference — orphaning the entry rather than removing it. `ClearNamedStrings`/`ClearNamedPageElements` run per `LayoutDocument` invocation, not per re-entry, so the pre-existing keep-with-next first-line retry (which does clear `_prologueDone`) already registered its box twice. Measured at 2 entries where 1 was correct. **The retry added here deliberately does *not* re-run the prologue** — everything it settles is either already consumed or overridden by the target — which is why the leak does not widen.

**Do not try to make the table engine re-runnable without reading this.** A repeating `<thead>` is detached from the tree and replaced by one `CssProxyBox` per page, and nothing removes the proxies; a second engine instance over the same table finds no header group (the markup's own is gone) while the previous run's proxies sit at their old coordinates. Restoring the structure first was tried and is *not* sufficient — the table then measures **73.5pt taller** on the second run (a plain table without a repeating header is perfectly idempotent across three layouts, so the header is the whole cause). Subtrees containing one therefore keep the translation. Filed as [#353](https://github.com/jhaygood86/PeachPDF/issues/353).

Tests: `EarlyBreakLayoutIntegrationTests` (13 — interior-gap and height assertions for both arms at three filler alignments, the move-at-most-once latch, the pass-count invariant, the run pull, and the resumed-pass boundary), `PrologueReentryRegistrationTests` (3), plus `RelocatedBox_MatchesWhatBreakInsideAvoidAlreadyDoes` promoted from characterization to invariant. Each guard was verified load-bearing by reverting it individually. Showcase: `paged_media_monolithic_content` gained a multi-line relocated card, **verified in both PDFium and MuPDF**. Of 63 showcases exactly 3 move (`paged_media_per_page_margins`, `paged_media_named_pages`, `paged_media_horizontal_reflow`), all in the same direction — a paragraph that used to leave one clipped line at a page boundary now starts whole on the next page; no page is added or lost. **Accepted gaps:** the first-line keep-with-next retry still has its own bespoke path ([#352](https://github.com/jhaygood86/PeachPDF/issues/352)); the table engine's two pre-checks and post-check still translate, blocked by the re-layout defect above ([#354](https://github.com/jhaygood86/PeachPDF/issues/354), which is itself blocked by [#353](https://github.com/jhaygood86/PeachPDF/issues/353)); and a run whose head settled on an earlier pass moves as a group rather than being re-run ([#355](https://github.com/jhaygood86/PeachPDF/issues/355)).
