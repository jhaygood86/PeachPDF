# SVG `clipPathUnits="objectBoundingBox"`

_Landed 2026-07-23._

**SVG `clipPathUnits="objectBoundingBox"`** (issue #168, [SVG 1.1 §14.3.5](https://www.w3.org/TR/SVG11/masking.html#ClipPathElement)): a `<clipPath>`'s `clipPathUnits` was never read, so `objectBoundingBox` clip geometry was mis-treated as literal `userSpaceOnUse` coordinates (a `0..1` shape became a 1-unit sliver at the origin instead of scaling to the referencing element). Fix: `SvgClipPath` gained `ClipPathUnitsUserSpaceOnUse` (default true), parsed in `SvgTreeBuilder.ResolveClipPath` (mirroring the mask/gradient `!Equals(attr,"objectBoundingBox")` convention). At the paint site (`SvgRenderer.RenderElement`), for `objectBoundingBox` the referencing element's bounding box (`SvgGeometryBounds.GetBoundingBox` — the same helper `objectBoundingBox` gradients/masks/patterns use) becomes the mapping matrix `RMatrix(bbox.W, 0, 0, bbox.H, bbox.X, bbox.Y)`, threaded into `BuildClipPath` as the initial *ambient* matrix. This **reuses the existing clip-shape transform baking** (issue #169's `AppendClipShapeGeometry` ambient-matrix path): the units matrix composes as the OUTER transform of every clip shape (after each shape's own `transform`), via the existing `MultiplyMatrix(shapeTransform, ambient)` — so `objectBoundingBox` + a per-shape/`<use>`/`<g>` transform compose correctly with no new geometry code. The clip is built in the element's local space (its own `transform` already pushed), the same space `GetBoundingBox` reports, so the mapping is exact. A missing/zero bbox falls back to no mapping. `userSpaceOnUse` (the default) is byte-identical to before. Verified in `SvgClipPathUnitsTests` (recording-graphics geometry: unit rect → element bbox, center-half mapping, transform composition, userSpaceOnUse unchanged) and an `objectBoundingBox` diamond swatch in the SVG showcase rasterized in **both** PDFium and MuPDF.
