# A flex item raised to its automatic minimum shrinks the others when the line no longer fits (#2295)

**Idea.** `DistributeFlex` decided grow-or-shrink from the hypothetical sizes *before* the automatic minimum (flexbox §4.5) was applied. A row of `width:60%`, `flex:1 1 30%` and `flex:2` holding a word has 26pt of free space on those sizes, so it took the grow path; the third item (basis 0) was then raised to its word's width, which used up more than the free space, and nothing took the difference back, so the line overflowed by about 29pt and the word was drawn past the page edge. §9.7 step 1 sums the hypothetical sizes, which are already clamped by the minimum: that sum is over the container, so the line shrinks, with the raised item frozen at its minimum (step 3, flex base size < hypothetical size) and the others giving up the overflow in proportion to shrink factor times size. A line that fills its container exactly (no free space) is the same case and is handled the same way.

**What changed.** `RecordAutoMinimum` keeps every item's minimum on a growing line (it used to keep only the ones above their hypothetical size); `DistributeFlex` switches to `ShrinkAgainstAutoMinimums` when the minimum-raised sizes no longer fit, and that loop starts with the raised items frozen at their minimum (`IsRaisedByMinimum`). A line where the raised sizes still fit takes the old grow path unchanged. The initial freeze is redundant for the result (an unfrozen raised item is violated and frozen on the second pass anyway) and is kept because it reads like the specification.

**`flex: none` was `0 1 auto`.** The shorthand's `none` keyword was handed to each longhand as the word "none", which none of them accepts, so all three kept their initial values: grow 0 and basis auto were right by accident, but shrink stayed 1 and the item was shrunk like any other. It stayed hidden because the grow path never shrinks anything; the new shrink path made it visible (a `flex:none` item gave up width to a raised sibling, where Chrome keeps it). `FlexNoneConverter` now hands `0`, `0` and `auto` to the three longhands. This also fixes a `flex:none` item shrinking on a line that overflows. Note that `flex: initial` is still not `0 1 auto` (its basis comes out as `0`); not touched here.

**Found by running.** The issue's document: the word was at x=254.0 (last digit cut by the page edge), now 224.6 against Chrome's 225.1 (the 0.5pt left is Chrome's own rounding of the text width; the word is 55.37pt in both). A review sweep of 48 hand-written layouts and about 1,000 generated rows and columns, each against a build of `main` and headless Edge: every layout that changed was one of the "free space on the base sizes, but the raised items no longer fit" shape and every one of them now matches Edge; none got worse. A build of the change from a half-edited tree showed a bogus regression (plain `flex:1` x3 collapsing to min-content), which is what to suspect if a similar sweep ever shows it: check the file under test is the final one.

**A percentage `width` caps the row minimum.** §4.5's minimum is the smaller of the specified size and the content size, and a percentage against the line's own main size is definite, but `ResolveAutoMinimums` skipped percentages. It only mattered once the shrink path existed: for `width:20%;flex:1 1 0` holding a 150px word beside `width:50%` and `width:30%`, `main` raised the first item and left the other two alone (150/200/120 against Chrome's 80/200/120); the first version of this change shrank the other two as well (150/156/94). A percentage `width` now caps the minimum (80/200/120). A percentage `height` in a column is still skipped.

**Not done.** A row with no growing item is never floored (`flex: 0 1 0` next to `width: 90%` holding a 150px word; Chrome 250/150, PeachPDF 360/0): see the accepted-gap note and its issue. The shrink factor is still scaled by the hypothetical size, where the specification scales by the flex base size; they differ only for an item whose hypothetical size was clamped.

**Evidence.** Engine tests, PeachBrackets.Tests and PeachPDF.Tests pass (counts in the PR); the new engine tests and the two PDF tests fail without the change, and a test kills each mutation tried on the new conditions (dropping the gap, the margins, the exactly-full case, the percentage cap, the `flex:none` converter). A row and a column fuzz against `main` and headless Edge after the last change: 776 rows and 300 columns identical, 41 rows and 24 columns fixed, none regressed; 14 rows and 11 columns are wrong in both builds, the percentage-height and no-growing-item gaps above among them.

**Review follow-up 1: a definite child `width` is the contribution, not a floor.** Making `flex: none` a real `0 0 auto` exposed an old measuring bug that the shrink path had been hiding. `GetMinMaxSumWords` read a descendant's definite `width` as a floor under the text it holds (`Math.Max`), so a `230px` block holding a 305px line of text contributed 305px; a `flex: none` item of three such blocks was laid out 75px too wide and the third overflowed the page (the `svg_3d_transforms` showcase). A box whose `width` is definite now contributes exactly that width (css-sizing-3 section 5.1: the text wraps inside it), and a `<br>` inside it no longer leaves a wider line in `widestLine`. Tables, table cells and captions, replaced boxes and plain `inline` boxes keep the floor reading (a table's columns cannot be narrower than their content; an `inline` box ignores `width`). `HasDefiniteWidthContribution` is the one place that says so. Trap: this feeds every shrink-to-fit measure (floats, inline-blocks, table cells' max-content), not only flex items, so a change here is checked against the whole suite and the showcases; none of the 19,398 engine tests or the three showcases that use `flex: none` moved the wrong way.

**Review follow-up 2: a wrapping row breaks lines on the minimum-clamped size.** `CollectLines` and `BuildLinesPerPage` summed the hypothetical size, which is the flex base size (0 for `flex: 1 1 0`); section 9.3 step 5 clamps it by the minimum first. With the shrink path now real, a row that `main` left over-full and unsized (and which happened to look right) was shrunk, wrapping the first item's text onto three lines. `LineBreakingSize` now takes the larger of the hypothetical size and the automatic minimum (`AutomaticMinimumWidth`, the same code `ResolveAutoMinimums` uses, so the two cannot disagree). A column container keeps the hypothetical size (its minimum needs a layout to learn).

**Evidence for the follow-ups.** A 478-container wrap fuzz against `main` and headless Edge (random bases, grow/shrink, widths, margins, gaps, min/max-width): 324 unchanged, 103 fixed, none regressed, 51 wrong in both builds. `svg_3d_transforms` is now 2.66pt mean x error against Chrome (main 4.53), `line_break_language` 38.7 (main 46.6), `container_queries` 70.0 (main 73.9). The new engine and PDF tests for both fail on the previous commit's source.
