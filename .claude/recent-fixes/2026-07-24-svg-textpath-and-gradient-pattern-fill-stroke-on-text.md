# SVG `<textPath>`, and gradient/pattern `fill` + `stroke` on `<text>`

_Landed 2026-07-24._

**SVG `<textPath>`, and gradient/pattern `fill` + `stroke` on `<text>`** ([issue #187](https://github.com/jhaygood86/PeachPDF/issues/187)): all three needed the same missing capability — treating each glyph's outline as an addressable, fillable/strokeable vector path — which the #175 color-emoji work already built (`GlyphOutlineDecoder`/`OpenTypeDescriptor.TryGetGlyphOutline`, font-agnostic over any `glyf` font, so this works for **regular plain-text fonts**, not just emoji). Pieces:
1. **Enabling seam `RGraphics.GetTextOutline(str, font, baselineOrigin, letterSpacing)`** (abstract; implemented in `GraphicsAdapter`): decodes a run into a single `RGraphicsPath` (one closed subpath per glyph contour, y-flipped, glyphs advancing by `GlyphIndexToWidth`), `FillMode.Nonzero`. Design-units → SVG user space via `scale = font.Size * PixelsPerPoint / UnitsPerEm` (the `PixelsPerPoint` cancels the `XFont.Size = cssSize / PixelsPerPoint` division, so the path lands in the same un-scaled user space shape paths use). Returns **null** when the font yields no `glyf` outlines (CFF/bitmap) — the caller's fallback cue. `PixelsPerPoint` is private to `GraphicsAdapter`, which is why the seam lives there, not in `SvgRenderer`. The two test-only `RGraphics` mocks (`SpyGraphics`, the various `RecordingGraphics`) return null; `TestRecordingGraphics` returns a faithful synthetic outline (one box per non-whitespace rune) so recording tests can drive the outline path.
2. **`PaintTextRun` rewrite** (`SvgRenderer`): `needsOutline = fill is GradientRef/PatternRef || (stroke && stroke-width>0)`. Plain solid non-stroked text keeps the **fast `DrawString` path** (selectable, tagged-friendly). Otherwise the run is outlined once and filled (gradient via `ResolvePaintBrush`/pattern via `PaintPatternFill`) then stroked (`ResolveStrokePen`), in SVG paint order. A CFF/bitmap font (outline == null) falls back to a solid `DrawString`.
3. **`objectBoundingBox` bounds threading**: since `SvgGeometryBounds.GetBoundingBox` has no text case, the run's measured box is threaded as an optional `RRect? boundsOverride` through `ResolvePaintBrush`/`ResolveGradientBrush`/`ResolveStrokePen`/`PaintPatternFill` (and `ResolveGradientPoint`/`ResolveGradientRadius`/`ExpandLinearSpread`/`ExpandRadialSpread`/`ResolvePatternRect`) via one shared `OwnerBounds(owner, boundsOverride)` helper; every non-text caller passes null (unchanged).
4. **`<textPath>`**: `SvgTextElement` gained `PathData`/`StartOffset`/`StartOffsetIsPercent`; `SvgTreeBuilder`'s text-child switch resolves a `<textPath href>` to a `<path>`'s `d` (via `_nodesById`, the `<use>`/`tref` idiom). `SvgTextPathGeometry` flattens the path to a polyline (cubics by de Casteljau, arcs via the SVG endpoint-to-center parameterization F.6.5/F.6.6, moveto gaps excluded from the length) and exposes `TotalLength` + `PointAtLength(s) → (x, y, tangentDegrees)`. `RenderTextPath` places each glyph at its own midpoint distance (honoring `startOffset` length-or-`%` and `text-anchor`), rotated to the tangent, dropping any glyph whose midpoint falls off the path; glyphs paint through the same fast-DrawString-or-outline logic. `AccumulateTextRunBounds` unions the flattened path bbox (inflated by ascent) so a textPath's opacity/mask group tile sizes correctly.
Verified in **both** PDFium and MuPDF (gradient/radial/pattern fill, stroked + outline-only text, text along a wavy curve/circle/arc). Tests: `GetTextOutlineTests`, `SvgTextPathGeometryTests`, `SvgTextOutlineTests` (recording-graphics adjacency: fill-then-stroke order, no-Tj-for-outlined, fast-path DrawString preserved, per-glyph textPath count + off-path drop), `SvgTextPaintIntegrationTests` (end-to-end content stream). Showcase: `svg_text_advanced`. Docs: `docs/supported-svg-features.md` Text section. **Accepted gaps** ([issue #289](https://github.com/jhaygood86/PeachPDF/issues/289)): see the [accepted-gaps entry](../accepted-gaps/svg-outlined-text-textpath-residuals.md).
