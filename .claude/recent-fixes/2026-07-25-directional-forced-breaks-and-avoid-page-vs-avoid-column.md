# Directional forced breaks, and `avoid-page` vs `avoid-column`

_Landed 2026-07-25._

**Directional forced breaks, and `avoid-page` vs `avoid-column`** (issues [#302](https://github.com/jhaygood86/PeachPDF/issues/302) and [#304](https://github.com/jhaygood86/PeachPDF/issues/304), the two #320 nominated next, [CSS Fragmentation 3 §3.1/§3.2](https://www.w3.org/TR/css-break-3/#break-between)). #299 stored every break value; nothing read the directional or targeted-avoid ones.

**#304 is five one-line edits**, and the reason it needs nothing more is the point: `CssBox`'s `break-inside` mover is a *page-context* mover by construction — it measures against `PageBandHeightOf` and relocates to `PageTopOf` — so the only question it can ask is "does this value forbid a **page** break?". That is `avoid` (which forbids one in every context, so including this one) and `avoid-page`; `avoid-column`/`avoid-region` name other contexts and must **not** suppress a page break. No context flag, no `FragmentainerContext` change. `avoid-column` is also already *structurally* satisfied — multicol never splits a child across a column — so honouring it would be implementing a no-op (that stays #313, wanting #322). `wikipedia.mhtml` really does use `break-inside: avoid-column`, so conflating it with `avoid` would have been a live regression.

New `Html/Core/Fragmentation/BreakValues.cs` is the single home for these questions, retiring `CssBox.IsForcedBreakValue` and the open-coded duplicate in `DomUtils.GetPrecedingKeepWithNextRun` (which existed only because the original was `private`). `PageRuleResolver.IsRightPage` is extracted for the same reason: a directional break now targets, *by construction*, the pages `@page :right` styles.

**The load-bearing discovery in #302 is that `ActualBottom`'s setter writes `Size.Height`.** The forced break was expressed by inflating the *previous sibling's* `ActualBottom` to the target, so a predecessor with a background or border already painted down to the page bottom — and across a manufactured blank page it would have painted straight over it *and* made that slot look printable, defeating the reservation. The target now travels on the box that takes the break (`_forcedBreakTop`, consumed in `PlaceBlockBox` like `_resumeTopOverride`).

**The parity decision belongs in `PlaceBlockBox`, not the prologue** — the post-change review found three separate defects that all followed from resolving it early. The prologue runs for **every** box, but only a placed, in-flow box ever takes the break, so a `display: none` or absolutely-positioned box carrying `break-before: right` reserved a page for a break it never took (a hidden section divider silently adding a blank page). And the preserved top margin — which only `PlaceBlockBox` knows — can itself carry the box past the slot the step just chose, so the side has to be checked against where the box *actually lands*. The step re-applies the margin and re-checks, bounded, so a box both keeps its margin and opens a page of the requested side rather than trading one for the other.

**Three more traps, each a real defect found by the 61-showcase diff rather than by the suite:**
(a) an **empty** `<div class="page-break">` is self-collapsing, so margin collapsing resolved the next section against the section *before* it and undid the break outright — the old stretch was accidentally propping this up. A box placed by a forced break now anchors what follows it (`PlacedByForcedBreak`), and the walk-back stops there.
(b) that same marker sits exactly on a slot top, and the flush-boundary convention reads one epsilon earlier as the *previous* slot, so §5.2 truncated a margin that adjoins a **forced** break. Guarded on `PlacedByForcedBreak && IsMarginCollapseThrough`.
(c) the margin carried across the break is `MarginTopCollapse(null)` — this box's own, collapsed with its adjoining first-child chain. Not `CollapsedMarginTop` (it also holds the *previous sibling's* margin-bottom, which belongs to the page being left, and carrying it across both shifts the box and double-counts once the rest of the set collapses) and not `ActualMarginTop` (it drops a first child's margin that collapses through, which is what `paged_media`'s own `<div class="page-break"><h2>` shape is).

A blank page needed representing: `FragmentTreeBuilder.Build` materializes a fragmentainer only for a slot with printable content (CSS Paged Media 3 §3.2), so without a reservation the builder would drop the skipped slot and `break-before: left` would be indistinguishable from `break-before: page`. Reservations live on `HtmlContainerInt` **keyed by the reserving box**, because the keep-with-next retry clears `_prologueDone` and re-runs a prologue *within the same layout generation* at a new position — a set could never retract the stale answer. The *trailing* reservation is a separate field rather than another entry under the last box's key: that box can itself have taken a `break-before`, and one slot per box silently dropped whichever reservation came second. They are **write-only during layout** (only the builder reads them), so they cannot feed back into positions or destabilise the reflow loop. The parity step is gated on `IsFragmenting`: inside monolithic content and measurement passes a box's coordinates are provisional, so a directional break degrades to a plain page break there (the #166 family).

**Trailing `break-after` is its own pass** (`ReserveTrailingDirectionalBreak`), since a break between siblings is taken by the box that *follows* it and at the end of the flow there is none. Same rule — only the stepped-over slot is reserved — so the document gains at most one page and ends such that the page after it falls on the requested side. This is the one case needing `CollectCandidateSlots`' second bound: a between-siblings reservation is inside the document height by construction, a trailing one is not.

Tests: `BreakValuesTests`, `DirectionalPageBreakIntegrationTests` (30, incl. PDF-level page-count/blank-stream assertions, per-page band overrides, a relatively-positioned predecessor, and characterizations of the two boundaries below), plus theories added to `PageBreakIntegrationTests` and `KeepWithNextIntegrationTests`. **All 61 pre-existing showcases rasterize pixel-identically in both PDFium and MuPDF** (acid2's sole byte difference is the `file://` URI naming each run's own working directory). New showcase `paged_media_directional_breaks`, verified in both renderers. **Accepted gaps:** a directional break before a container's **first** child is a no-op ([#347](https://github.com/jhaygood86/PeachPDF/issues/347) — the break is resolved against the preceding sibling; pre-existing for `page`, and the forced-break twin of the §5.2 first-child gap below, which #302's `_forcedBreakTop` move makes tractable); `@page :blank` is unsupported, so a manufactured page cannot be styled or have its margin boxes suppressed ([#348](https://github.com/jhaygood86/PeachPDF/issues/348)); the side is resolved from the **slot** index while the printed page number skips unmaterialized slots, so the two can disagree after a dropped slot (commented onto [#148](https://github.com/jhaygood86/PeachPDF/issues/148), which this promotes from a margin-box-selection concern to a layout one); and the `IsFragmenting` gate means a directional break inside flex/grid/table/multicol degrades to a plain page break (commented onto [#166](https://github.com/jhaygood86/PeachPDF/issues/166)).
