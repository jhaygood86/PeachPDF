# WinUI: typing into a text field

`HtmlView.TextInput.cs` carries text input to the engine's editing model (`GetEditState`, `InsertText`, `ReplaceEditText`, `SetEditSelection`, `GetEditPlace`, `GetEditIndexAt`). The caret arithmetic is `HtmlViewEditing` (pure, tested without a window); the key and character handlers take plain values (`HandleEditKey(VirtualKey)`, `TypeCharacter(char)`) so a window test can drive them.

- **Two input paths, one at a time.** `CoreTextEditContext` is created lazily from `CoreTextServicesManager.GetForCurrentView()` inside a try: WinUI 3 has no text services type of its own (`Microsoft.UI.Text.Core` does not exist in the SDK), and the Windows one is documented for CoreWindow apps, so whether it works in a desktop window is **not verified here** - it was built without a real input method to try. If it throws, `_editContext` stays null and `OnCharacterReceived` types the characters. When the context exists, `OnCharacterReceived` stands down, or each character would go in twice. Navigation keys (arrows, Home/End, Backspace, Delete, the clipboard chords) are always the view's own: text services deliver text, not those.
- **Echo.** Changes the text services themselves ask for (`TextUpdating`, `SelectionUpdating`) run under `InTextServices`, so `TellTextServices` does not report them back as `NotifyTextChanged`; reporting them back made a loop in the design, found by reading rather than by running.
- **Screen coordinates are approximate.** `LayoutRequested` wants the caret's rectangle in physical screen pixels; `ToScreen` adds the `AppWindow` position and an estimate of the frame to the canvas position scaled by the rasterization scale. An input method's candidate window may sit a few pixels off until this is checked on a real machine.
- **Pointer.** A click over a text field focuses it and puts the caret with `GetEditIndexAt` (nearest grapheme edge); dragging to select inside a field is not done (Shift+arrows is).
- **Value pattern.** `IValueProvider` on text and search boxes reads `GetFormState` and sets through `SetValue`; read-only follows the node.

Checked by `HtmlViewEditingTests` (caret arithmetic) and a window test (`TypingEditsTheFocusedTextFieldAndAScreenReaderReadsAndSetsIt`: typed characters including a surrogate pair, Backspace by grapheme, Home, the Value pattern). The text-services path, the blink timer, the clipboard and the pointer are in `HtmlView.TextInput.cs`, which the coverage measure leaves out like the other window-bound files.
