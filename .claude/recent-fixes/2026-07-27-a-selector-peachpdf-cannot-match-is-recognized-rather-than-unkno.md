# A selector PeachPDF cannot match is recognized rather than unknown

_Landed 2026-07-27._

**A selector PeachPDF cannot match is recognized rather than unknown** (issues [#407](https://github.com/jhaygood86/PeachPDF/issues/407) and [#405](https://github.com/jhaygood86/PeachPDF/issues/405), [CSS Selectors 3 §4](https://www.w3.org/TR/selectors-3/#Conformance)). An unknown pseudo-class invalidates the **whole selector list** it appears in, and Tailwind v4 emits its entire design-token block as `:root, :host` — so one unregistered `:host` discarded 39 `--color-*`, 6 `--font-*` and the `--spacing` token, leaving 116 `var()` references guaranteed-invalid across the document. The document rendered with almost none of its intended colour, typography or spacing, silently.

**The load-bearing idea is that "PeachPDF has no elements for this" is a *matching* answer, not a *parsing* one** — which is the treatment `:visited`/`:active` already got in `CssData.DoesSelectorMatch`. New `CSS/Factories/UnmatchableSelectors.cs` is the one list of names that parse and select nothing, and the two factories now build their dictionaries from it rather than each carrying their own half. It covers the state-based set (no interaction, focus, form state, media playback or browsing history in a PDF), the Shadow DOM set (`:host`, `:host()`, `:host-context()`, `:defined`, `:state()`, `::part()`, `::slotted()`), and the pseudo-elements that generate no box (`::placeholder`, `::backdrop`, `::file-selector-button`, `::target-text`, `::highlight()`, `::view-transition*`, …).

**A vendor extension is accepted wholesale rather than enumerated.** A leading hyphen (CSS Syntax 3 §2) marks a UA-internal box or state, so `::-webkit-file-upload-button`, `::-moz-focus-inner`, `:-moz-focusring` name something PeachPDF cannot have *by definition* — enumerating them is hopeless and unnecessary. This is deliberately **not** blanket acceptance: a genuine typo still invalidates its list, as a browser's would. `:-webkit-any()`/`:-moz-any()` are the one pair that get the *real* matcher instead, since they are the legacy spellings of `:is()`.

**The functional forms are built by `SelectorConstructor`, not the factories**, because the argument is part of the selector's identity — `FunctionToken.ToValue()` already yields `"part(foo)"`, so the whole text becomes the selector's name and `::part(a)`/`::part(b)` stay distinct. `OnPseudoElement` gained a `Function` arm for this; it previously accepted only an `Ident`, so every functional pseudo-element was unparseable.

**Found on the way in: the lookups were case-sensitive.** Both factories froze their dictionary with the default comparer while building the source set with `OrdinalIgnoreCase`, and the lexer does not normalize an ident's case — so `:HOVER` and `::BEFORE` failed to parse and invalidated their lists, though pseudo names are ASCII case-insensitive.

**#405 is the same defect one level on.** `CreateStyle` pushes its rule onto the composer's node stack *before* filling declarations and only drops it afterwards, so a rule whose selector failed to parse is the "parent" while its block is consumed — and `CreateNestedStyleRule` read `parent.SelectorText`, which is `Selector.Text`, on a rule whose `Selector` setter had removed the child. Any nested construct inside such a rule threw. Registering `::placeholder` removes Tailwind's own instance of it; the guard (`parent?.Selector?.Text`) removes the class. Asking for the text directly also keeps "no selector" distinguishable from "empty selector", which `ResolveNestedSelector` would otherwise scope under `:is(*)`. `StyleRule.SelectorText` is null-safe too, since `ToCss` reads it unconditionally.

Tests: `UnmatchableSelectorRegistrationTests` (87 — the reported `:root, :host` shape and its `var()` consumers, a 54-case theory over every registered name sharing a list with a real selector, the same names selecting nothing, no pseudo-element box synthesized, unknown names still invalidating, `:-webkit-any()` as `:is()`, case-insensitivity, selector-text round-trips, and #405's construct parsing rather than throwing). Each piece was verified load-bearing by neutralizing it individually — the vendor rule (13 failures), each factory's union (28 and 12), each functional path (5 and 10), the case-insensitive lookups (4), the `:is()` aliases (2), and #405's two guards together (2, with the reported `NullReferenceException`). Full net8.0 suite green (6546), CLI green (96); **100% diff coverage**. One pre-existing expectation moved: `SelectorsTests.FindAllStandardPseudoElementSelectors(false, true, …)` goes 0 → 6, because bootstrap's own `::-moz-placeholder`/`::-webkit-input-placeholder`/`::-ms-expand` rules now survive strict parsing too, not only under `AllowInvalidSelectors`.

**All 66 pre-existing showcases are unchanged** — none of them has a rule that was being dropped (65 byte-identical; `acid2` differs only by the `file://` URI naming each run's own working directory and is pixel-identical on both pages). New showcase `unmatchable_selectors` does have such rules: every colour, font and measure on it arrives through a list shared with an unmatchable selector, and **on the unfixed build the page renders completely unstyled**. Verified in both PDFium and MuPDF.

**Accepted gap surfaced (not caused) by the list:** three of the recognized names — `:empty`, `:any-link`, `:scope` — depend only on the document tree and so are evaluable in principle; they are unmatched because `CssData.DoesSelectorMatch` answers only `:root` and `:link`. Pre-existing, filed as [#417](https://github.com/jhaygood86/PeachPDF/issues/417) and flagged in `UnmatchableSelectors` rather than left silent among the genuinely-unmatchable names.
