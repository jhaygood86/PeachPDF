# The collapsed margin before a child is the frame's question

_Landed 2026-07-27._

**The collapsed margin before a child is the frame's question** ([issue #390](https://github.com/jhaygood86/PeachPDF/issues/390), stage 2's second half). Stage 1 moved a block box's *position* into the frame above it; the value that position is built from was still resolved by the child, in a 170-line `MarginTopCollapse` that walked both the parent's child list and its own subtree.

**The load-bearing observation is that [§8.3.1](https://www.w3.org/TR/CSS21/box.html#collapsing-margins)'s adjoining set spans two frames**, which is why it could not stay on either box alone. What *precedes* the child — a predecessor's bottom margin, and, through a run of self-collapsing predecessors, everything those fold in — is a backwards walk of the frame's own child list, which no box can do from inside itself (`FoldMarginsPrecedingChild`). The child's own top margin and the chain of first-in-flow-child margins adjoining it is a walk into its own subtree and stays there (`FoldOwnAdjoiningTopMargins`). `CollapsedMarginBefore` on the frame folds both into **one** `AdjoiningMarginSet`, because the spec collapses the whole set at once — resolving the halves separately and combining them afterwards is the bug an earlier version of this code already had (a chain member's small margin displacing the group's larger value).

**The one-shot override is now stated as one**: `TryTakeGroupTopMarginOverride` consumes the value an ancestor's lookahead left, rather than the read and the clear being two statements a caller could get half-right.

**What stage 2 still does not do.** Its first sentence — return a size and leave `Location` unwritten until the parent assigns it — is not this. The offset is already computable before the child lays out (every input is style-derived, which is why the current order works at all), so flipping to "assign after `PerformLayout` returns" buys nothing on its own; what it buys in Blink is that the child's layout is *position-independent*, and here it is not: fragmentation asks its questions against absolute document Y throughout (`CssRect.WouldStraddleFragmentainer`, `PageIndexOf`, the §5.2 boundary test). That flip needs those questions restated relative to the fragmentainer, which is its own piece of work and is what stage 3's retraction retirement waits on.

**Behaviour-neutral apart from `<hr>`**, and verified as such: **all 65 showcases are byte-identical** to `main` rendered from the same working directory (the path is embedded in `acid2`'s own `file://` reference, and its length shifts every xref offset — compare from one directory or the diff is noise). Full net8.0 suite green (6417), CLI suite green (96); **100% diff coverage**. Tests: `CollapsedMarginBeforeTests` (6 — both halves and the boundary between them: adjoining siblings collapsing to the larger, mixed signs summing, a self-collapsing sibling joining the run, a first-child chain taken once, a border on the parent blocking the chain, and a float summing rather than merging) and `HrPlacementTests` (5 — one per drifted rule, the §5.2 truncation the rule newly gets, and a width regression guard). None of the §8.3.1 cases existed before; the rule was pinned only indirectly, through Acid2. The three `<hr>` cases were each **verified load-bearing by running them against the unfixed build**, where all three fail and the width guard passes — which is the only evidence there is for that half, since no showcase puts an `<hr>` after a floated, offset or bordered sibling and all 65 stay byte-identical through the fix.

**And the one box that never went through the seam now does** ([issue #396](https://github.com/jhaygood86/PeachPDF/issues/396), found by this work rather than caused by it). `CssBoxHr` positioned itself with a copy of the formula, and the copy had drifted on **three** rules: it read the predecessor's `ActualBottom` rather than `StaticBottom`, so a relatively-positioned sibling dragged the rule along (CSS 2.1 §9.4.3 makes a relative offset purely visual — measured at 72.1 → 92.1); it asked `GetPreviousSibling(this)` with the default `includeFloats: true`, so a floated sibling became its margin-collapse partner (§8.3.1 collapses only against the nearest in-flow predecessor — 110 against the correct 90); and it added that sibling's bottom border on top of `ActualBottom`, which already contains it — the exact double-count the shared path carries a comment about having fixed.

**The rule's *size* is still its own; only its position moved**, and the order of the two had to swap: width is resolved **before** the placement so a floated rule reaches `FloatBox` at its real width, while height stays **after**, because the placement writes `ActualBottom` and so clears `ActualHeight` — which is precisely what makes the 2pt/1px-border fallback fire on a re-layout instead of reading the previous pass's height. Getting that backwards is silent: the first pass looks right either way.

**The trap in bringing it in is the pass lifecycle, not the geometry.** `CssBoxHr.PerformLayoutImp` replaces the base wholesale, so it never ran `BeginLayoutPass` — harmless while the rule could not take part in fragmentation at all, and immediately fatal once it could: the frame's §5.2 branch can now conclude the break falls *before* the rule, and with nothing clearing `RequestedBreakBeforeTop` at the start of the next pass the rule asked for the same break again, the pass made no progress, and the driver's own backstop threw. It now begins its pass like any other box (`BeginLayoutPass` is `private protected` for it). Worth knowing before bringing in the other self-placing boxes stage 4 has to: an override that skips the base's entry point skips the whole lifecycle with it, and that is invisible until the box is asked a fragmentation question.

`MarginTopCollapse` is gone with it — it existed only for this caller. The rule now also gets §5.2 margin truncation, which it never had: an oversized `margin-top` no longer paginates through as blank space.
