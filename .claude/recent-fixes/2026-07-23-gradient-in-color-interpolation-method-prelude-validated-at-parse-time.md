# Gradient `in <color-interpolation-method>` prelude validated at parse time; two parsers unified onto one grammar

_Landed 2026-07-23._

**Gradient `in <color-interpolation-method>` prelude validated at parse time; two parsers unified onto one grammar** (issue #245): the CSS-OM value converter (`GradientConverter.ConvertFirstArgument`, all three of linear/radial/conic) accepted *any* first comma-group that merely contained an `in` ident via `CreatePlaceholder` — so `linear-gradient(in nonsense garbage, red, blue)` was wrongly accepted as valid CSS — while the render-time parser (`CssValueParser.TryParseInColorSpace`) independently re-parsed the same `in <colorspace> [<hue-method>]` grammar and silently mapped an unknown space to `Srgb`. Two disjoint parsers of one grammar, disagreeing — the anti-pattern the "one grammar, one parser" convention exists to prevent. (The renderer *did* already honor valid spaces end-to-end — `CssImagePainter` → `ColorSpaceConverter.Interpolate` → `ColorSpaceMath` — so the issue's "renders in sRGB regardless" was stale for valid spaces; the live defect was the missing validation + the divergence.) Fix: a new shared `ColorInterpolationMethodGrammar` (`src/PeachPDF/CSS/`, mirroring `BackgroundPositionGrammar`/`BasicShapeGrammar`/`CalcParser`) is the single source of truth for the [CSS Images 4 §3.1](https://drafts.csswg.org/css-images-4/#color-interpolation-method) grammar `in [ <rectangular-color-space> | <polar-color-space> <hue-interpolation-method>? ]`. Its `TryExtractInterpolationMethod(group, out remainder, out hasIn)` validates the `in …` slice (rejecting an unknown/unsupported space, a hue method without the trailing `hue`, and `in` with nothing after) and returns the group minus the contiguous `in …` slice as `remainder` for the caller to validate as the gradient's own direction/shape (the two combine with `||` in either order, so `in oklab to right` and `to right in oklab` both work; a hue method left on a rectangular space, e.g. `in oklab longer hue`, falls out as an invalid direction remainder and is dropped). Layer A (`GradientConverter`) drops a malformed prelude per the cascade's invalid-value rules; Layer B (`CssValueParser`) sources its color-space membership/polar classification from the same grammar, so the two layers can no longer disagree. The accepted set is exactly the 11 spaces PeachPDF's interpolation math implements. Verified by `ColorInterpolationMethodGrammarTests` (grammar unit) + `GradientTests` accept/reject theories (mirroring the #244 conic validator) + `ColorSpaceGradientIntegrationTests` (combined `to right in oklab` still emits an oklab stitching function; invalid/unsupported preludes emit no shading). **Accepted gap:** the wide-gamut RGB interpolation spaces `a98-rgb`/`prophoto-rgb`/`rec2020` are valid CSS 4 but unimplemented, so a gradient requesting one is **rejected at parse time** (chosen over silent sRGB approximation, for exact parse/render agreement) — a CSS Images 4 §3.1 deviation (a UA would render them), filed as [issue #267](https://github.com/jhaygood86/PeachPDF/issues/267).
