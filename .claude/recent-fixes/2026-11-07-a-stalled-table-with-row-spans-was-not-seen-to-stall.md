# A table with row spans that stalls was never seen to stall

A document (a `thead`, a table cell with `rowspan`, a nested table whose cell has a `rowspan`, and a float no band can hold, issue #2293) never finished layout. The driver (`HtmlContainerInt.LayoutDocument`) catches a run of passes that resume at the same point (`IsSameProgress`, 16 in a row) and lays the rest out in one piece; that guard worked for the same document without the spans (18 pages, 0.9s) and never fired with them.

- **Found by running it:** `dotnet-stack report` on the spinning CLI showed the thread in `LayoutBodyRow` under `LayoutDocument`, so it was the pass loop, not a loop in the table engine. A temporary log of each pass showed 7,000 passes in 8s, each resuming at the same place one slot later. Walking the two tokens level by level showed every level slot-neutral equal except the table's, and there `RowSpannedBoxes` held the same `CssBox` once more on each pass (`0:A,A,A` against `0:A,A`): `LayoutBodyRow` lists a spanning cell with `rowSpannedBoxesForRow.Add(cell)`, and a pass that resumes the row starts from the list carried in the token, so a cell re-placed on every pass was added again each time and the token's content equality (`TableBreakToken.Equals`) never saw two passes as equal.
- **The fix:** list a spanning cell once. The list is read through a `Union` (`boxesToVerticallyAlign`) and by the token comparison, so the duplicates carried no meaning. `StalledPaginationTests` (three variants, header height pinned so the narrow window - a float about 79 to 93pt tall on a 160pt page - does not move with the font; 86pt is its middle, with the spans in either or both tables, `MaxFragmentainersOverride` = 300 so a regression fails at 301 passes instead of after minutes) and `RowSpanStallPdfTests` (through `PdfGenerator`; fails after a 60s timeout without the fix) both fail without it.
- **Left alone:** `SeedCrossBoundaryRowSpans` adds a header cell to the same kind of list with a plain `Add` and looks like it can accumulate the same way for a header cell that spans into the body. A document with such a header and the stalling float did not stall at all (0 last-resort relayouts, with or without a change there), so no test can tell, and it is unchanged. The stall itself is not fixed: the 16 stalled passes are 16 empty pages where Chrome puts the float on the second page (#2297, [the accepted-gap note](../accepted-gaps/a-float-that-fits-no-band-under-a-repeated-header-makes-sixteen-empty-pages.md)). A review also found that the guard is blind to flex and grid tokens (`SlotNeutral` returns null for them), so a flex or grid container around the same table never finishes, with or without spans (#2298), and that an absolutely positioned box has its own pass loop with only a cap (10,001 pages, #2299): both the same on `main` and not touched here.
