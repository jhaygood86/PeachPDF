# Inline-only multi-column containers columnize

**Load-bearing idea:** `CssBox.LayoutContents` sends a multi-column box to the columns engine only when it has a block-level child, and that choice rests on `DomUtils.ContainsInlinesOnly` ("every child is inline"). A container whose children are all text therefore took the inline branch and never reached `CssLayoutEngineColumns`. The fix is a box-generation step: `DomParser.CorrectInlineBoxesParent` wraps such a run in an anonymous block, the shape the engine fragments. Widening the dispatch instead is wrong. The columns engine fragments block-level content, and handed a box of bare inline content it drops words.

**Floats:** a float joins the wrapped run, as it does in any block, so the inline flow places it beside the text. An earlier version kept floats out of the run, so the columns engine placed each float in its own column and nothing moved the text on its line beside it. The float then covered those words. [The overlap fix](2026-10-20-a-float-after-text-moves-the-text-beside-it.md) removes that for every container. A box holding only floats is not wrapped: it already reaches the engine through `CssBox`'s float disjunct, and a test pins that.

**Scroll containers:** a text-only multi-column container that clips (`overflow` other than `visible`) and has a `height` or `max-height` is not wrapped (`DomParser.IsHeightBoundedScrollContainer`) and keeps `main`'s inline flow. Wrapped, it reaches the columns engine, which skips words when it fills columns of a bounded height (40 words, `columns:3; height:100px`: 15 inside the box on `main` and in Chrome, 5 wrapped), and an explicit `<div>` skips the same words on `main`, so the wrapper was not equivalent to a `<div>` there either. Tracked as #1849 with [an accepted gap](../accepted-gaps/text-only-multicol-scroll-container-of-bounded-height-is-not-columnized.md). `CssBox`'s `suppressMonolithicBreaking` keeps `main`'s exemption for a box that dispatches to the columns engine; a scroll container with block children is unchanged.

**Vertical writing modes** keep the inline path. Measured on a 225pt x 90pt `vertical-rl; column-count: 2` box holding one run of text: `CreateVerticalLineBoxes` keeps the content inside the box (72pt x 58pt), while the columns engine stacks it into a single 511pt run that leaves the box entirely.

**Found by running it:**

- 21 generated block-content `overflow` containers with columns render identically to `main` (word positions and page count).
- 39 generated inline-only `overflow` containers render identically to `main` with a hand-written `<div>` inside them.
- `overflow: scroll; height: 660pt; columns: 2` with 30 lines: two columns, word positions matching Chrome.
- Float placement hangs, found by fuzzing the PR over four rounds of review. None is specific to multi-column: each also hangs on `main` with a hand-written `<div>` wrapper (or without `columns` at all), and inline-only content reaches them far more often. They share one shape, so the fix is the shape and not each trigger: `FloatBoxLeft`/`FloatBoxRight` search by moving a candidate position until no earlier float blocks it, and a "drop below the blockers" step ends the search for a blocker only if the dropped position is **not found blocked by the same blocker again**.
  - *The drop must clear the edge the conflict test reads.* `DomUtils.IsFloatIntersecting` compares the candidate's margin-edge top (`CssFloatCoordinates.OuterTop`) with a blocker's border-box bottom (`ActualBottom`). `CssFloatCoordinates.DropTo(clearEdge)` now sets `Top` and `OuterTop` together so `OuterTop >= clearEdge`, and `FloatBoxRight` takes `clearEdge` as `max(ActualBottom, ActualBottom + ActualMarginBottom)` of the blocker, never above its border box. Every drop therefore moves strictly past the blocker that forced it. Before, a negative `margin-top` on the dropped float (right floats left it out of the coordinates, so `OuterTop` equalled `Top`, which the drop put above the blocker's bottom) or a negative `margin-bottom` on the blocker (the drop used its margin edge, which is inside its border box) put the drop back inside the blocker, the same state came round and each pass cleared the tried-position set, so nothing ended it.
  - *Blockers that displace each other.* Two floats each moved the search's edge to a place the other moved back, so the same `(Left, Right, Top)` came round without any drop. `FloatBoxRight` and `FloatBoxLeft` both remember the states they have tried and, on a repeat, drop as above. Pinned by `RightFloatsTallerThanTheColumn_DoNotStallFloatPlacement` and `LeftFloatWithNegativeMarginLeft_BesideAWideRightFloat_DoesNotStallFloatPlacement` (the left guard fails that test after 30s when neutered).
  - *Initial `OuterTop`.* A left float starts from `Top` with a negative margin-top taken back out, as `main` does. A right float starts from the position it was given (`OuterTop = startY`), as `main` read it; reading the margin there put a second right float with a larger negative `margin-top` over the first. `SecondRightFloatWithNegativeMarginTop_SitsBesideTheFirst` pins it. The left-float mirror of that case still overlaps, as on `main` (accepted: [float placement differences](../accepted-gaps/float-after-text-differs-from-a-browsers-line-layout.md), #1786).
  - A seeded sweep (`FloatsOfAnySizeAndMargin_DoNotStallFloatPlacement`: both sides, margins of either sign on all four edges, `clear`, floats taller than the column, in a plain block and two multi-column containers) fails within its timeout when the `Math.Max` above is removed, so the next member of the class is found by a test and not by a review. Measured with the CLI over 100 seeded documents per container kind, 8s timeout, floats up to 1200px tall: `main` hangs on 4 (plain block), 4 (multi-column, inline text), 20 (multi-column holding a `<div>`) and 4 (fixed-height multi-column scroll container); this branch hangs on none. Over 300 left-float documents with negative margin-left against wide right floats, `main` hangs on 33, this branch without the left guard on 5, and with it on 0.
- A float after the text, in a multi-column container, made `CssLayoutEngineColumns` size the balanced column to the float's absolute bottom, which it reads from the measurement pass that laid all the text out in one column: the columns grew to hold all of it, the text ran down column 1, and an `overflow: hidden` container clipped most of it (31 words, `height: 400px`, 3 columns: 22 shown, 9 lost). Floats inside the anonymous wrapper are therefore no longer counted in the balance's float reach; only the container's own floats are (`FloatReach`). A tried height term for the floats among the text changed no rendering and no test, so it was removed. Pinned by `FloatAfterTheText_DoesNotCollapseTheColumns`.
- Pre-existing and reachable on `main` through a hand-written `<div>`, not introduced here:
  - A float that follows text on the same line was drawn over the words before it, in a plain block and a multi-column container alike. Fixed in [the overlap fix](2026-10-20-a-float-after-text-moves-the-text-beside-it.md).
  - In a fixed-height `overflow` multi-column container, the second column can skip words. In 5 of 39 generated inline-only documents, column 2 starts at a later word than Chrome's (for example `w076` where Chrome has `w041`).

**Deliberately not done:**

- Keeping an inline-only scroll container monolithic while it is columnized. That needs the columns engine to lay out inside a detached fragmentainer, which it does not do.
- Fixing the two pre-existing columns-engine defects above. They live in the columns engine's line and fragment handling, not in the box generation this change touches.
