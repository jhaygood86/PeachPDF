# Single auto margins resolve for in-flow tables

A shrink-to-fit table's layout engine knows its used width only after it has negotiated the columns. CSS 2.1 §17.4 puts a table's margins on its block-level table wrapper, so §10.3.3's single-auto rule applies there too. `CssLayoutEngineTable` already passes that settled width to `GetActualMarginLeft` for the both-auto centering case, but the single-auto resolver admitted only ordinary in-flow blocks (`IsInFlowBlockLevel`) and returned zero for tables.

The fix treats a non-null width passed by the table engine as the evidence that the table's used width is now known, but takes that path only for an in-flow `display: table` box (`IsInNormalFlow`: not floated or absolutely positioned, and not a flex or grid item). The single-auto path computes free space from `ContainingContentWidth - usedWidth`, subtracts the other margin and clamps the result to zero. A null width still means the table has not reached its width-settled callback; it must not guess or recursively measure the table during initial placement. Ordinary block behavior and the established both-auto table-centering path remain unchanged.

The gate is load-bearing. Without it, the table engine's offset is added on top of the position that flex layout, float placement and absolute positioning already set: a table that is a flex item with `margin-left: auto` moved past the end of its 400pt container, and floats, `inline-table` and absolutely positioned tables shifted by the free space a second time. `AutoMarginWidthIntegrationTests` covers each of these (flex item, float, `inline-table`, absolute with a static position and with `left`). On the ungated resolver those five fail with 420 vs 210, 200 vs 100, 100 vs 0, 100 vs 0 and 150 vs 50.

`AutoMarginWidthIntegrationTests` also checks the resolved margins and the final table position and width for left-auto, right-auto, a non-zero other margin, an over-wide table, and intrinsic widths (`auto`, `fit-content`, `min-content`, `max-content`), where the table's end edge must land on the containing block's end edge. The `table_auto_margins` TestHarness showcase presents the two one-auto cases beside the existing centered comparison.

Verification: the full net8.0 `PeachPDF.Tests` run passed (16,468 passed, 9 skipped, 0 failed) with no compiler warnings in its build output. Line coverage of the changed lines in `CssLayoutEngine.cs`, measured against `main`, is 100% (15 of 15 executable lines). The TestHarness showcases were last regenerated before the gate and have not been rerun since.

Not closed here: a narrow table in an `rtl` containing block is still anchored at the physical left rather than the right-hand inline-start edge. Issue #1251 remains open; the accepted-gap note and support matrix describe only that remaining behavior. One residual case is `<table align=left>` with an explicit `margin-left: auto`. `align` on a table maps to `text-align` (`DomParser.TranslateGenericAlign`) rather than a float, so the table is now in flow and moves to the end edge, where Chrome floats it to the start edge. `main` matched Chrome there only by pinning the table to the start edge.
