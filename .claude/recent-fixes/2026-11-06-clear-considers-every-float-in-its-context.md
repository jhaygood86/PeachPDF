# `clear` considers every float of its own formatting context, and only those of its own column

`ClearBox` found what a box with `clear` has to go below by calling `GetClearance` on each earlier sibling. That looked at the floats among a box's children and, by recursing into the grandchildren, among their children: floats one and three levels down an earlier sibling were found, floats two and four levels down never (`<div><div><div style="float:left">`, then a float with `clear: left`: y=0, Chrome 60). It is now one walk, `LowestFloatBottomIn`, that is a float itself or looks at every child, to any depth.

- **A formatting context of its own is not looked into** (`DomUtils.EstablishesIndependentFormattingContext`, CSS 2.1 §9.4.1), as in the rule-5 lookup. The old code looked into everything, so a float inside a fixed-height `overflow: hidden` or `display: flow-root` box held a later float with `clear` down although it was not in its formatting context (Chrome 10, here 60). A float counts itself and its contents are not looked into.
- **The static bottom, as before**: the walk carries the relative offsets of the boxes above the float, so a `position: relative` wrapper moves where a float is drawn, not where it clears (CSS 2.1 §9.4.3). The side filter (`clear: left` does not clear a right float) is applied at every depth.
- **Multi-column**: floats of an earlier column are measured from that column's own top, so a float starting the second column was cleared by the first column's. The column fill tells each block the column resumes in which of its children the column starts at (`CssBox.CurrentColumnFirstChild`, set for every link of the carried break token by `CssLayoutEngineColumns.MarkColumnStart`, reset after the column), and `ClearBox` starts at it. A block that spans columns is covered through its own link of the chain. The search honours the mark of every block it walks into (`LowestFloatBottomInChildren`), so a float in the first column of the child the column resumes in is not counted either, and the floats a block carried into the column (below) are.

What was found by running it: Chrome ignores `break-before: column` on a float and on the first in-flow child of a multi-column container (there is no break point before it), so the sample in the issue does not break columns in Chrome as written; the cases here put an in-flow block before the break. Content after a block that fills a column of fixed height stays in the first column, below it, with `column-fill: auto` ([#2238](../accepted-gaps/column-fill-auto-with-a-fixed-height-does-not-start-the-next-column.md)): the cases here break the column with `break-before` for that reason.

Evidence: 21 cases against headless Chrome (levels 0 to 5, block and float clearing, `clear` side, formatting contexts of four kinds, relative offsets, six multi-column shapes) all match except one that is `#2227`; on `main` the levels, the formatting-context and the multi-column cases differ. Each guard (formatting-context stop, column start, static bottom, side filter) was removed in turn and a test fails.

**Found by a review: floats deferred into the column.** A float that does not fit at the foot of a column is carried into the next one (`DeferredFloats`) and laid out at its top, but its index in `Boxes` is below the child the column resumes at, so starting the sibling loop at that child skipped it: a `clear` block in the column was drawn across it (a balanced article with `h2 { clear: both }` after a deferred figure: y=60 where Chrome and `main` have 120). The block now also keeps the floats it laid out at the top of the column (`CssBox.CarriedFloatsInThisColumn`, reset with the column start) and `ClearBox` looks at them too. Lowering the start index to the first deferred float was not the answer: it brings back floats between it and the resume child, which stayed in the column before. Known, left alone: a `clear` right after a `column-span: all` no longer avoids a float from before the span (the run after a span starts at the child after it, and PeachPDF's balancing lets that float overflow below the span, which is the older gap).

**Found by a review: what the walk must not count.** `LowestFloatBottomIn` was a near copy of `DomUtils.LowestFloatBottomInOwnFormattingContext` (the section 10.6.7 walk) without its guards, which mattered now that it reaches every depth: floats in a `display: none` / `hidden` subtree (never laid out, so they keep the geometry of a layout that did not happen: a 70px hidden float held a clear 60px down), in an absolutely positioned box that also says `float` (computes to `none`, CSS 2.1 section 9.7), and in a running element are skipped, and the stop is `ContainsItsFloats` so a multi-column sibling shorter than its float stops the walk too. Main had the first by accident at odd depths. The same review found the one case where `main` was right by accident and the branch was not: a table, table cell or inline-block holding only a float. `IsMarginCollapseThrough` treated it as empty, so the block after it was placed at its top, and `main`'s old walk hid that at odd depths by reaching the float for a `clear`. The fix is at the root: a formatting-context root that holds a float is not collapse-through (as overflow, flow-root and multi-column already were), checked only when the document has floats. This also fixes the same placement without `clear`, which was wrong on `main`.

Known and not done (reviewed against Chrome, all older than this change): floats before an ancestor of the cleared box are not seen ([#2239](../accepted-gaps/clear-does-not-see-floats-before-an-ancestor.md)); `contain: paint|layout|content|strict`, `content-visibility: auto`, `<fieldset>` and `<button style="display:block">` are not formatting-context roots in `EstablishesIndependentFormattingContext`, so a float in a short one is cleared; block-in-inline reordering (`<span><div>...</div><div style="float:left">`) puts a later float before the clearer; `<br clear>` is not honoured.

**Found by the maintainer's review: a table cell with a fixed height holds its float.** `<div style="display:table-cell;height:20px"><div style="float:left;height:80px">` followed by a `clear: left` block: `main` y=80 like Chrome, the branch y=20. Not caused by the stop at a formatting-context root, which is right (section 9.4.1): `main`'s old walk reached into the cell and hid that a cell with a fixed `height` stayed at it and let the float overhang (a real `<td style="height:20px">` was wrong in both). The float growth of section 10.6.7 in `CssLayoutEngine`'s height step is gated on `!isDefiniteHeight`, since a definite `height` is the used height of an ordinary box; but the `height` of a table cell is a minimum (section 17.5.3), so the gate lets a table cell through (`ActualDisplay == TableCell`). Measured against Chrome on the table-cell wrapper, with `display: table` around it, the float two levels down, `<td>` with and without `vertical-align`, a taller cell, a row with a text cell beside it, and a following row: all match; the engine tests and `PeachPDF.Tests` pass and the 240 showcases render identically to the commit before this change.
