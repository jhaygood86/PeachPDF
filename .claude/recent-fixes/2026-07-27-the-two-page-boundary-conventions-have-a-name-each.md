# The two page-boundary conventions have a name each

_Landed 2026-07-27._

**The two page-boundary conventions have a name each** ([issue #400](https://github.com/jhaygood86/PeachPDF/issues/400) (a), the first step of what [#390](https://github.com/jhaygood86/PeachPDF/issues/390) stage 3 is blocked on). `HtmlContainerInt.PageIndexOf` answers about a *coordinate*, and a coordinate exactly on a slot boundary is ambiguous — it is both the end of one band and the start of the next. An *edge* is not ambiguous, and which way it resolves depends on which edge it is, so every call site spelt out its own `± PageBoundaryEpsilon`: 24 of them, in eight files.

`SlotStartingAt(y)` (a top edge flush on a boundary begins the **later** slot) and `SlotEndingAt(y)` (a bottom edge flush on one ends the **earlier** slot) state it once. The epsilon is 0.5pt — a real tolerance for the arithmetic noise a relocated or fragmented box's Y accumulates, not floating-point dust — so picking the wrong one lands a box a whole page out, which is a defect this codebase has already had.

**The naming is worth more than the deduplication, because it makes the two deliberate asymmetries visible.** `CssBox.PlaceBlockChild`'s §5.2 boundary test asks `SlotEndingAt` of the child's **own top**, and so does the keep-with-next run head beside it. That is correct and load-bearing: `baseTop` *is* the predecessor's bottom edge, and asking the same of `top` is what stops a child landing flush **on** a boundary from counting as having crossed it — it is the first thing in the next band, so there is no span for the margin to be truncated against. `SlotStartingAt` there would truncate a margin that never crossed anything. Both sites now say so.

**A mechanical rewrite ate its own definitions**, which is worth recording because the failure mode is invisible to the compiler: the two helpers were appended to `HtmlContainerInt` *before* the conversion pass ran over the same file, so their own bodies (`PageIndexOf(y + PageBoundaryEpsilon)`) were rewritten into `SlotStartingAt(y) => SlotStartingAt(y)`. C# warns on nothing, the solution builds clean, and the suite reports **passing** — a partial run of 10, 29 or 209 tests, because the host had crashed with SIGABRT and the summary line counts only what completed. Read the count, not the word.

Behaviour-neutral: **all 65 showcases are byte-identical**, full net8.0 suite green (6420), 0 warnings. Tests: 3 in `HtmlContainerIntPageGridTests` — each convention at an exact boundary, and that the two disagree *only* there.

**What this does not do, and the measurement behind it** ([#400](https://github.com/jhaygood86/PeachPDF/issues/400)): stage 3 wants a retraction retired, which needs stage 2's flip, which needs the child's layout to stop depending on absolute document Y — and it depends on it in ~70 places outside `HtmlContainerInt` (39 in `CssBox` alone, 15 in the table engine). `CssRect.WouldStraddleFragmentainer` is the shape of it in miniature: **two** arms answering one question, a column arm that asks the fragmentainer's own band and a page arm that asks the page grid. The page arm cannot simply adopt the column arm's form, because a box being laid out is not guaranteed to be inside the fragmentainer being filled — monolithic content, the engines' measurement passes, and a box below a tall margin all put geometry outside the current band. That is a model change, and it is staged in #400.
