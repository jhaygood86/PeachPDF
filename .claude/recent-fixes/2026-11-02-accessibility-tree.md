# The accessibility tree

`HtmlDocument.GetAccessibilityTree()` builds a hierarchy of roles, names and states from the box tree (what each element is) and the fragment tree (where each part landed), and replaces the flat text-run `GetAccessibleNodes`. The WinUI and Android views are built over it.

- **Two trees, one walk.** `AccessibilityTreeBuilder` (`Html/Core/Semantics/`) walks the *box* tree for semantics and reads page rectangles from the *fragment* tree into a box-to-bounds map first. Fragment rectangles are fragmentainer-local, so they go through the same `TextRunCollector.Frame` conversion the text runs use; use that, not a second one.
- **A repeating table header is not in `Boxes`.** A `thead`/`tfoot` that repeats on every page is detached and replaced by one `CssProxyBox` per page. Skipping proxies (as the text-run and tagging code rightly do) drops the header from the tree: the builder visits `proxy.SourceBox` once, at the first proxy, and indexes ids through it. A test that has a `thead` is what catches this; one without does not.
- **Boxes that are not shown are not there.** `display: none` makes no box, so an `aria-labelledby` that points at one finds nothing, and `display: contents` elements have no box either. Both are documented limits, not bugs to chase in the builder.
- **Role, name and state are separate decisions.** `RoleResolver` (explicit role first, then HTML-AAM), `ComputeName` (accname order), `ApplyStates`. A generic role is hoisted (its content goes to its parent), and a presentational role is ignored on something focusable.
- **What a host reads.** The tree keeps text nodes (a later text pattern needs their rectangles), so a host would read an element's text twice. `ReadingText` and `ReadingChildren` are the one place that is decided; both hosts use them. `HtmlViewLogic` and the Android `AccessibilityMapping` keep only the platform vocabulary (control type, class name).
- **Not done on purpose:** table positions and spans, header associations, relations (`aria-controls`, `aria-owns`, `aria-flowto`), SVG `<title>`/`<desc>`, MathML speech, focus order. They are the next slices of the plan, and the limits are listed in `docs/accessibility.md`.
- Evidence: `PeachBrackets.Tests` 272 passed (`AccessibilityTreeTests`), Android logic tests 72, WinUI logic tests 48, WinUI window tests 11 (real UI Automation peers); the Android view compiles under the 10.0.403 SDK (the RC SDK has no android workload) with no warnings.
