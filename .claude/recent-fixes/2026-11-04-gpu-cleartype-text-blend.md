# ClearType text is blended on the GPU (HtmlView scrolling)

**Symptom.** Scrolling the one very long page still hung, stalled and jittered in Release. Measured in a real window (`PeachBrackets.WinUI.Example --scroll-bench <file> screen_long_page`, Release, 1200x800): every revealed 1200x504 strip took 108-140 ms on the UI thread, UI-thread callback latency p95 was 47-93 ms with callbacks over 100 ms, and the profile put 83% of the time in `Win2dCanvas.DrawString`: per word, read the pixels behind it back from the GPU, blend on the CPU, make a new GPU bitmap, draw it. GC and the engine's tree walk were not the problem.

**What did not work.** The round-2 "grayscale while scrolling, restore LCD when idle" timer: the restore repainted the whole visible area (800 ms+ of per-word readback) between scroll events, so a 3 s drag took over 25 s. Removed. Grayscale-only text is blurry on high-resolution LCD screens, so it was not an option anyway.

**What does.** `Win2dCanvas.FromRenderTarget` (new public API) lets the canvas sample the target it draws into. Text runs are queued and composited in one pass by a pixel shader (`Shaders/LcdBlend.hlsl`, compiled with `fxc` and embedded): `backdrop * (1 - coverage) + ink` per colour channel, against a copy of the target, with the two layers (ink times coverage, coverage) summed from cached per-run bitmaps. `HtmlView` paints each invalidated region into a render target of its own and copies that onto the control's surface, because the surface's session cannot be sampled.

**Traps found by running it.**
- The shader's output has no edge: drawing it into the target with a `Copy` blend replaced everything outside the text with black. It is rendered into a scratch target first and only the area is copied back.
- A queued run has to be drawn before anything drawn later that overlaps it (and before any clip, layer or blend change), or later content would be hidden under, or text would appear over, the wrong things; and two overlapping queued runs would blend with the backdrop and not with each other. Masks carry a one-pixel margin where there is no ink, so adjacent words do not count as overlapping (`QueueText` tests the ink rectangle).
- Evicting a cached bitmap while it is still queued would draw a disposed bitmap; bitmaps are fetched while the layers are built, never at queue time.
- Win2D tests run on the software device (WARP), which rounds differently from a GPU: up to 11 levels difference against the old path on a few channels, 1 level on the hardware GPU. The equivalence tests allow 24.

**Evidence.** A spike first (the opt-in `GpuTextSpike` test, a no-op unless `PEACH_SPIKE_SHADER` is set): 351 words over a gradient, 0.7-0.9 ms against 43-46 ms with readback on the hardware GPU (5 ms against 42 ms on WARP); a tracker-style cache of finished bitmaps over a flat background was 0.3 ms, so it was not worth a second mechanism (and covers only flat backgrounds; gradients were about 20% of runs on peachstatetechnologies.com). Then in the view, `--scroll-bench` Release: UI latency p95 0.3 / 12 / 14 ms (steady drag / wheel bursts / fling, was 47 / 75 / 93), worst 67 / 36 / 31 ms (was 127 / 106 / 129), none over 100 ms; strips 37-45 ms each (was 108-140). `PeachDrawing.Win2D.Tests` 221, `PeachBrackets.WinUI.Tests` 212 and `PeachBrackets.WinUI.UITests` 66 pass.

**The larger find, afterwards.** A hit counter on the word-mask cache showed 1.35 million lookups for 26 strips: every strip was drawing every word of the page and the clip discarded them. A canvas's tracked clip bound is the last rectangle pushed, so the page-wide clip the painter pushes replaced the region (see [the invariant](../invariants/paint-a-canvas-clip-bound-is-the-last-rectangle-pushed-not-the-intersection.md)). `PaintPageRegionAsync` now tells the painter the region (`HtmlContainerInt.PaintRegion`) and it narrows its own page clip. Result in `--scroll-bench` (Release): lookups 1.35 million -> 13 thousand; strips p50 2-12 ms (was 37-45), UI latency p95 0.2-0.3 ms in all three scenarios, worst callback wait 39 ms in the first (cold) scenario and under 3 ms after, none over 50 ms.

**Glyph cache.** New words are built from cached per-letter masks (`Win2dGlyphMaskCache`: letters rasterized once per font, size and position within the pixel, 1/16 px horizontally, quantized *downward* vertically so the hinted baseline rounds to the same row the whole word would have used). Cold strips improved only about 20% (38 -> 31 ms per megapixel in the first scenario), because most of a cold strip is no longer rasterizing: the profile of what is left is creating two GPU bitmaps per new word and colour (about 28%), the glyph rasterizer for first-seen letters (about 12%) and polygon fills (6%). Words equal the whole-word result to a mean of about 1 level of 255 (largest 23-40, on letter edges).

**Not done.** Cold strips are still the slow ones (first view of new text, about 8-12 ms for a typical strip, one 47 ms outlier at the start of the first scenario that includes first-use work like shader creation and JIT). The next steps would be a packed atlas for the per-word bitmaps instead of two textures per word (updating a region of one big bitmap is much cheaper than creating a texture), a glyph-level alpha bitmap shared across words, and warming the shader and scratch targets when a document loads. Region painting is not time-budgeted or banded, and there is no prefetch. The `Win2dComposer` still uses the readback path (its export is grayscale by default). Hover still reparses the whole document (the incremental restyle plan is unchanged).
