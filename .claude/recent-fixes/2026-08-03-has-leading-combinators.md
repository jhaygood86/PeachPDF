# `:has()` leading combinators (`:has(> S)`/`:has(+ S)`/`:has(~ S)`)

_Landed 2026-08-03._

**`:has()` only supported the default descendant relative-selector form** (issue #611): `SelectorConstructor.Insert(ISelector)` (`SelectorConstructor.cs`) discarded whatever combinator was on `_combinators` whenever `_temp == null` — the exact situation at the start of `:has(...)`'s nested argument parse, since `HasFunctionState` hands it a brand-new child `SelectorConstructor`. Even had the combinator survived parsing, `CssData.HasDescendantMatch` was combinator-blind — a plain any-depth recursive descendant search regardless of what was passed.

Fixed on both sides. Parsing: `SelectorConstructor` now captures the resolved leading combinator (reusing the existing `GetCombinator()`, which already collapses e.g. a trailing whitespace-induced `Descendent` on top of a real `>`/`+`/`~` token) into `_pendingLeadingCombinator`, and a new `GetRelativeResult()` (parallel to, not replacing, `GetResult()`) wraps each alternative with it via a new `RelativeSelector(Combinator, ISelector)` node — only for `Child`/`AdjacentSibling`/`Sibling`; anything else (the default `Descendent`, or an edge case like a namespace pipe reaching this position) stays unwrapped, reproducing the pre-existing discard behavior exactly for those cases, since only the three combinators the issue names get new semantics. Only `HasFunctionState.Produce()` calls `GetRelativeResult()` — `:not()`/`:is()`/`:where()`/`:host-context()` still call the untouched `GetResult()`, so none of them are affected by this at all.

Matching: `CssData.HasRelativeMatch` unwraps a `RelativeSelector` (or recurses into a `ListSelector` of them, for `:has()`'s forgiving-relative-selector-list) and calls a new `MatchesRelativeChain`. The plain-selector (no wrapper) case still falls through to the original `HasDescendantMatch`, unchanged.

**First implementation anchored the WHOLE relative-selector chain against a single one-hop candidate, which is wrong for a multi-compound argument** — caught by a post-change review pass (per this repo's CLAUDE.md convention) before landing, with a probe test confirming it live: `div:has(> .a .b)` against `<div><section class='a'><span class='b'></span></section></div>` incorrectly failed to match, because the first version tested `DoesSelectorMatch(fullChain, directChild)` - treating the direct child as the chain's SUBJECT (rightmost compound, `.b`) rather than anchoring only the chain's FIRST compound (`.a`) to it. The same pass caught a second bug: the child-combinator branch didn't filter to element children the way the sibling branches did, so `:has(> *)` incorrectly matched a `<div>` whose only child was a text node (`AllSelector` matches any non-root node, including an anonymous text-run box). Fixed by replacing the one-hop dispatch with `MatchesRelativeChain`/`MatchesChainStep`, a small forward chain-walker: it decomposes a `ComplexSelector` argument into its ordered `CombinatorSelector` entries, anchors entry 0 to the scope element via the leading combinator, and recursively anchors each later entry to the PREVIOUS entry's match via that entry's own `Delimiter` (mapped back to a `Combinator` via `DelimiterToCombinator`) - so `.b` in `:has(> .a .b)` is now correctly required to be a descendant of the specific `.a` element that satisfied the child relationship, not of :scope directly. `RelativeCandidates` (child/adjacent-sibling/sibling/descendant candidate generation, shared by every step) filters to real elements (`TagName is not null`) uniformly, closing the `:has(> *)` gap.

**Comma lists needed a parallel per-alternative combinator list, not a single field** — `:has()` already supports `:has(.a, .b)` (existing test), and each alternative in a forgiving-relative-selector-list can carry its own leading combinator (`:has(> .a, + .b)`). A single `_pendingLeadingCombinator` field would get clobbered across `InsertOr()` boundaries, so `InsertOr()` now also appends to a `_leadingCombinators` list kept parallel to `_group`'s members (both only ever grow together, inside `InsertOr()`), and resets `_pendingLeadingCombinator` back to `Descendent` for the next alternative.

**No other exhaustive selector-type switch needed a `RelativeSelector` case** — checked `CssData.CollectIndexKeys` (rule-selector indexing, never descends into a `HasSelector`'s `Inner`) and `CssData.MatchesAsFirstLineSelector` (unrelated). `RelativeSelector` only ever appears nested inside `HasSelector.Inner`, and `HasRelativeMatch`/`MatchesRelativeChain` always unwrap it before recursing into `DoesSelectorMatch(compound, ...)` — it's never handed to the generic `DoesSelectorMatch(ISelector, node)` dispatcher itself.

**`FollowingSiblingElements` materializes the filtered sibling list once**, not per step - a `GetNextSiblingElement`-chained loop (the first version's `:has(~ S)` implementation) re-walks and re-filters `parent.Children` on every hop, which is O(n²) over a long run of siblings; `MatchesChainStep`'s per-step candidate generation goes through `RelativeCandidates` → `FollowingSiblingElements` instead, an O(n) single-pass generator. `GetNextSiblingElement` itself is unchanged (still used for the single-hop adjacent-sibling case, and by the pre-existing `DoesSelectorMatch(ComplexSelector, node)`'s own `+`/`~` cases, which walk backward/preceding rather than forward).

Verified: full net8.0 suite green, zero-warning `dotnet build -t:Rebuild`. Tests in `RelationalPseudoClassSelectorTests.cs` cover each combinator form matching only its stated relationship (and *not* matching what plain `:has(S)` would), a multi-compound relative selector (`:has(> .a .b)`, the review-caught bug), the universal-selector/text-only-child case (`:has(> *)`, the other review-caught bug), a mixed-leading-combinator comma list, and `.SelectorText` round-tripping (`div:has(> .a,+ .b)` — no space after the comma, matching `ListSelector.ToCss`'s existing, pre-existing convention).
