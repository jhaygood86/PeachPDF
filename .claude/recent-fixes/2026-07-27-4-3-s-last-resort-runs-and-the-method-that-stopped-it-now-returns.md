# §4.3's last resort runs, and the method that stopped it now returns the exception instead of throwing it

_Landed 2026-07-27._

[Issue #404](https://github.com/jhaygood86/PeachPDF/issues/404). `HtmlContainerInt.LayoutDocument`'s no-progress backstop is written to *recover* — a pass that reproduces the record it was handed can never advance, so the remainder is laid out monolithically and the document renders with one overflowing page. It sat after `ReportError`, which threw. Every statement of it was dead code, and **it had never once run**: any input reaching that branch failed the whole render.

**The load-bearing idea is that the name was the defect, and renaming it is not enough.** `[DoesNotReturn]` does *not* end a code path as far as the C# compiler is concerned — verified rather than assumed: deleting the dead `return` after such a call produces **CS0161**, and leaving it produces no CS0162. So the compiler could neither accept the statement's absence nor warn about its presence, and a reader had only the name to go on. `RenderError` now **returns** the `HtmlRenderException` and every call site spells `throw container.RenderError(…)`. After a literal `throw` the compiler does both things, so this class of dead code is a build warning from here on, in a repo whose rule is zero warnings.

**There was exactly one other caller written as if it returned**, which is what #404 asked to be checked: `StylesheetLoadHandler.LoadStylesheet`'s `return (null, null)`. Its own `<returns>` doc said "both null on failure" and **both callers still null-check** a result that has never been null — while the three *handled* failures beside it (unresolvable href, missing resource, wrong `Content-Type`) deliberately degrade so the rest of the document renders. The dead statement is gone and the doc corrected; the behaviour is deliberately unchanged, because which policy is right is a judgement call rather than a defect in that catch ([#416](https://github.com/jhaygood86/PeachPDF/issues/416)). The other nine sites are catch blocks with the call last, so nothing was dead there.

**The stall is provoked by a box, not by markup, and that is the honest boundary.** Which *content* stalls the driver is #403, still open and alignment-sensitive; six sweeps here — the reported three-declaration shape across 3,240 configurations, §5.2 truncation on a first child with and without a collapse-blocking border, degenerate `@page` bands, and two broad fixture families — reached it **zero** times. What the driver does *once* a pass has made no progress is a property of the driver alone, so `NoProgressBackstopTests.StallingBox` states the condition directly: a `CssBox` subclass that hands back the same record every pass, which is exactly what a box the driver cannot get past looks like from the loop's side. It defers only while `IsFragmenting`, which is also what makes the recovery pass identifiable — that pass is suppressed, so the box stops asking and the layout ends.

**The stub has to *defer*, not merely report, and getting that wrong makes the tests vacuous** — found by the post-change review, which measured it: with the first version, which called `RecordBreak` on the context directly and set no `PendingBreakToken`, **four of five tests passed with the whole recovery body deleted**. The reason is that the first pass then lays the entire document out and emits it *before* the stall is reported, so "the content is all there" holds for a recovery that does nothing. A pending record stops the parent's child loop, which is what leaves the siblings after the stall box for the recovery alone to place. Now 3 of 6 fail with the body removed and 5 of 6 with the throw restored — the two neuterings catch different halves, and only the ordinary-document control passes both.

**And the stub then hit #396's lesson exactly**: an override of `PerformLayoutImp` that never calls `BeginLayoutPass` skips the whole box lifecycle — including the clear of `PendingBreakToken` — so the record set on the stalling pass was still there on the *suppressed* one, the parent's loop stopped again, and the deferred siblings were **never laid out at all**. That looked exactly like the driver dropping content (the review's H1), and was three lines of fixture. Worth knowing before writing any other `CssBox` stub: clear what the lifecycle would have cleared, or call the base.

**`LastResortRelayouts` is the only signal there is**, since PeachPDF has no non-fatal diagnostic channel; it is reset per `LayoutDocument`, not per document (invariant 11 — `ShrinkToFit` and the reflow loop each re-run it), and that reset is pinned by a fixture with per-page left/right `@page` margins, which is what puts `PerformLayout` into its reflow loop. **The one thing the recovery cannot reach** is a slot *below* the one it is filling: a box it places back above that fragmentainer is rescued only if it already had a fragment there, since repositioning it then un-freezes that band through `InvalidateEmittedFragmentsFor`. Re-emitting the slot the failed pass had already frozen is fine and deliberate — `FragmentEmitter.EmitSlot` replaces, and its own comment names this caller.

**The rename cost coverage before it paid it**, which is worth knowing before touching any other error path: those nine catch blocks had **no tests at all**, so merely retyping their lines dropped diff coverage to **55%**. `RenderErrorReportingTests` (8) now covers them — each engine named in its own message, a block box, paint, and the stylesheet fetch with its missing-stylesheet control — using the same `CssBox`-subclass technique (a box whose layout throws). Only `DomParser`'s block-inside-inline catch is left uncovered.

Tests: `NoProgressBackstopTests` (6 — the document renders, the recovery is counted, it runs with breaking suppressed, every word is claimed exactly once, the count is per *layout* rather than per document, and an ordinary paginated document as the control) and `RenderErrorReportingTests` (8). `LayoutHarness.LayoutAsync` gained a `prepare` callback for putting a box in the tree the parser cannot produce; `TestRecordingGraphics` is no longer sealed. Full net8.0 suite green (6582), CLI green (96), 0 warnings; **93% diff coverage**. **66 of 67 showcases byte-identical** and acid2 **pixel-identical in PDFium** (its only difference is the `file://` URI naming each run's own working directory).

**Found by the sweep and filed rather than fixed:** an `<h2>` followed by a `break-inside: avoid` block, twice, straddling a page boundary throws `An item with the same key has already been added` out of `CssLineBox.AssignRectanglesToBoxes` — #374's crash from a fifth direction, on the page grid this time, where the re-entry is #355's keep-with-next pass re-entry rather than a multicol retry. Minimal and deterministic, reproduces on `main`, and plausibly the same family as #403. [#415](https://github.com/jhaygood86/PeachPDF/issues/415).
