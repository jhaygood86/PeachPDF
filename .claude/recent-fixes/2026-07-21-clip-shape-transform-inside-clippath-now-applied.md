# Clip-shape `transform` inside `<clipPath>` now applied

_Landed 2026-07-21._

**Clip-shape `transform` inside `<clipPath>` now applied** (issue #169): a clip shape's own `transform` — set directly, on a wrapping `<g>`, or on a `<use>` (including its `x`/`y` offset) — was silently dropped, so a clipPath authored with transforms (e.g. one shape reused at several positions via multiple `<use transform="translate(…)">`) clipped to the wrong region. Root cause: a `<clipPath>`'s shapes are unioned into a single `RGraphicsPath` pushed via `PushClip` (which *intersects*), so the transform can't ride the graphics-state CTM the way the normal render path does (`RenderElement`'s `g.PushTransform`) — it must be baked into the clip geometry's coordinates. Fix: `SvgRenderer.AppendClipShapeGeometry` now threads an accumulated `RMatrix?` (composed with the existing `MultiplyMatrix`, innermost-first — folding each shape's own `Transform`, a `<use>`'s `translate(x,y)`+`Transform`, and a `<g>`'s `Transform`) and, when a transform is active, builds the leaf shape into its own sub-path, transforms it, and merges it (the no-transform case still appends straight into the combined path, byte-identical). Two new general path primitives back this: `RGraphicsPath.Transform(RMatrix)` / `AddPath(RGraphicsPath)`, implemented in `GraphicsPathAdapter` over `XGraphicsPath` (a new `Transform(XMatrix)` + the previously-stubbed `AddPath` now delegating to a new `CoreGraphicsPath.Transform`/`Append`). This is **exact for any affine** (translate/scale/rotate/skew), not just translate/scale, because `CoreGraphicsPath` already flattens arcs to Béziers on add and a Bézier is closed under affine transforms — so no SVG-arc endpoint→center decomposition is needed (unlike the gradient code's documented rotation caveat). Offsets are applied as-is (no `PixelsPerPoint`), matching the raw un-scaled clip coords the backend consumes via `IntersectClip` and the existing `ApplyMatrix`/`gradientTransform` user-space convention. Verified end-to-end by rasterizing a four-tile reused-clip showcase in both PDFium and MuPDF. (`clipPathUnits="objectBoundingBox"` — issue #168 — reuses this same ambient-matrix path and is now also implemented; see its Recent-fixes entry above.) See `SvgClipPathTransformTests` (recording-graphics geometry assertions, incl. exact `rotate(90)`), `SvgIntegrationTests.ClipShapeTransform_ProducesSameGeometryAsDirectlyAuthoredShape` (real-adapter content-stream equality).
