# The driver rolls the box tree back when it re-enters a pass

_Landed 2026-07-27._

**The driver rolls the box tree back when it re-enters a pass** ([issue #415](https://github.com/jhaygood86/PeachPDF/issues/415), [CSS Fragmentation 3 §4.3](https://www.w3.org/TR/css-break-3/#possible-breaks)). A keep-with-next run pull whose head sits in a fragmentainer the driver has already filled re-enters the pass that placed it ([#355](https://github.com/jhaygood86/PeachPDF/issues/355)). It handed that pass the record it was entered with and un-froze the fragments from its slot on — and **undid nothing else**. Un-freezing a fragment says only that it will be built again; the box tree still held everything the discarded passes wrote.

**The one that matters is line boxes, and the reason is that two mechanisms both decline to clear them.** A resumed flow deliberately does not clear its line list (`CssLayoutEngine.CreateLineBoxes` clears only when `resume is null`), and a box's prologue — which owns `RectanglesReset` — is once per box per *layout*, not per pass. So the box the record resumes into kept every line the discarded passes appended, and `FinalizeLineBoxes` ran from the record's own `CompletedLineCount` straight over them: `CssLineBox.AssignRectanglesToBoxes` added a per-line rectangle a second time and threw `An item with the same key has already been added`. #374's crash, on the page grid, from the driver rather than from the columns engine.

**The fix is not a new mechanism, because the columns engine already states what undoing an abandoned attempt is.** `RewindForRefill` walked the resumption chain applying the three-way split a resumed pass needs — below the resume point untouched, at it discard what this attempt added, above it reset outright — and every word of that is about *a pass*, not about columns. It moved to `Html/Core/Fragmentation/PassRewind.RollBackTo`, and `TryRewindForRunPull` calls it. Two callers, one rollback — **including the no-record branch**, which post-change review caught: a rewind to the *first* pass carries a null token, and guarding the call on the token being non-null skipped the rollback in exactly the commonest shape of the bug. The boundary child is also settled by **identity** rather than by index, because between the pass that recorded a token and the pass being re-run a child list can be restructured (a repeating `<thead>` is detached and replaced by proxies).

**What running it bought, and what reading it would not have.** The issue's own fixture does not reproduce here — it is font-metric-sensitive, and the reporter's line breaks are not this machine's. What does reproduce is the *condition*: a temporary counter incremented when the rewound pass's token contains an `InlineBreakToken` with a non-zero `CompletedLineCount` matched the crashing fixtures **exactly**, 5 for 5 across 480 swept combinations, and nothing else crashed. That is the whole statement of the bug — the pass being re-entered is one that was entered mid-paragraph — and it is what turned an unreproducible report into a fixture in one sweep.

**Two pre-existing defects the fixtures walked into**, both present identically with and without the pull, both filed rather than fixed:

- A word the pass never reached still carries document Y 0, which lies inside the **first** slot's own band, so page 0's fragment claims it and paints it in the top margin ([#433](https://github.com/jhaygood86/PeachPDF/issues/433)). `AwaitsTheNextFragmentainer` covers §4.1's discarded line and not this. It is why the "every word claimed exactly once" invariant is asked here of the blocks the pull moves rather than of the whole document.
- The third pass re-entry, `widows`' own (`TryRewindForWidows`), still undoes only its box's lines and not what the pass placed after it. Widening it to the shared rollback is a two-line change that **loses content** — 16 words of `paged_media_horizontal_reflow`, measured — so it is stated as deliberate in that method's remarks and filed as [#440](https://github.com/jhaygood86/PeachPDF/issues/440) with the measurement.
- A `break-before: page` below a box the re-entry replays is **lost** ([#434](https://github.com/jhaygood86/PeachPDF/issues/434)): the prologue that takes it is once per layout, so a box whose prologue ran in a discarded pass never takes it again. `RollBackTo` lets a prologue back in for the direct children of each box the chain names — but a rewind to the *first* pass carries a null token and so rolls nothing back, and the reset is one level deep. Same family as #395.

Tests: `EarlyBreakLayoutIntegrationTests` (+9 — the five swept combinations laying out with each of the resumed paragraph's own words on exactly one of its own line boxes, each heading still landing with its block, and #374's claimed-exactly-once invariant over the blocks the pull moves). Every one was verified load-bearing by removing the `RollBackTo` call: all 9 fail. Full net8.0 suite green (6632), CLI green (96); **100% diff coverage**. New `HtmlContainerInt.PassRewinds` is what makes "the driver really went back to a finished pass" assertable rather than assumed, the same job `FragmentainerPasses` does for resumption. **66 of 68 showcases byte-identical** (acid2's sole difference is the `file://` URI naming each run's own working directory; it is pixel-identical). `paged_media_keep_with_next` gained a second section whose running text carries across the first page boundary, so the pass re-entered is one that stopped mid-paragraph — **on the unfixed build the showcase run dies there**, 19 showcases in. Verified in both PDFium and MuPDF.

**#403 is not this, and the sweeps say so.** ~1,700 combinations over three shapes — the issue's own three declarations on ordinary block content, a realistic justified-text document with the callout last, and a 3pt page-height sweep — reached the driver's no-progress backstop **zero** times. #415 is a crash and #403 is a stall; they share `break-inside: avoid` at a boundary and nothing else that has been demonstrated.
