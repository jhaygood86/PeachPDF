# line-height computes to a length where it is declared; plus the line-box properties built on it

- **Load-bearing idea:** a `line-height` that is a length, percentage or `calc()` is resolved ONCE, against the element that declares it, and descendants inherit the resulting `pt` length (CSS 2.1 §10.8.1, CSS Values 4 §6.1.1); only a unitless number is inherited as a number. `CssBox.ResolveLineHeightValueComputation` (the `valueComputation: "line-height"` hook) now only records that the box declared one (`LineHeightDeclared`); `DomParser.CascadeApplyStyles` calls `box.ResolveDeclaredLineHeight()` after `ResolveRelativeFontWeight`, once `font-size` is final.
- **Trap, found by running it:** declarations apply in SOURCE ORDER, so resolving in the hook itself (the old `Nlh` path) saw whatever `font-size` was set so far: `line-height:1.5em; font-size:20px` came out as 1.5 of the inherited size. Resolve after the whole cascade. A box that inherits the value never goes through the hook, so it keeps the parent's already-absolute length.
- `lh` inside the property is the PARENT's line height: `DerivedStyle.ResolveLineHeightAtDeclaration` runs with `_resolvingLineHeight = true`. `calc(1lh + 8px)` therefore no longer adds its 8px once per generation.
- **Negative values** are invalid at parse time (`Converters.LineHeightConverter`, and `CssValueParser.TryParseLengthOrUnitless`, which only line-height reads): the declaration is dropped, so the inherited value applies. A `calc()` that resolves negative is clamped to 0.
- **Form controls** get `line-height: normal` in the UA sheet (`CssDefaults`).
- **#2233:** `ApplyVerticalAlignment` seeded `lineTop` from `min(FlowTop, every rectangle's top)`. A text box's content area can overflow the line box (the font's content area is taller than its `normal` line), so a top-aligned inline-block aligned to the topmost ink, ~0.1pt above the line top. With a `FlowTop` and a `BaselineExtent` the rectangles are no longer folded in; the extent already holds the strut and every contribution.
- **Non-inherited properties go in a non-inherited area.** `InheritStyle` adopts the whole `TextArea` from the parent and restores only `unicode-bidi`, `vertical-align`, `text-overflow` and `line-clamp`: `text-box-trim` placed in `TextArea` was inherited by every child (each `<p>` inside a trimmed container was trimmed too). It lives in `TextDecorationArea` (non-inherited). `text-combine-upright` IS inherited by the spec and sits in `TextArea`.
- **New:** `line-height-step` (`CommitLineExtent` and the `ApplyVerticalAlignment` rebuild both call `StepExtent`; the vertical column thickness is stepped in `CreateVerticalLineBoxes`), `block-step-*` (`CssBox.ApplyBlockStep` after `ApplyHeight`; the margin-box insert is `_blockStepMarginTop/Bottom` folded into `ActualMarginTop/Bottom`), `text-box-trim`/`text-box-edge` (`CssBox.ApplyTextBoxTrim` before `ApplyHeight`; first/last line found through in-flow block descendants), emphasis marks reserving line room (`WithEmphasisReach`), vertical emphasis marks (`PaintUprightTextEmphasis`, sideways runs through the rotated frame), `text-shadow` on marks, `text-combine-upright` (`CssRect.CombineUpright`, `MergeIntoCombinedWord`, `PaintCombinedUprightRun`) and the `text-decoration-skip` values (`DecorationSkips`, `DecorationContent`).
- **Evidence:** `LineHeightComputedAtDeclarationTests`, `LineHeightStepTests`, `BlockStepTests`, `TextBoxTrimTests`, `VerticalAlignTopInlineBlockTests`, `TextEmphasisTests`; the full engine suite passes.
