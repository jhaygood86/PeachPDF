# A whole-box `slice` decoration is measured against the concatenation of a box's column fragments

_Landed 2026-07-26._

**A whole-box `slice` decoration is measured against the concatenation of a box's column fragments** ([issue #376](https://github.com/jhaygood86/PeachPDF/issues/376), [CSS Fragmentation 3 §6.2](https://www.w3.org/TR/css-break-3/#break-decoration)). #368 gave `SliceGeometry` its block-axis *edges*; what it did not change is the rectangle the rest of the decoration is resolved against. `border-radius`, a gradient/image background layer and a `box-shadow` still measured from the fragment's own block extent at a column break — `clone`'s rendering under the `slice` value.

**The load-bearing idea is that the page grid and a nested fragmentainer need different inputs, and one rule cannot serve both.** On the page grid every fragment of a box already reports the box's *whole* bounds (nothing cuts them until the page clip does, at paint), so the strip is the bounds and summing would describe a box N pages tall. In a column each fragment reports *its own* extent — two columns share a band, so the extent is the only thing that tells them apart — so there the strip is exactly the concatenation, positioned per fragment as the transpose of the inline rule (`strip.Y = rect.Y − preceding`, so the strip's ends are the box's own ends).

**The concatenation needs every fragment's extent before the first fragment is built**, which is what #376 sized as a measuring pre-pass. It is smaller than that: `BoundsOf(Draft, List<BoxFragment>)` measured a continuing box from its *materialized* children, so it could only be asked during materialization. Recast as `ExtentOf(Draft)` over the **draft** tree — with `RectOf(Draft)` for the `BoxFragment.Rect` half — both memoized, the whole set is available up front and `Materialize` reads the same two functions. `UnionRects` and the old `BoundsOf` overload are gone; this is a dedup, not a second measurement.

**The equivalence short-circuit is what keeps it free.** A box with one fragment concatenates to itself, so `BoxDecorationGeometry.For` still takes its direct path and emits no clip; only a genuinely split box with a radius, an image layer or a shadow pays.

Tests: `FragmentEmitterTests` (+3 — the concatenation and its per-fragment positioning, the page grid still being its own whole box, and an unfragmented box in a column), `BoxDecorationBreakPaintIntegrationTests` (+2 — a gradient running through every column fragment under `slice` and restarting in each under `clone`). Full net8.0 suite green (6370); **100% diff coverage**. **All 64 pre-existing showcases are pixel-identical in PDFium**, which is the expected result — none has a whole-box decoration split at a column boundary. `multicol` gained section 9, which puts the same gradient-filled, rounded paragraph in the same box twice and differs only in its `box-decoration-break` value; **on the unfixed build the two are indistinguishable, because `slice` restarts the gradient in each column exactly as `clone` does**. Verified in both PDFium and MuPDF. **Accepted gap:** an **inline** box that wraps *and* crosses a column boundary still gets one strip per column, because its rectangles are keyed by fragmentainer instance and the inline order (`Y`, then `X`) cannot separate two columns that share a Y range — the merge wants fill order first ([#385](https://github.com/jhaygood86/PeachPDF/issues/385)).
