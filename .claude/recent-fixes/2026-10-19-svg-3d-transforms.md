# 3D transforms on SVG elements, and the shared projective code behind them

CSS Transforms 2 §11 puts the 3D functions, `perspective`, `perspective-origin`, `transform-style` and `backface-visibility` on SVG elements. They now work, by pointing the HTML painter's machinery at an `SvgElement` rather than building a second one.

**The load-bearing idea.** `ProjectiveRaster` (`Html/Core/Paint/ProjectiveRaster.cs`) holds everything that did not need a `BoxFragment`: `ProjectivePlane<T>` (the plane struct, generic over what it is painted from), `Locate`/`Project`/`OrderBackToFront`, `Paint` (one warped plane) and `Compose` (a depth-tested context), `FacesAway`, `ProjectsToSliver`, `Magnification`, `Linearise`, plus the two vector fast paths below. `FragmentPainter` keeps only what is box-specific (extents, link placement, the text layer). `SvgRenderer.Projective.cs` is the SVG counterpart: everything is measured in the user space of the element's parent, which is the space `BeginRasterSurface` speaks in, so no page coordinates exist on that side. `Canvas.RasterizationDpi` is the one new public member (a surface that wants more pixels than the default needs the default to scale).

**Found by running it, not reading it.**
- `Canvas.GetClip()` is recorded in the space the clip was pushed in, and an SVG pushes its viewport clip *before* its viewBox transform. Using it as the visible region cropped every warped element at the page's width in layout points, read in user units. The SVG renderer tracks the root viewport and its entry transform instead (`VisibleRegion`); see the invariant file.
- A 3D function that does not resolve (a bare-number angle, `rotateY(60)`) must still make the list a 3D list, or a gradient's `gradientTransform` is not ignored whole (the other functions would apply).
- `perspective: 0` is none (a browser's rule), `perspective(0)` does nothing, and a distance under one pixel is one pixel; the HTML parser and `ActualPerspective` had no 1px clamp until now.
- A context's root plane with no paint of its own still has its box as a source in HTML, so a tilted child "pierces" it at z = 0 and defeats the vector ordering (see the accepted gap).
- A test that counts bitmaps in a PDF (`CollapsedTransformTests`) had encoded "a `preserve-3d` root is composed as a bitmap" as the PDF/A-1b rejection case; with the vector ordering a context of affine planes needs no bitmap, so the test now uses a tilted child under perspective for the visible case.

**Vectorization.** (1) `TryFitAffine`: a projective map within a quarter of a device pixel of its tangent at the centre is written as a `cm` (HTML and SVG), where the old test was an absolute `1e-8` on the divisor entries, which sent `rotateY(1deg)` under a 2000px perspective to a bitmap. (2) `TryResolveOrder`: planes that are only tilted and never pierce draw back to front under their own affine matrices; pairs are ordered by the depth difference over their bounding-box overlap (affine depth, so the corners decide), which is *not* the order of their centres. A cycle is impossible for pairwise-overlapping boxes (Helly), so that branch is defensive. (3) `Warp.SampleRow` steps the inverse map's raw `(u, v, w)` along the row instead of recomputing it with its two neighbours per pixel, compares squared step lengths against 1/4/9/16 instead of taking a root, and hoists the sampling rate out of the row for an affine map; `StoreAveraged` is one vector op. A 1600x1600 warp went from 287 ms to 206 ms (perspective) and 220 ms to 118 ms (affine) in Release, with the same output checksum. Geometry is allowed platform rounding (docs/architecture.md, Determinism); the integer pixel kernels are unchanged and have scalar-reference equality tests. What is left of the perspective case is the supersampling (up to 16 bilinear taps a pixel where the plane recedes), which wants mip levels, not more SIMD.

**Not done.** Selectable text and exact links under a projective warp in SVG (#1812); projecting paths as vector under a real perspective (#1813); `vector-effect` does not exist in the renderer at all, so the spec's non-scaling-stroke clause has nothing to apply to. A container with `opacity` that holds a 3D child sizes its group tile from the child's orthographic extent, which can clip a strongly projected child.

**Evidence.** Full net8.0 suite; the `svg_3d_transforms` showcase rasterized through both PDFium and MuPDF, the two agreeing; new `SvgProjectiveTests` rasterize an inline SVG and assert pixels, `VectorProjectiveTests` assert what is a bitmap in the PDF.
