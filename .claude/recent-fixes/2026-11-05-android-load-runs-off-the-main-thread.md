# `HtmlView` loads and lays out the document off the main thread

The `emulator` job of the Android workflow failed twice on an unrelated PR (head 14f973b8, table layout only; the sample page has no table) and passed on the third attempt. The logs showed `MISSING: ... Tab ...` and, in `dumpsys window`, `Application Not Responding` as the focused window, so the window the keys went to was the system's dialog, not the app.

**Found by running it, not reading it.** The smoke script reproduces on a local emulator (`LowEnd_API_35`): the second of three runs hung. `/data/anr/anr_*` said `Input dispatching timed out ... Waited 5053ms for FocusEvent(hasFocus=true)`, with the main thread idle by the time the dump was taken, so it had been busy from the activity's first focus until after the page had loaded. Stopwatch logs in `ReloadAsync` (thread id 1 throughout) put the whole load on the main thread: fonts 0.1-0.2 s, `HtmlDocument.LoadAsync` 0.8-1.5 s, `LayoutAsync` 0.2-0.3 s on a fast development machine, a cold Mono runtime compiling the engine's code as it goes. A CI emulator is several times slower, which is the five seconds. The engine's async methods do no asynchronous work, so every `await` in `ReloadAsync` completed in place and the "async" load never let the looper run. An earlier guess that the Tab focus steps were slow was wrong: `FocusAsync` takes about 0.1 s and `SetFocusAsync` 1 ms.

**What it does now.** `ReloadAsync` builds the options on the main thread, runs `LoadDocumentAsync` (fonts, load, layout) in `Task.Run`, and takes the document in on the main thread. Three consequences were handled rather than left:
- The device fonts were registered once per context through a plain `HashSet` that was marked before the work was done; two loads in flight (a resize reflow while the first load runs) would now race, and the second would lay out without the fonts. The first caller's `Task` is kept per context (`ConditionalWeakTable`, a faulted one is retried) and every load awaits it.
- `OnDetachedFromWindow` disposed the render context while a pool thread could still be using it. A context a load holds is retired and disposed by the last load to finish (`BeginLoad`/`EndLoad`/`RetireContext`, main thread only).
- A document whose layout throws is disposed rather than dropped.

**Evidence.** The sample activity now times its main thread (a 50 ms heartbeat from `OnCreate` to `DocumentLoaded`, logged as `ui-stall-ms`) and `android-smoke.sh` fails above 3000 ms. On the local emulator the stall is 1.1-1.8 s on the old code and 0.31-0.40 s now (five cold starts); the smoke script then ran clean repeatedly. Not done: the focus, selection and tile paths still run on the main thread (all measured in milliseconds here); the engine's own `HtmlDocument` is not made thread-safe, as before a paint on the GL thread can still overlap a restyle.
