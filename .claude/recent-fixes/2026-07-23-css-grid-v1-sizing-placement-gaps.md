# CSS Grid v1 sizing/placement gaps

_Landed 2026-07-23._

**CSS Grid v1 sizing/placement gaps** (issue #265 — six of the seven consolidated gaps; the seventh, writing-mode/RTL, was split out to [#278](https://github.com/jhaygood86/PeachPDF/issues/278)). All localized to `CssLayoutEngineGrid`/`GridTrackListGrammar`, reusing existing primitives (`GetMinContentWidth`, `CssValueParser.ParseLength` calc evaluation, `CalcParser.IsCalcFamily`, the flex baseline helpers):
1. **`calc()` in track-sizing functions** ([§7.2.1](https://www.w3.org/TR/css-grid-2/#track-sizing)). `GridTrackListGrammar` now accepts a math function (`calc()`/`min()`/`max()`/`clamp()`) as a track breadth — bare, and inside `minmax()`/`fit-content()`/`repeat()` — via a new `IsLengthPercentageCalc` gate (validates through `CalcParser.Parse` + `CalcTypeChecker.Check`, accepting only length/percentage categories so a wrong-category math function drops the whole track list at parse). The calc text is stored as a `GridTrackSize.Length`; the existing `ResolveFixedLength`/`InitTrack`/`FloorSize` paths already funnel `def.Value` through `ParseLength`, which evaluates calc — so no engine change was needed. **Accepted edge:** a `%`-bearing calc resolves its `%` against 0 in a row / auto-fill-count context (identical to a plain `Percent` there).
2. **`min-content` vs `max-content`** and **spanning-item intrinsics** (§11.5). `MeasureColumnIntrinsics` now returns *both* a min-content and max-content outer-contribution array (single-span items measure both via `GetMinContentWidth`/`GetMaxContentWidth`); `InitTrack` sizes a `min-content` track (and the intrinsic sides of `minmax()`, via `IntrinsicMin`/`IntrinsicMax`) to the appropriate one instead of always max-content. A multi-column item now distributes the part of its contribution the spanned tracks don't already cover (fixed sizes + gaps + current contributions) across the intrinsic columns it spans (`DistributeSpanContribution`), so a spanned `auto`/`min-content` column no longer collapses to 0. `fit-content(L)` keeps capping at `min(max-content, L)` (content wider than L overflows the track — matches browsers and the pre-existing `FitContentColumn_CapsAtArgument` test; adding a min-content floor there is deliberately *not* done). **Accepted simplification:** the full §11.5 per-span-count ordering / growth-limit distinction is not modeled.
3. **Percentage rows against an indefinite height** (§7.2.1). In the normal rows branch, a `Percent` row def is mapped to `auto` (`PercentToAuto`) when the container height is indefinite, so it content-sizes instead of seeding to 0 and staying "fixed" (which collapsed it). Definite-height and subgrid/adopted-row paths unchanged.
4. **Implicit tracks from explicit placement** (§8.3/§8.5). `PlaceItems` computes a `minorCount` that grows the minor axis beyond the explicit track count to fit an item explicitly placed past the grid (`grid-column: 5` in a 3-col grid) or whose span alone exceeds it — generating implicit minor tracks instead of clamping into range (which overlapped). Line-number/negative resolution still uses the explicit `fixedCount`; `colCount`/`rowCount` already grow from the placement extent.
5. **Block-axis `baseline` item alignment** ([CSS Align §9.3](https://www.w3.org/TR/css-align-3/#baseline-values)). The flex baseline helpers (`GetItemBaselineOffset`/`FindFirstLineBox`) were extracted into a shared `BaselineAlignment` static (flex delegates — pure extraction, zero behavior change). A new `AlignRowBaselines` post-pass shifts each single-row `align-items`/`align-self: baseline` item down so all baseline items in a row share a common first baseline. `justify-*: baseline` (inline axis) stays `start` — undefined without a vertical writing mode, so it folds into #278. **Accepted gap** ([#280](https://github.com/jhaygood86/PeachPDF/issues/280)): the post-pass shifts but does not grow the row to the baseline group's `max-ascent + max-descent` (CSS Align §9.3), so an item with a disproportionately large descent-below-baseline could overflow the row — for standard text with a normal line-height the shift always fits, so the common case is exact.
100% diff coverage; full net8.0 suite green (5572 tests, no regressions). Verified by new `GridTrackListGrammarTests` (calc accept/reject) + `GridLayoutIntegrationTests` (`Gap4`–`Gap7` geometry) and a `css_grid_intrinsic` showcase rasterized in **both** PDFium and MuPDF.
