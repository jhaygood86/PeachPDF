# `widows` moves the lines it takes, not the whole box

_Landed 2026-07-26._

**`widows` moves the lines it takes, not the whole box** ([issue #371](https://github.com/jhaygood86/PeachPDF/issues/371), [CSS Fragmentation 3 §5.4](https://www.w3.org/TR/css-break-3/#widows-orphans)). #301's `orphans` half is decided at the break point because the count of lines *before* a break is settled the moment it is taken. `widows` cannot be: the count after it depends on content not yet flowed, so it is answered on the pass that **completes** the box — which is a later pass than the one that placed the fragment that has to give a line up.

**The load-bearing idea is that the pass does not have to be re-derived, only re-entered.** In block flow the box whose inline flow stopped is the **last** content in the fragmentainer it stopped in, so keeping fewer lines there shortens that fragmentainer's tail and moves *nothing else in it*. Everything that follows the box does move, and that is exactly what re-running the pass lays out again. So the driver does not roll back to the pass that *started* the box, as the issue scoped it — it re-enters the pass it has just finished with a **rebuilt resumption record**, and the fragment before the break is corrected by the ordinary resumed-flow path.

**That also means no line budget was needed in `FlowBox`.** The issue's item 1 asked for one; trimming the lines already produced (`CssBox.DiscardLineBoxesFrom`, from #374) and lowering the record's `CompletedLineCount`/`ResumeWordIndex` expresses the same thing with machinery that already exists. The one addition is `CssLineBox.StartOrdinal` — a line's position in `FlowBox`'s walk, recorded where `LineStartOrdinal` already was — because the record resumes at a **word ordinal** and the budget is a **line count**, and nothing previously mapped one to the other.

**Three retractions, which is #374's lesson in a different shape.** The box's lines past the budget go; the words on them go with them (`DiscardLineBoxesFrom` marks them `AwaitsTheNextFragmentainer`, self-healing because `CssRect.Top`'s setter clears it); and the fragment the earlier pass froze is un-frozen (`FragmentEmitter.InvalidateFrom`), because it is about to describe fewer lines. The invariant that catches both directions of getting this wrong is #375's: **every word claimed exactly once** over the fragment tree.

**Three guards.** Two fragments only — the budget is a line count for *one* fragment, so a box spread over three or more fragmentainers would be asking a fragmentainer that is not being re-run to give lines up; such a box keeps the whole-box push. The budget must also satisfy `orphans`, or the two constraints are traded rather than both met (§4.3 gives one up instead). And one rewind per box per layout: the rewound pass reaches the same epilogue again.

**Gated by `OrphansAndWidowsMayMoveABreak`** (renamed from `OrphansMayMoveABreak`), i.e. off under per-page left/right `@page` margins — #373's gate, for the same reason and found the same way: ungated it changed `paged_media_horizontal_reflow` from 8 pages to 7 by feeding a break decision into the very loop that is settling which page each box is on. The 7-page result looked *better*, which is exactly why the gate matters — #373 records that this loop stopped converging on `windows-latest` only.

Tests: `OrphansWidowsIntegrationTests` (+4, and 2 re-pinned from the whole-box push to the per-line move — that is the behavioural change). Full net8.0 suite green (6327); **98% diff coverage** (the uncovered line is `TryRebuildForBudget`'s defensive "the record does not name this box" arm). **All 63 pre-existing showcases are pixel-identical**; new showcase `paged_media_orphans_widows` puts the same paragraph in the same place twice, once unconstrained and once at `widows: 4`, so the correction is visible as 10/1 against 7/4 — **on the unfixed build the constrained one is pushed whole and leaves the foot of its page blank**. Verified in both PDFium and MuPDF.
