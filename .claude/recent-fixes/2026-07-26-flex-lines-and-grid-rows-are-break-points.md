# Flex lines and grid rows are break points

_Landed 2026-07-26._

**Flex lines and grid rows are break points** ([issue #315](https://github.com/jhaygood86/PeachPDF/issues/315), [CSS Fragmentation 3 §3.1/§3.2](https://www.w3.org/TR/css-break-3/#break-between)). PR #351 sized this precisely and the sizing held: `IsFragmenting` is *already* false throughout every item layout, so there was no guard to delete — `AssignLocations`/`PlaceItemInCell` only **translate** an already-laid-out item, and #315 has to **add** the pass that breaking can be enabled in.

**The pass runs where the items finally are.** Every earlier phase lays an item out at the container's content origin purely to *measure* it, so a break decided during one names a position the item is about to be moved away from — which is why they stay suppressed. `RelocateLinesAcrossFragmentainers` (flex) and `RelocateRowsAcrossFragmentainers` (grid) run after placement, which is the only point where "does this fit in the fragmentainer?" can be asked of the right coordinates. `CssBox.LayoutEngineContent` replaces `LayoutMonolithicContent` for these two so the engine can tell "this container is being paginated" from "something is measuring it" — with `LayoutOutOfFlowChildren` keeping a suppressed scope of its **own**, which is not incidental: it discards any resumption record a child leaves behind and is the only way an abs-pos child of these containers is laid out at all.

**A line or row moves, not the item that asked** — the cross-axis phases aligned them against each other, and §3.1's break points in a flex container are between lines rather than between the items sharing one. An item spanning several grid rows travels with the first.

**Three deliberate limits.** The line is *translated* rather than laid out again, inverting #332's choice, and it has to be: an item's position is assigned by the engine rather than derived from its own layout, so re-flowing it at a new position changes the measurement the container's size came from. An item with **no** break value is left where it is and the boundary cuts it — moving every straddling line would paginate flex quite differently from how it renders now, a larger change than the break values ask for. And item *content* is not fragmented: the engines would have to become resumable, and their measurement phases re-lay every item out, so a resumed pass would need line/track geometry rebuilt without disturbing what an earlier page already placed.

**The gate is `IsFragmenting`, and the test that found it is the one #351 warned about.** Ungated, a flex container inside a **table cell** had its line shifted against the *page* grid while the table engine was placing it against its own row grid (`FlexReplacedElementPageBreakIntegrationTests.InlineSvg_SoleFlexItem_InTableCellRelocatedAcrossPageBreak_StaysInsideItsOwnBox`). `inline-flex`/`inline-grid` are excluded on the same grounds — an atomic inline's position is the line it is on to decide, which also leaves #346's guard exactly as it was.

Tests: `FlexGridFragmentationIntegrationTests` (14 — `avoid`/`avoid-page`, §2 monolithic, forced breaks, the whole line/row moving together, no-break-value left alone, taller-than-the-band left alone, and the table-cell boundary), for both engines. Full net8.0 suite green (6284); **100% diff coverage**. **All 63 showcases are pixel-identical**, which is the expected result — none had a straddling line that asks not to be broken; `paged_media_monolithic_content` gained a section that does, **verified in both PDFium and MuPDF**. **Accepted gaps:** item content is not fragmented, so the `IsFragmenting` gates #349 and #351 had to add stay where they are for content *inside* an item, and the flex/grid half of [#335](https://github.com/jhaygood86/PeachPDF/issues/335) is unchanged.
