# `box-decoration-break` honored at page and line breaks, and room reserved for `clone`

_Landed 2026-07-25._

**`box-decoration-break` honored at page and line breaks, and room reserved for `clone`** (issues [#309](https://github.com/jhaygood86/PeachPDF/issues/309) `slice`, [#310](https://github.com/jhaygood86/PeachPDF/issues/310) `clone`, [#311](https://github.com/jhaygood86/PeachPDF/issues/311) the line-break axis — done as one change per #320, [CSS Fragmentation 3 §6.2](https://www.w3.org/TR/css-break-3/#break-decoration)). #300 stored the value; nothing read it, so the output was a blend of the two matching neither (see that entry for the diagnosis). Three commits:
1. **`SliceGeometry` on `LineFragment`** (behaviour-neutral). `Fragments/Fragment.cs` gains `SliceGeometry(UnbrokenStrip, FragmentRect, HasLeftEdge, HasRightEdge)`, computed in `FragmentTreeBuilder` — the only place that can see **every** rectangle a box produced across **every** page, which paint never does (it sees one fragmentainer's survivors). **The load-bearing idea:** the unbroken box of an inline broken across lines is the box on *one infinitely long line*, so its width is `Σ` of the rectangles' widths — exactly right because `CssLineBox.UpdateRectangle` adds the leading spacing only on the box's first hosting line and the trailing only on its last, counting each border/padding once. Positioning that strip **per rectangle** (`strip.X = rect.X − preceding`) makes its left edge coincide with the first rectangle's left and its right edge with the last rectangle's right, so a decoration resolved against the strip and clipped to the rectangle rounds *only the true ends* with **no per-corner special-casing**. Same shape as WebKit's `InlineFlowBox::paintFillLayer` (`totalLogicalWidth`/`logicalOffsetOnLine`). `FragmentRect` is the rectangle cut to its own band (via the same `BandOf` helper `IntersectsBand` uses, so a fixed box can't be cut against a band it doesn't live in) — what `clone` closes off. **Edge flags are physical and derived from the two rects** (`Rect.Left ≈ Strip.Left`), so they cannot disagree with the strip and stay correct when RTL reverses the inline progression.
2. **`Paint/BoxDecorationGeometry.cs` owns the whole §6.2 decision.** `For(box, line)` → `(DecorationRect, ClipRect, HasLeftEdge, HasRightEdge, NeedsClip)`: `slice` resolves against `UnbrokenStrip` and clips to the line; `clone` resolves against `FragmentRect` with both edges its own and no clip. The painter never branches on the property. **Equivalence short-circuit** (`NeedsUnbrokenGeometry`): a decoration that paints the same wherever it is measured from takes the direct per-rectangle path, so a plain solid background keeps a byte-identical content stream. Its members were each verified load-bearing: radii (`ComputeRadii`'s reduction scales with width), any `background-image` layer, `box-shadow`, and a non-`border-box` `background-clip` (the solid fill's inset belongs at the box's true ends). **`background-origin` is deliberately absent** — it positions image layers only, and its initial value is `padding-box`, so testing it would put *every* box on the unbroken path and defeat the short-circuit (caught in implementation).
3. **`clone` space reservation in layout** (§6.2 requires it). Amounts are **pure functions of the ancestor chain** (`DomUtils.ClonedBlockStart`/`ClonedBlockEnd`/`ClonedInlineStart`/`ClonedInlineEnd`) rather than a counter maintained as layout enters/leaves boxes, so there is no per-pass state to keep in sync; `HtmlContainerInt.HasCloneDecorations` settles once before the first pass (cascaded style only) so a document that clones nothing never pays for the walk. `CssRect.WouldStraddleFragmentainer` makes a word clear the cloned bottom border+padding; `CreateLineBoxes` starts a resumed flow below what the reopening fragment re-opens with; `FlowBox`'s wrap test **and hyphenation budget** leave room for cloning ancestors' trailing spacing and a wrap re-adds their leading spacing; `UpdateRectangle` gives every cloned line both spacings so the rect and the reserved room agree.

**Four things the post-change review caught, each a real defect while it was missing:** (a) **only a box broken by *someone else's* line breaks gets a strip** — a box that owns the line boxes its rectangles are keyed by (a `display: block` `::before` holding its own text) has them stacked down the *block* axis, and concatenating their widths described a box that does not exist; the guard is `ReferenceEquals(line.OwnerBox, box)`. Note a `display: inline-block` generated-content box does **not** qualify: PeachPDF flows its text into the parent block's own line boxes, so it really is one inline run and the strip is right for it. (b) **`BandCut` insets by the *ancestors'* cloned decorations**, or every level of a nested cloning stack closes on the same line — each border drawn over the last — while layout, which reserves the whole nested sum, leaves the gap between them blank. (c) **The cloned insets count towards `WouldStraddleFragmentainer`'s "too tall to fit anywhere" guard.** Without that, an inset larger than the band makes every pass break again on the page it just resumed on: verified to produce a **zero-page document** (`Clone_InsetTallerThanThePage_OverflowsInsteadOfPaginatingForever` fails with 0 fragmentainers if the guard is narrowed back). (d) **`EdgeEpsilon` is `RRect`'s own 0.001 equality tolerance**, not a finer one — paint compares the strip to the rectangle with `==` to decide whether anything needs slicing, so a finer tolerance here could call an edge broken on a rectangle paint had already judged unbroken.

**Margin is cloned on the inline axis and not on the block axis**, which looks inconsistent and isn't: §6.2 wraps each fragment with "the border, padding, and margin", but on the block axis [§5.2](https://www.w3.org/TR/css-break-3/#break-margins) truncates a margin adjoining an unforced break to zero, so there is no margin left at a page break to clone. Including it inline also removed a real asymmetry — the *trailing* spacing reserved on every line has always included the margin.

**Three more traps worth keeping:** (a) `BoxFragment.IsFirstFragment`/`IsLastFragment` are **not** the §6.2 edges — their `BandSpan` is unioned with *descendants'*, so a box whose own geometry starts on page 2 reports `IsFirstFragment` on page 1; their doc comment said otherwise and is fixed. (b) `box.FirstHostingLineBox` was **not** usable either — a resumed pass re-entered `FlowBox` and reassigned it, double-adding `leftSpacing` to the resumed page's first line ([#336](https://github.com/jhaygood86/PeachPDF/issues/336), **now fixed** — see the Recent-fixes entry). The edges stay geometric regardless: `FirstHostingLineBox` names a line, and a line cannot see across pages, so it can never answer §6.2's question for a box that crosses one. (c) A sliced shadow's break-edge clamp must be built from **finite geometry** (the shadow layers' own offset+blur+spread), *not* from `g.GetClip()`, which reports the last rect pushed and is unbounded on an unclipped surface — inflating that yields meaningless coordinates.

Dropping `CssImagePainter`'s `isFirst` parameter is a consequence, not a cleanup: a layer positioned in whatever box §6.2 hands it lands where it belongs on its own (`background-position: right` now on the **last** line, not the first) and repeats per fragment under `clone`. It is only safe because `BackgroundImages` is in `NeedsUnbrokenGeometry` — noted next to the predicate, since a later "simplify the predicate" pass would silently break it. Tests: `BoxDecorationBreakPaintIntegrationTests` (16, incl. a cross-axis case where an inline crosses *both* a wrap and a page — the old per-page `i == 0` drew a spurious border there — and an equivalence pin asserting the short-circuit emits no clip), `BoxDecorationBreakLayoutIntegrationTests` (6, real geometry), `FragmentTreeBuilderTests` (6, incl. rowspan/unfragmented cases); `TestRecordingGraphics.DrawPathCall` gained the path's points, since a rounded background is a path and its rect was previously invisible to tests. **Verified in both PDFium and MuPDF** via the new `box_decoration_break` showcase, and all 59 pre-existing showcase PDFs are byte-identical after normalization (acid2's sole difference is annotation UUIDs plus a `file://` URI naming each run's own working directory; its content streams are identical and it is pixel-identical in both renderers). **Accepted gaps:** reservation is block/inline flow only, a tall `line-height`'s leading below the last line isn't counted, and multicol never clones ([#335](https://github.com/jhaygood86/PeachPDF/issues/335)); the strip assumes one inline direction per block ([#337](https://github.com/jhaygood86/PeachPDF/issues/337), blocked by #176); plus #336 above (since fixed, which is what makes the strip exact for a box that both wraps and crosses a page). `border-image` is parsed but never painted, so §6.2's treatment of it is vacuous; a replaced element is monolithic and never cloned.
