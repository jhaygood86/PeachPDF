# A table with a repeating header survives being laid out again

_Landed 2026-07-27._

**A table with a repeating header survives being laid out again** ([issue #353](https://github.com/jhaygood86/PeachPDF/issues/353)). `CssLayoutEngineTable` assumes it runs once per table box: `RemoveHeaderFooterFromTree` detaches the repeating `<thead>`/`<tfoot>` and puts one `CssProxyBox` per page in its place, and nothing removed the proxies.

**The symptom is worse than the issue recorded.** A proxy inherits the source group's style, so its `Display` *is* `table-header-group`; a second run's `AssignBoxKinds` therefore took the first stale proxy as `_headerBox` and classified the rest as body rows — and a proxy has no cells, so positioning such a "row" threw `Sequence contains no elements` out of `row.Boxes.Min(...)`. Not a 73.5pt drift: a **crash**, which is what `CssBox.ContainsARepeatingTable` has actually been guarding against.

**The proxies are the only surviving reference to the detached group**, which is what makes the restore go through them: the engine is constructed afresh per layout and detaching nulls the group's `ParentBox`, so a new instance cannot reach it any other way. Each proxy carries the index its source was taken from (`CssProxyBox.SourceIndex`) — the one piece of that state nothing else records — and `RestoreStructureFromAnyPreviousRun` drops the proxies and re-inserts each source once.

**The height half was the restore adding the group twice, and it is worth knowing why that took a trace to find.** `CssBox.ParentBox`'s setter is what re-parents, and it **appends** to the new parent's `Boxes` — so `Boxes.Insert(index, source)` followed by `source.ParentBox = _tableBox` puts the group in the child list at *both* places. `AssignBoxKinds` then took the first as `_headerBox` and pushed the second onto `_bodyRows`, where the body-row loop laid it out after the last real row: exactly one header row plus the vertical spacing, independent of how many pages the table spans, which is precisely the shape #353 recorded as not scaling with the number of repeats. The index is now applied by *moving* the box after the setter has re-parented it.

**What the bisection bought, and the order to do it in.** The drift was invisible from the outside — body rows identical, proxies identical, proxy layout identical on every pass — until the table's own child list was printed either side of the restore. Two cheap experiments came first and both paid: a fixture matrix (no `<thead>` is perfectly idempotent; with one, the drift is the same 14.7pt whether the table spans one page or three) and resetting the restored source's geometry (changed nothing, which ruled out a stale value being read back). Console output is swallowed by the test host — `Console.SetOut` inside the test is what makes an engine trace readable.

The table is now reproduced **exactly** across three layouts — geometry, body rows and its own height. All 65 showcases byte-identical and the full net8.0 suite green (6455), which is expected: `ContainsARepeatingTable` still keeps any production path from laying such a table out twice, so this is a latent-path fix that unblocks the reachable work ([#354](https://github.com/jhaygood86/PeachPDF/issues/354), then [#314](https://github.com/jhaygood86/PeachPDF/issues/314) and [#406](https://github.com/jhaygood86/PeachPDF/issues/406)). Tests: 5 in `EngineRelayoutIdempotencyTests`.
