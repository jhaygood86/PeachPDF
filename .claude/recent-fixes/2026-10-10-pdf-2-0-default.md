# PdfVersion defaults to Pdf20

`PdfGenerateConfig._pdfVersion` starts at `Pdf20`. The piece that makes this safe is the resolution in `PdfGenerator.EstablishDocumentOptions`: if
`PdfVersionExplicit` is false and an earlier PDF/A or PDF/X level is requested, `requestedVersion` becomes `Pdf17` (the code then bumps the document to 1.7/1.6 per level
exactly as before); PDF/A-4 and X-6 resolve to `Pdf20`. Only an *assigned* `PdfVersion` that contradicts the level throws.

- Measured breakage from flipping the default: 20 tests, all assertions about a `1.4` header/`Version == 14`, or inflating raw Flate raster streams. Once Brotli became
  opt-in the latter vanished (they never needed pinning); the former were updated to say what they now mean (`Default_IsPdf20`, `ExplicitPdf17_KeepsTheHistoricalVersion14`).
- The raw `PdfDocumentOptions` (a hand-built `PdfSharpCore` document) still defaults to `Pdf17`; only the public config defaults to 2.0.
- Multiple `AddPdfPages` calls: the version established by the first call must match; an unconformant first page followed by a PDF/A one now throws the "same version" error
  (the conformance mismatch would have thrown anyway).
- Decision record: the first plan made Brotli default-on under PDF 2.0. pypdfium2 (PDFium 152) rendered such a file blank while PDF 2.0 + Flate rendered fine, so Brotli stays opt-in.
