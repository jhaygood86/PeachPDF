# mad4mod.space/gallery: flex figures that shrink, and photos that fill them

The gallery is a grid of cards: `a.gallery-card { display: flex; flex-direction: column }` as a grid item with a fixed row height, holding a `figure { flex: 1 1 auto; min-height: 0; overflow: hidden }` and a caption; the photo is `width: 100%; height: 100%; object-fit: cover`. Photos were drawn at their natural height over the captions and into the next row. Reduced to one card (`m4r.html` style) and compared with Chromium; four separate defects:

**1. A flex item shrunk by `flex-shrink` was grown back to its content at the end.** `ResolveFlexibleLengths` gave the figure 100px, `ResizeItem` laid it out at that size, then `ItemContentCommit.CommitLayout` pinned it and the final layout's `ApplyHeight` took `neverShrinksBelowContent` (written for an auto-height scroll container that breaks across pages, whose pinned height is only the unbroken measurement) and kept the content's 400px. A flex item whose size the algorithm took below its content (`FlexItem.NaturalMainSize`) now carries `CssBox.ShrunkByFlexBelowContent`, set on every pass, and the carve-out skips it. `ClippingFlexItemDecorationTests` (the overflow:hidden cases fail without it; `overflow: clip` is not a scroll container, so its automatic minimum size keeps it at its content, as in Chromium: that case is tested with an explicit height).

**2. The fragment emitter grew a pinned flex item's painted box to its content (`BoundsEndAtItsContent`, #569), whatever the author's height.** CSS 2.1 section 10.6.3: a definite `height` is the used height, and content past it is overflow (Chromium: a `height: 20pt` flex item holding 80px of rows is a 26.7px box with a background 26.7px tall). The extension now applies only to an item whose author height was auto, that the flex algorithm did not shrink, and that does not clip. The two #569 tests had `height: 20pt` in their fixtures and asserted the decoration followed the content past it; that asserted the deviation, so they now use auto-height items (the case #569 is about) and `AFlexItemWithADefiniteHeight_KeepsItsDecorationAtItsOwnHeight` pins the spec behaviour. Trap: `CssBox.ClipsOverflowVertically` is true for `overflow: visible` (it reads "not clip-without-scrolling"), so it cannot be used to ask "does this box clip"; use `OverflowY.Value == Visible`.

**3. `height: 100%` on a replaced element was never resolved** (only `min-`/`max-height` percentages were). `MeasureIntrinsicSize` resolves it against the containing block when that is definite (`IsHeightDefinite`, which includes a flex/grid item's algorithmic height).

**4. A percentage `width` made the engine overwrite an explicit height, and a resolved height overwrite a percentage width.** `width: 100%` set `scaleImageHeight`, which recomputed the height from the ratio even when the height was explicit; and with the height resolved and the width a percentage, the width was recomputed from the height. Both now keep what the author wrote (CSS 2.1 section 10.6.2). `PercentageHeightReplacedElementTests`.

Not engine bugs on that page: the photos are lazy-loaded in the browser (Chromium shows broken-image icons in the pane); caption wrapping matches.

**Evidence:** `PeachBrackets.Engine.Tests` 18721, `PeachPDF.Tests` 1663, `PeachBrackets.Tests` 964 pass; the gallery's first rows match Chromium's card structure.
