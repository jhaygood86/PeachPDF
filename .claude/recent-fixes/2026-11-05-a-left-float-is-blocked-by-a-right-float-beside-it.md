# A left float is blocked by a right float beside it; a float is not placed above an earlier float's top

Fixes #2219, #2221 and #2224. Two parts of CSS 2.1 §9.5.1 that the float placement did not implement, and the formatting-context boundary of the blocker scan (§9.4.1) that the first one made matter.

## 1. Rules 1-3: a left float over a right float

`<div style="float:right;width:300px"></div><div style="float:left;width:200px"></div>` in a 400px container left the second float at the top, drawn over the first; Chrome puts it below. Left-then-right already worked, and so did two floats on the same side. It reached the table `align="right"` then `align="left"` pair through the float mapping, but is plain float placement and older than that change.

**Cause.** `DomUtils.IsFloatIntersecting`'s `Floating.Left` case is a point test: a blocker counts only when the candidate's left edge lies inside it. A right float further along never contains that point, although `FloatBoxLeft`'s own switch already had a `Floating.Right` arm waiting for one.

**Fix.** A second `Floating.Left` case: an earlier right float whose margin box starts before this float's margin box ends (`Left + ReferenceWidth + MarginRight`) and reaches past its left edge. Not under `LeftFloatsOnly`, the line flow's lookup (its `ReferenceWidth` is 0 and it must not see right floats). The overlap is tested with `FloatFitTolerance` (0.02pt): 70% and 30% of the same width add up to it only to within rounding, and without the tolerance the left float went below the right one at 333, 347 and 523px containers while Chrome keeps them on one row. The first version used 1e-6 and then 0.01pt, both too small: a used width is a single-precision value, so two of them are off by a few 1e-5, and a browser floors each width to 1/64px, so a row of a few floats can be a few hundredths of a point over and still be one row there (0.02pt is 0.027px, about where Chrome starts to split rows: reviews measured 0.02px as one row in some arrangements and two in others, and 0.03px and more splitting in Chrome and here alike; three 233.34px floats in 700px, 0.02px over, are one row in Chrome and need more than 0.01pt) (`66.6667%` + `33.3333%` of 700px, or 14.2857% + 85.7143% of 1000px, were 1.4e-5 over). Every fit test has to use the same tolerance, not only the blocker test: the fit checks in `FloatBoxLeft`/`FloatBoxRight` run after a genuine blocker moved the float sideways, and two floats on the same side (a left float of 66.6667% then one of 33.3333%) reach only those. `FloatBoxLeft`'s fit check also adds the float's `margin-right` once a right blocker set the right limit (`rightMargin`, reset on a drop). That line is not needed for correctness: without it the margin-only case "fits" once, is found again in the same state and the repeated-state guard drops it to the same place. It sends the float down at once instead of leaning on the guard, which is why no test fails without it.

## 2. Rule 5: not above an earlier float's top

The second of three left floats of 300, 200 and 50 in a 400 container goes below the first; the third fits beside the first at y=0, above the second. Chrome puts it beside the second at y=50. `DomUtils.GetLowestEarlierFloatTop` climbs the same way the blocker scan does (earlier siblings at each level, stopping from the second level up at a formatting-context root) and returns the lowest margin-edge top of an earlier float, not looking inside a float or a formatting-context sibling; `CssLayoutEngine.NotAboveAnEarlierFloat` raises the float's start to it before placement.

- **Margin edges, not border tops.** A first version compared border tops and moved two floats with negative `margin-top` (`FirstChildFloat_AppliesItsNegativeMarginTop_*`, `SecondRightFloatWithNegativeMarginTop_*`); rule 5 compares outer tops.
- **Multi-column containers.** A column's `Y` is measured from its own top, so the top of a float at the foot of column 1 is not comparable with column 2's; the first version held a column 2 float down to it (found by a review: `FloatInTheSecondColumn_IsNotHeldDownByAFloatAtTheFootOfTheFirst`). `GetLowestEarlierFloatTop` now returns nothing once its climb reaches a multi-column container, so inside one rule 5 is not applied at all (the behaviour before this change), including between floats of the same column.
- **Formatting contexts in the blocker scan.** The new `Floating.Left` case meets right floats, and `GetNextIntersectingFloatBox` descended into every preceding sibling, so a right float inside a fixed-height `overflow:hidden` card, a flex or grid container, an absolutely positioned panel or `contain:layout` box pushed a later left float down (`main` matched Chrome there, since it never saw right floats). It now does not look inside a box that is a formatting context of its own, a float included (CSS 2.1 §9.4.1), which is also the old left-after-left case of #2224, so that issue is closed by this change too. Cases with no fixed height, where the box grows to contain the float, were never affected.
- **Relative offset.** See the review round below: the first version of this (`StaticTop`) corrected only the float's own offset.
- **`clear`.** A float is placed once before `ClearBox` moves it. With the new blocker the first placement drops a `clear:left` float below a right float it never needed to clear, and `ClearBox` then seeds clearance from that lowered `Y`, so it could not come back up. `FloatBox` now restores the start `Y` (`flowY`) before `ClearBox`, and the re-placement after clearance gets the rule 5 start too.

## Maintainer review round: four cases where `main` matched Chrome and this change did not

Found by the maintainer's Chrome grid; each is a minimal HTML sample in the review thread.

1. **Rounding.** See the tolerance above. `triedPositions` needs none: the same blocker gives bit-identical arithmetic, so a repeated state repeats exactly, and a chain of states that differ by 1e-12 is bounded by `MaxFloatPlacementAttempts`.
2. **A right float after an inline-block that fills the line.** `main` was right by accident: it descended into the inline-block and found the floats inside it. Not looking inside a formatting context (needed for `overflow:hidden` cards and the like) lost that, and an inline-block that is not a float and holds no float of its own was never a blocker (`main` put the float over it too). Two mechanisms, since an inline-block reaches the line two ways. One that holds block-level content (and an inline-flex, -grid or -table) has a box with a location: `GetNextIntersectingFloatBox` counts it by its own margin box for a *right* float, only when it is a **sibling** of the float being placed (an inline-block inside an earlier block is on that block's line, not the float's: a review found a float pushed down by a taller inline-block of a fixed-height row above it), and the blocker switch in `FloatBoxRight` treats a non-float blocker as sitting at the line start. One whose content flows into the line has no location while the line is built, only reserved width (`ReserveAtomicInlineUsedWidth`): `CssLineBox.AtomicInlineRight` records its right edge and `FlowFloatChild` reads it through `FloatOverlapsLineBox`, placing the right float at the line's bottom (`PlaceFloatAtLineTop`'s `top` argument) and leaving the line open, so what follows the float in the source goes on after the box, as in a browser (an earlier version opened a new line and the content after the float jumped to it). A left float is deliberately not given this: the words on its line move beside it (`ShiftLineBesideFloat`), which an already placed box with content of its own cannot, so a left float after an inline-block still lands over it as on `main` ([#2227](../accepted-gaps/a-left-float-after-an-inline-block-is-drawn-over-it.md)). The float goes at the line's bottom as it stands when it is met, so later content that makes the line taller is not counted, and an inline-block with a `margin-top` lands about 20px short of Chrome with a 10px margin (both in the gap file).
3. **A relative offset leaking into blockers.** A box's relative offset is applied to its `Location` **before** its content is laid out (`CommitBlockChildOffset`), so a float inside an offset box has the offsets of the boxes it lies in in its own coordinates, and the blockers it is compared with, found by scanning an earlier sibling of one of its ancestors, have that sibling's. The first version corrected only the blockers (a review caught that this put a float inside an offset box in the wrong frame, a regression for floats in offset boxes next to floats outside). Both are now taken to one frame: the scan accumulates the offsets from the blocker up to the sibling being scanned (`GetNextIntersectingFloatBox`), and starts from minus the offsets of the boxes the float lies in up to the level being scanned (`FindIntersectingFloatBox`'s `frameOffsetX/Y`; the float's own offset is applied after it is placed, so it is not in it). The hit stores the sum on `CssFloatCoordinates` (`BlockerOffsetX`/`Y`) for `FloatBoxLeft`/`FloatBoxRight`, which read the blocker's edges through it (position, the bottom a float drops to), as do the four edge reads in `IsFloatIntersecting`, `LowestFloatTopIn` (rule 5) and the clearance walk (`LowestFloatBottomIn`). **The line flow's lookups stay on drawn edges** (`CssFloatCoordinates.LeftFloatsOnly`): making only the test static stacked all the words of a line on top of each other for `left:-9999px`, because the advance read the float's own drawn edge; text beside such a float is tracked in [#2229](../accepted-gaps/text-beside-a-float-in-a-relative-box-uses-its-drawn-position.md). A `position:relative` float itself is never drawn at its offset ([#2230](../accepted-gaps/a-float-with-position-relative-is-drawn-at-its-static-position.md)).
4. **Clearance between floats with margins.** A float that clears earlier floats goes below their bottom outer edges by its *own outer edge* (CSS 2.1 §9.5.2's last constraint, on floats): its `margin-top` sits between, so `margin: 8px 0; clear: both` floats are 16px apart (Chrome 8, 80, 152; `main` had 8, 72, 136). `ClearBox` (reached only by `FloatBox`, for floats and for blocks that have a `clear`) put the border box at the bottom outer edge, which is clearance, the rule for a block. For a float it is now `max(Location.Y, lowest cleared edge + margin-top)`, so a negative margin-top reaches back above the float it clears and a float with nothing to clear is no longer clamped to the container's top (a review found a negative-margin float clamped to 0 and the next float then held down by rule 5, a regression against `main`). A block with `clear` is unchanged. The gap was older than the first commit of this change (`main` was 8, 72, 136); restoring the start `Y` before `ClearBox` (above) made the second step of the sequence worse, and `screen_chat_messages.html` is such a page: it now matches Chrome. Also from the reviews: `FloatBoxLeft` dropped a float below its blocker's border-box bottom, where `FloatBoxRight` used the margin box, so a left float after a blocker with a bottom margin was too high (now both use the margin edge, rule 8); The conflict test itself now compares margin boxes when a float is placed (`IsFloatIntersecting`: the blocker's top less its margin-top, its bottom plus its margin-bottom; the line flow's lookup keeps border boxes), which is what rules 1-3 say and what the drop to the blocker's margin edge needs to stay consistent: with the border box in the test, a negative margin-bottom put the drop back inside the blocker and the same blocker was found again for ever, which is why the older code clamped the drop to the border box and two older tests asserted the clamp (`Float_BelowABlockerWithANegativeMarginBottom_StillEndsItsSearch`, `BlockerWithNegativeMarginBottom_DoesNotStallFloatPlacement`: their no-stall point is kept, their expected position is now the margin edge, which is where Chrome puts the float). A later review's regression hunt found the two cases the clamp had been hiding (a left float with `clear: right` after a right float with a negative margin-bottom, and a cleared float with a negative margin-top after a float with a margin-top: Chrome 20 and 63, the first version here 30 and 25); a float with a `margin-top` was also not a blocker for a float starting above its border box. `clear` missed floats two levels down and counted floats of other columns, fixed by [the follow-up](2026-11-06-clear-considers-every-float-in-its-context.md).

## Checked

Chrome (headless `getBoundingClientRect` against PeachPDF's fills): the sample, fits beside, margins either side, left-then-right, a short right float, three-float sequences, percent widths, `clear:left`, `<table align>` right then left. An independent grid of about 165 layouts (rtl, inline-start/end, nested containers, flow-root, table cells, flex/grid items, fixed-height multicol) found one regression, the `clear` case above, since fixed. 240 of 240 showcases render identically to `main`. A document of 3,000 random left and right floats takes 4 s, against 120 s before (the overlap made the search for floats run on). A long run of floats separated by paragraphs is up to about 30% slower at several thousand floats, because the rule 5 climb adds a scan of the earlier boxes per float on top of the blocker scan, which was already quadratic there.

## Left known

- Inside a multi-column container rule 5 is not applied ([#2225](../accepted-gaps/rule-5-is-not-applied-to-floats-inside-a-multi-column-container.md)).
- The "lowest blocker" gap below shows more often now: far more `R L L` sequences reach it. A right float 250x50, then two left floats 120x30: the second sits at y=50 where Chrome has y=30. Before, it overlapped the right float.

## Not fixed, all older

[#2222](../accepted-gaps/a-float-that-moves-down-goes-below-the-lowest-blocker-it-met.md) has its own gap file; blocks and BFC boxes not narrowing beside floats is #2187.

Tests: `LeftFloatBesideRightFloatTests`, `FloatTopNotAboveAnEarlierFloatTests`, `FloatBesideInlineLevelBoxTests`, `FloatAgainstRelativelyPositionedBlockersTests`, `FloatClearanceMarginTests` and two in `MulticolFloatIntegrationTests` (box tree), and `PeachPDF.Tests`' `FloatPlacementPdfTests` (the same through `PdfGenerator`, which is what the coverage gate measures: see [the invariant](../invariants/testing-engine-tests-do-not-count-towards-the-diff-coverage-gate.md)). Each guard was removed in turn and a test fails: the left-after-right case, the tolerance (2 of its 3 widths hit the rounding), the `clear` restore, the rule 5 clamp, the post-clearance re-placement, the climb across ancestors, the formatting-context stop in the climb and in `LowestFloatTopIn`, the margin-edge subtraction, the multi-column stop and the formatting-context stop in the blocker scan (`FloatInsideAFormattingContextSibling_*`, `FloatInsideAnAbsolutelyPositionedSibling_*`).

**Words moved beside a float that is below the line.** `FlowFloatChild` moved the words on a line beside a left float whenever the float's horizontal extent met theirs (`FloatOverlapsLineWords`), which was enough while a float always started at the line top. A left float that now goes below an earlier right float is not beside the line, so the words (and an inline-block holding text, which a review's CI run on Linux and macOS showed 150pt too far right: the test compared only Y and its fallback-font offset hid it on Windows) were shifted for nothing; the move now requires the float's margin-top edge to be above the line's bottom (`floatIsBesideTheLine`). Found by pinning `FloatPlacementPdfTests` to the bundled Liberation Sans, which made the failure reproduce on Windows. The 0.324pt offset of an inline-block that holds text is a separate, older defect ([#2233](../accepted-gaps/an-inline-block-with-text-is-drawn-a-few-tenths-of-a-point-below-the-line-top.md)).
