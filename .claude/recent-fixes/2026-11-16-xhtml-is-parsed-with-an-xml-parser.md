# XHTML is parsed with an XML parser

`XhtmlParser` (`Html/Core/Parse/Xhtml/`) builds the same synthetic-root box tree as `HtmlParser.ParseDocument` from an `XmlReader`, so the cascade and layout are untouched; `DomParser.GenerateCssTree` branches on `HtmlContainerInt.DocumentSyntax`, which comes from `HtmlDocumentOptions.Syntax` and so survives every re-parse of the source (reload, the container-query loop, the disclosure twin).

- **The syntax is chosen by the host, never from the text**, as a browser decides by MIME type. `RNetworkLoader.PrimaryContentType` (new, default null) carries the type from the loaders that know it; `PdfGenerator.AddPdfPages` reads it only for a document the loader supplied. A string has no type. This also keeps `parser-the-parse-is-a-pure-function-of-the-source` true: the same (source, options) always parse the same way.
- **Entities are a resolver, not a rewrite.** XML knows five, XHTML's DTD declares 248 more. `XhtmlEntityResolver` answers every external DTD from one embedded list (`xhtml-entities.dtd`, generated from the HTML 4 table) and everything else with an empty stream, so no DOCTYPE can reach the file system or the network. Two traps found by running it: the reader asks the resolver for the *public identifier* (`-//W3C//DTD XHTML 1.0 Strict//EN`) before the system identifier, so a name that is not a path has to be recognized as a DTD; and a DOCTYPE with no external subset (`<!DOCTYPE html>`) never asks at all, so `WithExternalSubset` adds one (a plain `SYSTEM` literal, or a system literal after a lone `PUBLIC` identifier) before the text reaches the reader. A document with no DOCTYPE gets no entities, as in a browser. `MaxCharactersFromEntities` caps expansion.
- **`CssBox.CreateBox(HtmlTag, ...)` picks the box class from the tag name alone**, so `<img>`, `<input>` or `<svg>` in some other namespace would have become a `CssBoxImage`, a form field or an inline SVG. `XhtmlParser` calls the factory only for the XHTML namespace and for `svg`/`math` in their own namespaces; anything else is a plain `new CssBox`.
- **HTML element names are lowercased**: the engine compares `html`, `body` and the rest ordinally in places (`CssLayoutEngine`, `DomUtils`), so a `<DIV>` is a `div` (a deviation from a browser, which makes it an unknown element; documented). Well-formedness itself is case-sensitive: `<p></P>` is an error.
- **The WPT runner had hidden real gaps.** It parsed `.xht` as HTML after stripping CDATA markers, so `body &gt; span` in a `<style>` stayed literal, matched nothing in the test *and* its reference, and the pair passed by both being unstyled. With a real XML parser the selector works and 33 `css2-flow` pairs (block-in-inline with borders) fail on a real engine gap, while 14 `css2-positioning` and a few others now pass; no module is below its floor. The runner also gives an XML document a self-closing `<base/>`.
- **Not done:** see the XHTML section of `docs/html-css-support.md` (fragments, `<?xml-stylesheet?>`, MHTML body parts, the `HtmlView` hosts, case of XHTML-namespace names).
- **Evidence:** engine `XhtmlParserTests` (entities, expansion bomb, external references, namespaces, errors with position, parity of layout with the same page as HTML), `DocumentSyntaxTests` (loader hints, malformed `.xhtml` throws, overrides), CLI tests, WPT runner tests; WPT before/after diff per test.
