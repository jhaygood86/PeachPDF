# Full `@property` support + a `<style>`-rawtext concatenation bug fix

_Landed 2026-07-22._

**Full `@property` support + a `<style>`-rawtext concatenation bug fix** ([CSS Properties & Values API Level 1](https://www.w3.org/TR/css-properties-values-api-1/)). The `@property` at-rule now parses (Layer A: `RuleNames.Property`/`RuleType.Property`, a `PropertyRule : DeclarationRule` mirroring `FontFaceRule` with a keyframes-style prelude `Name`, descriptors `syntax`/`initial-value`/`inherits` via a new `PropertyFactory.CreatePropertyDescriptor` — stored raw as `UnknownProperty`/`Converters.Any` since their values have no fixed grammar; `StylesheetComposer.CreateProperty` routed from `CreateAtRule`). A document-global registry (`HtmlContainerInt.RegisteredProperties`, case-sensitive) is built in `DomParser.GenerateCssTree` from all `PropertyRule`s (last-wins; invalid rules dropped) via `RegisteredProperty.FromRule` before the cascade runs. The registry threads into the cascade three ways: (1) **`initial-value`** — `CssVarResolver` gained an optional `VarContext(registry, valueParser)`; when a `var()` names an unset-but-registered property, `TryResolveCustomProperty` falls back to its `initial-value` (charts.css's palette `--color-1..10` are defined only this way). (2) **`inherits`** — `CssBoxProperties.InheritStyle` now drops `inherits:false` registered names from the inherited custom-property copy (child resolves them to their initial-value instead), and `DomParser.AssignCustomPropertyDeclaration` honors `inherits` for the `unset` keyword. (3) **`syntax`** — a set value not matching the registered syntax is invalid at computed-value time and also falls back to the initial-value; `RegisteredProperty.Accepts` validates every standard syntax data type — `<length>`/`<number>`/`<integer>`/`<percentage>`/`<length-percentage>`/`<color>`/`<angle>`/`<ratio>`/`<image>`/`<url>`/`<time>`/`<resolution>`/`<transform-function>`/`<transform-list>`/`<custom-ident>`/`<string>`, ident literals, `*`, `|` alternation, and `+`/`#` list multipliers — by reusing the Layer A grammar (`ToLength`/`ToColor`/`ToUri`/`ToTime`/`ToResolution` token extensions, `CssValueParser.ParseImage`, and `Converters.TransformConverter`) rather than a second parser (issue #212). An `initial-value` is additionally held to the §3 computational-independence rule (`forInitialValue` threaded through the matcher into `CalcIsComputationallyIndependent`, which walks the `CalcParser` tree and rejects percentage/font-relative terms — absolute lengths, plain numbers, and angles only). **Root-cause bug found and fixed along the way:** MimeKit's `HtmlTokenizer` splits a `<style>` element's raw text into a *separate data token at every `<`* (so `syntax: "<color>"` — or any `content: "<"`) produced multiple child text boxes, and `DomParser.CascadeParseStyles` was parsing *each fragment as its own stylesheet*, splitting declarations mid-value so every rule after the `<` silently failed. Fixed by concatenating a `<style>`'s child texts before parsing (`string.Concat(box.Boxes.Select(c => c.Text))`) — a general correctness fix, not just for `@property`. See `AtPropertyTests` (Layer A parse), `RegisteredPropertyTests` (rule validity + syntax matcher), `AtPropertyCascadeIntegrationTests` (initial-value/inherits/syntax-fallback end-to-end), `StyleElementTextConcatenationTests` (the `<`-in-`<style>` regression). Issue #212 (unmodeled `syntax` data types degrading to accept, and calc computational-independence for `initial-value`) is now fixed — all standard data types are validated and an `initial-value` calc must be computationally independent (see `RegisteredPropertyTests`). **Issue #229 (the four residual narrowings) is now fixed too:** (1) calc() is category-checked against the declared type (`CalcMatchesCategory` reuses `CalcTypeChecker.Check`'s subset-test, the `CalcValueConverter` pattern), and a percentage is now treated as computationally independent (it computes to itself), so `calc(50%)` registers for `<length-percentage>`/`<percentage>` but is still rejected for `<length>`; (2) `<time>`/`<resolution>` accept `calc()` — the shared calc engine gained `TimeCalcNode`/`ResolutionCalcNode` + `CalcCategory.Time`/`Resolution` with cases in `CalcParser`/`CalcTypeChecker`/`CalcEvaluator`/`CalcSerializer` (no time/resolution `CalcValueConverter` is registered, so these nodes only arise from `@property` validation and never reach layout evaluation); (3) `<image>` accepts `image-set()`/`cross-fade()`/`element()` via a syntax-only `CssValueParser.IsExtendedImageFunction` (validated for registration; still not rendered — they paint nothing when consumed, an engine-wide image-function gap unchanged by this); (4) a `syntax` naming an unknown `<foo>` now invalidates the whole rule (`FromRule`'s `IsValidSyntaxString` checks each component against a `KnownDataTypes` allow-list), instead of degrading to accept. See the added `RegisteredPropertyTests` cases. (`@property` registration in *standalone* SVG `var()` resolution — the former issue #213 gap — is now fixed; see the SVG `@property` bullet above.)
