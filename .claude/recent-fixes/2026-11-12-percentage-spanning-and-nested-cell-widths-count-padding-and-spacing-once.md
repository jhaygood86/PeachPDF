# Percentage, spanning and nested declared cell widths count padding and spacing once

Follow-up to [the default cell padding](2026-11-12-table-cells-have-a-default-padding-and-a-nested-table-keeps-its-spacing.md). The default `padding: 1px` made three older mis-sizings visible; each had been matching Chrome only because the cells had no padding. They were reported on the review of that change (the review's fourth case, a float holding a table with a CSS width, did not reproduce; see below).

**What was wrong, and the one-line fix for each**

1. `CalculateColumnWidths` added `CellInlineSizeExcludes` (padding plus border) to every declared cell width. For a length that is right (content-box). A percentage is a share of the grid that already includes the cell's padding in Chrome: `width:50%; padding:20px` beside an unsized cell is 225/225 of 450, and 30% is 135/315. Fix: skip the addition for a percentage.
2. `SpreadSpannedWidth` compared a spanning cell's need to the sum of its columns only. The cell also fills the `border-spacing` between those columns, so it was widened by one spacing too many. Fix: `required - total - GetInteriorSpacing(col, colSpan)`. Old main matched Chrome here by accident: no padding, plus one spacing too many, equals the padding Chrome has.
3. `GetMinMaxSumWords` called `UpdateMinWidth` with a child's declared width for every child, so a `td width=80` in a nested table made the whole nested table at least 80px + padding + spacing wide, and the outer `td width=80` grew. A cell's declared width is its column's preferred width, not a floor (Chrome keeps the outer cell at its declared 80px plus padding). Fix: skip the floor for a table cell. A block child's definite width is still a floor.
4. A review of the first version found that rule 1 exposed a fourth defect: a percentage column narrower than its content (`width:10%; padding:40px` in a 400px table) was raised to its minimum by `EnforceMinimumSize` and nothing gave the difference back, so the table came out wider than its declared width. Chrome keeps the table at its width and takes the difference from the columns that did not declare a share; a column that asked for a share keeps it. Fix: `CalculateColumnWidths` records which columns declared a width (`_columnWidthDeclared`), `EnforceMinimumSize` notes whether it raised any column, and then `TakeExcessFromUndeclaredColumns` removes the excess from the undeclared columns in proportion to what each can spare above the width its content cannot shrink below (`GetColumnsMinMaxWidthByContent`'s minimums). The first version also called `ShrinkColumnsToFitAvailableWidth` for what was left; see the second review below for why that was wrong. Shrinking alone was tried first and split the columns wrongly (51 against Chrome's 60 for the third column of a 5% / unsized / 20% table), because it also shrank the declared 20% column. `<td style="width:5%">Quantity</td><td>b</td>` overflowed even before the default padding; it is now right too.

5. The second review (a maintainer's comparison against Chrome of random tables) found two regressions in the same code. **Columns below their content:** `<table style="width:300px">` with a `colspan=2` row and a second row whose first cell holds an unbreakable 400px box: the second column came out 10.9pt against Chrome's and main's 16.5, and a spanning row first with a 25% cell gave zero-wide columns that overprinted. `ShrinkColumnsToFitAvailableWidth` and the first `TakeExcessFromUndeclaredColumns` both measured a column's floor with `GetColumnMinWidths()`, which was 5.6pt lower than the content minimum `GetColumnsMinMaxWidthByContent` gives in that table (295.9 and 10.9 against 301.5 and 16.5; why the two differ was not chased), so the give-back squeezed columns under their content; main hid this because `EnforceMinimumSize`'s `Math.Max` against the content minimum ran last. Fix: the give-back takes the content minimums as a parameter and the round-robin shrink is gone from that path. **A nested table in any shrink-to-fit context** (float, inline-block, absolutely positioned): the nested `td width=80` came out 38.5pt where Chrome has 61.5. Skipping the floor in rule 3 was not the defect: the walk's max-content was right (67.5 for the outer cell, traced), and the float was sized correctly (80.2). The auto-width branch of `DetermineMissingColumnWidths` then spread the surplus in one pass, giving each column `(available - used) / (n - i)` and never offering what a capped column left behind to the others, so a 22.5-to-67.5 column beside a 6.7 one in 74pt of room got 45. Main hid it because the floor made the column's minimum 66. Fix: the surplus is shared equally among the columns that can still grow, again, until used or none can grow (at most one pass per column).

**Found by running it.** The review's figures were the symptoms; what moved each to Chrome's number to 0.01pt was reading Chrome's border-box shares and the nested outer cell (61.5pt, 82px) directly. A wide nested cell (a 120px box) still widens the outer cell (96pt in both), which is what a "never a floor" change would have broken.

**Not done.**
- The review's case 3 (a float holding a table with `width:350px` and `border-spacing:5px`, a `colspan=2 width=80` row, then a `width:90px` cell with five words) did not reproduce: the table is 262.5pt (350px) in Chrome and here, floated, in a floated div, in a cell, with `width` as an attribute or style. What does differ there is the column split of the second row (Chrome 69/182pt, here 174/77pt), which is the same on the build before the padding change, so it is not part of this.
- The nested table in the `width=80` cell is 59.5pt here against Chrome's 60 (the cell that holds it is exact); the half point is not understood and was not chased.

**Pre-existing, same on the build before the padding change, not fixed here** (each measured against Chrome): a colspan cell's declared width ignores the interior `border-spacing` in `CalculateColumnWidths` (`border-spacing:10px`, `colspan=3 width:300px`: Chrome 302/94 per column, here 320/100); a percentage on a colspan cell beside other percentages; a nested table in a narrow container (Chrome 109.1, here 75.7); how declared widths 300/80 shrink in a 120px container; `visibility:collapse` `<col>` with a percentage and a span; a percentage colspan in `vertical-rl`; when every column declared a share and the table is too wide, `ShrinkColumnsToFitAvailableWidth` takes a point at a time round-robin where Chrome gives each column the excess in proportion (10%/30%/60% with long words in a 400px table: Chrome 130.9/91.1/178, here about 131/74.5/194.5; `60%` beside `80%` gives Chrome 240/160 and here 160/240), which on the build before simply overflowed; `table-layout:fixed` with `width:50%;padding:20px` (Chrome 240/160, here 200/200, because fixed layout does not add the padding).

**Evidence.** Each of the four rules fails a test when reverted (engine `TableCellWidthRulesTests`, PDF-level `TableDefaultPaddingPdfTests`); some cases in those theories (`padding:0`, `border-box`, the zero-spacing span, a content column wider than its 5%) pass either way and are there as guards that the browser's figure holds. The give-back in rule 4 runs for any raised column, not only a percentage one; the random sweeps cover that, and a vertical table with no definite height skips it exactly as `ShrinkColumnsToFitAvailableWidth` does (`HasNoDefiniteExtentToShrinkToward`; written from reading, with no test of its own). Random nested tables against Chrome (two seeds of 60): no case worse than the build before, six better. The flexbox showcase's label column now starts where Chrome puts it (480.76pt against 480.7; the build before had 503). Diff coverage of the change is 100%. The second review's repros are pinned by `AColumnRaisedToItsContentNeverTakesTheWidthOfAnotherBelowItsOwnContent`, `ColumnsOfATableNarrowerThanItsContentDoNotOverlapWhenARowSpansThem` and `ANestedTablesDeclaredCellWidthIsItsPreferredWidthWhereTheTableShrinksToFit` (float, inline-block, absolute), each failing before the fix; against headless Chrome 157 they now match to 0.1pt, and the round-1 probes (percentage plus padding, spanning cell, nested `width=80`) are unchanged or closer. Not fixed, same on main: a `colspan=3` row first with a 25% column (Chrome 9/301.5/9/301.5, here a 612pt spanning cell), and a 10% first column beside a spanning row (main 500pt, now matches Chrome).
