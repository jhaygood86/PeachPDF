# An inline SVG starts from the font size of its HTML parent, and `rem` is the HTML root's

The svg tree's font context was seeded with the UA constants, whatever the page around the `<svg>` said: text with no `font-size` was the 11 of `DefaultFontResolver.FontSize`, a geometry `em` with no declared size was 16px, and `rem` was the size of the `<svg>` root element. Chrome, with `body { font-size: 12px }`: text 12px, `font-size="2em"` 24px, `font-size="150%"` 18px, `<circle r="2em">` 24, and with `html { font-size: 20px }` a `2rem` is 40px (also under `svg { font-size: 10px }`, where the old basis gave 20).

**The fix is one seam, two values.** `ISvgSourceNode.InheritedFontSizePx` (the computed size of the svg box's parent, in px) seeds the root `FontContext` (`Size`, and `SizeDeclared = true` so a geometry `em` means it); `RootFontSizePx` (`CssBox.GetRemHeight()`, the HTML root) is what `rem` is everywhere: `_rootFontSize`, `LengthBasis.RootEmPx`, and `RemSize` in the animation's walks (a `font-size` chain, and an inherited length such as a group's `stroke-width: 2rem`). Both default to null, which is every standalone SVG and keeps its old numbers. The svg's *own* `font-size` (a rule, a presentation attribute) is read from the tree as before, against the new seed, so `svg { font-size: 2em }` is 2em of the page.

**Traps.**
- `_rootFontSize` has to be set **before** `ComputeFontContext(root)`, or `svg { font-size: 2rem }` resolves its own rem against the constant (a mutation test pins it).
- The animation reads the chain in static helpers (`FontSizeAt`, `FontSizeToPixels`, `AnimatedInitialValue`) with their own fallbacks at the top of the chain (16px, and the resting 11): each now asks the root node for the inherited size, or the animated value of an ancestor's `2em` is of 16px while the static one is of the page (the 32 against 24 of the issue). The rem of those walks is the HTML root's too (`2rem` then `2em` inside, animated to 100px, is 90 halfway in Chrome).
- A box tree with no container (a unit test of the builder) has no render context to measure a font with and `GetEmHeight()` throws: `CssBoxSvgSourceNode` answers null there.
- The `html` UA default in PeachPDF is `DefaultFontResolver.FontSize` (11pt, 14.67px), not Chrome's 16px, so an unstyled page's `2rem` is 29.33 against 32 in Chrome. That is the library's default, not part of this change.

**A negative length is zero where it is used (and the animation's sample clamp stays).** A `calc(5px - 1em)` is still function text when a keyframe is sampled exactly at its own offset, so the sample clamp (a plain negative number only) missed it, and a static `calc()` that came out negative was never clamped at all (`r: calc(5px - 30px)` drew a circle of radius 25, as the renderer takes `Math.Abs`). `BuildCircle`/`BuildRect`/`BuildEllipse`, the `stroke-width` of `ApplyCommon` and the font size of `ComputeFontContext` now take `Math.Max(0, ...)` once the length is a number, which covers the rule, the attribute and every keyframe path; the sample clamp below stays because the font-size walk and the `r` lookups of the animation read the sampled text.

**A negative `calc()` in a keyframe clamps to zero.** A folded `calc(-5px)` was kept as `-5px` while mixing (right: Chrome mixes first, clamps where used: -5px to 20px is 2.5 at 30%) but a sample of it at the first or last keyframe reached the circle as `-5px`, which draws radius 5. `SampleElement` now clamps the *sampled* value of `r`/`rx`/`ry`/`width`/`height`/`stroke-width`/`font-size` to `0px`, never the keyframe stops themselves (clamping a stop would make that 6, not 2.5). Chrome: 0 at the start for `r`, and 0 at the end for `width` and `stroke-width`; reverting the clamp fails 5 tests.

**The `initial` keyword is medium.** A keyframe `font-size: initial` (and a declared one) went through the same fallback as "nothing above gives a value", so it took the inherited size (12 to 60 is 36); Chrome takes the CSS medium, 16px (38). `InitialKeywordValue` is the keyword's, `AnimatedInitialValue` stays the inherited one.

**`rex`/`rch`/`rcap`/`ric`/`rlh` measure the HTML root's font.** With only `RootEmPx` moved to the HTML root, the unit was the HTML root's size times the ratio of the svg root's font, two bases mixed (`2rex` with html 20px: Chrome 17.9, main 16, that head 21). `ISvgSourceNode.GetRootFontRatio` asks the HTML root element's own font (`DerivedStyle`'s `IFontMetricSource` with `rootElement: true`), and `LengthBasis.GetRatio(rootElement)` uses it before the svg root's. A test with a monospace root (`2rch` of a 20px root, Arial parent: 24) pins it.

**A `.svg` given to the CLI.** The CLI parses it as inline SVG, so it takes the page default (text 14.67px, `em` 14.67px: Chrome opening the file gives 16px for both). Left, and said in the units row, the animation bullet's neighbour and the migration note, rather than keeping a second set of numbers for one path.

**Not changed.** An svg that is a direct child of a `display: contents` element still reads its grandparent's size, as the seed is `ParentBox` and that element has no box (#2165); `font-family` of an inline svg is still not inherited from the HTML parent (only the size is), and a keyword or `vw` size on an ancestor is still not resolved by the animation (#2131).

**Evidence.** Static and animated probes against Chrome (18 cases: body/html sizes, `em`/`%`/`rem` on the text, a group, the svg and geometry, nested rem then em, keyframes that omit `font-size`) match. A review ran 47 single-edit mutations: every one that changes a result is caught by a test (the first draft left the `rem` of an inherited length such as a group's `stroke-width: 2rem` under animation, the rem of `letter-spacing`/`word-spacing`, the clamp's property set, and the `initial` keyword uncovered, and each got its own test). The mutations that still survive are equivalent ones: the `?? default` fallbacks that only a standalone SVG reaches (it is never animated) and `RootOf(node)` against `node` (every node of an inline svg gives the same root size). The engine suite (17,439), `PeachPDF.Tests` (1,565 and 9 skipped) and `PeachBrackets.Tests` (507) pass. All 233 showcases rasterize pixel-identical to main at 60 dpi, apart from two that differ between two runs of main as well (a clock in the form and filter output), so no existing document changes: the showcases that put text in an inline svg declare their sizes.
