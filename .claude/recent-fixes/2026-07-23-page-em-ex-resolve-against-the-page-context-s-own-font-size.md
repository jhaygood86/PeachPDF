# `@page` `em`/`ex` resolve against the page context's own `font-size`

_Landed 2026-07-23._

**`@page` `em`/`ex` resolve against the page context's own `font-size`** (issue #162, [css-page-3 §7.1](https://www.w3.org/TR/css-page-3/#page-size-prop)): font-relative lengths in `@page` `size` and `@page` margins resolved against the *root element's* font, so a `@page { font-size: 30pt }` had no effect on `size: 10em` / `margin-top: 2em` (which should be 300pt / 60pt). Root cause: the shared `PageLengthContext` (`EmPt`/`RemPt`/`HundredPercentPt`) captured `EmPt = root.GetEmHeight()` once in `DomParser.CascadeApplyPageStyles` and never re-derived it from a `@page` rule's own `font-size`. Fix, reusing `MarginBoxRenderer.ResolveFontSizePt` (which already resolves a page/margin context's own font-size and already builds a per-box `PageLengthContext`): (1) a new `ResolveFontSizePt(string)` overload (the `StyleDeclaration` overload delegates to it); (2) `CascadeApplyPageStyles` derives the stored context's `EmPt` from the last non-empty base (`Selector == null`) `@page` rule's `font-size` when set, else the root font — fixing base margins (via `ParseMarginLength`) and `size` (via `ParseSizeDimensionToPdfPoints`), which both draw `EmPt` from that one context; (3) `PageRuleResolver.ResolvePageMargins` re-bases `EmPt` (via a `with` on the record struct) on the *winning per-page rule's* own `font-size` when set, else keeps the captured context (whose `EmPt` already carries the base `@page` font, so a per-page rule inherits it). `rem` stays root-based; `ex` follows `em` automatically (`ex = EmPt/2` in `Length.ToPixels`). **Scoped to change behavior only when a `@page` sets `font-size`** — the documented root-based convention is preserved otherwise. **Accepted edges:** (a) `ResolvePageMargins` uses `SelectPageRule`'s single winner, so a `font-size` on a *different* matching `@page` selector than the one winning a given margin isn't merged into that margin's `em` basis — inherent to the pre-existing single-winner margin model; (b) a *relative*/keyword `@page` `font-size` (e.g. `@page { font-size: 2em }` or `large`) resolves against the CSS initial (`ResolveFontSizePt(string)` → `FontSizeResolver` with the initial as both parent and rem), not against the root element's font the page box inherits per §7.1 — the issue's target (an absolute `@page { font-size }` like `30pt`) is exact, and this only bites when the page font-size is itself relative *and* the root font differs from the initial. See `PageSizeUnitIntegrationTests` (size against page font / rem stays root), `PageMarginUnitConsistencyIntegrationTests` (base + per-page margins, per-page inherits base font, no-font-size regression).
