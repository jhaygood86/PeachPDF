# `clear` sees floats before its ancestors, `<br clear>`, floats after a block in an inline, and a float drops to the first bottom that makes room

Four of the defects left open by [the `clear` rework](2026-11-06-clear-considers-every-float-in-its-context.md), plus the float drop gap.

- **`clear` and floats before an ancestor** (#2239). `ClearBox` scanned only the earlier children of the cleared box's parent. It now also climbs (`LowestFloatBottomBeforeContainingBlock`): the earlier siblings of each ancestor, through `LowestFloatBottomInChildren` so the multi-column mark (`CurrentColumnFirstChild`) and carried floats still apply, stopping at a root of its own formatting context (`ContainsItsFloats`, `ColumnsBesideFloats`) and at a multi-column container. The relative offsets of the boxes passed on the way are taken off every float found, as `GetLowestEarlierFloatTop` does for tops. *Found by running it:* `Acid2FeatureVerificationTests.ParentFirstChildTopCollapse_ChildClearance_BlocksEscape` had encoded the bug (child 30pt below the parent): the float is before the parent, so the child is cleared to the float's bottom (60pt) and the parent stays at the top (CSS 2.1 section 9.5.2). The test now asserts that.
- **`<br clear>`** (#2243). The attribute is mapped onto the `clear` property in `DomParser.TranslateAttributes` (`left`, `right`, `all`/`both`; anything else nothing; an author `clear` wins). A break closes its line and the engine places its word on the *next* line (`DropATrailingForcedBreaksOwnLine`), so the clearance is applied right after `OpenNextLine` for a break word (`ClearAfterBreak`): the line just opened goes down to the floats before the break and `MaxBottom` with it. That also puts a block after a trailing break at the float's bottom, as Chrome does. *Trap:* the break's words are in an anonymous child box of the `br` box when text precedes it (`x<br>y`), so the hook looks at `b.ParentBox` as well as `b`.
- **Float after a block in an inline** (#2244). `CorrectBlockSplitBadBox` put the right-hand piece before `Boxes[1]` even after the recursion had already hoisted the block (and so moved it out of `splitBox`), which put the float's piece in front of the block. The move now happens only while `splitBox` is still in the parent.
- **`fieldset` and `button`** (#2242, partly). `EstablishesIndependentFormattingContext` lists them. `contain: layout|paint` and `content-visibility` are not done: the engine does not parse or store `contain` at all, so that is a feature, not a predicate.
- **A float drops to the first bottom that makes room** (#2222). The drop used `MaxBottom` (the lowest blocker met). It now uses `CssFloatCoordinates.DropEdge`, the smallest blocker bottom above the float's outer top (falling back to `MaxBottom`), re-scanning from there, which is CSS 2.1 section 9.5.1 rules 7 and 8. *Trap:* `FloatBoxRight` did not reset `Left` after a drop (harmless while a drop passed every blocker); with the first-bottom drop a left float that had ended still held the float in, so it is reset to `startX` as `FloatBoxLeft` does.

Not done: margin collapsing still ignores clearance in the adjoining set ([gap](../accepted-gaps/margin-collapsing-ignores-clearance.md)); it needs clearance, which is known only once a box is positioned, before the fold that runs ahead of it. `legend` is not `display: block` in the user-agent sheet, which the fieldset sample in the issue also needs.
