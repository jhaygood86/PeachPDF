# Layout fragments during layout, not after it

_Landed 2026-07-25._

**Layout fragments during layout, not after it** ([issue #321](https://github.com/jhaygood86/PeachPDF/issues/321), [CSS Fragmentation 3 §2/§4.4](https://www.w3.org/TR/css-break-3/)). #298 made the fragment tree layout's output but left *when* fragmentation happens unchanged: the document was laid out as one continuous flow and `FragmentTreeBuilder` sliced it afterwards. Now `HtmlContainerInt.LayoutDocument` is a driver that fills one fragmentainer at a time and resumes from a recorded break token. New namespace `Html/Core/Fragmentation/` — deliberately **not** under `Fragments/`, which is the immutable output; this is layout's control state. Landed as four commits:
1. **`BreakToken` + `FragmentainerContext` + phase split** (behaviour-neutral, pixel-identical). `BlockBreakToken.IsBreakBefore` is the load-bearing discriminator — §4.4's "no fragment in the earlier fragmentainer" is *structural* when a box was never entered. `FragmentainerContext` is a **cursor over the existing page grid**, not a second notion of where a page starts, so `PageTopOf`/`PageBottomOf`/`PageBandHeightOf` stay the only source of truth. `CssBox.PerformLayoutImp` split into `PerformLayoutPrologue` / `LayoutContents` / `PerformLayoutEpilogue` along the seam a resumed pass needs; the split was chosen so **no re-indentation** was required. Two phase-B locals became fields (`_isForcedBreak`, `_shouldRegisterPage`) — and `_shouldRegisterPage` in particular must be *carried*, never re-derived, since the early registration mutates `ActivePageName` (the existing comment at `CssBox.cs` says so).
2. **Driver + block resumption.** The decision converted is §5.2 margin truncation, already a break-before in all but name. Its computed target travels as `ResumeTopOverride` and is **consumed on arrival**, short-circuiting the branch — re-deriving it would reach the same "does not fit" conclusion and break forever. The keep-with-next pull runs in the pass that takes the break, which is why its adjusted target has to travel too.
3. **The `+1` removal** (spec fix, migration note). `CssRect.BreakPage` relocated to `NextPageTopOf(Top) + 1`; §2 puts a fragment at the content edge. Six showcases moved, all explained: four pure `(0, -1)` shifts, one fitting an extra line per page, and `paged_media_horizontal_reflow` landing on a *different fixpoint* of the bounded per-page-width reflow loop (7→8 pages, slightly **more** text, regular ten-paragraphs-per-page distribution replacing a split paragraph).
4. **Resumable inline flow + line atomicity.** Resumption uses an **ordinal into `FlowBox`'s walk**, not a path: the walk order is fixed, so an ordinal names a position without threading a path through the recursion. The break falls at the *line start*, so a mixed-height line moves whole (§4.1) instead of stranding its shorter words.

**Four traps, each of which was a real defect while it was missing** — re-read these before touching this area:
- **`IsFragmenting` (may a break token be recorded?) and `SuppressWordPageBreaks` (the legacy per-word relocation) are different questions.** Conflating them regressed the `multicol` showcase in both renderers: a multi-column container is monolithic to the driver *while its content still paginates word by word*.
- **The resume slot must come from where the break fell**, never from "the pass after this one". A box placed far down the document — past a tall spacer, or by an engine positioning its own children — overflows a fragmentainer that is not the next one. Getting this wrong sent a paragraph's text back to page 1 and dropped it from its own page (caught by three `FragmentTreeBuilderTests`).
- **A resumed pass must not `RectanglesReset`** (it blanks an inline's background/borders on every page but the last) and must **finalize only the lines it produced** (re-aligning earlier lines against a later pass's `MaxRight`).
- **A resumed flow's seed line is abandoned when its first word wraps** (a `<br>`, or content that no longer fits). Left behind it puts an empty line box mid-block — which orphans/widows counts and `::first-line` indexes — and honouring its wrap consumes a blank line's height at the page top. Both symptoms showed up in `OrphansWidowsIntegrationTests`.

**Deliberately outside the model** (and not gaps to relitigate): flex/grid/table/multicol are **monolithic** (`LayoutMonolithicContent`) since each paginates its own content; and the **retroactive movers** — keep-with-next pull, `break-inside: avoid`, `orphans`/`widows`, the first-line retry — relocate *already-placed* content, which a forward-only record cannot express, so they stay bounded corrections within one pass (§4.3 sanctions this). Note the keep-with-next pull's own `runStartsOnSamePage` guard is what keeps it inside the current pass. Tests: `FragmentainerContextTests`, `BreakTokenTests`, `ResumableBlockLayoutIntegrationTests`, `ResumableInlineLayoutIntegrationTests` (+ `HtmlContainerInt.FragmentainerPasses`, which is what makes "it actually resumed" assertable rather than assumed). **Since fixed:** layout now emits its own `BoxFragment`s ([#331](https://github.com/jhaygood86/PeachPDF/issues/331) — `FragmentTreeBuilder` is deleted; see the Recent-fixes entry, including the four defects the showcase diff found and the unit suite did not). The retroactive movers are tracked as [#332](https://github.com/jhaygood86/PeachPDF/issues/332), and `OffsetFlowedWords`' surviving per-word relocation as [#333](https://github.com/jhaygood86/PeachPDF/issues/333) — closing that one is what would let `CssRect.BreakPage` be deleted. Docs: `docs/architecture.md` §5/§6, `docs/html-css-support.md` Page Breaks (two migration notes).
