# A run travels at a column boundary, and a page break does not stop at one

_Landed 2026-07-27._

**A run travels at a column boundary, and a page break does not stop at one** (issues [#383](https://github.com/jhaygood86/PeachPDF/issues/383) and [#382](https://github.com/jhaygood86/PeachPDF/issues/382), [CSS Fragmentation 3 §3.1](https://www.w3.org/TR/css-break-3/#break-between)). The two column-context residuals #380 left, and both are about a break a multi-column container may not answer the way it answers its own.

**#383's load-bearing idea is that the run does not need somewhere to be moved to — it needs the break stated before its head.** Every page-context site answers keep-with-next by *moving* the run's members to a lower coordinate, which is why `GetPrecedingKeepWithNextRun` was the page question asked unconditionally: a column has no such coordinate, since every column of a container begins at the same block-axis one. The answer is the shape `avoid-column` already took in the child loop beside it — raise the break before the run's head and let the next column's fill lay the whole run out there. Nothing is translated and no group offset is computed, exactly as in `TryRestartAt`.

**Which column a run member is in is an *index* question here, not a geometric one.** Two columns share one block-axis band, so a member of an earlier column has a document Y indistinguishable from this one's: the "does the run start in the fragmentainer being left" guard the page sites answer with coordinates (`EarlyBreak.Discover`'s `ownPageTop`) says nothing at all, and the index this column's fill began at is the only thing that does. §4.3's ladder is otherwise unchanged — a run that will not fit the destination column alongside the box it is chained to is trimmed from its front.

**The pull is only made where the box's height is known, which excludes the `avoid-column` arm entirely** — and that was found by review, after the first version pulled there too. A box raising that arm has a *pending record*, which is precisely the statement that its epilogue has not run, so `ActualBottom` is still its own top and the fit test silently reduces to "does the run alone fit the band", i.e. always. Measured: a heading moved into a column of its own while the content it was chained to broke again in the next one — worse than leaving it, and a wasted column besides. §4.3 gives a constraint up rather than acting on one it cannot show satisfiable, so the content moves alone. **The showcase had to be rebuilt on the overflow arm because of this, and the rebuild is itself a finding:** `column-fill: balance` derives its column height from the content, and the two conditions the pull needs (`filler + heading ≤ target` and `heading + panel ≤ target`, against `filler + heading + panel > target`) are then unsatisfiable for any content — the algebra reduces to `heading ≤ 0`. Only a page-bounded column has a height of its own to fit a run into.

`DomUtils.GetPrecedingKeepWithNextRun` now takes its `FragmentationContext`, at all six call sites: `avoid-column` forbids nothing at a page boundary, `avoid-page` nothing at a column one, and a forced break of the *other* context does not break the chain either.

**#382: the record has to say what placement cannot.** A forced page break is realized by placing the box at the next page's content top, and from inside a column that lands it past the column band — which the container's own overflow arm reads as "open the next column", one column over instead of one page over. So `BlockBreakToken` gains `EscapesNestedFragmentainer`: `CssLayoutEngineColumns.FillColumns` ends its loop on such a record instead of opening another column, and `RetargetToTheNextPage` leaves the target and slot exactly as they are — they already name the page grid, and a directional break's target may be several slots on, which "the slot after this one" would quietly discard.

**The mark travels only while a nested fragmentainer is being filled, and that boundary is load-bearing.** Above the last of them nothing reads it, and intercepting there would skip two arms a page-context loop *does* have answers for — in particular §3.1 propagation, which for an escaping record from a multicol container can genuinely fire (`PropagatesBreakBeforeOutward` is structural, so a container's first in-flow child satisfies it whatever its break value) and would move the container rather than leave it with an empty column.

**The parity step is no longer suppressed inside a column**, because the break now reaches the page it names: the coordinates it steps through were always the page grid's, and it was excluded only because reserving a blank page while the box merely moved to the next column honoured half of a decision.

**What the escaping arm settles has to travel with the request, and both halves of that were live defects the review caught.** The forced-break arm runs on the pass that *declines* to place the box; the pass that places it takes the resumed-target branch, which is not the branch that asserts anything — and in between, the columns engine re-opens the box's prologue (`ResetChildrenForRefill`), which retracts both. So `PlacedByForcedBreak` was lost, and with it §5.2's governance: an empty `<div style="break-before:page">` marker read as an ordinary collapse-through box and the sibling after it anchored to the box *before* the marker, **landing on the page the break was leaving** — a regression against the pre-fix behaviour, which at least kept it after the break. And the blank slot a directional break reserved was lost, so `break-before: right` landed on the **second printed page**, a left-hand one: the slot index satisfied the parity test while the page a reader counts did not. `_escapedForcedBreakPending`/`_escapedForcedBreakBlankSlot` carry both across, cleared per layout like the other one-shot latches and deliberately **not** by the prologue. The lesson generalizes: the prologue's retractions exist so a *re-decided* break can re-assert them, and a decision already taken and travelling in a record is not that.

**`column-fill: balance` needed the escape to be treated as an end of flow**, which the showcase found and the suite did not. A forced break ends this fragment's flow as surely as running out of content does, but the target it was filled at was estimated over content reaching past the break — so the columns before it piled into the first one and the rest were left empty. The two steps are a continuation's own: fill the budget to learn the height of what precedes the break, then take an even share of it.

Tests: `MulticolLayoutIntegrationTests` (+15 — the run travelling for all three chain spellings, the no-chain and `avoid-page` controls, front-trimming, the head of the column's own fill, the `avoid-column` arm moving alone, §5.2's governance surviving the escape, the escape at depth and through a *nested* container, the directional parity **and the blank page it reserves being materialized**, the balanced columns before the break, and every word claimed exactly once), and two re-pinned: the forced-page-break characterization, and a named-page transition, which forces a page break and so escapes too. Full net8.0 suite green (6421), CLI green (96); **97% diff coverage**. **63 of 65 showcases are byte-identical** (acid2's sole difference is the `file://` URI naming each run's own working directory; it is pixel-identical). `multicol` gained sections 10 and 11, and **on the unfixed build section 10's two panels are indistinguishable** — the UA sheet's own `h1-h6 { page-break-after: avoid }` is what makes "auto" rather than the absence of a declaration the control there. Verified in both PDFium and MuPDF.

**One guard is deliberately kept without a fixture that reaches it.** `headIndex <= start` is soundness — a head below this column's start would state a record whose resume index is behind the column's own start, and the next column would lay that content out twice — but the fit test reaches the same conclusions first, because it is *exact* for a whole box: a head it accepts really does fit the destination, so the destination does not overflow and is not asked again. Verified by neutralizing it (nothing fails). Kept because that argument depends on the fit test staying exact, which is not a property to build on.

**Accepted gap:** a forced break declared *below* the container's own child is lost entirely — no page break and no column break — because `_forcedBreakTop` is a one-shot and the measurement pass that sizes the fill spends it, since only the container's own children have their prologue re-opened (`ResetChildrenForRefill`). Pre-existing, and the reason the direct-child case had an observable behaviour to fix at all. Filed as [#395](https://github.com/jhaygood86/PeachPDF/issues/395) and characterized rather than left silent.
