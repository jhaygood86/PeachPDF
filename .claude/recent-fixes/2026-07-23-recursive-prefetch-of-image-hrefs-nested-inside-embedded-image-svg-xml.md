# Recursive prefetch of `<image>` hrefs nested inside embedded `image/svg+xml` payloads

_Landed 2026-07-23._

**Recursive prefetch of `<image>` hrefs nested inside embedded `image/svg+xml` payloads** (issue #251, the last accepted gap from the #190 SVG-`<image>`-network work): a network/file `<image>` href living *inside* an `image/svg+xml` payload — itself referenced by an outer `<image>` (a `data:image/svg+xml` URI or a fetched `.svg`) — rendered nothing, because the #190 async prefetch (`SvgTreeBuilder.PrefetchImageResourcesAsync`) walked only the **outer** source tree; the nested SVG was parsed lazily and synchronously in `BuildImage`/`BuildNestedSvgDocument` *after* the prefetch finished, so its own `<image>` hrefs were never fetched. Per [SVG 1.1 §5.6](https://www.w3.org/TR/SVG11/struct.html#ImageElement) an `<image>` may reference another SVG whose own `<image>`s are valid at any depth. Fix (all in `SvgTreeBuilder.cs`): the prefetch became recursive via a **per-document child map** — `SvgImageResource` gained `IReadOnlyDictionary<string, SvgImageResource>? NestedImages`, and the per-href worker (`PrefetchImageAsync`), on fetching (or `data:`-decoding) an `image/svg+xml` payload, parses it and recursively prefetches *its* `<image>` hrefs into a separate child map keyed by that nested document's own raw hrefs. Because each nested document carries its own map, the existing flat href-keying never collides across differing bases (no base-URI field needed on the record). A fetched SVG's nested hrefs resolve against **its own fetched URL** (`PrefetchNestedSvgAsync(bytes, container, uri, depth)`); a `data:` SVG's nested hrefs resolve against the *current* base (`data:` has no location). Threaded down the synchronous build: `BuildNestedSvgDocument(bytes, nestedImages)` now passes the child map into the nested `Build(...)` (it previously dropped it — the latent second half of the bug), and `BuildImage` supplies it from `resource.NestedImages` (prefetched path) or `NestedImagesFor(href)` (`data:` path). A cheap `text.IndexOf("<image", …)` gate skips parsing image-less payloads; recursion is depth-guarded (`MaxImageNestingDepth = 8`, mirroring `MaxUseDepth`); malformed nested XML (via the shared `TryParseSvgRoot`, factored out of `BuildNestedSvgDocument`) and transport failures still fail softly (the `<image>` renders nothing, the rest of the page paints). No caller change (they already await the prefetch and pass the map into `Build`). See `SvgTreeBuilderTests` (recursive-map harness: leaf resolves via `NestedImages`, stays unresolved without it) and `SvgIntegrationTests` (fetched-outer + `data:`-outer doubly-nested network raster embeds its XObject, inner relative href resolves against the nested SVG's own location, malformed nested payload renders the rest of the page).
