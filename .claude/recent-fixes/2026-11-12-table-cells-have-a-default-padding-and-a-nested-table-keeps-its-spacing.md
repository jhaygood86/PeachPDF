# Table cells have the default 1px padding, and a table in a cell keeps its border-spacing (#2373)

**What changed.** The UA sheet (`CssDefaults.cs`) now has `td, th { padding: 1px }` (HTML Standard 15.3.12; Chrome's computed padding on a bare cell is `1px`), where it had none, so an unstyled cell was 0.75pt tighter than Chrome's on every side. A `cellpadding` attribute and any author `padding` still replace it: the attribute is applied by `TranslateTableCellAttributes` after the UA sheet, as before. And `CssBox.MeasureContentWidth` now carries a table's `border-spacing` in the decoration its descendants carry, so a cell that holds a table is as wide as the table.

**The trap in the second part.** The spacing was already added to `paddingSum` for a `Table`, but every table row opens a line of its own (`StartsNewLine`) and restarts `paddingSum` from `inheritedDecoration`, which did not include it. The spacing was added and then thrown away before any cell was measured, so a nested table's cell came out two spacings (4px by default) short. The fix is to put the spacing in `descendantDecoration`, not only in the running total. Two companions: `GetTableSpacing` counted the columns by walking `tableBox.Boxes` inside its row-group case (the table's own children, where it meant the group's rows), so every table with a `tbody` (all of them, the parser adds one) counted zero columns and one spacing; and it ignored `thead`/`tfoot` and `inline-table`. A declared `width` on a table is the whole table with its spacing inside it, so the explicit-width path subtracts the spacing again.

**Found by running it.** The sample in the original report (a left float in a cell) matched Chrome to 0.01pt on current `main`; the 1.5px it described was this padding, on a table that had left `cellpadding` unset. A 40-case random nested-table sweep against Chrome (`SIMPLE`, no spans/widths/borders): 2 of 40 within 1pt on `main`, 10 of 40 here, no regression, total error 1567pt to 1345pt. The rest are the bug below, not this.

**Existing tests.** 22 engine tests failed on the new padding, all of them pinned numbers or a premise that held only with unpadded cells. Most fixtures switch the padding off (`td, th { padding: 0 }`) because the geometry they pin is the subject; `Cellpadding_OfAnOuterTable_DoesNotReachANestedTablesCells` now expects the default 1px (its comment said "a browser's is 1px"). `NestedTableUnderRepeatedTheadTests` asserts the gap under a repeated header is the same on every page, which cannot hold with padding (a cell's padding is at its start only, `box-decoration-break: slice`), so its fixture has no cell padding.

**Not done.** A nested table whose cells hold block-level content is measured as its widest cell, not their sum (outer cell 50pt, Chrome 99.98pt, for two 50pt blocks): same on `main`, filed as #2374. A `display: none` cell and a trailing `colspan` each add a column of spacing to the table's own layout (68pt against Chrome's 62pt), so `GetTableSpacing`'s plain `Boxes.Count` agrees with the layout rather than with Chrome; filed as #2375, and skipping the hidden cell in the estimate alone only put the cell narrower than its table (tried, reverted). `GetTableSpacing` reads the horizontal spacing and counts cells per row whatever the writing mode, so a vertical table with different horizontal and vertical spacing is estimated wrong, as it always was but now it matters; no test has unequal spacing there. A declarative `Cell()` does not get the default padding (the UA rule does not reach builder boxes; `ADeclarativeTableCellIsNotGivenTheDefaultPadding` pins it). Showcases: 250 of 252 byte-equal in content; `table_track_backgrounds` (flex items holding tables with spacing) moved from 21.6 and 23.2pt to 10.0pt off Chrome, `writing_mode`'s vertical tables are now 46.5pt wide like Chrome's.
