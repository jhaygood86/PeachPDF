# Nested `opacity` no longer double-blends — the general gap is fully closed for CSS and SVG

_Landed 2026-07-23._

**Nested `opacity` no longer double-blends — the general gap is fully closed for CSS and SVG** (issue #157, [CSS Color 4 §4](https://www.w3.org/TR/css-color-4/#transparency) / SVG rendering model: `opacity` establishes a group — descendants composite *within* the group at full alpha, then the group blends **once**). CSS (`CssBox.PaintWithOpacity`) and SVG containers (`SvgRenderer.RenderContainerOpacityGroup`) already isolated the subtree into an isolated PDF transparency-group Form XObject (`/Group << /S /Transparency /I true >>`) composited once via a `/ca`+`/CA` ExtGState (`XGraphicsPdfRenderer.DrawImageWithOpacity`). This change closes the two remaining SVG residuals, both rooted in `RenderContainerOpacityGroup` sizing its tile from `SvgGeometryBounds.GetBoundingBox` and **falling back to the old double-blend-prone per-shape alpha multiply when that returned null**: (1) groups whose only content is `<text>` (unbounded — needs font measurement), `<image>`, or a nested `<svg>` (its type wasn't in the bounds switch at all); (2) a `<use opacity>` referencing a container (`<g>`/`<symbol>`/nested `<svg>`), which — being neither `SvgGroupElement` nor `SvgNestedSvgElement` — never entered the group path (`NeedsContainerOpacityGroup` now also routes `<use>`-of-a-container). **Coordinate-space crux:** the tile paints children at raw local user-space coords and is placed in `g`'s current space, so the region must be in the element's **local space** — `g.GetClip()` (what CSS uses) is wrong here because `RenderInto` pushes the viewport clip *before* the viewBox transform, so it returns page-space coords; the document viewBox rect is wrong under any ancestor/own `transform` or nested viewport. Fix makes the previously-unbounded content **boundable in local space** via a renderer-local `GetOpacityGroupBounds` (kept OUT of `SvgGeometryBounds` so `objectBoundingBox` gradient/mask/clip resolution, which relies on those types reporting `null` there, is unperturbed): `<image>`/nested-`<svg>`/`<symbol>`-viewport/`<use>` bounds are exact from their own `x/y/width/height`; `<text>` reuses `RenderTextRun`'s exact cursor/anchor/`MeasureString`/`Ascent` math (`MeasureTextBounds`/`AccumulateTextRunBounds`, kept adjacent to `RenderTextRun` to prevent region↔paint drift; a per-glyph `rotate` bounded via `RotateRectBounds`). Both paths now flow through the one tile routine; the `CreateTile == null` no-page-context fallback stays. Verified in **both** PDFium and MuPDF (overlapping text, `<use>`-of-`<g>`, nested-`<svg>` — top shape wins the overlap, no double-darkening). See `SvgIntegrationTests` (`InlineSvg_GroupOpacity_OverlappingText_DoNotDoubleBlend`, `InlineSvg_UseOpacity_ContainerTarget_DoNotDoubleBlend`, text-only/image/symbol/nested-svg/anchored/rotated cases; the former `..._NoBoundableContent_FallsBackToPerShapeAlpha` test was inverted). No opacity double-blend residual remains.
