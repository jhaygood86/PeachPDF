# A percentage `line-height` is a share of the element's own font size

`DerivedStyle.ActualLineHeight` resolved a percentage (and the percentages inside a `calc()`) against `Owner.Size.Height`, the box's own height, which is 0 while its lines are being laid out: every line of `line-height: 150%` was 0 tall, consecutive blocks were drawn at the same y and had no height (issue #2253; a table cell holding one was 0px tall). The basis is now the box's own font size in layout units (`LineHeightPercentageBasis`: `GetEmHeight()` times `LayoutUnitsPerPoint`, the same figure the unit-less number and `em` use; CSS 2.1 section 10.8.1).

- **Found by running it, not by reading it:** the reviewer's pointer to `ActualLineHeight` was right, but only the one `ParseLength` argument was wrong. `Length.ToPixels` already takes percentages in layout units without the `PixelsPerPoint` catch-up, so the basis is `em * LayoutUnitsPerPoint` and nothing else needs scaling.
- **Left alone:** the percentage is still inherited as written and resolved against each descendant's own font size, exactly as `em` is (#2254): `line-height: 150%` on a 14px parent with a 21px `h2` inside gives the `h2` 31.5px lines where a browser inherits the computed 21px. Fixing it means resolving at the declaring element (as `ResolveLineHeightValueComputation` already does for `lh`) and is one change for `em` and `%` together, so it stays with #2254.
- **Evidence:** `LineHeightPercentageTests` (150%, 200%, 50%, `calc(100% + 5px)`, plus the unit-less and `em` spellings that already worked, and two font sizes) fails 5 of 7 with the old basis; the issue's sample in the CLI puts the lines 21px apart and the `20px`/`10px` blocks 22.5pt/11.25pt tall. Engine (18,796), `PeachPDF.Tests` (1,708 + 9 skipped) and `PeachBrackets.Tests` (995) pass.
