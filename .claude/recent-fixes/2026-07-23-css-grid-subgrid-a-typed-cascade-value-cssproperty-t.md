# CSS Grid `subgrid` + a typed cascade value `CssProperty<T>`

_Landed 2026-07-23._

**CSS Grid `subgrid` + a typed cascade value `CssProperty<T>`** (issue #262 — [CSS Grid Level 2 §9](https://www.w3.org/TR/css-grid-2/#subgrids)): a `subgrid` grid item adopts its parent grid's tracks along the subgridded axis, on either or both axes. Two pieces:
1. **Typed cascade channel (`CssProperty<T>`).** `grid-template-columns`/`-rows` changed from `string` box fields to `CssProperty<GridTemplate>` (`src/PeachPDF/CSS/CssProperty.cs`) — the first adopter of a typed box value that carries the **parsed** value through the cascade so the engine never re-parses. `CssProperty<T>` has three states: a CSS-wide keyword (`CssGlobalKeyword?` enum), *unresolved* (`var()` still present — no `T` until resolution), or a resolved `T`. Layer A's `GridTemplateValueConverter` now **keeps** the `GridTemplate` it already parses to validate and exposes it via a new generic `ITypedPropertyValue<T>` (`IPropertyValue.cs`, with a `TryGetValue<T>` extension); `DomParser.AssignCssBlock`/`ApplyResolvedPropertyValue` hand that typed value straight to the box (via `CssUtils.TrySetTypedPropertyValue` + a name-keyed typed-setter map) for any non-global, non-`var()` value, so the converter's parse is the *only* parse. The string setter path (`GridTemplateValueConverter.FromCssText`, a CSS-OM-layer factory the `CssUtils` string setter calls — it tokenizes via the CSS-OM `Lexer`, keeping all `CssProperty` construction in Layer A) remains for the seed/global-keyword/inherit/`var()`-resolved-string cases and builds the `Global`/`Unresolved`/resolved `CssProperty` accordingly. The engine (`CssLayoutEngineGrid`) reads `_gridBox.GridTemplateColumns.Value` directly, eliminating the former 3×-per-layout re-parse (`ResolveColumnTemplate`/`ExpandTemplate`/`BuildLineNames` now take a `GridTemplate?`). Grid getter/snapshot/revert stays string-based via `ToString()`.
2. **Subgrid track adoption (engine).** `GridTrackListGrammar` accepts `subgrid [ <line-name-list> ]?` (→ `GridTemplate.IsSubgrid`; a track size after `subgrid`, or `repeat()` in the line-name list, is rejected). The parent threads its spanned track geometry into a subgrid child through a transient `CssBox.SubgridContext` (`GridSubgridContext`: adopted column/row **sizes**, gaps, and a report/adopt row mode), set immediately before the child lays out and cleared after. The child builds its adopted tracks from those *sizes* positioned from its own client origin, so the existing `PlaceItemInCell` provisional-origin→`OffsetLeft`/`OffsetTop` translation lands them exactly on the parent lines (no new positioning code). **Row-axis feedback**: a row-subgrid child is first laid out in *report mode* (adopted columns, self-sized rows) so its per-subrow heights grow the parent's spanned **auto** rows one-for-one — this is what makes several subgrids' rows share a common, content-fitting size (the card-deck idiom). With no parent grid, `subgrid` falls back to `none`. Non-subgrid children keep the exact prior path (zero regression — full suite green, 5537 tests). Verified by `GridTrackListGrammarTests`/`TypedCssPropertyTests`, `GridLayoutIntegrationTests` (column/row adoption, auto-row band alignment, `var()`-resolved template, no-parent fallback), and a `css_grid_subgrid` showcase rasterized in **both** PDFium and MuPDF. **Accepted gaps** ([#276](https://github.com/jhaygood86/PeachPDF/issues/276)): subgrid margin/border/padding doesn't inset the adopted tracks (exact only for a zero-inset subgrid — the common case), parent line-name inheritance into the subgrid isn't threaded (the subgrid's own `[name]` lines *do* work), a subgrid's content doesn't feed the parent's auto *column* sizing (row axis only; matches #265's spanning-item gap), and the `grid`/`grid-template` mega-shorthands don't accept `subgrid`.
