# `<table align>` places the table; `cellpadding`/`border` are hints a cell's own CSS beats (#2184)

Found by rendering an HTML email (a centered 530px wrapper table, `cellpadding="0"`, cells with inline `padding`) and comparing with headless Chrome: the wrapper sat at the left edge, its text was centered, and every inline cell padding was gone. Two independent causes.

**`align` on a table.** `TranslateGenericAlign` turned it into `text-align` on the table, which the cells inherited. The HTML Standard maps `table[align]` to the table's own placement: `left`/`right` are floats, `center` is auto side margins, `text-align` is untouched. `<hr>` already had its own arm; `TranslateTableAlign` is the table's, sharing `SetHorizontalMargins` with it. The match is the exact value, ASCII case-insensitively, no trimming (`align=" center "` is nothing, as in Chrome). `align` on a `td`/`tr`/`div`/`p` stays `text-align`, which is right for them. A table with a valid `align` also resets its own `text-align` to `start`: found by review against Chrome, a `<td align=center>` or `<center>` around `<table align=left>` otherwise passed its centering into the table's cells (Chrome never does, and the old translation had reset it by accident). The reset is not exact, since a CSS `text-align: center` on the parent is inherited by a table in a browser (see [the accepted gap](../accepted-gaps/legacy-center-alignment-is-a-plain-text-align.md), #2186).

**`cellpadding`/`border` overwrote the cell.** `ApplyTablePresentationalAttributesToCells` ran after the whole cascade and assigned to every cell, so it beat inline style and stylesheets, `!important` included. They are presentational hints, and every other hint is applied in `CascadeApplyStyles` between the UA sheet and the author rules (so any author rule wins). The table-to-cell write now happens there too, from the cell's own cascade (`TranslateTableCellAttributes`, called right after `TranslateAttributes`), reading the nearest ancestor `table`. The pass, `ApplyTableBorder`, `ApplyTablePadding` and `SetForAllCells` are deleted.

**The trap from #636 still applies, and is why this is not done from the table's cascade.** Writing a cell's property from the *table's* cascade diverges the cell's `ComputedStyle` from the shared default before the cell's own cascade runs, and that cascade's defaulting step then resets the value. From the cell's own cascade the defaulting step has already run, so the write survives; the earlier fix moved the write after everything, which is what made it too strong.

**Not done.** A trailing `<br/>` (or a bottom margin) in a cell shifts the cell's content down because the middle alignment measures the content short (#2185; it is why the email's first paragraph is still lower than Chrome's). A browser's UA sheet gives `td`/`th` `padding: 1px`; ours gives them none, so an unstyled cell is 1px (0.75pt) tighter on every side than Chrome. That predates this change and touches every table render, so it is its own change.

**Also not done.** A block-level table after a float is laid over it where Chrome puts it beside (#2187, [accepted gap](../accepted-gaps/a-block-level-table-is-laid-over-a-preceding-float.md)); `<table align=left|right>` makes this easier to hit than before, because such a table was in flow and stacked.

**Evidence.** `TableLegacyAttributeTests` (24 cases, every literal measured in Chrome; 14 fail without the change): table placement for each `align` value and case, float values, cells keep `text-align: start`, author margin beats the hint, and cellpadding/border yielding to inline, stylesheet, `!important` and single-side declarations. The email that started it now matches Chrome's layout (centered wrapper, padded cells, centered button). Solution rebuilds with 0 warnings.

**Review round (maintainer, on the first push).** Two cases `main` placed right and the first version did not, both from `align` now reaching code that was never exercised by a table:

- **A right-floated table was anchored with no width to subtract.** `CssBox.ResolveOwnInlineSize` skips a `display: table` box (its engine sizes it), so `CssLayoutEngine.FloatBox` ran with `ActualBoxSizingWidth == 0` and put a `float: right` table's left edge at the container's right edge: off the page, its cells outside the PDF. It showed when a block followed the table; with the table alone in its container it came out at the right place in the engine tests (why was not traced; the maintainer measured it a few px past the edge in a full render). The table engine now places a floated table again once `GetWidthSum()` is known, before the cells are laid out (`CssLayoutEngineTable`, the branch ahead of the auto-margin one); `FloatBox` restarts from the containing block, so it finds the same blockers. A float with a width of its own was never affected, and the `display: table` path was the only one that skipped the size.
- **A table wider than its container, centred, got a negative start margin.** The table path of `GetActualMarginLeft`/`Right` (the one the table engine calls back into with its settled width) halved the free space without the clamp at 0 that the block path has (`ResolveAutoHorizontalMargin`), so `margin: auto` on a 1000px table in 800px started at -100px. CSS 2.1 §10.3.3: an over-constrained box's auto margins are 0 and it overflows at the end. This also changes the CSS spelling (`margin-left/right: auto`), which `main` had wrong.

Tests: `RightFloatedTable_*`, `LeftFloatedTable_*` and `CenteredTable_WiderThanItsContainer_*` in `TableLegacyAttributeTests` (the right-float and over-wide cases fail without the change; the left-float case is a guard). An `rtl` container with an over-wide centred table is not changed here: with both margins 0 the over-constraint rule (§10.3.3) ignores `margin-left`, which `AnchorsTableToInlineEnd` does not do when a margin is `auto`.
