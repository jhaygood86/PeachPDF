# A table that did not break is moved by the same mover as everything else that cannot be broken

_Landed 2026-07-27._

**A table that did not break is moved by the same mover as everything else that cannot be broken** ([issue #354](https://github.com/jhaygood86/PeachPDF/issues/354)'s second half, [CSS Fragmentation 3 §4.3](https://www.w3.org/TR/css-break-3/#possible-breaks)). #332 expressed the block-flow §4.3 corrections as stated `EarlyBreak` decisions carried out by laying the box out again; three sites in `CssLayoutEngineTable` were left translating.

**The load-bearing statement is that a table which recorded no break between two of its own rows did not fragment**, which is what §2's own set says about itself *in advance* rather than after the fact. So the post-check — the genuinely retroactive one of the three — is not moved to a better place inside the engine; it is **deleted**, and `CssBox.PerformLayoutEpilogue`'s existing §4.3 mover covers it (`PaginatedItsOwnContentWithoutBreaking`, sitting beside `IsMonolithicBoxThisMoverMayMove`). The engine states the fact (`PageBreakBottoms`) and the epilogue takes the decision.

**The epilogue is not merely a tidier place for it — it is the only place the decision can be more than a translation.** The engine runs with the fragmentainer detached (#400 (c)), so `TakeEarlyBreak` from inside it always falls through to `TranslateForEarlyBreak`. Asked one frame out, with the fragmentainer restored, the table is laid out **again** at its destination like every other relocated box. `OffsetTopWithKeepWithNextRun` — the last caller — is gone with it.

**That is also what lifts the repeating-header and repeating-footer exclusions, and both were real gaps.** The old post-check carried `!_shouldRepeatHeaders && !_shouldRepeatFooters`, because a translation leaves the header's already-created `CssProxyBox` at the coordinates of the page the table is leaving. A re-layout rebuilds them from scratch, so the exclusion has nothing left to protect — closing [#152](https://github.com/jhaygood86/PeachPDF/issues/152) and, since the mover asks only whether the table broke rather than which groups it has, [#151](https://github.com/jhaygood86/PeachPDF/issues/151) as well. Both verified load-bearing by putting the exclusion back: the two tests fail, the other five pass.

**One real defect fell out of placing a table exactly at a page top**, and it is worth not re-deriving. `GetVerticalSpacing()` is **-1** for a collapsed-border table, so `startY` — the row cursor the engine derives from `ClientTop` — sits one point *above* the box. Asking `PageIndexOf(startY)` then names the page the table just left, and the pre-check below it duly moved the table one further point onto the next page: measured as Y=843 against a page top of 842, once but only once the mover started landing tables flush. Which fragmentainer a table begins in is a question about its own top edge, so it is now `SlotStartingAt(_tableBox.ClientTop)`.

**The pre-checks keep translating, deliberately**, and #354's own sizing says why: they run *before* the rows are placed, so there is no laid-out box for a stated decision to re-place, and deciding early is the right shape. What they no longer keep is their own copy of the keep-with-next guards — `EarlyBreak.TravellingRun` is extracted from `Discover` and shared, so the pre-checks gain §4.3's front-trimming tier and cannot drift from it. They pass an *estimate* as the subject extent, which is the one thing only they know.

**All 66 showcases byte-identical**, which is the expected result — none has a table the estimate misjudges. Full net8.0 suite green (6471), 0 warnings; **98% diff coverage**. Tests: `WholeTableRelocationTests` (7 — the misjudged estimate, the flush-placement fix, a table taller than a band left alone, a table that *did* break left alone, the keep-with-next run travelling, and the two newly-covered header/footer shapes).
