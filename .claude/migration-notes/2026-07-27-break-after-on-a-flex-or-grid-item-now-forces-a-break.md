# `break-after` on a flex or grid item now forces a break

**Landed:** 2026-07-27 (a5990ea5) — Take a flex or grid break from either side of its break point (#449)
**Doc section:** docs/html-css-support.md § [Page Breaks](../../docs/html-css-support.md#page-breaks)
**Verified against v0.9.6:** the note as originally written implied `break-before` on a flex/grid item already forced a coherent break at `v0.9.6`, with only `break-after` missing. That is not what `v0.9.6` did. Checked directly (`git grep -n "Page\|Break" v0.9.6:src/PeachPDF/Html/Core/Dom/CssLayoutEngineFlex.cs` and the grid equivalent): neither engine contains any break-value handling. Empirically reproduced against a `v0.9.6` worktree: a flex container with `break-before: page` on one item and, separately, `break-after: page` on the item before it, both produce the *same* incoherent artifact — a spurious extra blank page and later items shoved down by an unrelated gap — with the targeted item's own line never actually relocated. The two properties are symmetric in `v0.9.6`, and neither works.

Neither `break-before` nor `break-after` on a flex or grid item had a coherent effect at `v0.9.6` — a flex/grid item is measured via a shared, common provisional layout pass (`PerformLayoutBlockified`) before being repositioned by a pure offset (`AssignLocations`'s `OffsetLeft`/`OffsetTop`), and that measurement pass incidentally runs the ordinary block-level forced-break check (`CssBox.PerformLayoutImp`'s `previousSiblingForBreak` handling) against whichever DOM sibling happens to precede the item — a side effect of sharing that code path, not an intentional line-aware break. The result was neither a moved line nor a no-op: it was a spurious extra page and a displaced gap among later items, regardless of which of the two properties was set. `break-after` now forces a break exactly as `break-before` does, taking it from either side of the break point, so a document that already declares either one gains a real, coherent page break — and possibly a page — it did not have before. See [Forward compatibility](#forward-compatibility).
