# `position: fixed` content positioned inside the page margins now paints

**Landed:** 2026-08-31 — Fix position:fixed content silently never painting whenever any @page rule exists (issue #880)
**Doc section:** docs/html-css-support.md § position/sticky and pagination (line ~1139)
**Verified against v0.9.15:** `git show v0.9.15:docs/html-css-support.md` has no mention of fixed-positioned content being dropped when it falls inside the page margins — this was an undocumented defect, not a documented boundary, so there is no prior wording to reconcile; the fix is purely a correctness change.

A `position: fixed` box positioned so that any part of it falls inside the page's own margins (a realistic placement — a corner badge, watermark, or running header genuinely meant to sit near the physical edge of the sheet) previously never painted into the PDF at all, on **every** page including the first, as soon as the document had any `@page` rule in effect (even a bare `@page { size: A4; }` with no margin or size override). Two independent, compounding bugs caused this: `PdfGenerator`'s per-page paint loop intersected the content-area clip directly on the raw graphics context, ahead of the higher-level clip-stack abstraction a fixed box's own paint relies on to reach back out to its true containing block (the page box, margins included, per CSS2.1 §10.1); and the fragment tree's own per-page membership test for fixed content used the page's content band rather than its full physical sheet, excluding such a box from the materialized page structure entirely, not merely clipping it at paint time. Both are fixed. A fixed box positioned entirely within the ordinary content area was never affected.
