# A forced break on a first or last child now moves the container with it

**Landed:** 2026-07-26 (4fd44118) — Emit fragments from layout rather than walking the finished box tree
**Doc section:** docs/html-css-support.md § [Page Breaks](../../docs/html-css-support.md#page-breaks)
**Verified against v0.9.6:** this note was not present in the `v0.9.6` tag's docs. The original text described an intermediate, development-only state — present only between commit `e5d3478` ("Take a forced break before a container's first child", 2026-07-26T01:02:59Z, which first made a first-child break move the *element*) and commit `ded092f` ("Propagate a forced break to the container the box begins", 2026-07-26T08:39:24Z, which fixed it to move the *container* too) — rather than v0.9.6's actual starting behavior. At `v0.9.6`, `DomUtils.GetPreviousSibling` (`src/PeachPDF/Html/Core/Utils/DomUtils.cs`) returns `null` for a first child (`index <= 0`) instead of climbing out to a container's own previous sibling, and both the forced-break block and the margin-truncation block in `CssBox.PerformLayoutImp` (`src/PeachPDF/Html/Core/Dom/CssBox.cs`) no-op whenever that lookup is `null` — so a forced break on a first/last in-flow child had **zero** layout effect at v0.9.6 (same underlying gap as the sibling note, [A break on a container's first in-flow child is now honored](2026-07-26-a-break-on-a-containers-first-in-flow-child-is-now-honored.md)), not a container that merely failed to follow an already-working element move. Corrected below.

A forced break declared on a container's first in-flow child, and a `break-after` on its last, had no layout effect at all at v0.9.6: `break-before`/`break-after` was resolved only against a real previous/next sibling box within the same parent, and a first (or last) child has none, so the break point above (or below) the container went unrecognized and nothing moved — see the sibling note linked above. The value now propagates outward through every box the element begins or ends, and the outermost such container takes the break and moves with it — its own background, border, padding and margin begin the new page along with the element, instead of the container being left spanning the boundary with an empty copy of its chrome on the page the content left. A heading chained to such content by `break-after: avoid` now travels with it as well, instead of being stranded on the page the content left. See [Forward compatibility](#forward-compatibility).
