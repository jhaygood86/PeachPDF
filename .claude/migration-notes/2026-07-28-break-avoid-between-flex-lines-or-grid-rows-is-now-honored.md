# `break-after`/`break-before: avoid` between flex lines or grid rows is now honored

**Landed:** 2026-07-28 (a6171b71) — Repeat a `<thead>`/`<tfoot>` only where css-tables-3 §6.2 says it may, and fit the one that does not (#519)
**Doc section:** docs/html-css-support.md § [Page Breaks](../../docs/html-css-support.md#page-breaks)
**Verified against v0.9.6:** the note as originally written implied `break-inside` already worked between flex lines/grid rows at `v0.9.6`, with only `break-after`/`break-before: avoid` missing. Empirically disproved against a `v0.9.6` worktree: a flex item with `break-inside: avoid`, positioned so it straddles a page boundary, is rendered *identically* to the same item without `avoid` — it is left straddling the boundary, not moved to the next page — while an otherwise-identical **ordinary block** sibling (not a flex item) with the same `break-inside: avoid` correctly relocates flush to the next page's top. This isolates the gap to the flex engine specifically: the generic `break-inside: avoid` mechanism (`CssBox.PerformLayoutImp`) works, but flex/grid items never reach it meaningfully, for the same reason `break-before`/`break-after` don't (see the [`break-after` migration note](2026-07-27-break-after-on-a-flex-or-grid-item-now-forces-a-break.md)): an item is measured once at a shared provisional position via `PerformLayoutBlockified`, then relocated to its real line/row position by a pure offset that carries along whatever the measurement pass decided at the wrong position, rather than re-deciding anything against the item's real destination. `git grep -n "Page\|Break" v0.9.6:src/PeachPDF/Html/Core/Dom/CssLayoutEngineFlex.cs` (and the grid engine equivalent) confirms no break-value handling exists in either engine.

`break-after: avoid`, `break-before: avoid`, and `break-inside: avoid` between two flex lines or grid rows all previously had no effect at all. They now move the earlier line to join the later one, which the UA default `h1-h6 { break-after: avoid }` makes the ordinary case for a heading that is a flex item: a page that used to be filled to its foot may now leave that heading's worth of space there, with the heading itself on the following page. Two smaller corrections land with it: a directional value (`left`/`right`/`recto`/`verso`) on such an item now selects the page's *side*, inserting a blank page where one is needed, where before it opened the next page whichever side that was; and a line whose top already sits on a page's content top is no longer moved a further page by a forced break, so content that used to be attributed to the page after the one it printed on now agrees with `@page :left`/`:right`. See [Forward compatibility](#forward-compatibility).
