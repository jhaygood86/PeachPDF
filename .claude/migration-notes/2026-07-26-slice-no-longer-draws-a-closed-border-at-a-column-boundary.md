# `slice` no longer draws a closed border at a column boundary

**Landed:** 2026-07-26 (4d3b6789) — Leave the break edge open on a box split at a column boundary
**Doc section:** docs/html-css-support.md § [Decorations at a break](../../docs/html-css-support.md#decorations-at-a-break)
**Verified against v0.9.6:** this note's "before" clause described a bug from an intermediate development state of this rewrite, not `v0.9.6`'s shipped behavior — corrected below. `git show v0.9.6:src/PeachPDF/Html/Core/Dom/CssLayoutEngineColumns.cs` states its own scope in the file's header comment: children of a multi-column container "are laid out once as a single tall flow... then whole top-level children are reassigned — atomically, never split — to (page, column) slots by height... This means a single child... never itself splits across a column or page boundary." `v0.9.6`'s multi-column engine could not split a single box across a column boundary at all, so a box split at a column boundary — closed border or otherwise — could not occur; box-splitting-across-columns is itself new work introduced later in this rewrite (landing after `v0.9.6`, before this commit).

What this note actually documents is a bug introduced and fixed within that new column-fragmentation work: a box split at a **column** boundary briefly drew a closed border on each fragment — a bottom border at the break in the leading column and a top border at the break in the trailing one. That is `clone`'s behavior; under `slice` (the initial value) those two edges are not there at all, so such a box now reads as one box cut by the column edge. A page break always rendered this correctly (the page clip removed the border), which is why the bug was column-specific. Add `box-decoration-break: clone` to keep the previous appearance. See [Forward compatibility](#forward-compatibility).
