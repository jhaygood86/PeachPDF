# A PDF page's `/Group` transparency dictionary is no longer unconditional

**Landed:** 2026-09-05 — required prerequisite for opt-in PDF/A conformance (`PdfAConformance`), which needs real per-page transparency tracking to support PDF/A-1's "reject if the document actually uses transparency" behavior.
**Verified against v0.9.15:** `git show v0.9.15:src/PeachPDF/PdfSharpCore/Pdf/PdfPage.cs` confirms `TransparencyUsed = true; // TODO: check XObjects` was unconditional at that tag — confirmed genuine behavior change since 0.9.15, in scope for the next release notes.

Previously, every generated PDF page carried a `/Group << /S /Transparency /CS /DeviceRGB >>` dictionary regardless of its content — the check the code's own comment said it needed ("TODO: check XObjects") was never implemented, so the flag was simply forced on unconditionally for every page. Now the flag is set only when a page actually contains a construct that needs a transparency group: CSS/SVG `opacity` below 1, `fill-opacity`/`stroke-opacity` below 1, a semi-transparent gradient color stop, an SVG `<mask>`, or a non-default PDF blend mode (COLRv1 color-font compositing, or CSS `outline-color: invert`). A page with none of these no longer carries a `/Group` entry at all. (An image's own alpha-channel `/SMask` does not set this flag — that construct is honored directly by the imaging model and doesn't require the containing page to carry its own `/Group`.)

This is a pure size/cleanliness change for ordinary (non-PDF/A) output — dropping an unused dictionary entry does not change how the page renders in any conformant reader, and no test observed to depend on the entry's unconditional presence needed updating. It is mentioned here because it's a genuine, observable difference in the raw PDF bytes a byte-for-byte comparison against prior output would catch.
