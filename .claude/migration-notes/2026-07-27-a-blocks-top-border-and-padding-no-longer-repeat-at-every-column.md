# A block's top border/padding no longer re-opens at every multi-column continuation

**Landed:** 2026-07-27 (23820fd4) — Re-open a continuation column's block-start decorations only under clone (#470)
**Doc section:** docs/html-css-support.md § [Decorations at a break](../../docs/html-css-support.md#decorations-at-a-break)
**Verified against v0.9.6:** this note's "before" clause described a bug from an intermediate development state of this rewrite, not `v0.9.6`'s shipped behavior — corrected below. As with the sibling note on [slice no longer draws a closed border at a column boundary](2026-07-26-slice-no-longer-draws-a-closed-border-at-a-column-boundary.md), `git show v0.9.6:src/PeachPDF/Html/Core/Dom/CssLayoutEngineColumns.cs`'s own header comment states that a single child "never itself splits across a column or page boundary" in `v0.9.6` — only whole children were reassigned between columns. A **block** whose content is split at a **column** boundary, with a reserved-but-unpainted strip at the head of a continuation column or otherwise, could not occur in `v0.9.6`: that scenario requires real block-content fragmentation across columns, which this rewrite introduced after `v0.9.6` (and which this commit, `23820fd4`/#470, is itself still refining).

What this note actually documents is a bug introduced and fixed within that new column-fragmentation work: a block whose content is split at a column boundary briefly had its own top border and padding re-inserted at the head of every continuation column, whatever its `box-decoration-break` value — a strip of blank space with no border drawn in it, since the painter correctly treated a sliced continuation as having no top edge there while layout still reserved room for one. Under `slice` (the initial value) nothing is inserted at the break, so such a continuation now begins flush with the column's content top and the content below it moves up by that much. `clone` is unaffected: there each fragment does re-open with its own border and padding, and the room is reserved for them. See [Forward compatibility](#forward-compatibility).
