# Per-page horizontal reflow is scoped to auto-width main-column blocks

**Per-page horizontal reflow (issue #143) is scoped to auto-width main-column blocks.** The width seam (`CssLayoutEngine.GetBoxWidth`/`LineContentRightOf` → `HtmlContainerInt.PageContentRightOf`, gated by `IsMainColumnContainer` = root/`<html>`/`<body>`) reflows only auto-width block content whose containing block is the main column. The per-line text-wrap measure additionally requires the block itself to be an ordinary in-flow box that spans its own containing block's full width (`CssLayoutEngine.FillsContainingBlockWidth`): a table cell (CSS2.1 §17.5's column-width algorithm) or a flex/grid item (its own engine's sizing) shares its containing block's width with siblings rather than claiming all of it, and a float or an absolutely/fixed-positioned box is sized against its own placement — each keeps its one already-correct, page-independent measure unchanged rather than being fed its containing block's edge as if it filled the whole of it. Each remaining case is a genuine CSS Paged Media 3 §5 ("the edges of the page area act as a containing block for the layout that occurs between page breaks") deviation, tracked as its own issue: flex ([#196](https://github.com/jhaygood86/PeachPDF/issues/196)), tables ([#197](https://github.com/jhaygood86/PeachPDF/issues/197)), multicol ([#198](https://github.com/jhaygood86/PeachPDF/issues/198)) — the horizontal analogue of the #166 engine-independence family; percentage/fixed-`width` blocks ([#199](https://github.com/jhaygood86/PeachPDF/issues/199)); content nested below the main column, incl. a descendant that begins on a different page than its multi-page auto-width ancestor ([#200](https://github.com/jhaygood86/PeachPDF/issues/200)); the initial containing block's own WIDTH resolving against the base page area rather than the first page's `:first`-overridden area — narrowed from the ICB generally: the height dimension now correctly reads the first page's own resolved band (`PageGeometryTable.GetPage(0).BandHeight`), so only the width side of #201 remains open ([#201](https://github.com/jhaygood86/PeachPDF/issues/201)); and named-page (`page: <name>`) L/R overrides, whose width→height→page-name feedback the bounded reflow loop doesn't drive to convergence ([#202](https://github.com/jhaygood86/PeachPDF/issues/202)) — this now also covers a named/pseudo page's own `size` override: the page gets a genuinely independent physical `/MediaBox` (`PdfGenerator.AddPdfPages` reads each page's own resolved `PageBandGeometry.SheetWidthPt`/`SheetHeightPt`) and vertical pagination adapts to its own band height, but content still wraps at the document's base measure rather than that page's own (possibly different) width, same #202 gap, same tracked issue.

**No longer a gap**: an auto-width main-column block spanning a page boundary now genuinely re-wraps its own text at each fragment's own measure (css-break-3 §5.1: "a fragment ... is sized ... using the size of its own fragmentainer"), one line at a time (`CssLayoutEngine.LineContentRightOf`, refreshed at every line start/wrap point) — it no longer shares one inline size across every fragment the way an ordinary (non-text) box still does. What remains open: the block's own outer border box (`CssBox.Size`/`ActualRight`, and therefore its painted background/border, and any non-text content sized against its own width) is not re-derived per fragment — it stays pinned to whichever page placed it, even though the text inside it now wraps at each page's own measure. Tracked as [#876](https://github.com/jhaygood86/PeachPDF/issues/876) (`Draft.InlineExtent`, the fragment-tree contract change needed before a box's own frame — not just its text — can vary per fragment; every later layer that needs a differently-sized fragment, i.e. tables/flex+grid/multicol, depends on this same contract existing first).
