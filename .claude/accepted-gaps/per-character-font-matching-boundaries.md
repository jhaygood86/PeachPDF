# Per-character font matching: remaining coverage boundaries

Per-character font matching (`@font-face` `unicode-range` + glyph-coverage fallback across the `font-family` stack) is implemented (issue #158). Astral/supplementary-plane codepoints (above U+FFFF, i.e. emoji) are now supported via the cmap **format-12** subtable — glyph lookup (`OpenTypeDescriptor.CharCodeToGlyphIndexCore` → `CMap12.MapCodeToGlyph`) and coverage (`CMapCoverage.Extract(CMapTable)`) both consult it, so boundary (2) of the old #172 note is closed for monochrome-outline emoji. Remaining boundaries: (1) fallback walks only the declared `font-family` stack plus the default font, not a last-resort scan of every installed font, so a codepoint no declared family covers still shows a missing-glyph box (still [issue #172](https://github.com/jhaygood86/PeachPDF/issues/172)); (2) **color** emoji via **`COLR`/`CPAL`** (v0 layers + v1 paint graphs) is now supported — color glyphs are drawn as vector content (see the Recent-fixes entry), closing the `COLR` half of #175; the remaining unsupported color formats are bitmap `CBDT`/`CBLC` + `sbix`, SVG-in-OpenType, `COLR` over CFF outlines, and COLRv1 variable paints (tracked follow-ups in the Recent-fixes entry); (3) cmap format-14 variation sequences aren't applied, and a font with *only* a format-12 subtable (no format-4) still isn't usable (`CMapTable.Read` requires format-4 for the WinAnsi `Widths` loop). Note that format-14 is a *fidelity* gap only, no longer a visible-garbage one: a variation selector the font has no glyph for is dropped as a `Default_Ignorable_Code_Point` (`UnicodeDefaultIgnorables` → `ShapedGlyph.IsHiddenIgnorable` → `OpenTypeDescriptor.DropHiddenIgnorables`) rather than drawing `.notdef`, so `U+2764 U+FE0F` renders as a plain heart instead of a heart plus a tofu box. What format-14 would add is *non-default* UVS records, where the selector picks a genuinely different glyph than the base cmap does — measured against the real COLR v1 Noto Color Emoji, all 371 of its `U+FE0F` records are *default* UVS records (glyph `None` = "use the base cmap glyph"), so implementing it would change nothing for that font, and `U+1F600 U+FE0F` isn't in its UVS table at all. Emoji-sequence composition does **not** depend on this: it comes from `GSUB` `ccmp`, not from the cmap. Overlap tie-break for two ranged faces covering the same codepoint is last-declared-wins (CSS cascade order); real subsets are disjoint so this is an edge case. See [Per-character font matching](docs/html-css-support.md#per-character-font-matching-and-coverage-fallback), `UnicodeRangeLayoutIntegrationTests`, `FontResolverCodepointTests`, `Format12CmapAstralTests`.
