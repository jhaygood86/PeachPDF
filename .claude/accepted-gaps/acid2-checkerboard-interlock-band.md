# Acid2's checkerboard-interlock band at the shared clip edge

Acid2's own checkerboard-interlock trick (`#eyes-b`'s `background: fixed url(...)` and `#eyes-a object object object`'s `background: url(...) fixed 1px 0` — two identical 2×2 diagonal-transparency PNG tiles, offset by 1px, meant to interlock into solid yellow) renders correctly in the *majority* of the overlap region as of the `BordersDrawHandler`/`RImage.Interpolate`/float-margin/border-double-count fixes below, but a narrow (~1em-wide) band at the shared left clip edge of the two layers still shows the raw, un-interlocked checkerboard instead of solid yellow. Investigated and ruled out: paint order (confirmed correct — `#eyes-b` paints first, the inline object second, matching Appendix E), the PNG's `tRNS`-chunk color-key transparency (confirmed correctly decoded into a PDF `/Mask` stencil with byte-for-bit-correct values, verified by decompressing the actual embedded `/Mask` and image streams and hand-checking every pixel against the source PNG), and image smoothing (fixed separately below — was real, but doesn't explain this narrower residual band, which persists identically in both MuPDF and PDFium). The remaining band's width closely tracks `#eyes-b`'s own 1em `border-left` — not yet conclusively tied to a specific cause; the next step would be tracing the exact `cm`/`Do` placement of each tile in the raw PDF content stream at that specific X range, not re-deriving the mask/paint-order checks above.
- **Unrelated regression that briefly made this look far worse than the above (fixed):** `CssBox.Paint()`'s cheap visibility pre-check for a box with `Rectangles.Count > 0` intersected `ContainingBlock.ClientRectangle` (not the box's own rects) against the clip. `#eyes-a`'s nested, resolved `<object>` is exactly the case this breaks: its containing block (`#eyes-a` itself) is deliberately `height: 0` (its inline content is positioned purely via `line-height`/`vertical-align`), so that containing block's own client rectangle is always zero-height — the intersection was therefore always zero-area and the *entire* nested object (image and its own checkerboard background alike) silently skipped painting altogether, leaving only the other layer's raw, un-interlocked checkerboard visible across nearly the whole band, not just the narrow edge case above. Introduced by the `VisibilityClipEpsilon` fix for issue #113 (ghost text on page-boundary-relocated boxes) making that same pre-check newly strict enough to notice the zero-height client rectangle; the old, looser `clip != RRect.Empty` comparison had accidentally still treated it as "visible". Fixed by checking the box's own `Rectangles` entries individually (via the existing `IsRectVisible` helper, early-exiting on the first visible one) instead of `ContainingBlock.ClientRectangle` — restoring the interlock to exactly the narrow-band state described above, verified by rasterizing the real showcase PDF with both MuPDF and pdfium. See `Acid2RegressionTests.ZeroHeightContainer_OverflowingInlineReplacedContent_StillPaints`.
