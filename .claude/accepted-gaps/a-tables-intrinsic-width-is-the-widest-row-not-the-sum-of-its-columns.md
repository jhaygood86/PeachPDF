# A table's intrinsic width is the widest row, not the sum of its columns' widest cells

In a shrink-to-fit context (float, inline-block, absolutely positioned box, `flex: none` item, a table cell) a table whose cells hold block-level children measures as the widest ROW, where the spec (and Chrome) take each column as wide as its widest cell over all rows and add the columns. Where one row's cell declares a width that another row's cell in the same column exceeds, the declared width wins in the row that has it and the other row's content is not counted: `<td width="80"><div>long text</div></td>` over a row holding an unbreakable 176pt word measures 66pt for that column, and the table is shrunk to a width the second column's text then wraps in (64pt against Chrome's 146pt). Main measured this table right by accident (a declared width was a floor, so the text's width was counted); the row sum made the declared width a preferred width, which is right for a column nothing else widens.

A per-column measure (`MeasureTableByColumns`, tried and not kept) fixes that case but, over 1,200 random tables compared with headless Chrome 157, fixed 910 cells and broke 226 against 722 and 129 for the row sum, and six previously matching documents differed (8 to 17pt, in tables mixing a `colspan` cell with a percentage `width`). Whatever replaces the row sum has to be run through the same comparison. Tracking issue #2416.
