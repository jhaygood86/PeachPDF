# Content-empty page slots are not materialized

Acid2's fixture-own `100em` margins on `#top`/`.picture` (~3600pt combined, more than 2 A4 pages by themselves) previously paginated straight through as several genuinely blank pages, because PDF page count was a pure `ceil(ActualSize.Height / PageSize.Height)` with no awareness of what was actually painted anywhere. Fixed per CSS Paged Media Level 3 §3.2 ("User agents SHOULD avoid generating a large number of content-empty pages"): a page-slot is not materialized unless some box's own text/generated-content/image/background/border geometry actually intersects it (originally `HtmlContainerInt.GetPaginationSlots` backed by `DomUtils.CollectPrintableContentRanges`; both were retired by the #298 fragment tree, where the rule now falls out of the build), bringing the real fixture down to exactly 2 pages — matching Prince XML's own rendering of the same fixture. This is universal (no `overflow:hidden` detection needed) and non-destructive (no content is discarded or reflowed, only which slots get a `PdfPage` materialized) — confirmed via `Acid2FeatureVerificationTests.OverflowHiddenOnRootHtml_DoesNotClipLaterPages`, whose four page-break-driven sections each carry real text and so are correctly never skipped. One subtlety worth remembering if this area needs revisiting: `CssBox.Location`/`ActualBottom` only reflect true page-relative geometry for block-level boxes — an inline/text-run box's real per-line position lives in its own `Rectangles` (one rect per line it spans), so the printable-content test must read from `Rectangles` when present rather than `Location`/`ActualBottom`, which stay at a bogus, line-local value for such boxes (this was a real bug caught mid-implementation: every paragraph in a multi-page document reported the *same* wrong range, merging genuinely separate pages into one and collapsing a 3-page document down to 1).
