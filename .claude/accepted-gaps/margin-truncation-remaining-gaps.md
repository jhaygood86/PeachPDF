# Margins adjoining an unforced break are truncated — two remaining gaps

What *was* fixed (a distinct, larger problem from [Acid2's fixed bars repeating](acid2-fixed-bars-repeat.md)): before the margin-truncation fix described next, `#top`/`.picture`'s real content didn't just land on a different page than `.intro` — it landed ~350-450pt *into* that second page, nowhere near the fixed bars either, because `#top`'s `margin-top: 100em` paginated straight through as literal blank vertical space (the [page-slot-skip fix](content-empty-page-slots.md) only skips *wholly* blank pages; it doesn't stop content from resuming arbitrarily far into a *partially* blank one). Fixed per [CSS Fragmentation Module Level 3 §5.2](https://www.w3.org/TR/css-break-3/#break-margins) ("When an unforced break occurs before or after a block-level box, any margins adjoining the break are truncated to zero") — the same rule real browsers' print mode and Prince XML apply, confirmed by diffing PeachPDF's Acid2 output against Prince's own published Acid2 PDF sample directly. `CssBox.PerformLayoutImp`'s Static/Relative positioning branch now detects when a collapsed margin would push a box across one or more page boundaries by itself (as opposed to real content straddling a boundary, which `BreakInside: Avoid`/orphans-widows still handle separately) and, if so, discards the whole margin and starts the box flush at the top of the very next page instead — matching the same "land at `MarginTop` within the next page" convention the existing forced-break logic already used (`CssBox.cs`'s `IsForcedBreakValue` branch), just for *unforced* breaks. Margins after a *forced* break (`page-break-before: always` etc.) are explicitly excluded and still preserved un-truncated, per the same spec section. See `PageBreakIntegrationTests`' margin-truncation tests and `Acid2RegressionTests.FixedBars_AndFaceContent_LandOnSamePageNearItsTop`. Two narrower, deliberately-not-attempted gaps in this fix, found by post-change review and not exercised by Acid2 itself (`#top`'s previous sibling is `div.intro`, never null): (1) a box that's the *first* child of a container whose own border/padding blocks CSS2.1 margin-collapse-through has no `prevSibling`, so the truncation guard (`prevSibling is not null`) skips it entirely — an oversized `margin-top` on such a box still paginates through as blank space; (2) the fix lives solely in `PerformLayoutImp`'s Static/Relative branch — `CssLayoutEngineFlex`/`CssLayoutEngineTable`/`CssLayoutEngineColumns` position their own children independently and aren't covered, so an oversized unforced-break-adjoining margin inside a flex/table/multicol context isn't truncated either.
