# A ratio-only svg is sized by its containing block, not by the browsers' shrink-to-fit contribution

An inline `<svg>` with a `viewBox` and no `width`/`height` is laid out as a block-level replaced element with a ratio and no size: it takes the width its containing block has available, and the height follows (`CssLayoutEngine.RatioOnlyWidth`, matching Chromium for a block, and a block-level `<a>` around an `<i>`). In a containing block that is sized to its content - a float, an absolutely positioned box, an inline-block, a table cell, a flex or grid item with `width: auto` - Chromium and WebKit give it 0 width (it has no size to contribute), and so does `RatioOnlyWidth`. What is *not* modelled: Chromium's result when the svg is itself the direct flex item (400 wide in a 400px row flex container, where the flex algorithm stretches it), and the intrinsic-size contribution of a ratio-only svg to the min-content/max-content width of a table cell or grid track (those contexts report 0 here, as they do in Chromium for the cell, but the track sizing algorithms are not driven by the ratio). Expected sizes were measured in Chromium 152 (the built-in browser); WebKit was not run. Not tracked by an issue yet.
