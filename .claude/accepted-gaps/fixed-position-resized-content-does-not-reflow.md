# A resized `position: fixed` box's own content does not re-flow per page

**Not a spec deviation — this is the spec-correct behavior.** [CSS Position 3 §3](https://www.w3.org/TR/css-position-3/#fixed-positioning) is explicit that user agents must not paginate the content of fixed-positioned boxes. When a document mixes physical page sizes (`FragmentEmitter.ComputeFixedSizeOverride`, gated on `PageGeometryTable.HasSizeOverrides`), a fixed box's own **percentage** `width`/`height` genuinely resolves per page — its outer extent (`Draft.FixedSizeDeltaWidth`/`FixedSizeDeltaHeight`, consumed at `FragmentEmitter.ExtentOf`) is correctly resized, which reaches its background/border/clip and any replaced content (`<img>`, an inline `<svg>`) for free, since a replaced element has no wrapping algorithm to invalidate. What does **not** happen: the box's own lines/words (its internal layout) are laid out exactly once and stamped, unchanged, onto every page it repeats on — a non-replaced fixed box with real text content keeps the wrapping its single, global layout pass produced, which may leave visible slack or overflow its resized frame on a page whose measure genuinely differs from the base one.

Doing otherwise (re-flowing a fixed box's own content per page) would require running its internal layout once per distinct page measure rather than once globally, which the fragment tree's "one layout pass, stamped N times" model for fixed content does not support, and which the spec text above explicitly does not ask for.

Documented under "Known boundaries of per-page margins" in `docs/html-css-support.md`. No tracked issue: closing this would mean building spec-nonconformant behavior, not fixing a gap.
