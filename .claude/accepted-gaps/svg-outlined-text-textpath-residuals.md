# SVG outlined-text / `<textPath>` residual subset

**SVG outlined-text / `<textPath>` residual subset** (the accepted deviations from the #187 glyph-outline-text work — gradient/pattern `fill`/`stroke` on `<text>`, and `<textPath>` — narrowed by the #188 text-model generalization, which added `side`, basic-shape targets, nested `<tspan>` along the path, and per-character `rotate`/`dx`/`dy`). Remaining: `<textPath>` `method` (`stretch`) and `spacing` (`auto`) are not applied (only `method="align"`/`spacing="exact"`); gradient/pattern paint on a curved textPath glyph resolves in that glyph's own rotated frame — an `objectBoundingBox` server uses the glyph's own box (envelope approximation, since the run's straight bbox is meaningless once glyphs are rotated), and a `userSpaceOnUse` server rotates/translates with each glyph rather than staying fixed in the text's user space (`PaintGlyphAlongPath` paints inside the per-glyph rotate+translate frame). `objectBoundingBox` `clip-path`/`mask` on a `<text>` element uses no text bbox (`SvgGeometryBounds.GetBoundingBox` can't measure text statically). Outlined text (gradient/pattern/stroke/textPath) is vector art — not selectable, no `/ToUnicode`; and it needs a `glyf`-outline font, so a CFF/OpenType-CFF/bitmap font falls back to a plain solid fill (textPath falls back to the straight baseline). Cubic/arc flattening for the arc-length parameterization uses fixed (non-adaptive) subdivision. Filed as [issue #289](https://github.com/jhaygood86/PeachPDF/issues/289), verified in both PDFium and MuPDF.
